## 1. 总览：这个领域的整体形态

### 1.1 一句话概括

**现有框架全部是「单次编排（run-scoped orchestration）」范式**：一次 `run()` / `kickoff()` 解决一个任务，结束后把状态序列化到某个地方，下次再来一遍。没有任何一个框架内置「常驻的、跨运行的协作任务板」。这正是 collab-platform 要补的空位。

### 1.2 三个流派

| 流派 | 代表 | 组织方式 | 骨架在哪 |
|---|---|---|---|
| **流水线派** | MetaGPT、ChatDev 1.0、AgentVerse(tasksolving) | 模拟公司/社会，固定 SOP 分阶段 | 框架代码里的阶段序列（硬编码或 JSON/YAML 配置） |
| **群聊派** | AutoGen、CAMEL、AgentVerse(simulation)、Semantic Kernel GroupChat | 多 agent 共享一个会话，轮流发言 | 一个「下一个发言者是谁」的选择器 |
| **图编排派** | LangGraph、ChatDev 2.0、Google ADK | 显式图/层级结构，节点是 agent | 用户画的图 / 声明的层级 |

这三派在「**管理者角色**」上的答案，正好对应三种形态（详见 §2 与 §3）。

### 1.3 三个行业共识

1. **管理者普遍被建模成「一次 LLM 调用」或「一个编排器对象」，而不是一个有身份的实体。**
   - CrewAI 的 manager 是运行时临时造、工具被强制清空的 Agent 实例 `[源码]`；
   - LangGraph 旧的 `create_supervisor` 是「一次 LLM 调用 + handoff tool」，官方已放弃该包 `[官方]`；
   - Semantic Kernel 的 GroupChatManager「不是 Agent，不进 members、不能对话、无身份与权限」`[官方]`。

2. **human-in-the-loop 的成熟做法是「暂停 + 持久化 + 外部恢复」，不是阻塞式输入。**
   - LangGraph `interrupt()` + checkpointer `[官方]`；
   - OpenAI Agents SDK `needs_approval` + `RunState.to_json()` `[官方]`；
   - Google ADK `require_confirmation` + `LongRunningFunctionTool` `[官方]`；
   - AutoGen 反过来：`UserProxyAgent` 阻塞且「cannot be saved or resumed」，官方建议改用 `HandoffTermination` + save/load_state `[官方]`。

3. **状态持久化普遍止步于「会话/线程级」，跨运行的业务状态要靠外部系统。**
   - LangGraph 只有 checkpointer（thread 内）+ Store（跨 thread 的 KV），官方明说没有任务板 `[官方]`；
   - AutoGen 的 `save_state()` 返回一个 dict，要自己 `json.dump` 到文件或数据库 `[官方]`；
   - 行业实践（Temporal / Restate / DBOS）走的正是「把状态放到框架外的持久引擎」这条路 `[官方]`。

### 1.4 三个空白（对 collab-platform 直接相关）

| 空白 | 现状 | 我们的机会 |
|---|---|---|
| **常驻的跨运行协作状态** | 无任何框架内置持久任务板；最接近的是 CrewAI 企业版「审批队列」与 AutoGen 的 state dict | GM 的「协作事件流 + 任务板」是原生能力而非补丁 |
| **动作的三级授权 + 四态流转** | 只有工具级的 approve/reject（二元），没有「一级自主 / 二级留痕 / 三级待确认」这种分级；没有 `overridden`（人带理由强行通过）这类状态 | 这是本项目的独有语义，框架层无先例 |
| **「保留判断依据」的审计** | 所有框架的记录都是技术性日志（trace / checkpoint / 运行日志），没有「这条判断的依据是什么、谁授权的」这种业务审计 | GM 的「留下依据」是设计一等公民 |

> 关于 `overridden` 的最近似物：AutoGen 的 `ApprovalResponse(approved=False, reason="...")` 带 reason `[源码]`，但它是拒绝理由，不是「越权通过」；Temporal/DBOS 的审批模式记录「谁批的」，但没有「带理由推翻」的语义。

## 2. 逐框架

### 2.1 CrewAI

**核心抽象** `[官方]`
- **Agent**：`role` / `goal` / `backstory` 必填，另有 `llm`、`tools`、`allow_delegation`（默认 `False`）、`max_iter`、`max_retry_limit`。可脱离 Crew 用 `agent.kickoff()` 直接对话（内部走 `LiteAgent`）。
- **Task**：`description` + `expected_output` 必填，`agent` 可选；另有 `context`（`List[Task]`，指定哪些任务的输出作为本任务上下文）、`output_pydantic`、`guardrail` / `guardrail_max_retries`（默认 3）、`human_input`。
- **Crew**：`agents` + `tasks` + `process` 的编排容器，`kickoff()` 返回 `CrewOutput`。
- **Flow**：事件驱动编排（`@start` / `@listen` / `@router`），状态在 `self.state`。

来源：[Agents](https://docs.crewai.com/en/concepts/agents.md)、[Tasks](https://docs.crewai.com/en/concepts/tasks.md)、[Crews](https://docs.crewai.com/en/concepts/crews.md)

**角色从哪来** `[官方]` 四种：① JSONC（新项目默认，`agents/<name>.jsonc` + `crew.jsonc`）；② Classic YAML（`config/agents.yaml` + `@CrewBase`）；③ 直接 Python 实例化；④ **框架运行时动态生成** —— hierarchical 下未给 `manager_agent` 时，由 `_create_manager_agent()` 用 i18n 模板现建一个。

**任务怎么分配** `[官方]` sequential 静态按顺序；hierarchical **运行时决定** —— 官方原文：「Tasks are not pre-assigned; the manager allocates tasks to agents based on their capabilities」（[Processes](https://docs.crewai.com/en/concepts/processes.md)）。

**管理者角色（重点）** `[源码]`

`manager_llm` 是「自动创建的 manager 用哪个 LLM」，`manager_agent` 是「用户自己造一个 Agent 当 manager」，二者必居其一。`crew.py#L1531` 的 `_create_manager_agent()` 说明了一切：

- 传了 `manager_agent` → 强制 `allow_delegation = True`；**若它自带 tools，直接抛 `Exception("Manager agent should not have tools")`**；
- 没传 → 用 i18n 的 `hierarchical_manager_agent` 三个字段 + `AgentTools(agents).tools()`（只有 `DelegateWorkTool` + `AskQuestionTool`）新建一个 Agent。

**它是独立实体吗？——不是。** 四条证据：
1. 工具必须为空（源码硬否决）；
2. 它的工具是运行时注入的、不来自用户配置；
3. **不能单独设 `max_iter`**（自动创建时不传，吃 `BaseAgent` 默认 25）；
4. **不能停用**（hierarchical 必须有 manager，源码无 no-manager 分支）。

准确表述：它是一个被 Crew 接管、工具被强制清空并在引导期回填的 Agent 实例，**而非可独立对话 / 独立授权 / 独立停用的对等实体**。

**「validation」的名实之差** `[源码]`：官方文档说 manager 会「reviews outputs, and assesses task completion」，但 `crew_agent_executor.py` 全文只有 iterations 计数与 `has_reached_max_iterations`，**没有任何 validation / retry / replan 分支**。所谓"校验"在实现上等于「下一个 task 的 context 带上上一个 task 的产出」。真正带重试语义的是 **Task 的 guardrail**（`guardrail_max_retries` 默认 3，输出校验）。

**allow_delegation** `[官方]` 置 `True` 后自动获得 `Delegate work to coworker` 与 `Ask question to coworker` 两个工具 —— **普通 agent 之间可以互相委派**。源码另加约束：不能委派给自己、crew 至少两个 agent（`crew.py#L1826`）。

**HITL** `[官方]`+`[源码]`
- **`Task(human_input=True)`**：触发点钉死在最后一次 LLM 循环之后、写 memory 之前（`crew_agent_executor.py#L249`）。**是阻塞式终端输入** —— `SyncHumanInputProvider` 打印 Rich 面板后调用内置 `input()`；非交互环境会一直卡住。**位置在产出之后**：agent 已得出答案，人再决定是否让它改。
- **Flow 的 `@human_feedback`**（需 CrewAI 1.8.0+）：`message` / `emit`（结果标签列表）/ `llm`（把自由文本收敛成 emit 之一）/ `default_outcome` / `provider` / `learn`。**无 emit 只收集反馈；有 emit 则变成路由器**（`@listen("approved")` 分流）。
- **能不能在动作生效前拦住？** `@human_feedback` 拦的是「方法产出之后、下游 listener 之前」，**不拦工具或写操作**。要做到动作前拦截，走的是执行钩子：`@on(InterceptionPoint.PRE_TOOL_CALL, tools=[...])` 里 `raise HookAborted(reason=..., source=...)`，或官方示例的 `require_approval` 模式（在 `PRE_TOOL_CALL` 里调 `ctx.request_human_input()`）—— **这才是「动作生效前拦住」的原语** `[官方]`（[Execution Hooks](https://docs.crewai.com/en/learn/execution-hooks.md)）。
- **审批队列：核心库没有。** 只有企业版 AMP 有 HITL Pending Requests 列表（routing rules 按 `method_name` 通配、SLA、超时 auto-response、HMAC 签名 webhook、不可变审计日志）`[官方]`（[Flow HITL Management](https://docs-platform.crewai.com/platform/en/features/flow-hitl-management)）。

**状态持久化** `[官方]`+`[源码]`
- `crew.kickoff()` 结束 → 返回 `CrewOutput`；内存里 `task.output` 逐任务可取。
- 落盘三条显式路径：① `Crew(output_log_file=...)`; ② **checkpoint** —— 默认 `JsonProvider`，目录 `./.checkpoints/`，触发事件 `task_completed`；恢复用 `crew.kickoff(from_checkpoint=...)`；`Crew.fork(config, branch="experiment-a")` 可开分支；③ replay（`crewai replay -t <task_id>`）。
- **memory 体系已换代** `[官方]`：官方 PR #4420（2026-02-14 合并）用统一 `Memory` 类**移除了** `ShortTermMemory` / `LongTermMemory` / `EntityMemory` / `ExternalMemory`。现版本默认后端 **LanceDB**，源码取 `CREWAI_STORAGE_DIR/memory`，未设则为平台应用数据目录 `[源码]`。**跨运行保留**：文档写明 "memory persists across runs (backed by LanceDB on disk)"。组织方式不是三种 memory，而是**层次化 scope 树**（`/project/alpha`、`/agent/researcher`）+ `MemoryScope` / `MemorySlice`（可 `read_only=True`，写入抛 `PermissionError`）。
  - ⚠️ **文档与源码不一致**：官方 memory.md 称路径为 `./.crewai/memory`（project-local），源码为 `db_storage_path()/memory`（平台数据目录）。以源码为准。
- **Flows 的 `@persist`** 是纯元数据标记器，实际写由 Flow 引擎执行；默认后端 `SQLiteFlowPersistence`，存 `db_storage_path()/flow_states.db`，表 `flow_states` / `pending_feedback` `[源码]`。
- **跨运行持久任务板：未找到。** checkpoint 与 `@persist` 保存的是**某一次运行的进度快照**（语义是接着跑完或开分支），不是「一份跨运行、可被多个 crew 共享、独立于运行存在的任务板」。

**权限 / 审计** `[官方]`
- **核心库没有动作分级授权体系。** 可用手段：① 构造期工具白名单（`Agent(tools=...)` / `Task(tools=...)`）；② **运行期拦截**（`PRE_TOOL_CALL` + `HookAborted`，见上）；③ 事件总线可监听 `tool_usage_started/finished/error`、`HookDispatchedEvent`（含 outcome `proceeded|modified|aborted`、reason、source）；④ `SecurityConfig` 为 Crew/Agent/Task 生成 Fingerprint 做身份标识 `[官方]`。
- ⚠️ 一条重要取舍：`HookAborted` **按设计传播**并终止链，而**其他异常被吞掉（fail-open）** —— 官方原话 "don't rely on raising `ValueError` to stop a run"。
- 企业版有组织侧 RBAC（功能权限矩阵 + 部署级权限 `run`/`traces`/`manage_settings`/`human_in_the_loop`），属**组织权限**而非 agent 动作分级 `[官方]`。

### 2.2 Microsoft AutoGen（v0.2 与 v0.4+）

**v0.4 为什么分层** `[官方]`：官方迁移指南称 v0.4 是 from-the-ground-up rewrite，采用 asynchronous, event-driven architecture；**Core API** 是可扩展的事件驱动 actor 框架，**AgentChat API** 建在 Core 之上、是面向任务的高层框架。

**核心抽象**
- `[官方]` Core 层：`RoutedAgent` + `@message_handler`（用消息类型注解路由）、`AgentRuntime`（本地 `SingleThreadedAgentRuntime` / 分布式 `GrpcWorkerAgentRuntime`）、**Topic = (Type, Source)** + `TypeSubscription`。**注意**：Core 的 agent 不由应用实例化；AgentChat 的 agent 是应用自己造的。
- `[源码]` AgentChat 层：`AssistantAgent`（`name` / `description` / `system_message` / `tools` / `handoffs` / `model_context` / `max_tool_iterations`）。**硬约束**：`AssistantAgent` 不线程安全、不能跨任务共享。
- 角色从哪来：v0.2 与 v0.4 都是 `name` + `description` + `system_message`；官方明确「agents 的 name 和 description 被模型用来决定下一个发言者」`[官方]`。**v0.4 Core 层根本没有自然语言角色概念** —— 角色 = agent type + 能处理的消息类型。

**多 Agent 怎么组织** `[官方]`+`[源码]`

| 团队 | 谁决定下一个发言者 |
|---|---|
| `RoundRobinGroupChat` | 无 LLM，按 participant 顺序轮转 |
| `SelectorGroupChat` | **每条消息后用一次 ChatCompletion 模型选** |
| `Swarm` | **无中心调度**：反向遍历 thread 找最近一条 `HandoffMessage` 的 `target` |
| `MagenticOneGroupChat` | `MagenticOneOrchestrator` 做 ledger 驱动编排 |

- `Swarm` 的结构性限制 `[源码]`：**不支持内层 team 作为 participant**（类 docstring 明写）。稳定版与 main **均未**标 experimental/deprecated。（搜到的 Swarm deprecation 页属 AG2 fork，不是微软 AutoGen。）
- 新增 `GraphFlow`（0.7）支持 `DiGraphBuilder` + 条件边，但官方明确标 **experimental** `[官方]`。

**管理者角色（重点）**

*v0.2 的 `GroupChatManager`* `[源码]`：
- 默认 `speaker_selection_method = "auto"`（另有 `manual` / `random` / `round_robin`）。
- **auto 不是「一次 LLM 调用」，而是一个嵌套的两 agent 对话**：内部造 `checking_agent` + `speaker_selection_agent`，把群聊消息注入，反复追问直到提名**唯一** agent。`max_retries_for_selecting_speaker` 默认 2 → 最多 3 次尝试；选择过程 `cache=None`（不走 LLM 缓存）。
- 校验靠 `_mentioned_agents()` 做**正则匹配**；命中 0 个或多个就回灌追问；**耗尽尝试后退回 `next_agent`（即 round robin）**。
- prompt 分两条模板：`select_speaker_message_template`（含 `{roles}` 与 `{agentlist}`）与 `select_speaker_prompt_template`。
- `manual` 模式用 `IOStream` 让你敲；**你若放弃（返回 None），也会退化成 round robin**。

*v0.4 的 `SelectorGroupChat`* `[官方]`：
- 流程：① 用模型（看到对话历史 + 各 participant 的 `name`/`description`）选下一个发言者（默认不连续选同一人，除非 `allow_repeated_speaker=True`）；② 被选中者发言并**广播**给所有人；③ 检查终止条件。
- 可覆盖项：`selector_func`（自定义选择函数，覆盖模型选择）、`candidate_func`（先用代码缩小候选集）、`selector_prompt`（模板变量 `{roles}` / `{participants}` / `{history}`）。
- 官方建议：如果发现自己在给每个 agent 写多条选择条件，说明该改用自定义选择函数或拆成多个串行团队。

*v0.4 的 `Swarm`* `[源码]`：`SwarmGroupChatManager.select_speaker` 刻意被收窄成「只按 handoff 选人」—— 不看 LLM，只取最近 `HandoffMessage.target`；无 handoff 就让当前人继续说。另有一道校验 `validate_group_state`（启动消息或最新 handoff 的 target 不在名单里就抛 `ValueError`）。

*`MagenticOneGroupChat` 的 Orchestrator（**本报告中最接近「有独立状态的管理者」的案例**）* `[官方]`：
- Orchestrator 负责高层规划、指挥其他 agent、跟踪进度。
- 它维护两个账本：**Task Ledger**（先建计划、收集事实与推测）与 **Progress Ledger**（每一步自我反思进度、检查是否完成）。
- 结构上分**外循环**（更新 Task Ledger）与**内循环**（更新 Progress Ledger）；若连续多步无进展，则更新 Task Ledger 重新规划。
- ⚠️ 但请注意：Task Ledger / Progress Ledger **是 Orchestrator 提示词内的概念，不是可持久化的数据层** `[源码]`（autogen 的 state 文档与团队状态只覆盖 message thread 与 manager 状态）。

**HITL** `[官方]`
- **v0.2 的 `UserProxyAgent.human_input_mode`**（ALWAYS / TERMINATE / NEVER）在 v0.4 **没有对应物**。迁移指南原文：user proxy 现在只是「取用户输入的 agent」，「no other special configuration needed」；`max_consecutive_auto_reply` 与 `code_execution_config` 一并消失。
- v0.4 的 `UserProxyAgent` 只剩三个参数：`name` / `description` / `input_func`。
- 交回人类用 **`HandoffTermination(target="user")`**：收到 target 为 user 的 `HandoffMessage` 即终止，官方推荐它配合 save/load_state 处理慢响应，因为 **`UserProxyAgent` 会阻塞团队且「cannot be saved or resumed」** `[官方]`。
- **动作生效前拦住：`ApprovalRequest` / `ApprovalResponse` / `approval_func`（本报告最贴近「动作前审批 + 带理由」的 API）** `[源码]`：`CodeExecutorAgent.execute_code_block` 先调 `approval_func`，拿到 `ApprovalResponse`；`approved=False` 则不执行，返回 `exit_code=1`、`output="Code execution was not approved. Reason: <reason>"`。`ApprovalRequest` 携带 `code` 与 `context`（当前 model_context 消息），所以审批方可做模型化审查。链路：`CodeExecutorAgent(approval_func=...)` 与 `MagenticOne(approval_func=...)` 同机制。两点注意：设了 `approval_func` 该 agent 不能 `dump_component` 序列化；不设会发 `UserWarning` 提示代码将无监督执行。

**状态持久化** `[官方]`+`[源码]`
- `save_state()` 返回嵌套 dict：`{"agent_states": {名字: 状态}}`，**含每个参与者与 group chat manager**。Swarm 的管理器部分即 `SwarmManagerState{message_thread, current_turn, current_speaker}` —— 所以**消息 + manager 状态都覆盖**。
- v0.4.9 起键改为 agent 名（原先 agent ID）并移除 `team_id`。
- **不会自动落盘**：状态只是一个 dict，官方示范自行 `json.dump` 到文件或写数据库，再 `load_state` 到新建的 team。运行中调用可能不一致，建议停止后存。
- Teams 有状态，`run()` 后可**不 reset 直接继续**（resume）；`reset()` 清空全部 agent 状态 `[官方]`。
- **跨运行持久任务板：无。** Magentic-One 的 Task/Progress Ledger 属提示词内概念。

**权限 / 审计** `[官方]`
- AutoGen 官方对 Magentic-One 列了 6 条安全建议（用容器、虚拟环境、监控日志、人在环中、限制访问、保护数据），并警告「agents may occasionally attempt risky actions, such as **recruiting humans for help or accepting cookie agreements without human involvement**」，以及可能受网页 prompt injection 攻击 `[官方]`。
- 沙箱：`CodeExecutorAgent` 本身标 **Experimental**；官方推荐 Docker 隔离；`LocalCommandLineCodeExecutor` 在本机跑，`DockerCommandLineCodeExecutor` 提供镜像 `python:3-slim`、`timeout=60`、`work_dir`/`bind_dir` 挂载、`auto_remove`、`device_requests`（GPU）`[官方]`。
- **没有「谁授权它做的」这种内置审计数据结构** —— 最接近的就是上面那个带 `reason` 的 `ApprovalResponse`。

### 2.3 LangGraph（含 langgraph-supervisor）

**核心抽象** `[官方]`
- **State**：共享状态 schema（TypedDict/Pydantic），**每个键可带独立 reducer**（默认覆盖，`Annotated[..., add]` 累加）。
- **StateGraph / 节点 / 边**，编译后成图。
- **`Command`**：把状态更新与跳转合到一步（`update` / `goto` / `resume` / `graph`）。
- **`create_agent`**：LangChain 的 harness 工厂，产出一张编译好的 LangGraph 图（ReAct 循环）。

来源：[Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api.md)

**多 Agent 拓扑** `[官方]`：官方旧文档四分类（network / supervisor / hierarchical / custom），**新版改称五模式**：subagents / handoffs / skills / router / custom workflow（[Multi-agent](https://docs.langchain.com/oss/python/langchain/multi-agent/index.md)）。

**管理者角色（重点）——这里发生了本报告中最重要的一次「官方转向」**

1. `langgraph-supervisor` 的 `create_supervisor` **内部实现** `[源码]`：建一张 `StateGraph`，**supervisor 节点（一个 `create_react_agent`）与每个 worker 节点并存**，`add_edge(worker → supervisor)` 构成回边；路由靠把 handoff tools `bind_tools` 给 LLM，**由 tool_call 决定去哪个节点**。`create_handoff_tool` 确实建模成 tool call：工具名 `transfer_to_<agent>`，返回 `Command(goto=agent, graph=Command.PARENT)` + `ToolMessage`。`output_mode` 是 `create_supervisor` 参数：`full_history` 全量 / `last_message` 仅末条。

2. **官方已声明该包不再积极维护** `[官方]`，原文：「The `langgraph-supervisor` package is no longer actively maintained.」推荐改用 **subagents 模式**：一个主 agent 通过把 worker 包成 `@tool` 来协调（[迁移指南](https://docs.langchain.com/oss/python/migrate/langgraph-supervisor.md)）。

3. **这个管理者有没有独立身份？——没有。** 它是「一张编译好的图 + 一次 LLM 调用」，无法单独对话 / 单独授权 / 单独停用。迁移后的 subagents 模式里，管理者就是一个普通 `create_agent`，worker 是它的工具。

4. 一个对实现很关键的细节 `[官方]`：**`interrupt` 会从嵌套的 `create_agent` 层一路冒泡到最外层图**。要让这条链路成立：① **只有最外层图 compile 时带 checkpointer**，subagent 一律不带 `checkpointer=`（用 per-invocation persistence 继承父级）；② 外层 `invoke` 必须传 `thread_id`。

**HITL（重点）** `[官方]`（[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts.md)）
- `interrupt()` 用**抛异常**的方式暂停；靠 checkpointer 保存状态并**无限期等待**。
- 三个必要条件：checkpointer、`thread_id`、在需要暂停处调用 `interrupt()`（payload 必须 JSON 可序列化）。
- 恢复：`Command(resume=...)`，其值成为 `interrupt()` 的返回值。
- **为什么能「在动作生效前拦住」**：因为暂停点就在节点代码里、动作调用之前，且状态已落盘，图可以等任意长时间。
- **六条必须知道的规则**：
  1. **恢复时节点从节点开头整段重跑**（不是断点续行）→ `interrupt` 之前的副作用必须幂等；
  2. 不要用裸 `try/except` 包 `interrupt()`（会吞掉那个特殊异常）；
  3. 一个节点内多个 `interrupt()` 的**匹配是严格按索引**的，不能条件性跳过、不能 `while True` 循环调用；
  4. 不要传函数/类实例等不可序列化值；
  5. `interrupt_before` / `interrupt_after` 是**静态断点，官方明确不推荐用于 HITL**（只用于调试）；
  6. `response_schema` 可给 resume 值做类型校验（需 `langgraph>=1.2.12`）。
- `HumanInTheLoopMiddleware` 的 `interrupt_on` 支持四种决策：**approve / edit / reject / respond**，均为 **tool 级** `[官方]`（[HITL](https://docs.langchain.com/oss/python/langchain/human-in-the-loop.md)）。
- 工程注意：**不要把 `Command(update=...)` 当输入传进去**继续多轮对话 —— `Command(resume=...)` 是唯一设计为 `invoke()` 输入的 `Command` 形态。

**状态持久化（重点）** `[官方]`（[Persistence](https://docs.langchain.com/oss/python/langgraph/persistence.md)）

| | Checkpointer | Store |
|---|---|---|
| 持久化什么 | 图状态快照 | 应用自定义的键值数据 |
| 作用域 | **单个 thread** | **跨 thread** |
| 记忆类型 | 短期、thread 内 | 长期、跨 thread |
| 用途 | 对话连续性、HITL、时间旅行、容错 | 用户偏好、事实、共享知识 |
| 访问方式 | config 里传 `thread_id` | 节点内 `runtime.store` 读写 |

- **`thread_id` 就是持久游标**：复用同一 id → 续同一 checkpoint；换新值 → 开一个全新空状态的 thread。
- 生产必须用持久 checkpointer（`PostgresSaver` / `SqliteSaver`）；`MemorySaver` / `InMemorySaver` 存 RAM，**进程重启全部丢失**。`PostgresSaver` 的 `thread_id` 有长度限制（**保持在 255 字符以内**）。
- `get_state_history` 支持时间旅行。
- **LangGraph 有没有内置「跨运行持久任务板」？——没有。** 官方明确只有这两套持久化系统；要任务板必须自建 Store 命名空间（或外部系统）。中间件的 `TodoListMiddleware.write_todos` **只活在单 thread state 里**。
- 还有一个易踩的边界：**子图写状态时父图不一定立刻看到**（每个子图有自己的 checkpoint namespace），跨图边界要用 Store。

**权限 / 审计** `[官方]`
- **没有动作分级授权、没有 RBAC、没有专门的权限审计页。**
- 最接近的两样：工具级审批 `HumanInTheLoopMiddleware.interrupt_on`（含 `when` 谓词按参数门控、`edit` 决策改参数）；Deep Agents 侧另有 `permissions` 文件系统规则。
- **`resume` 值 + checkpointer 算不算审计记录？——不算。** 它存的是状态快照与技术性停机记录，**没有操作者身份、没有决策理由、没有不可篡改日志**。可溯源靠 LangSmith trace（外部系统）。

### 2.4 MetaGPT

**核心抽象** `[源码]`：**Role**（`name`/`profile`/`goal`/`constraints`/`actions` + `rc` 运行时上下文）· **Action**（`run`/`_aask`，最小执行单元）· **Message**（`content`/`cause_by`/`send_to`/`sent_from`，路由依据）· **Environment**（roles 字典 + history 内存 + `publish_message` 广播 / `put_message` 私投）· **Team**（env + roles + investment + idea）。

**协作机制** `[官方]`+`[源码]`：`run_project` 把 idea 封成 `Message(cause_by=UserRequirement)` 发布，`run` 循环 `env.run()` 直至 idle 或耗尽预算/轮次。订阅靠 `Role._watch([ActionX])` 写 `rc.watch`，`_observe` 只挑 `cause_by ∈ watch` 或 `self.name ∈ send_to` 的消息。**两条路线**：

### 2.5 OpenAI Agents SDK（原 Swarm）

**核心抽象** `[官方]`：**Agent** = LLM + instructions + tools + handoffs + guardrails 的**配置对象（非运行时）**；**Runner** 是执行器（`run` / `run_sync` / `run_streamed`），驱动回合循环直到产出最终输出或暂停；**RunResult** 携带 `final_output` / `new_items` / `last_agent` / `interruptions` / `to_state()`；**Session** 是跨 run 的会话记忆层；**function_tool** 按类型注解自动生成 schema 并用 Pydantic 校验。

**协作机制** `[官方]`（[Handoffs](https://openai.github.io/openai-agents-python/handoffs/)）
- **`handoff` 被建模成给 LLM 的工具**，名为 `transfer_to_<agent_name>` —— 所以**默认由 LLM 决定交接**；只有目标要由代码在调用时选定时，才自定义 `Handoff` 子类。
- `Agent.as_tool()` 与 handoff 的区别：**as_tool 让 manager 保住控制权**、汇总多个专家输出、统一跑 guardrail；**handoff 把本回合余下部分交给专家**，专家成为当前 agent 并直接答复。
- `on_handoff` = 交接被调用时的回调（可接 `input_type` 带来的模型参数，用于日志或授权，**失败须抛异常，不能只是返回**）；`input_filter` 改写下家看到的历史；`is_enabled` 可动态启停某个交接。

**管理者角色** `[官方]`（[Multi-agent](https://openai.github.io/openai-agents-python/multi_agent/)）
- **有 manager 说法，但没有 manager 类。** 官方原文：agents-as-tools 模式下「A manager agent keeps control of the conversation and calls specialist agents through `Agent.as_tool()`」 —— **它就是普通 Agent，无独立身份或类型**。
- 官方对「LLM 决定 vs 代码决定」是**并列两条路**：Orchestrating via LLM（handoffs / tools，投资 prompt 与 evals）与 Orchestrating via code（结构化输出分类后再挑 agent、链式传递、while + 评估器、`asyncio.gather` 并行），两者可混用，**代码路更确定**（速度/成本可预测）。
- triage agent 即用 `handoffs=[...]` 做分诊路由、专才接管本回合。
- **单独停用只能靠 `handoff(is_enabled=)` 或从 tools/handoffs 移除；授权是工具级，没有管理者级权限实体。**

**HITL（重点）** `[官方]`（[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)）
- ⚠️ **任务指定的 `developers.openai.com/.../guardrails-approvals` 在本次调研中返回 403**（整站被 WAF 拦：直连、Playwright 浏览器、代理均同）。以下等价机制以 SDK 官方文档为准，**这条是「未取到原文」，不是「没有」**。
- SDK 确有 **`needs_approval`**：可用于 `function_tool`、`Agent.as_tool`、`ShellTool`、`ApplyPatchTool`，MCP 用 `require_approval`；取 `True` 或 per-call 回调；**参数无法安全解析时 fail closed 转人工**。
- 流程：结果出现 `interruptions`（`ToolApprovalItem`）→ `result.to_state()` → `state.approve()` / `state.reject()` → `Runner.run(agent, state[, session])` 续跑；`always_approve` / `always_reject` 是粘性决策。
- **`RunState` 可 `to_json` / `from_json`、`to_string` / `from_string` 存库后恢复**（面向「人几小时后才批」的长时审批）；跨 handoff 与嵌套 as_tool 的审批都在外层 `RunState` 上批。
- **guardrails** 用 `tripwire_triggered` 抛异常阻断；注意 **`run_in_parallel=False` 阻塞模式下模型与工具不会执行，默认并行则可能已执行** —— 这条对「动作生效前拦住」的可靠性判断很关键。

**状态持久化** `[官方]`（[Sessions](https://openai.github.io/openai-agents-python/sessions/)）
- **Session 是跨 run 会话记忆**：每次 run 前自动取历史前置、run 后把新 item 写回。实现含 `SQLiteSession`（内存/文件）、`OpenAIConversationsSession`（OpenAI 服务端托管）、Redis / SQLAlchemy / MongoDB / Dapr 等。
- `RunResult.to_input_list()` 把本次运行转成可重放的输入列表，供手工聊天循环下一轮传 `input=`。
- **没有跨运行的持久任务板**：Session 只存对话历史，`RunState` 只是单次暂停快照。

**权限 / 审计** `[官方]`：**无 RBAC、无角色分级**，授权粒度是工具级（`needs_approval` / MCP `require_approval` / as_tool 的 needs_approval）+ guardrail tripwire + sandbox agent 的 Unix 风格文件权限。**审计溯源靠 tracing**（默认开启，可关）：自动包 trace 与 agent / generation / function / guardrail / handoff span，可送 Traces dashboard；`new_items` 带 agent/tool/handoff/approval 元数据供日志与审计；`RunState` 可序列化存档。**独立于 tracing 的审计日志存储后端：未找到。**

### 2.6 CAMEL

**核心抽象** `[论文]`+`[官方]`：**ChatAgent** = 对话动作基元（父类 `BaseAgent` 只定 `reset`/`step`），承载系统消息、记忆、工具、结构化输出；**RolePlaying** = 两 agent 回合制会话容器；**Task** = 可分解的层级任务（state/subtasks）；**Workforce** = 多 agent 协作引擎；**Society** = 模拟社会行为模块。**Inception Prompting** 用 AIUser / AIAssistant 双角色系统消息把任务注入会话，并内建「不换角色 / 不以 Next request 结尾」等护栏。
来源：[arXiv:2303.17760](https://arxiv.org/abs/2303.17760)

**协作机制** `[官方]`：RolePlaying 的 `init_chat()` 重置双方并返回初始消息，`step(assistant_msg)` 先 `user_agent.step` 再 `assistant_agent.step`，循环靠 `terminated` / `CAMEL_TASK_DONE` 终止。
**Workforce**：`task_agent` 分解 → `coordinator_agent` 分配 → worker 并行执行 → 失败走恢复策略。**分配是运行时由 LLM 按 worker 描述 + 工具清单决定**（`ASSIGN_TASK_PROMPT` / `_find_assignee`），非静态；worker 有 `SingleAgentWorker` / `RolePlayingWorker` 两类，**可运行期动态新建**。

**管理者角色** `[官方]`+`[源码]`：**coordinator 与 task_agent 都是独立 `ChatAgent`**（可传自定义实例，workforce 会保留其模型/记忆/工具并拼接自己的系统消息），**不是普通函数**。`task_agent` 负责分解、合成结果，还兼失败分析与质量评分。`task_specifier` 属**旧 RolePlaying 线**（`TaskSpecifyAgent` 把粗提示细化）；`critic` 为可选裁判 agent。**动态造角色可以**：`RoleAssignmentAgent` 按任务生成专家角色，`RoleNameGenerator` 还支持从角色文件组合角色。

**HITL** `[官方]`：有两层，但**默认都拦不住动作**。
- **HumanToolkit**：`ask_human_via_console` / `send_message_to_user` —— agent **自愿调用**、阻塞等输入，属咨询而非拦截。
- **Workforce 内置人工干预**：`pause` / `resume` / `stop_gracefully` / `skip_gracefully` / `add_task` / `reorder_tasks` / `resume_from_task` —— **可在任务层面暂停或改内容**（这是本报告里少见的「任务级人工干预」API）。
- **真正「动作生效前拦住」的是 `LLMGuardRuntime`**（见下）。**全仓未见 `human_in_the_loop` 函数/参数名**。

**状态持久化** `[官方]`+`[源码]`：**ChatHistoryMemory** 默认 `InMemoryKeyValueStorage`（进程内、**重启即失**）；**VectorDBMemory** 默认 QdrantStorage，可换 Milvus / Chroma / pgvector；**LongtermAgentMemory** 两者混合；Mem0Storage 可云同步。跨运行 checkpoint：Workforce 有 `save_snapshot` / `list_snapshots` / `resume_from_task` 与 `WorkforceSnapshot`，**但属内存态、非落盘** `[源码]`。`ChatAgent.summarize` 另把上下文摘要写成 md 文件。**未见落盘式 checkpoint（未找到）。**

**权限 / 审计（本报告中最"像"分级授权的一个）** `[官方]`+`[源码]`：
- **`LLMGuardRuntime`** 在包装函数被调用时，**先用 LLM 对「函数名 + 描述 + 实际参数」打风险分**（`FunctionRiskToolkit`：1 无危害 / 2 轻微 / 3 有风险），`threshold < score` 即拒绝执行并返回 error；默认 `threshold=2`；可用 `IgnoreRiskToolkit` 人工豁免。**这是「按动作风险分级 + 可豁免」的少见的框架内建实现**，但仍是一次 LLM 判定、非组织级策略。
- 沙箱：`DockerRuntime` / `UbuntuDockerRuntime` / `RemoteHttpRuntime` / `DaytonaRuntime`。
- 审计：`WorkforceLogger`（`WorkforceCallback` + `WorkforceMetrics`）记录 task_created / assigned / started / completed / failed、worker_created、token 用量等，`dump_to_json` 可落盘。
- **未见统一工具权限模型 / ACL（未找到）。**

### 2.7 AgentVerse

**核心抽象** `[源码]`：**没有 Task 基类**（这是最容易被误判的一点）。核心是「两条平行主线各自一套 Rule 组件」：
- **BaseAgent**：`name` / `llm` / `output_parser` / prompt 模板 / `role_description` / `memory` / `max_retry=3` / `receiver: Set[str] = {"all"}` / `async_mode`；抽象方法 `step()` / `astep()` / `reset()`。
- **BaseEnvironment**：`agents` / `rule` / `max_turns=10` / `cnt_turn` / `last_messages` / `rule_params`。
- **Rule**：simulation 线 = `SimulationRule`（固定五组件 `order` / `visibility` / `selector` / `updater` / `describer`）；tasksolving 线 = `TasksolvingRule`（固定四组件 `role_assigner` / `decision_maker` / `executor` / `evaluator`）。
- 任务实际由 `agentverse/tasks/<线>/<任务名>/config.yaml` + 两个 Runner（`TaskSolving` / `Simulation`）表达。

**协作机制** `[源码]`：四阶段**硬编码在 `BasicEnvironment.step()` 里**（源码用注释显式标出）：
`# ===== EXPERT RECRUITMENT =====` → `# ===== DECISION MAKING =====` → `# ===== EXECUTION =====` → `# ===== EVALUATION =====`。
接受判据内联：`score is True` 或全部 `>= 8` 则 `success = True`，源码紧跟一句 `# TODO: 8 is an arbitrary threshold`。`is_done()` = `cnt_turn >= max_turn or success`。`advice` 与 `previous_plan` **跨轮传递** —— 这就是论文说的「评估反馈回流到招募阶段」。

**角色：预定义还是动态生成？——两条线答案相反**：
- **tasksolving = 动态生成** `[论文]`+`[源码]`：`RoleAssignerAgent.astep(advice, task_description, cnt_critic_agents)` 让 LLM 生成专家描述列表，再由 `DescriptionAssigner` 写回 `member.role_description = description; member.name = description`。论文原文：「Instead of relying on pre-defined expert descriptions, [it] dynamically generates a set of expert descriptions」。
- **simulation = 预定义**：角色写死在 yaml。
- ⚠️ **一个容易误读的细节**：动态招募只决定「是什么专家」，**不决定「选几个」** —— 人数由配置 `cnt_agents` 固定。

**管理者角色（需要澄清）** `[源码]`：**「Manager」不是全局指挥者，而是一个可选的、仅在特定决策模式下启用的「从多条批评里挑一条」的选择器。**
- 三层结构：`TasksolvingRule`（流程编排者，**纯 Python 对象、非 LLM**）→ 四个策略对象（子 rule）→ `ManagerAgent`。
- `TasksolvingRule.decision_making` 里只有 `if "dynamic" in self.decision_maker.name:` 成立时才把 manager 传下去 —— **Manager 是否参与，取决于配置的 decision_maker 类型**。
- `ManagerAgent` 的实现很特别：让 LLM 输出一个角色名，然后用 `rapidfuzz.fuzz.ratio` 做**模糊字符串匹配**在候选批评里取最高分的那条。**它的输出是一条被选中的批评意见，不是计划、不是调度指令。**
- **`Controller` 这个名字在全仓库未找到**；实际承担流程控制的是 `TasksolvingRule` + `BasicEnvironment.step()` 的硬编码序列。

**HITL** `[论文]`+`[源码]`：**设计上支持，但 main 分支上不可用。**
- 论文 2.4 明确写 human-in-the-loop 是一种可选实现（引 Amershi et al., 2014）。
- 但代码里 `TasksolvingRule.evaluate()` 的整块 `if self.human_eval:` **被注释掉**（含四个维度的 `input()`）；当前生效路径是无条件走 `evaluator.astep(...)`。**全仓库检索 `input(` 只有这 5 处、且全部在注释内。**
- 配置项 `human_eval: false` 仍残留在 `pythoncalculator/config_html.yaml`，但**没有任何活跃代码读取它** —— 死开关。
- GUI 侧的人类输入口有**接线缺陷**：`gui.py` 仅对 `simulation/db_diag` 渲染输入框并调 `self.backend.submit(...)`，而 `Simulation` / `TaskSolving` **都没有 `submit` 方法**；另一条路径调 `self.backend.iter_run(...)`，而 **`iter_run` 全仓库无定义**。属重构遗留的失配代码。
- GUI 实际提供的是 `Next` / `start_autoplay` / `stop_autoplay` / `reset` —— **控制「节奏」而非「审批」**。
- Pokemon 线确实让人下场当玩家（`PokemonEnvironment.astep(..., player_content, ...)`），但那是**人作为对等参与者**，不是人类监督 / 审批 AI 的动作。
- **明确未找到**：审批、中断/暂停 API、人工确认闸门 —— 三类机制在仓库中均无实现。

**状态持久化** `[源码]`：**没有 checkpoint，没有跨运行的持久任务板；所有 agent 状态都在进程内存里。**
- 全仓库检索 `checkpoint|resume|load_state|save_state|pickle|shelve|redis|sqlite`（`*.py`）—— **零命中**。
- 所有 memory（`ChatHistoryMemory` / `SummaryMemory` / `VectorStoreMemory` / `SdeTeamMemory`）均为进程内对象，**memory 目录内没有任何落盘代码**。
- 落盘产物只有两处、都是「结果」不是「状态」：`TaskSolving.save_result()` 写 `./results/<task>.txt`（三段：`[Final Plan]` / `[Result]` / `[Spent]`，**一个 task 一个文件、覆盖写**）；benchmark 往 `results.jsonl` 逐行追加。
- ⚠️ benchmark 有个容易被误认为 checkpoint 的「续跑」：按 `results.jsonl` 行数 `skip_cnt` 跳过已完成的样本 —— **每个样本仍全新 `from_task(...)`，没有任何环境状态被恢复**。

**权限 / 审计** `[源码]`：**三者都没有。**
- **动作分级授权：未找到。** 唯一近似物 `BaseAgent.receiver` 是**消息路由/可见性**（配合 `BasicUpdater` 决定一条消息进谁的 memory），不是「动作准不准做」。工具是「配置即全部」：`ToolUsingExecutor` 从 json 装载工具，**全员共享同一份定义**，无按角色的差异化权限。
- **沙箱：没有，且存在两条会真实执行 LLM 生成代码的路径** ——
  - tasksolving 线：`subprocess.run(command, shell=True, ...)`，**源码上一行就是作者自留的 `# TODO: make it more secure`**；超时靠 `multiprocessing.Process` + `p.kill()`（真能终止）；
  - simulation 线：`exec(code, locals, locals)` / `eval(func_call)`，用 `ThreadPoolExecutor` + `future.result(timeout=5)` 包裹 —— **`concurrent.futures` 的 timeout 无法中断已在运行的线程，故该 5 秒超时对死循环形同虚设**（此点为本报告基于实现的分析，非官方陈述）。
  - 工具执行的隔离外推给 XAgent ToolServer（硬编码 `http://127.0.0.1:8080`），框架本身不做。
- **审计：没有安全审计，只有运行日志。** `Logger` 写 `logs/activity.log` / `error.log`，按「回合/标题」组织而非按「主体—动作—对象」记账，无防篡改设计、不区分 agent 归属。**该模块头注释还残留 Auto-GPT 血统。**

### 2.8 ChatDev

**版本前提** `[官方]`：`main` 分支已经是 **ChatDev 2.0 (DevAll)**，ChatChain / Phase / Role 那一套在 [`chatdev1.0` 分支](https://github.com/OpenBMB/ChatDev/tree/chatdev1.0)。

**核心抽象（1.0）** `[源码]`
- **ChatChain**：顶层编排类，加载三份 JSON（ChatChainConfig / PhaseConfig / RoleConfig），把 `config["chain"]` 存成 `self.chain`、`config["recruitments"]` 存成 `self.recruitments`。
- **Phase**（ABC）：一段「研讨会」的抽象，构造参数 `assistant_role_name` / `user_role_name` / `phase_prompt` / …；子类只需实现 `update_phase_env()` 与 `update_chat_env()` 两个钩子。内置 13 个 SimplePhase。
- **ComposedPhase**：把若干 SimplePhase 按 `cycle_num` 循环的组合体。**不支持嵌套**（源码有显式断言 `# right now we do not support nested composition`）。
- **`ComposedChat`：未找到** —— 我在 chatdev1.0 与 main 两分支全文检索、并在论文正文检索，**零命中**。最接近的真实符号是 `ComposedPhase`。
- **`Assistant` 类不存在** —— 最接近的是 `RoleType.ASSISTANT`（对话轮次身份）、`AssistantChatMessage`（消息载体）、`RolePlaying.assistant_agent`。
- **ChatAgent**：真正调 LLM 的单元（`system_message` + `memory` + `model`），核心 `step(input_message) -> ChatAgentResponse`。
- **RolePlaying**：把**两个** ChatAgent 配成 assistant/user 双人会话；`with_critic_in_the_loop=True` 直接 `raise ValueError("with_critic_in_the_loop not available")`。
- **角色从哪来**：`CompanyConfig/Default/RoleConfig.json`，键是角色名、值是字符串数组。默认 9 个角色（CEO / CPO / Counselor / CTO / CHRO / Programmer / Code Reviewer / Software Test Engineer / CCO）。

**协作机制** `[源码]`：**1.0 是「三级静态」流水线** —— ① 阶段序列静态（`ChatChainConfig.json` 的 `chain` 数组写死 8 项；`execute_chain()` 就是 `for phase_item in self.chain: self.execute_step(phase_item)`，**无分支、无重排、无运行时规划**）；② `phaseType` 只有 `SimplePhase` / `ComposedPhase` 两个合法值；③ **谁跟谁对话也是静态**（写在 `PhaseConfig.json` 的 `assistant_role_name` / `user_role_name`）。运行时唯一「动态」的是 prompt 内容与循环次数。
**MacNet**：链 → DAG，拓扑写在 `config.yaml` 的 `graph: ['0->1', '0->2', ...]`（纯边列表），按拓扑层推进。
**ChatDev 2.0 / DevAll**：换成**声明式可执行图 + cycle-aware 引擎** —— YAML 的 `nodes` + `edges`；DAG 走拓扑排序 + 同层并发；**含环图先用 Tarjan 求强连通分量、抽象成超级节点再递归执行**；**边级动态执行** `dynamic: {type: map|tree, split: ..., config: {max_parallel, group_size}}` —— **这才是「运行时决定任务分配」真正出现的地方**；节点类型是注册表式 8 种（`agent` / `human` / `subgraph` / `python` / `passthrough` / `literal` / `loop_counter` / `loop_timer`）。

**管理者角色** `[源码]`：**1.0 没有「协调者 agent」，协调者是 Python 控制流** —— `ChatChain.execute_chain()` / `execute_step()` 读数组、按 `phaseType` 分派、把 `chat_env` 往下传；**它不发消息、不调 LLM、不做任何判断**。
- CEO/CPO 这类角色**只是「角色文本」**。一个具体发现：**CEO 在全部 12 个 phase 里只出现在 `user_role_name`，从不做 assistant** —— 即它是「需求提出方」，不是下达指令的管理者。
- **CEO + Counselor 的唯一专属场合是「复盘」**：当 `need_reflect` 为 `"True"`，`Phase.self_reflection()` 把整段对话拼成 prompt，**以 `assistant_role_name="Chief Executive Officer"`、`user_role_name="Counselor"` 再起一场一次性的 RolePlaying** 逼出收敛结论。**注意：这仍不是人工介入，是自动自我反思。**
- **能不能被单独对话：不能。** 1.0 没有任何接口能与某个角色单独交谈；`ChatAgent` 实例在 phase 开始时当场新建、phase 一结束就被丢弃。
- **2.0 里「manager」变成用户自己拼的节点**：`yaml_instance/GameDev_with_manager.yaml` 有个 `id: manager` 的 `type: agent` 节点，role 全文是 "You are a manager in the AI driven game development process..."，通过 4 条边连向其他 agent —— **它是被编排出来的普通节点，不是框架内置的协调层**。

### 2.9 Microsoft Semantic Kernel Agent Framework

**核心抽象与组织** `[官方]`：`ChatCompletionAgent` = Kernel + 模型 + Instructions 的对话代理。**`AgentThread`**（SK 1.43 起）抽象会话状态：`ChatHistoryAgentThread` 存内存历史，AzureAI / Assistant / Bedrock 把状态放服务端、以 `thread_id` 续接。
**旧 `AgentGroupChat` + `selection_strategy`（`KernelFunctionSelectionStrategy` / `SequentialSelectionStrategy`）已归档不再维护**，被 `GroupChatOrchestration` 取代 `[官方]`（[归档页](https://learn.microsoft.com/en-us/semantic-kernel/support/archive/agent-chat)、[迁移指南](https://learn.microsoft.com/en-us/semantic-kernel/support/migration/group-chat-orchestration-migration-guide)）。
**五种编排模式**：Sequential（串行传结果）/ Concurrent（广播并收集）/ GroupChat（由 manager 调度）/ Handoff（按 `OrchestrationHandoffs` 移交控制）/ Magentic（由 manager 规划并跟踪进度）。
来源：[Agent orchestration](https://learn.microsoft.com/en-us/semantic-kernel/frameworks/agent/agent-orchestration/)

**管理者角色（重点）** `[官方]`：**两者都是独立类的实例、作编排器构造参数注入，但不是 Agent** —— **不进 members、不能对话、无身份与权限、不能单独授权，也没有「停用」开关，只能替换实现。**
- `RoundRobinGroupChatManager`：轮转发言、`MaximumInvocationCount` 限轮；每轮固定按 `ShouldRequestUserInput` → `ShouldTerminate` → `FilterResults` → `SelectNextAgent` 调用，覆写即改策略。
- `Magentic` 的 manager 是 `StandardMagenticManager`（提示词驱动、需结构化输出模型），SK 文档称其维护共享上下文与进度。
- ⚠️ **一处需要标注的跨版本引用**：`task_ledger`（facts/plan）、每轮 JSON `progress_ledger`、plan/replan 与 checkpoint 钩子这些细节，来自**后继 Microsoft Agent Framework 的同名 API 页**，SK 文档未写明 manager 内部的 ledger 字段结构。
- **未找到 `PromptBasedGroupChatManager` 这个类** —— SK 侧提示词驱动选人需自定义 `GroupChatManager` 子类；`prompt-based manager` 是后继 Agent Framework 的 API（`GroupChatBuilder().set_prompt_based_manager`）。

**HITL** `[官方]`：**有中断与人工参与，无审批工作流。**
- GroupChat 的 `ShouldRequestUserInput` 返回 true 即暂停等人，输入写入 manager 历史并广播全体。
- Handoff 用 `InteractiveCallback` / `human_response_function` 让人入对话，**但 handoffs 只在 agent 间连边，人不是 handoff 目标**。
- `Cancel()` **只停后续消息**，不停已在处理的、也不停 runtime。
- **能否拦住工具调用：能。** `FunctionChoiceBehavior.Auto(autoInvoke:false)` 时 SK 不自动执行工具、由调用方自行处理；`IAutoFunctionInvocationFilter` 可 `Terminate`，**filter 不调用 `next` 即阻断** `[官方]`（[Filters](https://learn.microsoft.com/en-us/semantic-kernel/concepts/enterprise-readiness/filters)）。

**状态持久化** `[官方]`：`AgentThread` 存会话消息与上下文（`ChatHistoryAgentThread` 是**进程内内存** `ChatHistory`；服务型 agent 的状态在被调服务端、仅以 `thread_id` 引用并可 `DeleteAsync`）。**编排状态只活在 runtime**（`InProcessRuntime` = 进程内内存消息总线），一次 `invoke` 结束后只剩返回值，**无内建跨运行持久任务板**；Magentic 的 ledger 属 manager 实例、**随本次运行生灭**。要跨运行得自行序列化 thread。

**权限 / 审计** `[官方]`：**无内建动作分级授权、审批流与审计日志。** 可用件：向模型广播的函数白名单（`FunctionChoiceBehavior.Auto(functions=…, filters 的 included/excluded_functions|plugins)`，**空列表即禁用函数调用**）；`IFunctionInvocationFilter` 可在调用前校验权限，**不调用 `next` 函数就不执行**（官方以「审批流前校验权限」举例）；`IPromptRenderFilter` 可改写或拦下提示词。**审计须在 filter 内自建**，或依赖 Azure AI 服务端记录。

### 2.10 Google ADK

**核心抽象与组织** `[官方]`：
- **`LlmAgent`** = LLM 驱动的非确定性执行单元（name / model / instruction / tools）。
- **Workflow Agents**（官方称 Template workflow）：`SequentialAgent` / `ParallelAgent` / `LoopAgent` —— **由代码而非模型控制子 agent 的执行顺序**。
- **Session** = 一条会话线程（id / app_name / user_id + events + state）；**State** = 该会话的键值草稿本（仅可序列化值）；**Event** = 信息流基本单位（author / content / actions，**携带 `state_delta`、`artifact_delta`、`transfer_to_agent`、`escalate` 等控制信号**）。
- **`sub_agents` 与 agents-as-tools 的区别（很关键）**：`sub_agents` 声明层级，LLM 调 `transfer_to_agent(agent_name)` **把回答责任整体移交**子 agent，**父 agent 退场**，后续用户输入由子 agent 应答；agents-as-tools 用 `AgentTool` 包装，**子 agent 结果回传父 agent 汇总后继续接待用户，控制权不丢**。
- `transfer_to_agent` 由 LLM 决定并产出 FunctionCall，框架写入 `event.actions.transfer_to_agent`；可用 `allow_transfer` 与 `disallow_transfer_to_parent/peers` 限制方向。

**管理者角色** `[官方]`：**ADK 没有名为 supervisor / manager 的原生概念。** 多 agent 的组织范式是「**层级 + 转移**」：中心 `LlmAgent`（文档称 Coordinator）持有 `sub_agents`，靠 LLM 决定 `transfer_to_agent` 交出控制权，或用 `AgentTool` 显式调用。
**ADK 2.0 补上协作工作流**：coordinator agent **自动为每个 subagent 注入同名委派工具**，subagent 用 `mode` 限定行为 —— `chat`（默认，自由对话、手动返父）/ `task`（可澄清、`finish_task` 自动返父）/ `single_turn`（不交互、可并行），**返回即交出控制权**。
**subagent 与 coordinator 都可有独立身份**（name / description / model / instruction / tools）—— 这一点与 CrewAI / LangGraph / SK 的做法**相反**。
`LoopAgent`：`max_iterations` 限定最大迭代轮数；`escalate` 是终止信号，子 agent 置 `tool_context.actions.escalate=True` 即让循环提前结束。

**HITL（四个层次，本报告中最完整的审批设计）** `[官方]`：
1. **工具确认**：`FunctionTool(require_confirmation=True)` 或传阈值函数**按参数动态要求确认**，工具暂停等 yes/no；advanced confirmation 用 `request_confirmation(hint, payload)` 收**结构化回填**（人可改 `approved_days` 等值）。
2. **`LongRunningFunctionTool`**（Go/Java/Kotlin 为 `is_long_running=true`）：`function_call.id` 进入 `event.long_running_tool_ids`，**应用等人工/外部系统回填 `function_response` 后继续，不阻塞循环**。
3. **图工作流 `RequestInput(message/payload/response_schema)`**：以无模型节点形式暂停，响应到达后再放行。
4. **`PolicyEngine` + `SecurityPlugin`**：`evaluate()` 返回 `PolicyOutcome.CONFIRM` 即弹确认。

**前置拦住** `[官方]`：`before_tool_callback` **返回非 None 字典 = 跳过工具本体并以该值作为结果**（返回 None 才放行），`before_agent_callback` 返回 Content 可跳过整个 agent；**Plugin 级钩子优先于 agent 级**。

**状态持久化（本报告中最细的分层）** `[官方]`：
- `InMemorySessionService` = 进程内存，**重启全丢**，仅开发测试；
- `DatabaseSessionService` = 自管关系库（PostgreSQL / MySQL / SQLite），**进程内锁串行化 `append_event` + 行级锁（`SELECT ... FOR UPDATE`）防多副本竞争**；
- `VertexAiSessionService` = Google Cloud Agent Runtime 托管。

**State 前缀语义**：无前缀 = 当前 session；`user:` = 该 user **跨全部 session**；`app:` = 该 app 全 user 全 session；`temp:` = **本次 invocation**，子 agent 共享、**调用结束即丢**。前三种在 Database / Vertex 下持久。
**Events** = 完整交互流水（含 function call/response、state_delta、控制信号、错误码，**即审计与恢复底稿**）；**Artifacts** = 按 filename 版本化的二进制（session 或 `user:` 命名空间），由 `ArtifactService` 管。
**跨运行持久任务板：官方无该原语**。最接近的是 `State(app:/user:)` + Resume 步骤检查点（记录 `current_sub_agent`、`times_looped`）。

**权限 / 审计** `[官方]`：**无统一「动作分级」模型，但有可组合的授权与审计面。**
- **授权三档**：**Agent-Auth**（工具以 agent 自身服务账号行事，靠外部 IAM 限权）、**User Auth**（工具带控制用户的 OAuth token，**只能做用户本人可做的事**）、**工具级策略**（`ToolContext` 传开发者设定的确定性 policy，在工具内校验参数与表白名单、只许 SELECT）。
- **工具确认是第二道闸**：`require_confirmation` 静态/动态阈值，或 `SecurityPlugin` 挂 `BasePolicyEngine`，`evaluate` 返回 `PolicyOutcome.CONFIRM` 时暂停并生成 `adk_request_confirmation` FunctionCall，**应用回 `confirmed + payload` 才执行 —— 可拦在生效前**。
- **审计**：Event 历史本身即流水；**OpenTelemetry GenAI 语义追踪**导出 `invoke_agent` / `execute_tool` / `generate_content` 等 span 与 token 用量；Logging / Debug Logging 插件；**可选 Tool Call Integrity 插件用密钥签名每个 function call，验签通过才允许执行工具**。
- **未找到**：统一的动作风险分级授权框架、内置审计日志存储/查询接口（审计靠 Event 历史 + OTel + 插件日志**外接**）。

## 3. 横向专题

### 3.1 专题一：任务状态是持久的吗？有没有跨运行的持久任务板？

**逐框架答案（「进程重启后，任务和进度还在吗？下次 run 是接着上次还是从零开始？」）**

| 框架 | 一次 run 结束后状态在哪 | 进程重启后 | 跨运行持久任务板 |
|---|---|---|---|
| **LangGraph** | checkpointer 存图状态快照（**thread 内**）+ Store 存自定义 KV（**跨 thread**） | `MemorySaver` 丢；`PostgresSaver`/`SqliteSaver` 留 | **没有**（官方明说只有这两套；任务板须自建） |
| **AutoGen v0.4** | `save_state()` 返回嵌套 dict（含 manager 状态），**要自己 `json.dump`** | 不落盘就丢 | **没有** |
| **CrewAI** | checkpoint（`./.checkpoints/`，`task_completed` 事件）+ `@persist`（SQLite）+ 统一 Memory（LanceDB） | checkpoint 与 Memory 留 | **没有**（企业版有「审批队列」，不是任务板） |
| **OpenAI Agents SDK** | `Session`（SQLite / Redis / Mongo…）存**对话历史**；`RunState` 是单次暂停快照 | Session 留，RunState 需自己存 | **没有** |
| **Google ADK** | `SessionService`（InMemory / Database / Vertex）+ State 前缀分层（`user:` / `app:` 跨 session） | Database / Vertex 留 | **没有**（最接近：State + Resume 检查点） |
| **Semantic Kernel** | `AgentThread`（内存）/ 服务端 thread_id；编排状态活在 `InProcessRuntime` | 进程内丢 | **没有** |
| **MetaGPT** | `workspace/storage/team/team.json`（含 env/roles/actions/memory/state），`--recover_path` 断点续跑 | **留**（这是少数能真正续跑的） | **没有任务板**（但有**可恢复的团队状态**） |
| **ChatDev 1.0** | `WareHouse/<project>_<org>_<timestamp>/` 产物目录（细节本次未取全） | 产物留 | **没有** |
| **CAMEL** | `ChatHistoryMemory` 默认内存；`WorkforceSnapshot` 内存态 | 丢 | **没有** |
| **AgentVerse** | 只有 `./results/<task>.txt` 与 `logs/`；memory 全内存 | **全丢** | **没有** |

**共同结论**：**10 个框架，0 个内置跨运行的持久任务板。** 状态持久化的上限是「会话/线程/单次运行的可恢复快照」。

**框架之外的行业做法（对 collab-platform 更有参考价值）** `[官方]`
有三条「durable execution」路线被明确用于 agent 的长跑工作流，理由一致：**人可能要几小时到几天才回，框架必须能跨重启与升级地等待。**

1. **DBOS**：状态用 `set_event` 外发，用 `DBOS.recv` 阻塞等批准；再用 `list_workflows(PENDING)` + `get_event` 捞出「所有等人批准的 agent」组成收件箱 —— **任务板就是数据库的 workflow 表** `[官方]`（[docs.dbos.dev/ai/hitl](https://docs.dbos.dev/ai/hitl)）。
2. **Restate**：`awakeable` 持久 promise，agent 挂起释放算力，审批人 HTTP resolve 后**从断点续跑**，超时也是持久 timer `[官方]`（[docs.restate.dev](https://docs.restate.dev/ai/patterns/human-in-the-loop)）。
3. **Temporal**：**每个 agent 调用落成 Activity、编排在 Workflow**，崩溃可续跑且**不重发 LLM 调用** `[官方]`（[temporal.io](https://temporal.io/blog/announcing-openai-agents-sdk-integration)）。
4. **GitHub Copilot coding agent**：**指派 issue 入队、draft PR 当状态机**；PR 必人工批准且**发起人不能自批**；agent 只读指派时刻的 issue 内容，后续评论须发在 PR 上。这套「issue = 任务、PR = 状态」的做法，与 collab-platform 的「协作事件流」在形态上最接近。

> **对本项目的启示**：这不是「框架没做好」，而是**分工不同** —— 编排框架管「这一次怎么跑」，durable execution 管「跨重启怎么等」。collab-platform 要的常驻协作状态，**应当做成平台自己的持久层（任务板 + 事件流）**，而把「单次执行」交给可替换的执行器（GM 的推理循环、CI 触发器等）。把这层交给任何现有框架都会拧。

### 3.2 专题二：权限 / 审批 / 审计

**（1）动作分级授权：有没有「一类动作自动执行、另一类必须人工批准」？**

- **有分级（但只有两级）**：CrewAI 的开源侧**没有**，只有构造期工具白名单 + 运行期 `PRE_TOOL_CALL` 钩子 `[官方]`；**CAMEL 的 `LLMGuardRuntime` 是唯一「按风险打分 + 阈值 + 可豁免」的实现**（LLM 对「函数名+描述+参数」打 1/2/3 分，`threshold < score` 拒绝，`IgnoreRiskToolkit` 豁免，默认阈值 2）`[官方]`。
- **有工具级审批（二元 approve/reject）**：LangGraph `HumanInTheLoopMiddleware.interrupt_on` 支持 **approve / edit / reject / respond** 四态 `[官方]`；OpenAI Agents SDK 的 `needs_approval`（可 per-call 回调，**参数无法安全解析时 fail closed**）`[官方]`；Google ADK 的 `require_confirmation`（**阈值函数可按参数动态要求确认**，人还能回填结构化 payload）`[官方]`；AutoGen 的 `ApprovalRequest` / `ApprovalResponse(approved, reason)` `[源码]`；SK 的 `IAutoFunctionInvocationFilter`（不调 `next` 即阻断）`[官方]`。
- **「三级自主 / 留痕 / 待确认」这种业务分级：10 个框架全部未找到。** 框架的分级维度是**工具**，不是**动作的业务后果**。
- **`overridden`（人带理由强行通过）：未找到对应物。** 最接近的是 AutoGen 的 `ApprovalResponse.reason`，但那是**拒绝理由**。

**（2）审计溯源：有没有「谁授权它做的」这种记录？**

| 框架 | 有无内置审计数据结构 | 实际靠什么 |
|---|---|---|
| LangGraph | **无** | LangSmith trace；`resume` 值 + checkpointer **不算审计**（无操作者身份、无理由、无防篡改） |
| AutoGen | **无** | 仅 `ApprovalResponse.reason` + tracing + Magentic-One 的安全建议清单 |
| CrewAI | **部分**：事件总线（`HookDispatchedEvent` 含 outcome/reason/source）+ `SecurityConfig` Fingerprint；企业版有**不可变审计日志**（属平台层） | 企业版才有真审计 |
| OpenAI SDK | **无专用存储** | tracing（agent/tool/handoff/approval span）+ `new_items` 元数据 |
| CAMEL | **部分**：`WorkforceLogger` 记录 task 生命周期 + token，`dump_to_json` | 自建 |
| **Google ADK** | **最接近**：**Event 历史即流水**（作者、函数调用、state_delta、错误码）+ OTel GenAI span + **可选 Tool Call Integrity 插件用密钥签名每个 function call，验签通过才允许执行** | Event + OTel + 插件 |
| SK / MetaGPT / ChatDev / AgentVerse | **无** | 调试日志（AgentVerse 明确定性为「debug 而非追责」） |

> **一句话结论**：**「谁授权了什么动作」这个概念，在所有框架里都不存在。** 它们记录的是「系统发生了什么」（trace / event / log），不是「谁批准的、依据是什么」。ADK 的 Tool Call Integrity 签名是唯一带**密码学强度**的动作授权校验，但它校验的是「调用未被篡改」，不是「有人授权」。

**（3）MCP 协议层：本项目对外提供能力的通道，规范怎么说？** `[规范]`（spec 版本 **2026-07-28**）

- **MCP 没有名为 "tool approval" 的规范。** 审批相关内容散在四处：
  1. **tools 章 Warning**：规定「SHOULD 始终有人能拒绝工具调用」，客户端应落确认提示 —— 但这是 **SHOULD 级**表述 `[规范]`；
  2. **tool annotations**（`readOnlyHint` / `destructiveHint` / `idempotentHint` / `openWorldHint`）供客户端判断是否需确认，**但明文规定是 hint、MUST 当不可信处理**；
  3. **elicitation**：server 向用户取补充信息；
  4. **Tasks 扩展**（SEP-2663）状态机的 **`input_required`** 才承担审批闸门 —— **这才是「暂停等人批准」的正式原语，taskId 即持久句柄**。
- **批准的执行点不在 server、也不在协议层，而在 client/host。** tools 章明确「协议本身不规定任何用户交互模型」；client SHOULD「对敏感操作提示用户确认」「调用前把工具入参展示给用户」。**官方博客据此建议**：可信 server 的 `readOnlyHint` 可自动放行、`destructiveHint` 弹确认，annotations 可喂给策略引擎（如「无批准不得执行 destructive 工具」），但**强调它不是强制手段 —— 硬保证要靠沙箱、网络控制或授权层** `[官方]`。
- **elicitation 的边界（很关键）** `[规范]`：
  - **form 模式**：`requestedSchema` **被限死为扁平对象 + 原始类型**（string / number / integer / boolean / enum，含单多选），**不支持嵌套与对象数组**；
  - **server MUST NOT 借此索取敏感信息**（密码 / API key / token / 支付凭据）；
  - **url 模式**（2025-11-25 引入，SEP-1036）：跳外部 URL，敏感信息不经过 MCP client，client MUST 展示完整 URL 并在用户明确同意后才打开；
  - 响应三态 **accept / decline / cancel**；
  - **规范未把 elicitation 定义为审批原语** —— `accept` 仅表示同意这次交互；且明确划分：授权 MCP client 访问 server 归 authorization 章，**server MUST NOT 用 url mode 给自己授权**。
- **authorization 章** `[规范]`：**MCP server = OAuth 2.1 resource server，MCP client = OAuth 2.1 client**，authorization server 负责与用户交互并发 token。组合 OAuth 2.1 draft-13 与 RFC 6750 / 8414 / 7591 / 8707 / 9207 / 9728。server MUST 实现 RFC 9728 Protected Resource Metadata 供发现；client MUST 带 `resource` 参数绑定受众。**渐进授权**用 `403 insufficient_scope` + `WWW-Authenticate scope=…` 触发 **step-up**。安全实践另要求 **MCP proxy MUST 逐客户端征得同意，并禁止 token passthrough**。
- **审批网关尚无正式规范**：**Interceptors WG**（SEP-1763，2026-04-21 立）正标准化 `validator` / `mutator` 两类拦截器与审计模式，**目的正是解决 sidecar / proxy / gateway 的 M×N 问题** `[官方]`（[Interceptors WG](https://modelcontextprotocol.io/community/working-groups/interceptors)）。

> **对本项目的启示（重要）**：collab-platform 要做「所有外部动作必须经平台中转」，这在 MCP 生态里**恰好是 Interceptors WG 正在标准化、但尚未定稿的那个位置**。这意味着：① 短期没有现成规范可依，平台自建中介层是对的；② 中长期可以对齐 SEP-1763 的 validator/mutator 模型，避免自成一套；③ **不能指望 MCP 的 elicitation 承担审批** —— 它被规范明确限死为「扁平 schema、非敏感信息、accept 只表示同意这次交互」，且有「server MUST NOT 用它给自己授权」的硬约束。要做审批，用 **Tasks 扩展的 `input_required`**（正式原语）或平台自己的审批对象。

### 4.1 可以直接借鉴的（按价值排序）

| # | 借鉴什么 | 出处 | 为什么值得 |
|---|---|---|---|
| 1 | **「暂停 + 落盘 + 外部恢复」的 HITL 形态，而不是阻塞式输入** | LangGraph `interrupt()` + checkpointer `[官方]`；OpenAI SDK `RunState.to_json()`；ADK `LongRunningFunctionTool` | GM 的三级动作里「三级待人确认」可能等几小时。AutoGen 的 `UserProxyAgent` 正是因为阻塞而「cannot be saved or resumed」——反面教材 |
| 2 | **审批对象带 `reason` 字段** | AutoGen `ApprovalResponse(approved, reason)` `[源码]`；ADK `request_confirmation(hint, payload)` 可回填结构化值 | `overridden` 四态里，`blocked` 和 `overridden` 都必须带理由——框架层已经证明了「理由要作为审批的一等字段」 |
| 3 | **按参数动态决定是否需要确认** | ADK `require_confirmation` 支持阈值函数；LangGraph `interrupt_on` 的 `when` 谓词 | 「触发结构化 + 判据自然语言」的策略配置，需要一个「按动作参数求值」的判据挂点 |

| 5 | **map/reduce 式边级动态执行** | ChatDev 2.0 的 `dynamic: {type: map\|tree, split, max_parallel}` `[官方]` | 把「一个事件触发 N 个子任务」做成配置而非代码 |
| 6 | **Task Ledger / Progress Ledger 双账本** | AutoGen Magentic-One Orchestrator `[官方]` | GM 要「判断这里有问题」，需要「目标账本」+「进度账本」两个结构化视角；注意它在 AutoGen 里只是提示词概念，**我们应当把它做成真数据** |
| 7 | **Event 历史即审计底稿** | Google ADK `[官方]` | Event 携带 author / content / actions / state_delta —— 「谁在何时做了什么、状态怎么变的」天然可追溯。比额外写一份审计日志更不容易漏 |
| 8 | **动作签名校验（Tool Call Integrity）** | Google ADK `[官方]` | 「所有外部动作必须经平台中转」的密码学加固：中转层验签后才放行 |
| 9 | **`workflow` 表即任务板** | DBOS（`list_workflows(PENDING)` + `get_event` 组收件箱）`[官方]` | 「待审批收件箱」不必另建一套存储，从持久执行引擎的待办表里捞即可 |
| 10 | **issue = 任务、PR = 状态机，且发起人不能自批** | GitHub Copilot coding agent `[官方]` | 面向真实工程协作，而不是模拟公司；「不能自批」这条可以直接用于 GM 的动作授权 |

### 4.2 我们的差异点（三点，都是框架层的空白）

**① 常驻（resident）**
- 现状：所有框架的 agent 都是「被 run 唤起 → 干活 → 结束」。没有 supervisor 是常驻的；Magentic-One 的 Orchestrator 状态是提示词内的、随 run 生灭。
- 我们：GM 订阅**协作事件流**、主动判断。它的存在不依附于某次运行。
- 结论：**GM 不能实现为「框架里的一个 supervisor 节点」** —— 那些节点的生命周期就是 run。GM 必须是平台自己的常驻服务，运行在事件流之上。

**② 跨运行（cross-run）**
- 现状：没有框架内置持久任务板；`thread_id` / `session_id` 的语义都是「一次会话」，不是「一个长期存在的任务」。
- 我们：任务板与事件流是平台的持久层，一次「GM 判断 → 动作 → 人审批」可以横跨多天、多个执行器、多个终端。
- 结论：**状态留在平台侧，执行器无状态**。这条与 CrewAI checkpoint（接着跑完一次 kickoff）和 LangGraph thread（续一次对话）都不同。

**③ 面向真实工程协作（real engineering collaboration）**
- 现状：CrewAI / MetaGPT / ChatDev 是「模拟一家公司」（角色扮演型流水线）；AutoGen / CAMEL 是「让 agent 互相聊天」；LangGraph / ADK 是「让工程师画图」。
- 我们：人和 AI 在**同一个共享空间**，动作对象是**真实的 Git 提交、CI 构建、任务状态、对话**。人不是「批准 agent 的一个工具调用」，而是**换一个座位在同一张桌上**。
- 结论：**「GM 判断的依据」这件事没有先例。** 框架的 recorder 都在记录「系统做了什么」（trace / event / checkpoint），**没有一家在记录「一次判断的依据是什么」**。这是本项目最独特、也最需要自己定义数据结构的地方（建议：判断 = 事件引用集合 + 判据版本 + 结论 + 动作清单 + 授权路径）。

### 4.3 三个明确的风险提示

1. **不要指望用现成框架的 supervisor 做 GM。** CrewAI 的 manager 不能带工具、不能单独授权；LangGraph 的 supervisor 包**已被官方放弃**；SK 的 manager「不是 Agent」；AutoGen 的 SelectorGroupChat 管理者是「一次模型调用」。它们的形态与「可被单独授权、单独停用的常驻管理者」正交。
2. **MCP 层不要自造审批原语。** elicitation 被规范限死（扁平 schema + 非敏感信息 + 不是授权原语），并明文禁止 server 用 url 模式给自己授权。审批走 Tasks 扩展的 `input_required` 或平台自定义对象，并**跟踪 SEP-1763（Interceptors WG）**以便未来对齐。
3. **「平台中转」必须做成强制路径，而不是约定。** AgentVerse / MetaGen 这类框架的教训是：一旦 agent 拿了直连工具（`subprocess.run(shell=True)`、`exec()`），审计与拦截同时失效。参考 ADK 的做法 —— **拦截器有权「以返回值代替执行」**，且**默认拒绝**（SK `autoInvoke:false` + 空函数列表即禁用；ADK 的 confirmation 是 fail closed）。`overridden` 这类「带理由强行通过」的通道，必须显式经过平台并落审计。

## 7. 一句话回答最初的六个问题

1. **有哪些主流框架？** 10 个：CrewAI、AutoGen、LangGraph、MetaGPT、OpenAI Agents SDK、CAMEL、AgentVerse、ChatDev、Semantic Kernel Agent Framework、Google ADK。另有可直接借鉴的非框架路线：Temporal / Restate / DBOS（durable execution）。
2. **怎么组织多个 Agent？** 三种形态：流水线派（固定 SOP）、群聊派（会话 + 发言者选择器）、图编排派（显式图/层级）。**角色来源**：代码/配置定义为主，真正「动态生成角色」的只有 AgentVerse（tasksolving 线，LLM 生成专家描述）与 CAMEL（`RoleAssignmentAgent`）。**任务分配**：CrewAI hierarchical、MetaGPT MGXEnv、CAMEL Workforce、AgentVerse tasksolving 是运行时决定，其余多为静态。
3. **有没有管理者 / 协调者？** 有，但**没有一个是有独立身份、可单独对话、可单独授权、可单独停用的实体**。CrewAI 的 manager 工具被清空且不可停用；AutoGen 的 `GroupChatManager` / `SelectorGroupChat` 是「一次模型调用」（v0.2 的 auto 甚至是嵌套两 agent 对话 + 正则匹配）；LangGraph 的 supervisor 是「一次 LLM 调用 + handoff tool」，且官方已放弃该包；SK 的 manager「不是 Agent、不进 members」；OpenAI SDK「有 manager 说法、没有 manager 类」；ADK 干脆没有这个概念。**唯一有独立状态的是 Magentic-One 的 Orchestrator（Task/Progress Ledger），但那是提示词概念、不可持久化。**
4. **人类怎么参与？** 成熟形态是「**暂停 + 持久化 + 外部恢复**」（LangGraph `interrupt` + checkpointer、OpenAI `RunState`、ADK `LongRunningFunctionTool`）。**能在动作生效前拦住**：LangGraph 的 tool 级 `interrupt`、ADK 的 `before_tool_callback` 返回非 None 即跳过工具、SK 的 filter 不调 `next` 即阻断、CrewAI 的 `PRE_TOOL_CALL` + `HookAborted`、AutoGen 的 `approval_func` / `ApprovalResponse`。**反面教材**：AutoGen v0.4 的 `UserProxyAgent` 阻塞且不可 save/resume；AgentVerse 的 HITL 论文承诺、代码不可用。
5. **任务状态持久吗？有没有跨运行的持久任务板？** 持久化上限是「会话/线程/单次运行的可恢复快照」（LangGraph checkpointer+Store、AutoGen state dict、CrewAI checkpoint+Memory、OpenAI Session、ADK SessionService、MetaGPT team.json）。**跨运行的持久任务板：10 个框架全部没有。** 行业做法是把状态放到框架外（Temporal / Restate / DBOS / GitHub Issues）。
6. **有权限 / 审批 / 审计吗？** 审批是**工具级二元**（approve/reject，最好的是 ADK 的 require_confirmation + 结构化回填、LangGraph 的四态决策），**没有业务动作的三级分级**。**审计：没有一家记录「谁授权了这个动作」** —— 记录的是系统流水（ADK Event + OTel + Tool Call Integrity 签名最接近），真正的审计要靠外部（LangSmith、企业版 AMP、自建）。**MCP 协议层**：没有 tool approval 规范，`elicitation` 被限死且不是授权原语，审批网关的标准化（SEP-1763）**尚在 Draft**。

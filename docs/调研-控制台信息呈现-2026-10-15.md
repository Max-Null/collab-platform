# 控制台信息呈现 · 业界模式调研（2026-10-15）

> 调研对象：`public/console.html`（882 行，单文件、内联 CSS/JS、零第三方依赖）。
> 上游：[控制台设计](控制台设计-2026-10-13.md)、[控制台功能点](控制台功能点-2026-10-13.md)。
> 触发问题（用户原话）：**「现在的信息展示方式几乎是纯文字，有没有更加友好的方式？」**
>
> **方法说明**：以下所有外部结论均来自本次联网检索，链接随文给出。凡我只读到标题、未读到正文的来源，会**明确标注为「标题级证据」**——不假装读过。

---

## 摘要

**结论一：「更友好」在这个平台上不等于「更多图形」。**

这个控制台不是一张白纸，它已经有五条硬判据（见 §一）。其中至少三条**明确地反对某些图形**：`error` 不许用绿色、样本 < 30 不画分布、控制台不下判断。所以任何建议如果只是「把文字换成图」，会直接撞上这些判据。

**结论二：当前真正「纯文字」的只有三处，而它们恰好是三个不同的问题。**

| 位置 | 现状 | 它其实在回答什么问题 | 该用什么表达 |
|---|---|---|---|
| 平台状态卡的 meta 行 | 一行 mono 小字 | 「它现在还在不在」**以及「它是断续的还是稳的」** | 一排心跳格（§二·模式 1） |
| 观察表「样本 N < 30，不画」 | 一句散文 | 「这条策略到底出了什么事」 | 点图，不画比例（§二·模式 6） |
| 待办卡 / 记录卡正文 | 结论长句 + 依据列表 | 「这一条要不要我现在处理」 | 一行可扫摘要 + 分组（§二·模式 3） |

**结论三：「图」的价值集中在一处** —— 把「需要你动作的」和「只是留了痕的」在视觉上分开。业界所有成熟做法（Buildkite、Linear、GitLab）都在做这同一件事，而它们的界面复杂度远高于本平台。**可以先只抄这一件事。**

## 一、先钉住：这个平台已有的判据（建议不得违反）

从 `public/console.html` 与两份上游文档中提取，以下五条是**有意为之**的设计决定，不是待改进项：

| # | 判据 | 出处 | 对本报告的约束 |
|---|---|---|---|
| 1 | **控制台不下判断**，只做「转述」与「提问」 | 设计 §一 | 不能加健康度评分、趋势判断、升级建议 |
| 2 | **未命中不进待办**；`error` 必须与 `miss` 并列、**永远不用绿色或「已通过」** | 设计 §2.2、功能点 A3/B2 | 色带/色块里不能给 `error` 一个「看起来还行」的颜色 |
| 3 | **统计按策略 + 版本分组**，不聚成一个数 | 设计 §3.7 二 | 不能建议「合并成一个总命中率」 |
| 4 | **样本 < 30 不画分布** —— 理由是图形比数字更有说服力，因而画错时更危险 | `TIPS.chart` | 不能建议「小样本也画个饼看看」（本报告的模式 6 说明为什么点图**不**违反这一条） |
| 5 | **TIPS 正文只有一份**（`console.html` 是事实源），文档只列要点 | 功能点 §开头 + `check-ssot.mjs` | 本报告不复制 TIPS 正文到别处 |

另外一条自我约束：**界面只排布服务端已经给出的值，不在前端派生新结论**。现有代码里 `renderStatus` 不自己算「多久没动静算停摆」、`renderStats` 不自己算健康信号，都是这条的体现。本报告的所有建议都遵守它。

## 二、八个可借鉴的模式

### 模式 1 —— 心跳格带：把「还在不在」从一句话变成一排格子

**解决的什么问题**：一个圆点只能回答「此刻」，回答不了「最近稳不稳」。而「每隔几轮就迟一次」和「一直很稳」在当前的实现里长得一模一样 —— 只有 `late` 与 `alive` 两种标题字，而历史上的抖动完全看不见。

**长什么样**（Grafana Status history）：

> "each field or series is rendered as a horizontal row, with multiple boxes showing the different statuses"

每条序列一行，横向排一列方块，每个方块一个时间片的状态。三个细节是它的精髓：

1. **"Unlike state timelines, status histories don't merge consecutive values."** —— 连续相同的状态**不合并**，一格就是一次。这正好对应本平台「每一轮心跳都落一条」的口径。
2. **缺数据不画颜色，画空隙**：文档的示例数据里 null 与空值 "visualized as gaps in the status history"。
3. **空值有独立的显示约定**：标准选项里 "No value: Enter what Grafana should display if the field value is empty or null. The default value is a hyphen (`-`)."

- 案例：[Grafana Status history 文档](https://grafana.com/docs/grafana-cloud/visualizations/panels-visualizations/visualizations/status-history/)
- 反面教材（标题级证据）：Grafana 官方仓库至今挂着两个相关 issue —— [State timeline with gap in data still display (#79675)](https://github.com/grafana/grafana/issues/79675)、[Status History not showing correct time range when data missing (#42995)](https://github.com/grafana/grafana/issues/42995)。两个标题说的都是同一件事：**缺口在色带类图里会被画错**。我只读到标题，但标题本身就是论点。

**更值得警惕的一条机制**（Datadog，已读正文）：

> "If metrics are absent from a monitor's evaluation window, and the monitor is not configured to anticipate no-data conditions, the evaluation may be skipped. In such a case, the monitor state is not updated, so a monitor previously in the `OK` state remains `OK`."

**没有数据的时候，状态不更新 —— 于是它保持上一次的绿。** 这正是 Datadog 那份文档里 "sparse metrics"（稀疏指标）一节的标题问题。同一份文档把 "No Data" 列为**独立状态**，并指出 `Require Full Window` 这类配置会让评估落进 No Data。

- 案例：[Datadog · Troubleshooting Monitor Alerts](https://docs.datadoghq.com/monitors/guide/troubleshooting-monitor-alerts/)（`monitor state and status`、`Sparse metrics`、`"No Data" status with rollup functions` 三节）
- 真实困惑（标题级证据）：Atlassian 社区有一条提问 [「we are not extracting any data from any apis still seeing green bars only in statuspage」](https://community.atlassian.com/forums/Statuspage-questions/we-are-not-extracting-any-data-from-any-apis-still-seeing-green/qaq-p/1870061)。标题说得很清楚：**根本没在取数，界面却还是绿的。** 我只读到标题。

**适不适合这个平台：适合，而且是第一优先。** 理由：

- 它回答的正是第一屏要回答的问题（设计文档把「平台状态」放在累计数字之上，理由写在 `console.html` 的注释里：一个停了 21 小时的平台，累计数字与一个正在跑的一模一样）。
- 实现成本极低：一排 `<span>` 或一个 `repeating-linear-gradient` 即可，零依赖，与现有 `.bar` / `.flow` 同构。
- **但有三条硬约束**，缺一条就会变成上面那个 Atlassian 帖子：
  1. **「没跑」必须是空隙，不能是灰块、更不能是绿块。** 灰块会被读成「跑过但没事」——那是 `miss` 的语义，不是 `absent` 的语义。
  2. **「从没跑过」与「跑过但停了」必须长得不一样。** 前者整条空，后者前面有格子、后面断掉。平台已经区分了这两种状态（`never` / `stopped`），格带必须把这个区分**可视化**，而不只是靠标题字。
  3. **格子的顺序要有明确的时间锚**（最近的一轮在右还是左，要写出来）。Grafana 那个「时间范围不正确」的 issue 就是栽在这里。

### 模式 2 —— 每段一个「净结果」，而不只是数字

**解决的什么问题**：五格流程图现在每格是「一个数字 + 一行小字」。读者要自己心算才能知道账平不平 —— 而这张图存在的全部理由就是「四段的数目要对得上账」。

**长什么样**（GitLab pipeline mini graph）：

> "Pipeline mini graphs take less space and can tell you at a quick glance if all jobs passed or something failed. They show all related jobs for a single commit and **the net result of each stage** of your pipeline."

要点：占位小、**每段给一个「净结果」而不是明细**、阶段可展开（"Stages in pipeline mini graphs are expandable"）。完整图则提供两种分组（按 stage / 按 `needs` 依赖），且依赖连线要显式打开（"optionally select **Show dependencies** to render lines"），悬停某个节点会高亮所有前置节点。

- 案例：[GitLab · CI/CD pipelines](https://docs.gitlab.com/ci/pipelines/)
- 对照（GitHub Actions，已读正文）："The graph displays each job in the workflow. **An icon to the left of the job name indicates the status of the job.** Lines between jobs indicate dependencies." 并且 "To view a job's log, click the job." —— **图本身就是入口**。[Using the visualization graph](https://docs.github.com/en/actions/how-tos/monitor-workflows/use-the-visualization-graph)
- 「什么时候图会失效」，Buildkite 自己承认了：Canvas 视图 "is not as useful when zoomed out on a large number of steps"。[Buildkite · Build page](https://buildkite.com/docs/pipelines/build-page)

**适不适合这个平台：适合，但只需抄「净结果」，不必抄「依赖图」。** 这里有一个读代码才看得出来的细节：

当前 `renderFlow()` 的五格里，**「判定」与「留痕」用的是同一个值**（都取 `f.judgments`）。也就是说这两格**永远相等**，它不是一个「可能被违反的账」，而是一个恒等式 —— 图上有两个占位、一份信息。

真正**可能不等的只有一处**：`表态` vs `事件`（代码里 `actCls = f.actions < f.events ? 'warn' : ''`，副标题写「⚠ 少于事件数 N」）。第三处恒等式是 `判定 = 命中 + 未命中 + 没做成`（三者本就同源）。

所以本平台能做的「净结果」只有一句话，可以做得非常强硬：

```
账对得上   ← 表态 == 事件
账不平：少 3 条  ← 红条 + 指出缺在哪一段
```

**建议**：在图的下方（不是每格里）加一行**对账条**，只在**不平**时出现，写明「少在哪一段、少几条」，并且**能点进去看是哪几条事件**（对应功能点 §四「每个统计数字旁边能点回原始记录」）。平的时候不出现 —— 这与平台自己的「有话说才发」（设计 §3.4）是同一条纪律。

同时，「判定」与「留痕」两格的恒等关系**值得在「?」里说清**：现在的 `TIPS.flow` 已经写了「留痕 = 判定数」，但读者看到两个相同的数字仍会怀疑自己看错了。这不需要加图形，只需要让文案承认这是一件事的两个说法。

> ⚠️ 注意：「账平不平」是**机械等式比较**，不是判断。它不产生新结论，只比较两个都来自记录的数 —— 因此不违反判据 1。

### 模式 3 —— 「需要你动作的」置顶，其余折叠

**解决的什么问题**：一个列表里混着「要你处理」和「只是留了痕」，读者就得逐条读过去才知道有没有自己的事。

**长什么样**（Buildkite）：

> "For large builds, group the sidebar by state and collapse lower-priority states such as **Waiting** and **Passed**. Steps grouped under **Waiting for input** need your action, so they're **kept near the top** instead."

配套还有：侧栏默认按 pipeline 顺序、**可切换为按状态分组**，且 Buildkite 会**记住你的选择**；`f` 键循环跳转到下一个失败。

- 案例：[Buildkite · Build page](https://buildkite.com/docs/pipelines/build-page)

**同一件事在工单队列里的形态**（Linear，两个已读正文的来源）：

1. **Triage**：一个特殊收件箱，"an opportunity to review, update, and prioritize issues before they are added to your team's workflow"。动作是 accept / decline / mark as duplicate / snooze（快捷键 1/2/3/H）。最狠的一条是：
   > "**By default, we exclude triage issues from all views** since triage is considered to be outside the normal workflow."
   要看它们必须**显式**加筛选条件。它不是「多一个标签」，是**默认从视图里消失**。
   还有一条可配置的门禁：「Can I require priority to be set before an issue leaves Triage? **Yes.**」
   [Linear · Triage](https://linear.app/docs/triage)
2. **Priority inbox**：
   > "The new **Priority** tab separates what needs your attention from what can wait, so something like a review blocking a release never gets buried."
   且默认挑选逻辑由产品给出（"Linear selects what appears in Priority by default"），用户可改。
   [Linear · Priority inbox changelog](https://linear.app/changelog/2026-09-03-priority-inbox)

**适不适合这个平台：适合，而且这一条比它看起来更重要。**

平台已经做对了一半：`miss` 不进待办（功能点 A1），待办只放 `hit` 与 `error`。但**待办内部没有分组**：功能点 A3 要求「需处置的**判断没做成**……在待办里排在最前」，而现在的实现里 `error` 卡片与 `hit` 卡片唯一的差别是一个标签的颜色（`.tag.error` 是土黄色）—— 在一屏十条卡片里，这**不足以**把最需要人处理的那类顶出来。

具体建议：

- **按结局分组，而不是按时间排序**：两组标题「**判断没做成 · N 条**」与「**等你表态 · N 条**」。前者在前。
- **给卡片加左边界色条**（现有 `.status` 卡片已经用了这个手法：`border-left:3px solid`），`error` 用 `--err`，`hit` 用 `--hit`。这比标签颜色醒目得多，且是同一个视觉语汇的复用。
- **把 `miss` 的默认可见性说清楚**：它现在在「判断记录」里完整保留（正确），但待办页不提它。Linear 的做法是「默认排除 + 显式筛选」；本平台的「判断记录 → 只看待回应」已经是这个思路，**不需要改**。

> 这一条严格服从判据 2：`error` 得到的是**最强的视觉重量**，不是最好的颜色。

### 模式 4 —— 空态必须说清「为什么空」，而且要保证那句话不是错的

**解决的什么问题**：一个空的列表，最坏的情况不是「没信息」，而是**给了错误的信息**。

**长什么样**（NN/g）：

> "Totally empty states cause confusion about how and whether the system is working."
> 更糟的是给出**不准确**的系统状态消息：先显示 "No records"，几秒后再填上内容 —— 这种消息 "particularly harmful"，最好的情况是用户等到了内容但**从此不再信任这个应用**，最坏的情况是用户早就走了。

正确做法是给一句具体的话，例如 "There are no records to display for the selected date range"。

- 案例：[NN/g · Designing Empty States in Complex Applications: 3 Guidelines](https://www.nngroup.com/articles/empty-state-interface-design/)
- 同一篇里给了一个正面例子（Datadog 的 "Star your favorites to list them here"）：空态顺便教你怎么让这个地方不再空。

**适不适合这个平台：这个平台已经做到了，而且是超出业界水平的**，两处值得点名表扬并**明确列为「不要动」**：

1. 待办空态写的是「没有待表态的判断」，并紧跟一句否定性提醒：**这不是「一切都好」——也可能是判据根本没跑过**。这正是 NN/g 说的「传达系统状态」，而且比 NN/g 的示例更强：它不仅说了「空」，还说了「空有两种含义，不要读错」。
2. **首屏不会闪过空态**：`renderTodo` 只在 `load()` 的 `fetch` 完成后被调用，初始 DOM 里 `#todoList` 是空的而不是「没有待表态的判断」。NN/g 点名的那个「先说不存在、再填内容」的坑，这里**天然不存在**。

**但有一个要修的地方**（这是本次调研唯一发现的**实现缺陷**）：

> 空态那句话的末尾是「**看上面运行图里的「策略」一格**」。而运行图现在的五格是 事件 / 判定 / 表态 / 留痕 / 人 —— **没有一格叫「策略」**。

「策略」这个词只出现在「留痕」格的副标题（「每条策略各留一条（N 条策略）」）和 `TIPS.flow` 的正文里。也就是说，这句指路**指到了一个已经不存在的名字上**。读者按它去找，找不到。

这类问题的性质与「不准确的空态消息」完全一样：**它不报错，只是把人引到错的地方。** 建议：改成与图一致的措辞（例如指向「事件」格或「留痕」格，取决于它想让人看什么），并且**把「空态的指代必须指向图上真实存在的标签」做成一次核对**——因为运行图改名（从「策略」演进到五格）会静默地让所有旧指代失效。

### 模式 5 —— 「什么都没跑」也是一个状态，要有位置

**解决的什么问题**：稀疏是常态。当大部分时间什么都没发生时，界面有两种错误反应：要么什么都不显示（读者分不清「没发生」和「没在看」），要么显示一个「正常」的占位（把「没有数据」冒充成「数据正常」）。

**长什么样**：

- **GitLab：被跳过的 pipeline 仍然被创建。** "An empty pipeline, with no jobs or stages, is still created in GitLab. The pipeline appears in the UI and can be returned in API responses. The pipeline status is **Skipped** in the UI, and `skipped` in the API." —— 什么都没跑，但**它有一个明确的状态值，且在 UI 和 API 里一致可见**。[GitLab · CI/CD pipelines](https://docs.gitlab.com/ci/pipelines/)
- **Datadog：`No Data` 是独立状态**，与 OK / Alert 并列，且有自己的成因说明（`Require Full Window`、rollup 与评估窗口不匹配）。[Datadog 文档](https://docs.datadoghq.com/monitors/guide/troubleshooting-monitor-alerts/)
- **Grafana：空值渲染成空隙**，且有专门的 "No value" 显示约定（默认 `-`）。[Grafana 文档](https://grafana.com/docs/grafana-cloud/visualizations/panels-visualizations/visualizations/status-history/)

**适不适合这个平台：适合，而且成本几乎为零 —— 因为数据已经有了。**

平台的状态判定已经是**四种**（`alive` / `late` / `stopped` / `never`），这比大多数监控产品还细。问题只在**呈现**：四种状态现在都渲染成「一个圆点 + 一句话」，而 `never`（还没部署）与 `stopped`（挂了）在视觉上只有文字差别。

- 模式 1 的心跳格带天然解决一半：`never` 是**整条空**，`stopped` 是**前面有格子、后面断掉**。
- 另外建议在状态卡上让 `never` 与 `stopped` 的**处置提示**分开（一个说「还没部署」，一个说「挂了，要拉起来」）—— 现有 `TIPS.status` 已经写了这个区分（「前者是还没部署，后者是挂了，要做的完全不同」），但那是藏在「?」里的，第一眼看不到。

### 模式 6 —— 小样本画「点」，而不是画「比例」

**解决的什么问题**：这是本报告里唯一直接触及既有判据的建议，所以先说结论：**它与「样本 < 30 不画」并不冲突，反而更彻底地执行了那条判据的意图。**

先看那条判据的原文理由（`TIPS.chart`）：样本不足时画图，「会把随机波动画成一个很大的扇形」。注意它反对的是**扇形/比例**这种把 n 归一化的表达 —— 5 个点里 3 个命中被画成 60% 的扇形，读者看到的是「60%」而不是「3 个点」。

**点图不做归一化**：一行固定宽度的格位（例如 30 格），每个记录占一格，按结局上色。读者看到的是「**确实只有 5 件事**」——它不会、也不能被读成比例。

- 依据（标题级证据）：一篇论文的标题就是论点 —— [Show the data instead of a bar graph for continuous data](https://openresearch-repository.anu.edu.au/server/api/core/bitstreams/adb57e57-ddc4-4472-ac26-2e720c4a6df9/content)。我只读到标题，未读到正文。
- 依据（已读正文）：Tufte 在 sparkline 一文的开篇引述自己的设计原则 **"General idea = max[data], min[design]"**，并强调 sparkline 的价值在于「把大量数据放进视野内、让人看见数据的纹理」，而不是把数据压成一个形状。[Tufte · Sparkline theory and practice](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)
- 同一篇里还有一条**警告**，正好是这个建议的反面约束：密集的线条会产生 "unintentional optical clutter"（摩尔纹般的视觉噪声），**当线条与间隙尺寸接近、且对比强烈时最糟**。所以点图的点**不能太密、不能高对比**；样本超过阈值后应当换回条形 —— 否则点图自己就变成了噪声源。

**适不适合这个平台：适合，而且我认为这是性价比最高的一条。**

现状：观察表里 `total < 30` 的行渲染出来的是一句散文（「样本 12 < 30，不画 —— 画出来会把噪声当模式」）。一屏五六个策略版本，就有五六句这样的散文 —— **这是「纯文字」抱怨最集中的地方**。

建议的具体形态：

| 样本量 | 画什么 | 为什么 |
|---|---|---|
| `total = 0` | **什么都不画**，留空 + 一行浅色说明 | 「没有这一行」与「这一行是 0」是两件事 |
| `1 ≤ total < 30` | **点图**：`total` 个格位，按结局上色；已回写过反应的点加实心描边 | 不做归一化，只显示「有几件、各是什么」 |
| `total ≥ 30` | 现有的分布条（不变） | 样本够了，比例才有意义 |

三点说明：

1. **点图顺便表达「看过」分母**：功能点 B3 要求把「被评估的次数」与「人真的表过态的次数」分开（`TIPS.denom` 专门讲了这件事）。点图里「实心点（已回写）vs 空心点（未回写）」一眼就能看出这两者的比例 —— 而这正是升级判据唯一认的那个分母。
2. **所有行用同一套格位宽度**，这样不同策略版本的点可以**纵向对齐比较**（Tufte 说的 "adjacent in space rather than stacked in time"）。这是列表做不到的。
3. `error` 点必须用 `--err`，**不能**用绿色或灰色 —— 判据 2 在这里同样适用，而且**点图里更容易犯这个错**（设计者容易把「大部分是绿的」当成「看起来不错」）。

> ⚠️ 必须写清的边界：**这份建议不是「把阈值降到 0」**。比例图仍然只能在 ≥30 时出现。点图是**另一个东西**，它回答的是「有几件」，不是「占多少」。

### 模式 7 —— 随机对照：值得知道，但**不值得做进界面**

**解决的什么问题**：人会在纯随机数据里看出「趋势」。

Tufte 给出了这个现象的完整描述与一个检验方法：

> "When people look at random number tables, they see all kinds of clusters and streaks (even in random data). Similarly, when people are asked to generate a random series of bits, they generate **too few long streaks** ... because their model of what is random greatly underestimates the amount of streakiness in genuinely random data."

他的做法叫 **Interocular Trauma Test**：把观察到的真实序列，与**按同样的总体比例重新随机生成的 10 条序列**并排放在一起对比。如果看不出区别，那么「你看到的那个模式」在随机数据里同样常见。

- 案例：[Tufte · Sparkline theory and practice](https://www.edwardtufte.com/notebook/sparkline-theory-and-practice-edward-tufte/)（文中 "Diluting Perceptual Cluster/Streak Bias" 一节，附一个可反复重生成的随机对照演示）

同一篇里另一条与本平台直接相关的警告：sparkline 可以带 "importance flags"（灰色带表示正常范围，越界即异常），但 ——

> "The color coding should be modest... We don't want to turn sparklines into **vulgar stoplight charts** (with their vivid red-yellow-green attitude)."

**适不适合这个平台：这条「值得知道」，但结论是「不进界面」。**

理由：它需要随机重排与并排展示，是一套**分析动作**，不是一个**展示元素**。而且本平台的读者面对的是「一条策略的一个版本、十几条记录」——在这个尺度上，正确的动作不是「把随机对照画出来」，而是**不画比例**（模式 6）。给一个只有 12 条记录的版本配上随机对照图，会让界面更热闹、却不增加任何判断力 —— 按任务书的要求，这属于**应明确标注为不值得做**的那一类。

**它真正该去的地方是「判据改进」的离线环节**：当有人主张「这条策略最近命中率明显变高」时，用脚本重排一次做对照，比在界面上争论有用。这与设计文档 §3.8 双轨的定位一致 —— 那是评估机制，不是展示机制。

### 模式 8 —— 队列门禁：让「离开队列」需要一个动作

**解决的什么问题**：队列里的人会顺手点「采纳」清空它，于是队列的数据质量下降，而**下降得看不出来**。

**长什么样**（Linear）：Triage 可以配置为「离开队列前必须补齐优先级」。同一处还给了另一条更轻的做法 —— **snooze**：把一条推到「你选定的时间，或这条有新活动时，**两者取先到**」，而不是无限期挂着。

- 案例：[Linear · Triage](https://linear.app/docs/triage)

**适不适合这个平台：部分适合，而且要有回退预案。**

现状：回写反应的输入框是选填的（`placeholder` 写着「为什么（判据要靠它改进，会进库）」）。而只有「明确否定」进升级条件（`TIPS.upgrade`），也就是说**否定是唯一有后果的那一种反应**。

建议：**只对「否定」要求填理由**，采纳与无视保持选填。理由：

- 否定是升级判据的唯一输入，它的理由质量直接决定判据能不能改进；
- 采纳与无视本身是低信息动作，对此强制只会让人干脆不回写 —— 而设计 §3.9 已经把「人愿意回写」当作整个机制的前置条件，**回写的量比每条回写的质量更重要**，不能拿它冒险。

配套的止退机制（必须有）：如果强制之后**单位时间的回写总数明显下降**，就退回选填。这与平台自己的「改口径的理由必须是原来的口径是错的，不能是数字不好看」（设计 §3.11 四）是同一条纪律的反面用法。

「snooze」这一条**不建议做**：本平台的待办项没有「以后再说」的语义 —— 一条判断要么被表态、要么一直在等你。加一个 snooze 会创造第三种状态，而它的时间到了之后仍然要处理，只是把问题推后。**这是让界面更复杂但不增加判断力的典型，明确不值得做。**

## 三、明确不适用的（以及为什么）

| 不适用 | 出处 | 为什么本平台不需要 |
|---|---|---|
| **时间范围选择器 + 缩放平移（pan/zoom）** | Grafana 的 status history 支持拖拽 zoom、双击 zoom out、拖 x 轴平移 [来源](https://grafana.com/docs/grafana-cloud/visualizations/panels-visualizations/visualizations/status-history/) | 那是给「找某个时刻发生了什么」的分析场景。本平台读者不是来分析历史的，他要知道「现在该不该管」。数据几百到几千条，一个「最近 7 / 30 天」开关就到顶了 |
| **Value mappings / thresholds 配置化** | Grafana 的字段配置体系（同上） | 零构建单文件里，中文文案直接写死更清楚。更要紧的是：**引入配置就等于引入第二份事实源**，与判据 5（SSOT）冲突 |
| **No Data 告警配置、alert flapping 抑制、group retention** | [Datadog 文档](https://docs.datadoghq.com/monitors/guide/troubleshooting-monitor-alerts/) | 这些是**告警通道**的事。本平台目前没有告警通道（播报是阶段三，且默认关着），现在配置它们是给不存在的问题写代码 |
| **NOC / 值班大屏** | —— | 大屏设计的全部前提是「远距离、多人在场、被动扫视」。这里读者是一个人坐在电脑前，主动打开页面 |
| **时间轴长卷（GitHub Activity 那种）** | —— | **我的判断**：稀疏事件会把时间轴拉成一堆空白加几个孤立小点，而读者要找的是「哪条要我处理」，不是「什么时候发生过什么」。列表 + 筛选在这个规模上严格更优。（Tufte 的 optical clutter 警告支持「别把稀疏数据摊成一条长带」这个方向，但他没直接谈时间轴长卷） |
| **热力格（GitHub contributions 那种）** | 相关证据：[Grafana #79675](https://github.com/grafana/grafana/issues/79675)、[#42995](https://github.com/grafana/grafana/issues/42995)（标题级） | **危险**。两个理由：① 本平台事件稀疏，热力格会几乎全空 —— 一整片空白比一句话更让人困惑；② 格位粒度（按小时/按天）会**制造**密度错觉，而无数据在热力格里通常被画成「最浅的色」= 看起来像「有数据但很少」。这正是两个 Grafana issue 说的那类错 |
| **饼图 / 环形图** | 平台自己在 `TIPS.chart` 里已论证 | 已是共识，无需重复 |
| **排行榜、环比箭头、趋势线** | 设计 §3.3 已禁 | 小样本下趋势线是最危险的一类图：它会把两三个点连成一条「上升」的线。且排行会变成 KPI |
| **脉动/呼吸的动画心跳点** | —— | **我的判断**：动画会被自动读成「活着」。而进程停了的时候，它不动的样子与「我没注意看」在视觉上无法区分 —— 换句话说，**动画把一个「需要被看见的状态」变成了「需要被察觉的变化」**。静态格带反而更可靠 |
| **深色主题 / 移动端适配 / 导出 CSV** | —— | 读者一个人在桌面上看。任何一条都会增加这个单文件的行数，而不增加判断力 |

## 四、如果只能做三件事

按**对「一眼看懂」的贡献**排序。

### 第一件：平台状态区加一条心跳格带（模式 1 + 5）

**做什么**：在状态卡里加一排历史心跳格（每格一轮，宽度约 5px），四种状态各有明确画法：正常 / 迟了 / 停了（后面断掉）/ 从没跑过（整条空）。悬停显示该轮的时间与结果。

**为什么排第一**：
- 它加在**第一屏的第一个元素**上 —— 一次改动影响每一次打开页面；
- 它把一个**需要读文字才能回答**的问题（「它还在不在，稳不稳」）变成不需要读的问题；
- 它是唯一一个能同时修掉「从没跑过 vs 跑过但停了长得一样」这个缺陷的形态；
- 实现成本最低（一排 span，零依赖，与现有 `.bar` 同构）。

**判据**：做完之后，一个从没部署过的环境与一个跑了三天后挂掉的环境，**不看文字也能分辨**。

### 第二件：观察表在小样本时画点，不写散文（模式 6）

**做什么**：`total` 在 1 到 29 之间时，画 `total` 个格位的点图（按结局上色，已回写的点实心）；`total ≥ 30` 时保持现有的分布条；`total = 0` 时留空。

**为什么排第二**：
- 这是「纯文字」抱怨最密集的地方（一屏五六句「样本 N < 30，不画」）；
- 它**顺便**把功能点 B3 那个「评估 vs 看过」的分母差显示出来了，而这个分母是升级判据唯一认的东西；
- 它是唯一一个能在同一屏里做**纵向对齐比较**的形态（不同策略版本的点对齐后，一眼能看出哪条版本的 error 点更多）。

**判据**：一眼能看出「哪条策略版本有 `error`」而不需要逐个读单元格。

### 第三件：待办按结局分组 + 卡片加左边界色条（模式 3）

**做什么**：待办区分成「判断没做成 · N 条」与「等你表态 · N 条」两组；卡片加 `border-left:3px`，`error` 走 `--err`、`hit` 走 `--hit`。

**为什么排第三**：
- 设计文档说「待办决定控制台有没有用」，而它现在是纯文字卡片流；
- 功能点 A3 已经要求 `error` 排在最前，但当前实现只用一个标签颜色体现 —— **要求与实现之间有落差**，这条改动是补上这个落差；
- 它复用已有的视觉语汇（`.status` 卡片的左边框），不引入新的表达方式。

**判据**：打开页面能立刻知道「有几件事等你，其中几件是失败的」。

### 紧随其后的第四件（如果还有余量）

修掉待办空态里那个**指向不存在的「策略」一格**的指代（模式 4），并顺手核对所有「看上面 X」的指代是否还指向图上真实存在的标签。这一条的价值不在视觉，而在**它现在是一句错的话**。

## 六、一句话总结

**这个控制台不需要变得像 Grafana，它需要变得像 GitLab 的 mini graph 加 Linear 的 Priority：把「需要你动作的」顶出来，把「一共只有这几件事」如实画出来，把「没有数据」老老实实留成空白。** 图形只在能减少一次心算的地方加；其余地方，让它继续是文字。

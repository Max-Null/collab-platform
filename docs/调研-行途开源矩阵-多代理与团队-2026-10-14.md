## 二、多代理 / 团队模式的核心资产

### 2.1 `xingtu-orchestrate` —— 编排入口（最完整的一份）

`xingtu-skills/skills/xingtu-orchestrate/SKILL.md`。主会话当**编排器**，子代理当 **worker**：

```
主会话（编排器）：拆任务 → 定依赖 → 派发 → 收口
子代理（worker）：干活，产物落盘
```

**六条铁律**（原文，值得逐条看）：

1. **并行 ≤3** —— 理由是「人的 review 带宽」，不是机器资源
2. **共享资产只读** —— 写冲突的任务改串行
3. **总控不代写** —— 主会话只拆解/派发/审核收口，不替子代理写内容
4. **消息只传状态，产物走落盘** —— 会话间不搬内容
5. **闸门静态** —— **路径动态编排 ≠ 免检**
6. **发布是外发动作** —— 自动跑到「产物齐备」为止，点发布要人拍板

**闸门注入点表**（每站过闸才放行）：

| 站点 | 闸门 |
|---|---|
| S1→S2 | 素材没有的不编造，【待补】留痕 |
| S2→S3 | 事实未被改动（只动表达） |
| S3→S4 | 审查 P0 清零，**审查结论必须回读** |
| S4→S5 | 发布包齐套（台账比对） |
| S5 | 隐私全绿 / 去 AI 味 / 时序 dry-run |
| S6 | **boss 显式拍板** |

**失败处理**：一路失败 → 带失败原因重派 1 次 → 再失败 → 降级为主会话串行，或报人弃/改。
**写冲突**：检测到冲突立即改串行，**已完成部分不回滚**。

### 2.2 `cavecrew` —— 子代理的输出契约（省主上下文）

三种子代理预设（investigator / builder / reviewer），**关键不在角色，在输出契约**：

```
investigator: <Header>:\n- path:line — `symbol` — note\ntotals: N.
builder:      <path:line-range> — <change ≤10 words>.\nverified: <OK | mismatch @ path:line>.
reviewer:     path:line: <emoji> <severity>: <problem>. <fix>.\ntotals: N🔴 N🟡 N🔵 N❓
```

**它解决的问题**：子代理的 tool result 会**原样注入主上下文**。一次返回 2k token 的散文，就吃掉 2k 的主上下文预算；同样结论压成 ~700 token，20 次委派下来就是「上下文耗尽」和「跑完」的差别。

判据（原文）：**「想让子代理的输出只占 1/3 token 就用它；想要散文就别用。」**

还有一条**自动降级**：安全警告、不可逆操作的确认、任何片段歧义会被误读的场合 → 子代理**临时改回正常语言**，之后再压。

### 2.3 `agent-patterns-template` —— 三形态选型

`xingtu-ai-engineering/methodology/agent-patterns-template.md`。基于 Anthropic 的《Building Effective Agents》（2024-12，8 模式）与《Common workflow patterns》（2025）。

| 维度 | Agent | Subagent | Workflow |
|---|---|---|---|
| 上下文 | 自持载入 | **派生即隔离** | 逐 agent 隔离 |
| 适用 | 单域专家 / 蜂群 | 2-5 文件 1-2 服务并行 | 跨 3+ 服务 / 需拓扑序屏障 |

**反模式**（原文）：单任务套重 Workflow｜多任务全串行｜不按依赖并行（共享文件冲突）｜N=1 开 Subagent。

**检查清单**里两条判据值得记：

- **选对形态？**（N=1→串行；2-5 文件→Subagent；跨 3+ 服务→Workflow；**P0→串行**）
- **文件冲突验证？**（修改清单交集 = ∅）

### 2.4 `xingtu-automations` —— 定时任务的工具中立清单

17 条定时任务，散在 WorkBuddy / Claude Code / cron 三个平台。它把每条任务落成**五个要素**：

| 要素 | 最容易丢的地方 |
|---|---|
| 触发 | rrule ↔ cron ↔ launchd 互转时写错星期/时区 |
| **工作目录** | **头号事故源**：路径指到历史残留目录，对着空壳干活 |
| 意图 | prompt 全文 —— 迁移时只搬了名字，prompt 留在原地 |
| 产物落点 | 没有落点 = 无法判断跑没跑 |
| 失败留痕 | 静默失败是常态 |

**一条纪律**：「**完成判定认落盘凭证**：产物 mtime / git log / 退出码，**不认模型自述「已跑」**。」

### 2.5 `case-003 跨 Agent 口径漂移` —— 与我们的平台最直接相关

`xingtu-sdd/case-studies/003-cross-agent-drift/case.md`。

**问题**：多 Agent 协作下，同一事实（工具清单 / Skill 实体数 / 编号号段 / 发布节奏）在工作区里有 **3-5 处副本**，各 Agent 只读被注入的那一份，改一处忘 N-1 处。

实测出来的四种漂移，其中两种特别值得看：

- **防线自带盲点**：「开工必读」的坏例索引自己烂了 —— 索引表停在旧编号，详情已有新条目，**入口比内容旧**
- **编号撞车**：按号写稿会拿错题（后果最重）

**方案三件套**：

| 层 | 做法 |
|---|---|
| **P1 规则** | 枚举类事实**禁止内联复述**，必须写「取值以 X 为准」 |
| **P2 注册表** | 机器可读清单收口一处，**消费脚本从注册表读值，脚本与文档同源** |
| **P3 守卫** | 单一命令扫全部声明面，漂移即非零退出；接入改动闸门 |

**非目标**（明确不做的）：不做跨 Agent 记忆同步总线；不做文档自动重写（**只报错，不擅自改人写的正文**）。

**验证方式（值得抄）**：**人造漂移夹具** —— 故意制造一次漂移（改号 / 重复编号），守卫**必须变红**；**抓不到 = 守卫无效**。

## 三、与我们平台的对照

这一节是这份调研真正要产出的东西。

### 3.1 位置不同，别抄错

他们是**编排器**（多代理怎么分工干活），我们是**闸门与账本**（干完之后谁来判断、依据留不留、人怎么表态）。

**所以**：他们的「编排模式映射表」「单篇 DAG」这些**对平台不直接适用** —— 平台不做编排，平台接的是编排产生的结果。

但**他们定义的「闸门」正是平台要实现的东西**，这一层可以直接对读。

### 3.2 独立得出同一条判据的，有三处

| 他们的原话 | 我们文档里的 |
|---|---|
| 「完成判定认落盘凭证，**不认模型自述「已跑」**」 | **评估失败 ≠ 通过**（三态结局，error 单列） |
| 「**审查结论必须回读**」（S3→S4 闸门） | 判断记录里存的是**当时模型说了什么**，不是可复现的推理过程 |
| 「**闸门静态**：路径动态编排 ≠ 免检」 | 策略的判据固定（有 id、有版本），事件是动态的 |

第一、二条是我们分别在两个独立场景里踩出来的同一条判据 —— 这种重合比互相引用更有说服力。

### 3.3 可以直接借鉴的四条

1. **「人造漂移夹具」的思路** —— 故意制造一个该被抓到的样例，守卫必须变红；抓不到就是守卫无效。
   → 我们的 `fixtures/events/mr-003-mismatch.json` 已经是这个形状（声称改错别字、实际改鉴权）。**可以把这条变成一个固定动作**：每条策略必须有一个人造命中样例，且它在管道里确实能命中。

2. **「消息只传状态，产物走落盘」** —— 会话间不搬内容，只传「产物在哪个路径」。
   → 我们的评论正文与判断记录是「产物」，评论里给的是**记录 id 与依据**，不是把整条推理搬进 MR。同一个原则。

3. **「总控不代写」** —— 编排者只拆解/派发/审核收口，不替 worker 写内容。
   → 对应我们的「控制台自己不下判断」：控制台只转述已有记录（并指回 id），要下判断就走策略。

4. **注册表 + 守卫防口径漂移** —— 枚举类事实禁止内联复述。
   → 我们有一处已经在漂：`docs/控制台功能点-2026-10-13.md` 里的「?」文案口径，与 `public/console.html` 的 `TIPS` 是**两份**。目前靠人同步。这条建议就是为它准备的。

### 3.4 明确不采纳的

| 他们的做法 | 为什么不采纳 |
|---|---|
| 并行 ≤3（理由：人的 review 带宽） | 那是**内容生产**场景的带宽约束。平台的并发是事件驱动的，按事件到达走，不设人为上限 |
| 深度档 / Flash 档的模型分档 | 平台不替策略选模型 —— 用哪家是配置（`LLM_*` 环境变量），不是编排决策 |
| 「不做跨 Agent 记忆同步总线」 | 这是在**没有平台**的前提下做的减法。GM 的长期记忆正是要解决跨会话这件事，只是我们把它放在**判断记录**这个可查证的地基上，而不是做同步总线 |

## 五、治理四件套（第二轮细读）

这一轮读的是 `governance/constitution-template.md` 与 `skills/xingtu-rule-keeper/SKILL.md`。
它们讲的**不是多代理怎么干活，而是规矩怎么立、怎么保证不烂** —— 这恰好是我们平台的正题。

### 5.1 「规则是愿望，hook 才是墙」

宪法模板对治理的反模式给了三条：

1. 只写愿望不写红线
2. **红线无机械拦截（规则是愿望，hook 才是墙）**
3. 红线泛滥无门禁

**第二条是本轮最有价值的一句。**

对照我们：策略就是那堵墙，而**处置级别就是墙的高度** ——

| 级别 | 墙的高度 | 他们的说法 |
|---|---|---|
| 1 只提示 | 不是墙 | 愿望 |
| 2 留痕 | 半堵墙 | 有记录但不拦 |
| 3 待人确认 | 墙 | 机械可拦 |

于是「观察期」这件事有了另一层说法：**它是把愿望升级成墙的过程，而升级的依据是「这堵墙拦对了没有」**。这跟我们定的「只有明确否定进升级条件」是同一件事的两半。

### 5.2 安全三条件：退出 / 幂等 / 回滚

宪法模板要求「计费/库存/权限」这类动作必填三条件：

| 条件 | 含义 | 我们的现状 |
|---|---|---|
| **退出** | 可中止 | `comment` 可删；`hold_merge` 未实现 |
| **幂等** | 重入安全 | **刚修过一个真 bug**：轮询反复拉到同一个 MR 会重复落记录 |
| **回滚** | 失败可恢复 | 没有 —— 发出去的评论收不回来 |

**这是平台动作设计该有的检查清单**，我把它列进了待办（见 §六）。

### 5.3 「复制 = 第二份 SSoT = 漂移源」

`xingtu-rule-keeper` 的铁律原话：

> 规则正文只存在于 `rules/RULES.d/`，本 skill **不缓存、不复制正文**（复制 = 第二份 SSoT = 漂移源）。

而且它有一条**专门的检查**（L6）：**skill 内嵌 ≥6 条规则 ID 且含规则正文特征 → 告警，提示改为实时抽取**。

**这直接击中我们一处真实问题**（上一轮就记下了）：控制台的「?」文案口径，在 `docs/控制台功能点-2026-10-13.md` 与 `public/console.html` 的 `TIPS` 里**是两份**，目前靠人同步。

按他们的判据，**SSoT 是代码里的 `TIPS`**（那是实际显示给人看的那一份），文档该改成只写「这一组要讲清什么」（元描述），不抄正文。

### 5.4 加规则的四联动 + dry-run + 自证

他们的 `rule_add.py` 把四步做成一条命令：

```
先备份 → 写分册（ID 递增）→ 回速查表 + 回计数 → 回写 CHANGELOG
默认 dry-run，逐处打印 old→new；--apply 才落盘
落盘后自跑 lint 自证
每个定位串必须唯一匹配，匹配 0 或多处会中止，不写任何文件
```

**这跟我们在设计文档 §3.7 里定的「改规矩也要带依据 / 版本历史 / 回滚」是同一条路，但他们做细了三处**：

- **默认 dry-run，逐处打印 old→new** —— 改之前先看见将要发生什么
- **落盘后自跑自证** —— 改完立刻验证，不靠人记得去验
- **定位串唯一匹配否则中止** —— 「防弹」，宁可不动也不改错地方

这三条都该进阶段四的策略管理。

### 5.5 体积门禁

宪法模板的检查清单里有一条：**体积 < 2.5KB（随阶段裁剪）**；配套还有 `harness-size.sh -g` 这样的机械门禁。

理由是不言自明的：**常驻配置会随时间膨胀**，而膨胀的配置会挤掉真正要紧的东西。
这与 `skills/harness-governance`（常驻配置治理）和 `skills/token-audit`（配置瘦身）是同一件事。

**对照我们的 GM 记忆**：我们定的四条失效触发里，**没有一条是「它太长了」**。
记忆的注入预算是个硬约束（设计 §3.10 里说了「只有可检验的才能自动生效」，但没说数量），**数量本身也该有闸**。

## 六、平台该不该发 skill（不只是 MCP）

### 6.1 缺口

平台现在对外只有 MCP。MCP 的 `tools/list` 给的是**工具名 + 参数 schema + 一句话描述**。它不告诉接入的 Agent：

| 它不知道 | 后果 |
|---|---|
| **什么时候该用** | 干完活不申报，平台什么都看不到 |
| **怎么组合** | `submit_change` 之后要不要 `record_reaction`？不知道 |
| **有什么坑** | `title` 是**被检验的主张**，随手写会让判据判错，而 Agent 无从知道这件事 |
| **边界** | 什么不该做、什么要等人 |

**一句话**：**MCP 提供能力，不提供用法。** 用法得另有载体 —— 那就是 skill。

### 6.2 形态

第一版可以是**一个只读工具**（`get_usage_guide`）返回一份 SKILL.md 全文，也可以把同一份内容**发布到 AI 中台的技能注册中心**（Nacos），让接中台的 Agent 自动装配。

**两条路共用同一份正文** —— 这正是 §5.3 那条铁律（只有一份 SSoT，其它都是引用）。

### 6.3 内容大纲（草案）

```
platform-usage（平台使用指引）
├─ 你是谁、这道闸门在哪儿（一句话定位，含「平台不写代码、不做编排」的边界）
├─ 什么时候要找平台
│    ├─ 干完一次变更 → submit_change（含「title 是主张不是依据」这条最容易写错的）
│    ├─ 看到一条判断不同意 → record_reaction（含「为什么」必须写，判据靠它改进）
│    └─ 接手一条工作线 → list_judgments 先看平台已经看过什么
├─ 每条工具的一句话口径（与 MCP 的 description 同源，不复制）
└─ 边界：平台不做的事（不编排、不代写、不替人拍板）
```

⚠️ 这份 skill **只写用法，不复制工具描述与判据正文** —— 复制就是第二份 SSoT。

## 七、第三轮：三条判据与一个解释了困境的洞察

这一轮读 `INSIGHTS.md` / `engineering/loop-engineering.md` / `methodology/quality-gate-template.md`。

### 7.1 「description 是常驻税」—— 直接击中我们刚发的 skill

`INSIGHTS.md` 的原文：

> **description 是常驻税**：全装 40 个实测 ≈7.1K token，为按场景分包的 4 倍。**省 token 的工具若写法不当反而成为最大税源。**

它给出的预算：**desc 字符 < 200；> 400 需理由；> 800 禁入**；正文 **< 200 行，超出下沉 `references/`**。

**为什么这击中我们**：`skills/platform-usage/SKILL.md` 的 frontmatter description 写了一百多字，正文也不短。那份指引是**给接入的 Agent 读的**，一旦按 skill 机制装配，description 就是每轮在场的税。**我们刚为了"讲清楚"把税写高了**。

**要做**：压 desc 到 200 字符以内，正文里能下沉的细节移到 references/。**这件事该有个守卫**（同 `check-ssot.mjs` 的思路）——笔头一直比闸门松。

同一份 INSIGHTS 里还有两条值得记：

- **「双胞胎技能不共存」** —— 两个 skill 职责重叠时，要在**双方的 description 里互相声明分工**，否则**双双误触发**。
- **「无 SKILL.md 的目录是僵尸」** —— 不生效，却制造「装了 = 有效」的错觉。（与我们「空跑出全部未命中比不跑更坏」同源。）

### 7.2 「无拦截价值的沉淀不必反哺」—— 记忆的第二条判据

`loop-engineering.md` 的循环是：

```
使用 → 问题 → 沉淀 → 反哺 → 下次自动拦截 → 回环使用
```

**每转一圈多拦一个坑。** 而其中最有用的一句是：

> **无拦截价值的沉淀不必反哺。**

对照我们在设计 §3.10 定的那条：「只有**可检验**的记忆才能自动生效」。

**这是同一件事的两半**：

| 判据 | 问的问题 |
|---|---|
| 可检验（我们的） | 这条记忆**错了**，会不会有记录显示出来？ |
| 有拦截价值（他们的） | 这条记忆**对了**，能不能挡住什么？ |

**两条都不满足的沉淀，既不会错也不会挡 —— 那就只是话。** 建议合并成一条：记忆必须同时可检验**且**能影响判断，否则不注入。

同一份里另有两条纪律值得抄：

- **「治理是节奏不是事件」** —— 周期跑审计，不是出了问题才跑。
- **「RED-5 追加式：反哺只做加法，不覆盖已有红线/规则/枚举值」** —— 与我们「策略只新增版本、不改历史」同源。

### 7.3 ⚠️ 「循环取胜的前提是验证成本低廉」—— 这一条解释了我们的困境

> **loops win where verification is cheap**（循环取胜的前提是验证成本低廉）。
> —— `loop-engineering.md` 〇节

**这句话正好戳中观察期跑不动的原因。**

我们的观察期要人**逐条回写反应**（采纳 / 否定 / 无视）。这是一次**高成本验证**：每条判断都要人重新看一眼、做个判断、写句理由。于是——

- 人不会做 → 数据攒不出来 → 升级阈值永远算不出来 → 后面三层机制（升级、双轨、记忆的反向证据）全部空转
- 而**这个死结不是靠"再强调一次请回写"能解开的**，因为它是成本问题，不是意愿问题

**修的方向只有一个：把验证变便宜。** 目前能看到三条，都还没定：

| 方向 | 做法 | 代价 |
|---|---|---|
| **区分「没人看过」与「看了没管」** | 现在是三态（采纳 / 否定 / 无视），缺**「没人看过」**这一态。观察期的分母应当是**被人看过的**，不是全部判定 | 要改 schema 与统计口径 |
| **批量表态** | 一次勾选多条、一键"这批都对" | 界面改动；且批量容易变成新的走过场 |
| **默认表态** | MR 合了、没人反对 → 自动记"默认采纳" | **会污染数据** —— 人没看和采纳是两回事，混起来正是我们一直在防的那种错 |

**第一条我认为是必须先做的**，而且它本身就是个正确性问题、不只是省事：

> 「**没人看过**」和「**看了但没管**」是两种东西。现在它们都落进 `ignored`，
> 于是统计上分不清「这条策略没人关注」和「这条策略被看过并被放过」——
> 而这两者对「该不该升级」的含义完全相反。

### 7.4 门禁的反模式：形同虚设比没有更糟

`quality-gate-template.md` 给门禁列了三条反模式：

1. 跳门禁（`--no-verify`）→ 事故漏网
2. 口头承诺无证据 → 无法复核
3. **形同虚设（空 check / 过不了就删）→ 更糟**

第三条对应我们一个还没有信号的场景：**一条策略跑了很久、一次都没命中** —— 是它没用，还是事件根本不在它的覆盖范围里？

平台现在**没有任何提示**这件事。可以借他们的做法：给策略加一个「**零命中**」信号（跑了 N 次、命中 0 次，且 N 够大时提示），因为**「拦不住」和「没什么可拦」在数据上长得一样** —— 又是那条判据换了个地方出现。

## 八、第四轮：常驻配置的减法治理

读 `xingtu-skills/skills/harness-governance/SKILL.md`（150 行，讲的是「怎么把常驻配置做小做准」）。

### 8.1 ⚠️ 膨胀的真代价不是 token，是「模型会选择性忽略」

原文第一句：

> 任何 agent 工作区的「常驻配置」（写给模型的系统提示 / 规则 / 技能 / 子代理 / 钩子 / 设置项）都会随时间膨胀，
> **膨胀到一定程度模型会选择性忽略，反而降低质量。**

**这比「占预算」严重得多。** 占预算是个可测量的成本，选择性忽略**不是**——它不会报错，模型会**照样自信地给出判断**，只是有些规则它已经不再真的在看了。

**直接对应 GM 的记忆**：我们定的四条失效触发（生存期 / 反向证据 / 锚点 / 冷退）管的是「记错了」。**没有一条管「记得太多」**。而记忆一多，GM 的行为不是「想得更周全」，是**开始漏看其中几条 —— 且它自己不知道**。

> 这也是「控制台」该显示而暂时没显示的一类东西：**GM 这次判断到底看了哪些记忆、漏了哪些**。

### 8.2 一条极简判据：「删掉它会犯错吗？不会 → 删 / 沉降」

它的四把标尺：

| 标尺 | 阈值 |
|---|---|
| 常驻上下文占比 | **< 有效窗口的 5%** |
| 主入口文件行数 | **< 200 行**（> 400 行模型开始漏读） |
| 单文件大小 | **< 16 KB** |
| **「写通过删除」** | **每条规则问一句：删掉它会犯错吗？不会 → 删 / 沉降** |

**最后一条最有用**，因为它可以逐条问，不需要统计。对照我们已有的两条判据：

| 判据 | 问的问题 |
|---|---|
| 可检验（设计 §3.10） | 它**错了**，有记录显示得出来吗？ |
| 有拦截价值（调研三轮 §7.2） | 它**对了**，能挡住什么吗？ |
| **删掉会犯错吗**（本轮） | 它**不在**，会出事吗？ |

三条是同一条判据的三个面。**第三条最好用**，因为它把问题从「它有没有用」换成了「没有它会怎样」—— 后者人答得出来，前者常常答不出来。

### 8.3 「机械门禁不因减文本而撤」

它给瘦身划了一条不许动的底线：

> **保留底线（瘦身时不许动）**：机械门禁类 —— 由 hook / 脚本强制的体积、格式、安全校验，**不因「减文本」而删除**。
> **人读得懂的规则可以沉，机器兜底的红线不能撤。**

对照我们：**策略的判据可以简化、可以降级观察，但「能不能拦」这件事本身不能被简化掉**。这正是设计 §3.7 说的「改规矩是重决定」。

三条纪律也值得抄：

1. **只移不删（沉降优先于删除）** —— 拿不准的先沉降为按需加载，不物理删。
2. **先删后加（unhobbling）** —— 不确定时**先删**、跑代表性任务看是否退化、退化了再**加回最小必要**；而不是攒着不敢删。
3. **人审恒定不可跳过** —— 语义取舍归人，agent 只做**可逆操作**。

第 2 条与我们「双轨」的形态不同但目的相同：**都是「先拿证据再定」，而不是「先争论再拍脑袋」**。

### 8.4 CONFLICT 的定位方法：「别一上来改 skill」

它专门用一节讲**冲突类问题**（同一件事有三套口径打架），其中一句判据非常准：

> **关键判据：skill 正文可能本来就是对的 —— 漂移根因高频藏在规则分册、AGENTS/系统提示类入口文件的旧默认兜底，以及跨层多套口径打架（同一约定三处三个版本）。别一上来改 skill。**

**这正好复核了我们处理 SSoT 漂移时的选择**：我们把 `docs/控制台功能点` 里抄来的正文删掉、保留 `console.html` 的 `TIPS` 作为事实源 —— **正是「先定哪一层是误导层，再动手」，而不是反过来**。

它还有两条**豁免铁律**，是给「全仓清扫旧口径」用的：

- **语境豁免** —— 出现在「禁用 / 作废 / 旧 / 仅…才用」等否定或历史语境中的是**合法残留**，不误删。
- **边界豁免** —— 不同子系统可能**合法使用另一套约定**，只清本辖区内的残留，别跨界误伤。

**这两条我们的守卫还没有。** `scripts/check-ssot.mjs` 现在的判据是「出现 ≥ 15 字符的子句就报」，于是两件事会误报：一是在**讨论某条 TIPS 措辞**的文档（引用是正当的），二是**调研笔记里引用别处文案**。目前没触发只是因为恰好没写；该补一个豁免标记。

> 顺带一条**自指检查**：这四条纪律里有一条是「**治理工具本身不得成为新污染源**」（只读优先 / 备份先行 / 范围隔离 / 单文件试点 / 可回滚）。我们的守卫也要守这条 —— 它别自己长成一个需要维护的东西。

### 8.5 治理是节奏，不是事件

它的周期设定：

- **模型升级 / 换代** → 全量深扫（旧兜底规则必过一遍）
- **定期** → 每 ~30 天轻扫；每半年或大版本一次 **ablation 式复核**（整段清空、只对真实失败点逐条加回）
- **每次改动后** → 回归体积量 + 一致性检查 + 功能冒烟

**ablation 式复核**这个做法本身值得记：不是「逐条找该删的」，而是**整段清掉、只把真实出错的地方加回来** —— 从「还有没有能删的」换成了「到底哪些是必需的」。这跟「删掉它会犯错吗」是同一个思路的极端版。

**对照我们**：`docs/待办.md`（T5）里记着「desc 预算还没有守卫」。这一节能补上守卫该守什么：**体积、入口行数、以及那条「删掉会犯错吗」的自查**。

## 九、第五轮：会话与记忆（对我们记忆设计最直接的一轮）

读 `engineering/context-engineering.md`、`session/` 下的三份模板、以及 `skills/session-sediment/SKILL.md`。

### 9.1 ⚠️ 缺的那条路径：记录 → 记忆 → 策略（「错只犯一次」）

`session-sediment` 的沉淀偏好表里有一条：

> **纠偏即时机械化**：高频纠偏 → 沉淀为铁律/清单，**错只犯一次**。

**我们的记忆设计里没有这条。** 回头清点一遍我们给记忆写了什么：

| 我们定过的 | 管什么 |
|---|---|
| 来源、版本、批准人 | 它是怎么来的 |
| 生存期 / 反向证据 / 锚点 / 冷退 | 它什么时候**失效** |
| 可检验性安全阀 | 它**能不能自动生效** |
| 注入留痕 | 它**影响过**哪些判断 |

**全是「记忆作为背景知识怎么活下去」，没有一条是「一条记忆什么时候该毕业」。**

而它的路径是清晰的：**坑 → BCI → Gate → 自动拦截**。对应到我们这边就是：

```
判断记录  →  记忆  →  策略
（每次判定）  （归纳出的模式）  （固化成判据，机械执行）
```

**这与第 5.1 条「规则是愿望，hook 才是墙」是同一个洞察的第二个落点**：记忆是愿望（影响判断但不强制），策略是墙。一条反复被验证的记忆**停在愿望这一层就是浪费** —— 它明明已经够格变成墙了。

**判据（待定，但方向清楚）**：同一条记忆被**反复用上**、且它影响过的判断**被人采纳**，就该提议升级为策略。

> ⚠️ 这条与「双轨」的关系要想清楚：双轨是「改已有判据」的对照机制；升级是「新增一条判据」。后者更容易——它不影响任何现有判断，只是多一道闸。**所以升级的评审成本可以比双轨低。**

### 9.2 记忆的两条新要求：记原因 + 记可执行动作

`session-sediment` 的偏好表第一条：

> **Why + How to apply**：每条记忆记原因 + 可执行动作。

对照我们定的「可检验」（它**错了**，有记录显示得出来吗？）。**这两个是不同的轴**：

| 要求 | 问的问题 | 缺了会怎样 |
|---|---|---|
| **可检验**（我们的） | 它**错了**，看得出来吗？ | 错了也不会退场，永久带偏 |
| **可执行**（他们的） | 它**对了**，我该做什么？ | 读了等于没读，白占一份常驻税 |

**两条都要。** 一条记忆如果既检验不了、又执行不了，那它就只是一句话 —— 而每句话都在交常驻税（§9.3）。

同一张表里另有几条可直接抄的：

- **决策链记 Why** —— 记推理依据，不只结论。（我们判断记录里的 `reason` 就是这个，但**记忆**里还没这个要求。）
- **诚实讲局限：不夸大成败，数据双向交叉** —— 与「统计口径不能为了好看而调」同源。
- **时间戳纪律：写前 `date` 取真值，禁编造。**
- **不擅自产出文档：先询问用户。** —— 精神是「不要自己决定产出什么」。

### 9.3 「每 KB 常驻 = 固定上下文税」，以及 context rot

`context-engineering.md` 把它量化了：

- **5% 规则**：常驻 token ≤ 有效窗口的 5%
- **每 KB 常驻 = 固定上下文税**；**> 64K token 性能退化 30%+**
- 引 Anthropic 的表述：**上下文是稀缺资源，token 越多模型检索/推理能力越退化（context rot）**

**「context rot」这个词比「膨胀」准**：它不是「占地方」，是**能力随注入量上升而下降** —— 与第 8.1 条的「选择性忽略」是同一件事的两种说法。

**这给记忆设计一个硬约束**：记忆的注入量不能只受「预算」管，要受**「能力退化」**管。我们的四条失效触发里应当补一条与**总量**有关的闸（已在 §8.1 记下）。

### 9.4 写入前的三条纪律：先查后写 / 单一事实源 / 增量沉淀

`session-sediment` 的铁律前三条：

1. **先查后写**（grep 已有，不重复造）
2. **单一事实源**（同事实只落一处，别处**指路不复制**）
3. **增量沉淀**（只写本次新增）

**第 1 条正是「膨胀」这个缺口的一半**：膨胀的来源之一是**重复** —— 同一条经验被记了三遍，因为写的时候没人回头看。这条纪律我们的记忆写入流程里**没有**。

### 9.5 「不改口径消 FAIL」

`context-engineering.md` 讲体积门禁时有一句：

> FAIL = 治理信号（登记 CHANGELOG + 达标路径），**不改口径消 FAIL**。

**这与我们的「评估失败不等于通过」是同一条判据。**

而且它顺手澄清了我们自己刚做过的一件事：我们把观察期的分母从「评估」改成「看过」（`604b25c`）。**那算「改口径」吗？** 不算——判据是：

> **改口径的理由必须是「原来的口径是错的」，不能是「原来的数字不好看」。**

前者的证据是「用错了分母」（跑了 100 次、99 次没人理，用 100 当分母等于把没人理算成没被推翻）；后者只会说「这样更好看」。**这条区分值得写进平台的判据里。**

### 9.6 「断更修复」与「不遗漏」

它还有两条铁律式的规定：

- **断更修复**：memory 日志若有某天空白，**下次沉淀时必须回溯重建**（从 jsonl / git log），**不允许出现空白日**。
- **不遗漏**：成果必须在**产生的那个会话**里立即沉淀，不能依赖后续回溯 —— **回溯会丢失决策链和上下文**。

**对照我们**：判断记录的「空白段」（平台某段时间没跑、或跑了但全落 error）目前**没有信号**。这与 T4 那条「零命中」是近亲 —— 都属于「**沉默也可能是故障**」。

## 十、第六轮：对抗审查（多视角交叉，不用 LLM 当法官）

读 `xingtu-skills/skills/adversarial-review/SKILL.md`。

核心主张一句话：**单一视角的审查有固有盲区**。多角色从对立视角独立审查 → **脚本交叉验证** → 仅保留高置信度发现。

### 10.1 ⭐「交叉验证 = ≥2 个视角独立发现同一件事」

它的置信度分级只有两档：

```
✅ 交叉验证 = ≥2 个角色独立报告了同一发现
🔹 单独     = 仅 1 个角色报告
```

**这一条可能解开我们「数据够了算够」那个死结。**

回顾困境（调研三轮 §7.3）：双轨产出的是**差异集**，而差异集本身不告诉你哪个对 —— 它需要**地面真值**，而这个平台的地面真值只有「人回写的反应」。于是所有置信度都卡在同一个瓶颈上：**人得先看**。

**而交叉验证提供了另一条路：不需要人、也不需要地面真值的置信度信号。** 两个独立视角都发现了同一件事 —— 这件事**至少不是某个视角的幻觉**。

平台能怎么用这条，有两处：

| 用法 | 怎么做 | 要注意 |
|---|---|---|
| **判据的稳定性作信号** | 同一条判据跑两次（不同温度或不同模型），**结论一致 = 高置信**，不一致 = 低置信 | 我们已经观察过这个现象（同一个 MR 两次跑，结论一致但 items 表述不同），只是当成了缺陷记着，没当成信号用 |
| **多条策略命中同一处** | 两条独立策略都指向同一个文件/同一段 diff | **难点是「同一处」怎么判定** —— 目前两条策略的 `reason` 与 `evidence` 结构不同，没有共同的锚点 |

**第二条其实有个现成的锚**：我们已经在 `evidence` 里放了 `changed_file`（含具体路径）。**两条策略命中了同一个文件**，就是一个可算的、不需要人的重合信号。

⚠️ 但这**不能直接替代人的反应**。它证明的是「不是幻觉」，不是「判断正确」—— 一条判据可以稳定地、被两个视角一致地判错。所以它的定位是**先验置信度**，用来决定「哪些判断值得优先给人看」，而不是「哪些判断可以自动通过」。

### 10.2 职责隔离要写「不看什么」

四个角色，每个都明确划了反面：

| 角色 | 看什么 | **不看什么** |
|---|---|---|
| 怀疑论者 Refuter | 论证的薄弱点、证据是否充分、有没有反例 | 不改建议、不优化格式 |
| 优化者 Optimizer | 能不能更好、更省 | **不找逻辑错误** |
| 审计员 Auditor | 数据与引用是否真实、口径是否一致 | **不做价值判断** |
| 过滤器 Filter | 这条发现是真问题还是噪音 | **不新增发现、不修改发现内容 —— 只做减法** |

**「不看什么」比「看什么」更能防止职责重叠。** 对照我们的策略：两条策略（路径匹配 / 语义对照）现在不重叠，但**没有把这件事写下来** —— 将来加第三条时，凭手感判断重不重叠，就迟了。

**建议**：策略的结构里补一个 `notFor`（这条策略不负责判断什么），与 `description`（负责什么）成对。

### 10.3 位置漂移 → 用结构化锚点，不用行号

它专门解决了一个经典问题：**AI 评论的位置对不上实际内容**。

```
❌ 旧方式（位置漂移）：位置: S05 封面 第 3 行
✅ 新方式（字段定位）：位置: 封面 S05 big 字段（HTML: <span class="big">）
```

**对照我们**：`evidence` 已经分四类 —— `changed_file`（文件路径，**结构化锚点**）、`rule`（模型说的话）、`gather`、`model`。

**这个分法本身就是这条原则的落实**：凡是能被机器定位的，就用路径/行号/sha；模型的话归 `rule`，且**明确标注它是措辞而不是事实**。我们当初分开四类是因为「依据来源要可追溯」，它给出的是另一半理由：**锚点不牢的位置信息会漂**。

### 10.4 两条 Token 纪律与一条成本意识

- **TKR-2：Round 2 的交叉验证用脚本（grep / ls / diff / 查库），不用 LLM 当法官** —— 省一份法官的 token，也省掉「法官也会错」这一层不确定性。
  → 对照我们：敏感路径那条**纯规则策略**就是这个思路。**能用确定性规则做的不交给模型。**
- **TKR-3：每个角色发现上限 7 条** —— 太少=草率，太多=噪音浪费 token。
- **Filter 的目标是拦掉 30–50% 的低质量发现**（标准：没有具体证据的 / 纯主观偏好的 / 表述模糊的）。

**「发现上限」这条对我们有直接启发**：一条策略在一次事件上**命中太多条**时，它是真的发现了那么多问题，还是判据太宽？**上限本身是个信号**。

### 10.5 ⚠️ 它照出我们一个已知简化：策略的「触发」还没实现

它把审查分了三档：

| 级别 | 触发 | 角色数 | Token 估算 |
|---|---|---|---|
| 轻量 | 单篇封面/标题 | 3 | ~10K |
| 标准 | 单篇文章正文/数据 | 4 | ~25K |
| 重量 | 系列规划/付费方案/合集 | 4 + 领域专家 | ~50K |

**不是所有对象都跑全部角色** —— 按对象的重要性分级。

**对照我们**：策略的三段是「触发 / 判据 / 处置」，而 `src/types.ts` 的 `Policy` 接口**只有 `evaluate` 与 `disposal`，没有 trigger**；管道对**每个事件跑每一条策略**。

在只有两条策略时这不是问题。**但策略一多就会**：每条都调 LLM，成本随「策略数 × 事件数」线性涨，而其中大量事件根本不在那条策略的覆盖范围内。

**这条记进待办**：策略结构补 `trigger`（结构化条件），否则加第三条策略时就要面对这个问题。

## 十一、第七轮：隐形契约审计（整批里与我们同题程度最高的一份）

读 `xingtu-skills/skills/hidden-contract-audit/SKILL.md`（314 行）。

### 11.1 它的题目就是我们的题目

> **算法很少错；错的是那些「没人当成契约」的东西 —— 键、缓存、落盘文件、派生副本、定义位置。**
>
> `if` 写反会崩，测试会红。但「缓存键少放一个因子」不会崩 —— 它只是**安静地给你旧结果**。

它明说自己「**专抓那类不报错、只静默走错分支或静默不生效的缺陷**」。

**这正是这个平台从头到尾在防的那一类。** 我们反复撞见的同一条判据（沉默承担不了「通过」），在他们的语境里有另一个名字叫**静默失效**。七轮调研读下来，这是唯一一份**题目相同**的材料。

它的核心动作是一个三连问，对象是「每一个由别的东西算出来的东西」：

| # | 问题 | 答不上来 = 缺陷 |
|:-:|---|---|
| 1 | 这东西**由什么决定**？（把决定它的输入列全） | 列不全 → 键会漏因子 |
| 2 | 用户改了 X 之后，**键变了吗**？ | 不变 → 改了不生效 |
| 3 | 产物**会重算吗**？重算的是全部还是只该重算的那部分？ | 不重算 = 静默旧值；全重算 = 白烧钱 |

**共同点（它自己总结的）**：绝大多数是「某物由 X 决定」这句话**没说全** —— 要么漏了因子，要么**干脆没定义**。

### 11.2 ⭐「一个标签如果可能对应两种截然不同的现实，它就不是个合格的探针」

它讲的第三个变体是**状态标签二义**：

> 同一个值 `miss` 同时表示「查了、没命中」和「根本没启用」→ 用户无法判断是**缓存坏了**还是**我关了它**。

**要求状态必须能区分三态：`hit / miss / off`。**

**这条判据直接可用**，而且它指出了我们一个真实的空白：

| 我们已有的三态 | 它要求的第四态 |
|---|---|
| `hit` 命中 / `miss` 未命中 / `error` 判断没做成 | **`off` —— 这条策略根本没启用** |

**现在「策略被停用」和「策略跑了但没事件」在数据上长得一样**（都是 0 条判定记录）。而这又正好是 T4 那条「零命中」的近亲 —— **「拦不住」「没什么可拦」「根本没开」三者必须分得开**。

同一节里还有个更隐蔽的子类：**名词一名两用** —— 日志写「分镜：N 字」，而 N 其实是**输入**字数，读者会猜成产出的大小。**对照我们**：运行图上写「判定 10」，那是 **5 事件 × 2 策略**；「命中 3」是**次数**不是条数。目前表头写得清楚，但这类风险随指标变多会上升。

### 11.3 「文档声称的可改点必须实测手改一次」

案例 5 很扎心：项目文档声称「可以手改 `outline.json` 生效」，实际无效 —— 因为每次 `build()` 都会重建它，落盘的文件白存。

> **「人工可改口子」是文档里的谎言** → **文档声称的可改点必须实测手改一次**。

**对照我们**：README 与 skill 里写了不少「怎么用」。**跑过一次的**有：`npm test` / `demo` / `console` / `mcp` / `guard`、GitLab 那段、LLM 那段 —— 都实测过。

**没实测过的**是那些「改了就会生效」类声称，比如本机 MCP 包装脚本注释里写的「改源码后要先 `npm run build`」。这条**逻辑上成立**（跑的是 dist），但**没有验证过**：改一处源码、不 build、看 DSH 里是否真的还是旧行为。

—— 按它的判据，这条该验一次。**记进待办。**

### 11.4 「注释记的是写那一刻的意图」

> 案例 11：注释写着「供 prompt 注入使用」，实际**零调用点**。
> **注释记的是写那一刻的意图**；代码演进后用途变了，注释没人回头改。**读者对代码注释的默认信任度比文档更高，所以更隐蔽。**

它给的动作是 30 秒的：**读到「供 X 使用」这类用途声明 → 搜一遍调用点。**

**我对自己做了一遍**：搜 `src/` 里所有 export 的引用次数，**没有零调用点的导出**；三处「用于 X」的声明都在 MCP 工具描述里（那是给 Agent 看的对外说明，不是代码注释），且它们描述的用途都能走通。**这一项我们暂时干净。**

但这条判据值得留住 —— 它的价值在于**读者对代码注释的信任度高于文档**，所以过时的注释比过时的文档更危险。

### 11.5 「同一段逻辑出现 ≥2 次且会互相失效 → 它就不是巧合，是缺陷」

案例 14：6 个模块各自写了一份「找项目根」的逻辑（`Path(__file__).parents[2]`）。移目录时它们**不同步** —— 有的指对、有的指空、**有的正好还指对**。

> **判据：同一段逻辑若出现 ≥2 次，且其中任一处改动会让其余处失效 → 它就不是巧合，是缺陷。**

案例 15 是它的另一种形态：**共享数据寄居在其中一个消费者家里**（`CONCEPTS` 本是领域契约，却定义在先用到它的图标层里），第二个消费者出现时依赖方向就反了。

**共同点**：没说全的是「**这东西该由谁定义**」—— **定义位置本身是隐形契约**。

**对照我们**：`check-ssot.mjs` 守的正是这一类（同一句文案不许有两份）。但它是**针对文案**的；案例 14/15 说的是**逻辑与定义位置**。目前我们只有一份「找数据」的逻辑（`wire()`），没有重复；**但这条判据在加第三条策略、或 CLI 与 MCP 各长一套装配时就会用上**（那正是我们当初抽 `wiring.ts` 的理由，只是当时凭的是直觉）。

### 11.6 另外两条值得记的

- **对外宣称的数字也是「派生值」**：slogan 里的「3 秒完成」「不到 1MB」不在代码里、没有测试，也没人会在改完代码后想起它 —— 但它**一旦被实测打脸，损耗的是整条内容的可信度**。它的动作是：列成表、逐个回挂**可复现的实测命令**、且**数字要落成区间而不是点值**（点值必然会被某一次运行打破）。
  → 对照我们：控制台右下角那句「每个数字都能走回来源」是同一条判据的正面表述。**区别是他们还要「落成区间」** —— 这一条我们没有。
- **多入口的能力分叉**：项目长出第二个入口后，缓存/能力只接在其中一条上，两条路从此行为不同（走 A 改了没反应、走 B 每次都重来）。症状是**同一份数据、两种行为**。
  → 对照我们：CLI 与 MCP 是两个入口。我们抽 `wiring.ts` 正是为了避免这个，**但那是「现在不重叠」，不是「保证一直不重叠」**。

## 十二、第八轮：可证伪闸门与五类靶

读 `xingtu-skills/skills/spec-driven-adversarial-workflow/SKILL.md`（134 行，方案级的对抗流程）。

### 12.1 ⭐「对外断言先过可证伪闸门」——我们的判断记录缺「条件成立」这一态

它的第七条核心纪律原文：

> **对外断言先过「可证伪闸门」**：交付 / 文案 / spec 里任何「能做什么·有多快·完全离线·零损耗·已通过 X·100% 覆盖」式承诺，落笔前先设计一个**能失败的实测**并如实取数；
> **结论只允许 为真 / 为假 / 条件成立（注明已知缺口）三态**，用真实数字替换会被打脸的口号 —— 实测跑不了的断言要么改文本、要么显式登记缺口，**绝不靠形容词自证**。

**它的三态和我们的三态长得像，但第三态不一样**：

| 我们的 | 它的 |
|---|---|
| `hit` / `miss` / **`error`（这次没做成）** | 为真 / 为假 / **条件成立（注明已知缺口）** |

**这两个第三态是不同的东西，而且我们缺的是它那个。**

- 我们的 `error` 说的是「**这次**判断没做成」（取不到数、模型调不通）—— 是**过程**的失败
- 它说的「条件成立」是「**结论对，但有前提**」—— 是**结论**的限定

**举个在我们的场景里立刻能想到的例子**：GM 判「改动与声称不符」，但这个判断**只在描述写得过于简略时成立** —— 描述详细的时候它是误报。那是个**条件结论**，而现在它只能表达成无条件的 `hit`。

**而这不是措辞问题**：一条无条件的 `hit` 会进人的待办、会被要求表态、会算进否定率。**它的前提没有地方放** —— 于是人只能就「对/不对」表态，而这个表态对一条条件结论来说是**没有意义的**。

> **这条记进设计**：判断记录需要能表达「这个结论在什么前提下成立」。

它同时给了这条纪律的定位，值得抄：「**第 5 条管方案结论、第 6 条管执行验收、本条管「嘴上对读者说的每句话」**」。**我们的平台正好是「替 GM 说话」的那一层** —— 它说的每句话都该过这道闸。

### 12.2 「核验落空先疑自己的探针口径，再下结论」

Step 5 里有一条实测踩出来的坑：

> 核验落空**先疑自己的探针口径再下结论**：键名/路径对不上时先打印产物真实结构核对，别把「探针写错键名」误判成「它没做」（实测坑：`track_c` vs 真实键 `track_c_decay`）。

**对照我们**：这正是「判断没做成」的归因纪律。我们的 `error` 已经分了三种原因（取不到 / 模型失败 / 格式不对），**方向是对的**；这条补的是**顺序**：出问题时**先查自己取数这一侧**，再怀疑被审对象。

### 12.3 「待拍板必须带默认值」

> **待拍板必须带默认值**，禁开放式问题占决策人带宽（≤2 个 A/B 选择题）。

它的 00 总纲里有一节叫「**待决策拍板表（每项带默认值，未回即按默认执行，不阻塞往下写）**」。

**对照我们**：`docs/待决问题.md` 里那 6 条都定案了，但**控制台设计 §六 还挂着 5 条待决，没有一条写了默认值**。

这条纪律的好处是**它不阻塞**：未回按默认走，人不回也知道会发生什么。**我们的待决清单现在是「不回就悬着」**。

### 12.4 「五类靶」——其中一条直接命中我们的策略设计

它列的红队攻击面是固定的五类：

**引用证伪 / 单一信号绑架 / 平行系统 / 口径污染 / 副本腐烂**

**第二条「单一信号绑架」直接命中我们**：`review-claim-mismatch` 就是**一个信号**（模型读 diff 与声称后给的意见）。它的解法正是第六轮那条 —— **多视角交叉验证**。

**五类靶可以当作我们设计新策略时的自检清单**：

| 靶 | 对我们的问法 |
|---|---|
| 引用证伪 | 这条判据引用的东西（文件、字段、来源）真实存在吗？ |
| **单一信号绑架** | **这条判据是不是只凭一个信号就下结论？** |
| 平行系统 | 这条策略和已有的重不重叠？（T8 的 `notFor` 就是为此） |
| 口径污染 | 同一个词在判据与展示里是不是两个意思？（第七轮 §11.2 的「名词一名两用」） |
| 副本腐烂 | 这条判据的说明是不是在别处又有一份？ |

### 12.5 「不写行号，写可 grep 的原文片段」+ 三级定位

> 红队引用问题**不写行号**，写**可 grep 的原文片段**（那句话 / 那个字段名 / 那个小节标题）+ 文件路径。
> **三级定位**：① 片段 grep ② 全文相似扫描 ③ 人工确认。

**对照我们**：`evidence` 里的 `changed_file` 走的就是这个思路（用路径作锚，不用行号）。**行号会随下次提交漂掉，路径与片段不会。**

### 12.6 另外两条已经同源或已落地的

- **「完成判定查落盘凭证，不问模型自述」**（Step 4）—— 这是我们第四次读到同一条判据（前三次：第三轮的「不认模型自述已跑」、第一轮的「审查结论必须回读」、我们的「评估失败 ≠ 通过」）。
- **「不成立项也要写理由，不许静默丢弃」**（Step 3）—— 与双轨差异集评审里「两个都不对」是同一类要求：**否定的结论也是结论，它比沉默有信息量**。

## 十三、第九轮：实践案例（经验那部分）

读 `xingtu-sdd/case-studies/` 的索引与 `004-team-agent-orchestration/case.md`。案例库的定位是「可验证证据层」—— **每个案例都来自真实跑通、有验收凭证的实践**，且尾部必挂「踩坑 → 规则反哺」。

### 13.1 Case 004：给一批单角色 Agent 加 Team 抽象层

**背景痛点**（三条，都是"临时拼装"的代价）：

1. 每次都要**重新决定**组合
2. 协作模式**存在对话上下文里、不可传承**
3. 没有「该场景最优搭配」的**沉淀机制**

**做法**：轻量 `Team YAML`（每 Team 一个），四要素 **成员 / 协作协议 / 交付物契约 / 冲突仲裁**（+ 触发场景 / 验收标准两个可选）。它对比后否掉了「纯提示词层」，理由是**无契约、不可传承**。

**三条踩坑反哺**，每条都能直接对上我们：

| 它的踩坑 | 它的规则 | 对我们的对应 |
|---|---|---|
| 协作靠主 Agent 临时拼装 → **会话结束即丢** | 协作模式必须**契约化**（四要素沉淀） | 我们的策略配置就是契约化的；判断记录是「跑过的组合」的沉淀 |
| 大改现有体系 → 回归成本爆炸 | **叠加不重构**：新抽象层纯新增，**现有组件零改动作为验收项** | **加第三条策略时该照这个走**（见 13.2） |
| 方案 A/B 难取舍 | Spec 里先写**方案对比表（含被否选项与理由）**再拍板，**被否选项留痕可复用** | 我们的《设计修正提案》里那 26 条「不建议采纳」正是这个习惯 |

### 13.2 ⭐「叠加不重构」对我们加第三条策略的意义

它的 G1 验收项是：**「Team 层存在且原有单角色文件零改动」** —— 把「没破坏现状」变成了一条**机器可查的验收项**，而不是一句承诺。

**对照我们**：加一条新策略**应该只是「一个文件 + 装配里一行」**。而这件事现在**没有验收项** —— 我们靠的是「上次加第二条时确实没动第一条」。

**建议**：把这条写进策略的加入流程 —— **新策略不得要求修改 `pipeline.ts` 与已有策略文件**；若确实需要改管道，那说明缺的是一个**扩展点**，该补扩展点而不是改管道。

> 这与「策略结构补 `trigger` / `notFor`」（T7 / T8）是同一件事的两面：**扩展点补得越全，加策略越接近纯新增。**

### 13.3 Team 契约四要素里的「冲突仲裁」，我们没有

它的 Team YAML 四要素是 **成员 / 协作协议 / 交付物契约 / 冲突仲裁**。

前三个我们都有对应物（策略 / 判据与处置 / 评论与记录），**第四个没有**：**两条策略给出相反意见时，谁说了算？**

现在 `pipeline.ts` 的实际行为是「**取级别最高的那条策略**」—— 一条要求挂起、另一条只提示，整体按挂起算。**那是一种仲裁**（保守仲裁：只会取严，不会取松），但**它是实现细节，不是写下来的规则**。

**要写下来**，因为它是可变的：将来可能出现「A 说拦、B 说放」这种真正的冲突（不只是级别不同）。**那时如果仲裁规则只活在代码里，改它就等于改管道**（违反 13.2）。

### 13.4 案例库自己的两条纪律

**收录标准四条**，其中第 4 条是：

> **反哺闭环**：案例必须有「踩坑 → 规则」映射，反哺引擎方法论。

**对照我们**：这份调研笔记每轮都有「对我们的意义」，**但没有回指「这条后来变成了哪条判据/哪个待办」**。我们的判据落在设计文档与 `待决问题.md` 的待办表里，两边**没有互相指**。加回指的成本很低，收益是**看得出哪些调研真的落了地**（否则半年后回看，会以为读了九轮什么都没改）。

**另一条是脱敏红线**：它明说某些内容「**任何情况下不进公开仓**」，本地保留、案例库直接排除。

**对照我们**：平台对外公开之前，`docs/` 里曾经有过**真实的内网地址**与**真实的人名**（MR 作者、仓库提交者）。**2026-10-14 做公开仓时集中处理过一次**：域名与仓库路径换成占位、人名换掉、凭据指向那句删掉。**这类债要趁它小的时候还** —— 拖到要公开时才动手，改的就是几十处「实测记录」里的原话，而那会让记录看起来像是瞎编的。

### 13.5 案例库的分层：L1 一句话卡 / L2 全文

它的索引表分两层：**精选（全文收录）** 与 **候选索引（L1，一句话卡 + 目录名）**。

**对照我们**：`docs/` 现在是平铺的 13 个文档，还不到需要分层的规模。**但调研笔记这一份已经在 1000 行上下**，且还有更多轮次可加 —— 届时该按同样办法拆：**索引留一句话，细节下沉**。

## 一、最重要的结论：这不是空白领域

开工前最该知道的一件事——**这个方向已经有人在做，且不止一家**：

| 我们设计里的东西 | 已有产品里的对应物 |
|---|---|
| GM（常驻、主动判断） | Asana **Dash**（自称 AI Chief of Staff）· 阿里云「万有无界」的 **PMO Agent「小有」** · IBM 的 AI scrum master |
| 判断记录（主张 + 依据 + 结果） | 「万有无界」：**「项目中的决策与判断依据按照项目留存」** |
| 策略（可配置、不写死） | 「万有无界」：**SOP 模板** |
| 平台内核（身份 / 收件箱 / 线程 / Git 可审计） | **mcp_agent_mail**（开源，已实现，且已有 Rust 重写版） |
| 「待办必须落在平台上，不依赖 Agent 记忆」 | **Praukron**：「without relying on hidden agent memory」 |
| 「平台不写代码、只做载体」 | **Praukron**：「owns project understanding, not project execution」 |
| 一次实现、两个出口（人看 dashboard、Agent 拿结构化上下文） | **Praukron** 同款表述 |

⇒ 我们的定位描述，**逐条都能在已存在的产品里找到对应物**。这不代表不该做，但意味着差异点必须重新论证。

## 二、逐项发现

### 2.1 mcp_agent_mail —— 与我们平台内核重合度最高的开源实现

仓库：<https://github.com/Dicklesworthstone/mcp_agent_mail>（Python 版**已停止维护**，官方指向 Rust 重写版 `mcp_agent_mail_rust`）

**自我定位**：「*It's like gmail for your coding agents*」——coding agents 的异步协调层，FastMCP over Streamable HTTP，Git（人类可审计的产物）+ SQLite FTS5（索引与查询）双持久化。

**它为什么存在**（原文列的三条痛点，第三条与我们完全同源）：

> - Overwrite each other's edits or panic on unexpected diffs
> - Miss critical context from parallel workstreams
> - **Require humans to "liaison" messages across tools and teams**

**它的能力清单**：

| 能力 | 具体实现 |
|---|---|
| **身份** | `register_agent(project_key, program, model, name?, task_description?)`——生成记忆化的形容词+名词名（如 GreenCastle），落 Git，可 `whois` |
| **收件箱 / 发件箱** | `send_message` / `fetch_inbox` / `acknowledge_message`；消息同时写 canonical + outbox + 每个收件人的 inbox 副本 |
| **线程与检索** | `thread_id` 贯穿；`search_messages`（FTS5）、`summarize_thread` |
| **文件租约（leases）** | `file_reservation_paths(paths[], ttl_seconds, exclusive, reason)`——**advisory**，冲突照样授予但会报出来 |
| **提交守卫** | 可安装 `pre-commit` / `pre-push` hook：**阻止与别人活跃独占租约冲突的提交** |
| **构建槽位** | `acquire/renew/release_build_slot`——长任务（dev server、watcher）的粗粒度锁 |
| **联系人同意模型** | contact policy：`open` / `auto` / `contacts_only` / `block_all`；`request_contact` / `respond_contact`——**防冷启动骚扰** |
| **产品总线** | 把 frontend / backend / infra 多仓归到一个 product 下，做产品级 inbox / search |
| **人类界面** | 内置 Web UI（`/mail`），可浏览项目、inbox、消息、附件、租约，支持全文搜索 |

**它的数据模型里有两个字段值得我们注意**：

- `message_recipients(message_id, agent_id, kind, **read_ts**, **ack_ts**)` —— **读**和**确认**是两个独立时间戳。
- `messages(..., importance, **ack_required**, ...)` —— 可以要求对方确认。

⇒ 这直接印证了我们第 1 条结论里的「**已读 ≠ 已处理**」，而且给出了一个现成的字段设计。

**它没有的（我们的空间所在）**：
- **没有主动判断者**——它是纯被动的协调层，不判断、不提议、不拦（唯一的拦是租约冲突这种机械拦截）
- 没有策略概念，没有动作分级，没有「拦下动作等人拍板」

### 2.2 Asana Agentic Work Management（AWM）

来源：[Cloudfresh 报道](https://cloudfresh.com/gc/news/asana-agentic-work-management/) · [Asana 新闻稿](https://asana.com/press/releases/pr/asana-unveils-operating-system-for-human-agent-teams/f12f477a-7c35-4365-9771-578a294abc0d)

**自我定位**：「**human-agent teams 的操作系统**」。四个支柱：Enterprise Work Graph · shared memory · multiplayer coordination · **governance**。

**它对「AI 为什么没产生价值」的诊断（四条，与我们推理高度一致）**：
1. 团队找不到合适的 agent；
2. **agents 不是为「多人模式」设计的**（agents aren't built to work in multiplayer mode）；
3. agent 不知道团队怎么运作、之前决定了什么；
4. IT 担心 agent 无节制访问数据、没有成本管控。

**产品构成**：AI Teammates（chat 前台 + 技能库 + 集成）· AI Studio（无代码自动化）· Cross-system execution（收购 StackAI 打通 CRM/ERP）。

**在路上的**：**Asana Dash**——「an **AI Chief of Staff** that turns follow-ups from meetings, Slack, and email into structured work」。另有 Command（工程团队）、Service Management、Client Management。

### 2.3 阿里云「万有无界」（Wanyou Wujie）

来源：[品玩报道](https://www.pingwest.com/w/317000) · [TMTPOST](https://en.tmtpost.com/news/8125952)

**自我定位**：企业级**人与 Agent 协作平台**、多角色 Agent 协作工作台。2026-09-02 公测。

**核心构成**：
- **项目空间**——组织协作的容器（群聊、成员、资产）
- **两个主 Agent**：**「小有」= PMO Agent**（归属于项目，**依据 SOP 模板动态规划任务、分配给人与 Agent 成员、推动进展、组织复盘**）；**「小万」**= 个人总助理
- **资产库**——自动留存过程产出
- **AI 商城**——管理员筛选配置 AI 资源
- 可接入**符合 A2A 协议**的本地部署 Agent

**它对「与传统 AI Agent 的差别」的表述（逐条命中我们的设计）**：

> Agent 拥有**长期身份、组织记忆、权限边界与协作机制**——可被指派、被考核，产出归属明确；
> **项目中的决策与判断依据按照项目留存**，在授权范围内可被其他项目引用；
> **记忆、资产、工具的可用范围由管理员定义，Agent 只在受控边界内行动**；
> 多人与多 Agent 按节点分工、按前后置条件接力推进项目，**人可以在关键节点验收和纠偏**。

⇒ 「判断依据留存」「受控边界」「人可验收纠偏」——这三条与我们已定的判断记录 / 动作分级 / 四态机**是同一件事**。

### 2.4 Praukron（原 Prokron）

来源：[Zenodo 记录](https://zenodo.org/records/22926802) · 代码 <https://github.com/qomero/praukron>（Apache-2.0）

**自我定位**：**repository-native project-state protocol**，面向**异步 human-AI 软件开发**。把 phases / tasks / dependencies / decisions / **acceptance contracts** / **evidence** 以**版本化 Markdown 存在仓库里**；一个**确定性编译器**（Python 标准库、无网络、无模型）从这些记录推导项目状态，投影成**给人的交互式 dashboard** 和**给 agent 的结构化上下文**。

**原文里三句与我们的设计逐字对应的话**：
- 「preserve project authority, causal history and definition of done across asynchronous human and AI work **without relying on hidden agent memory**」
- 「**owns project understanding, not project execution**」
- 关键词里直接有：project memory · project governance · shared project state · **acceptance contracts** · software provenance

**它的空白**：**没有主动判断者**。它是一个被动的状态载体与投影，不是「会指出问题」的一方。

### 2.7 MCP 生态与协议选型（专项调研，已完成）

详细报告：[调研-MCP生态与Agent协议选型-2026-10-13.md](调研-MCP生态与Agent协议选型-2026-10-13.md)（含全部来源 URL，协议行为均引官方规范原文）

**四条规范级结论**：

| # | 结论 | 依据 |
|---|---|---|
| 1 | 「轮询 + 顺带投递、不做推送」**成立**，且理由从「工程取舍」升级为「**规范遵从**」 | SEP-2260（**Final**）禁止 standalone server-initiated requests；官方 Tasks 扩展原文 **"Polling is the default."** |
| 2 | MCP 协议版本**对齐 2025-06-18**，不要对齐 2026-07-28 | 第三方全量探测 10,716 个活跃端点，其中**能识别出版本的那部分样本**里 2025-06-18 占 86%（411 / 476，**分母口径待原报告补充**）；2026-07-28 是破坏性重构（去 session、去 GET 流、MRTR 取代 server-initiated requests），新特性在真实终端基本接不上 |
| 3 | **elicitation 做不了「平台主动问 Agent」** | ① 规范要求它嵌套在客户端请求内；② SEP-2260 禁止独立发起。「**发通知**」与「**请求输入**」必须是两条路径 |
| 4 | **审批的标准形态在 A2A，不在 MCP** | A2A（已捐 Linux Foundation 旗下 AAIF，v1.0 稳定）的形态是：任务进入 `input-required` / `auth-required` 状态 + push notification + **带外凭证**。**不要自造 Approval 对象** |

**可直接采纳的设计项**：

- ✅ **inbox 状态集参照 A2A `TaskState`**——但**两套拼写不一致，别混**：A2A 用 `input-required` / `canceled`（连字符、单 l），MCP Tasks 用 `input_required` / `cancelled`（下划线、双 l）。完整状态集必须含 **`auth-required`**——**审批场景正是靠它表达的，漏了它整套词表就不解决我们的问题**。
  > ⚠️ 本节早前的写法（`submitted / working / input_required / completed / failed / cancelled`）有一处自造（`submitted` 在两套规范里都不存在）、一处拼错、且恰好漏掉 `auth-required`，却写成「一次设计两头通」。**实际需要一层拼写映射，不是直接照抄。**
- ✅ **「外部能力经平台中转」有 IETF 草案级设计可抄**：`draft-abbott-mcp-ax-00` 定义了聚合器 / 命名空间委派 / 逐跳独立鉴权 / **不可逆性门控**。最值得抄的是门控的 proof 要求，原文：*Without this requirement, an autonomous model client can trivially self-confirm ... rendering the gate ineffective* —— 即**审批凭据必须来自请求方之外的信任锚**。
  > ⚠️ **信任锚不限于「人」**：该草案明确允许**三种**——人工签名 · **外部策略引擎签的 nonce** · 带外审批服务令牌。写成「必须由人操作」是窄化。
  > ⚠️ 另外它是 **Individual Internet-Draft，不代表 IETF 背书、无 RFC 地位**——**可借鉴设计，不能当规范引用**。
- ✅ **中转层要做契约快照 + 变更告警**：全量实测显示 MCP registry 里 **19% 端点已坏**、只有 **18%** 声明 `outputSchema`、**4.4% 的 server 在 36 小时内改过工具契约**。

**可参考的开源项目**：

| 项目 | 定位 | 许可 |
|---|---|---|
| **IBM ContextForge** | 企业级 MCP + A2A 网关，16 万+ 用户生产验证 | Apache-2.0 |
| **phodal/routa** | 看板即协调总线，集成 MCP / ACP / A2A / AG-UI | MIT |
| **jentrix-au/stacks-ai** | **人和 Agent 共用一块板** | —— |

⚠️ MCP 官方 reference server 里**一个协作类都没有**，且 README 明确写「not production-ready」。

**规范未规定的事项**（避免后续有人去猜）：业务通知无任何原语 · 收件箱无概念 · A2A 无 Approval 对象 · artifact 版本链不属于 A2A 规范 · registry 不是质量信号。

**⚠️ 两条已经死掉的路**（将来一定会有人重新提起，先记下免得重复调研）：

- **`sampling` 已 Deprecated**（2026-07-28 弃用注册表，迁移路径写的是「直接调 LLM provider API」）。它是「平台借 Agent 的模型做推理」最接近的历史答案——**新实现不应再基于它做任何设计**。
- **`notifications` 不是业务消息总线**：规范逐条定义了每个通知的用途——`notifications/message` 被定义为**日志**（且 2026-07-28 起是请求作用域的，servers MUST NOT 对不含该字段的请求发出它），`notifications/progress` 有「**MUST** only reference tokens that were provided in an active request」的硬约束。**「你有 3 条待办」不属于其中任何一条的既定语义。**

**⚠️ 最容易踩的坑（下一个设计环节就会遇到）**：**MCP 授权规范管的是「客户端访问受保护服务器」，不是「平台内角色动作要不要人批准」。** `scope` / `audience` / step-up 授权那一套，与我们的三级动作 + 四态机看起来极其对口——但**管的不是同一件事**。把它当成内部审批模型来用，会得到一个**形态相似、语义错位**的设计。

**三个「将来重估」信号**：

1. Triggers & Events WG 的 RFC 何时从 `Ideating` 落地 → 落地则重估「不做推送」
2. MCP Tasks 扩展的客户端采纳（官方 client-matrix 目前主流客户端一个都没列）→ 支持则可把顺带投递升级为 task 句柄 + 按 `pollIntervalMs` 轮询
3. registry 版本分布里 2026-07-28 的占比 → 抬头才值得接入 `subscriptions/listen` 与 MRTR

### 2.8 GM 动作审计 / 人在回路 / Agent 身份 / 合规留痕（专项调研，已完成）

详细报告：[调研-GM动作审计与人在回路-业界做法-2026-10-13.md](调研-GM动作审计与人在回路-业界做法-2026-10-13.md)

**本轮最重要的产出：我们最核心的三样东西，业界穷举之后确实没有标准。**

| 证据强度 | 空白 | 支撑 |
|---|---|---|
| **强** | **「依据什么」的结构化表达无标准** | 六个主流可观测性产品（OTel GenAI / LangSmith / Langfuse / AgentOps / Weave / Phoenix）**全无** rationale / decision / justification 字段（82 个 `gen_ai.*` 属性逐一 grep）；全行业只有一份**个人** IETF 草案给了 `routing rationale` + `rule reference` |
| **强** | **执行层证据缺失** | OAuth 体系自己承认：*grant-layer tokens prove **potential**, not the legitimacy of a specific, executed transaction* |
| 中 | `overridden` 没有标准语义与留痕约定 | 有优先级概念（Devin 的 `Deny > Ask > Allow`），有 NIST 的 `appeal and override` 词，但无人把它定义成**带留痕的动作状态** |
| 中 | 多人 / 组织级授权主体模型 | OAuth 按客户端建模、非按组 |
| 中 | 撤权事件本身如何入审计流 | 无规定 |
| 弱-中 | 「带理由拒绝」的理由分类学 | 无 |

**五条核心结论**：

1. **「为什么做这个决定」在主流可观测性标准里没有结构化字段**——LangSmith 的 `extra`、Langfuse 的 `metadata` 只是任意 KV 容器，非契约；唯一有 `reasoning` 字段的 W&B Weave 存的是**模型自述文本，不可校验**。
2. **标准明确反对把推理链当问责条件**——IETF `REQ-AUD-3` 原文：协议**不得**把收集私有推理轨迹作为问责的前提条件。⇒ **审计留痕 ≠ 存思维链**。
3. **「三级动作」有现成命名可参照**：`AUTONOMOUS` / `ASSISTED` / `ESCALATED`（OMP 的 EU AI Act Art 12 Profile）。
   > ⚠️ **三重限定，一个都不能丢**：该草案状态已是 **`Expired & archived`**；它是 Veridom Ltd 提交的**个人草案、非 IETF 工作组产出、不具标准效力**；且它**只面向「受 Art 12 约束的高风险 AI 系统运营方」**。**只能当命名参照，不能当依据引用。**
4. **「Agent 是一等身份」已有生产实现**：AWS Bedrock AgentCore 的 **workload identity** 被官方称为 "a new identity primitive"（agent 专属、独立 ARN、创建 Runtime 时自动分配、由服务关联角色背书），官方比喻是「**agent 有自己的护照，用户有自己的护照；代用户行动时两本护照都在场**」；委托链的成熟做法是 RFC 8693 令牌交换（`subject_token`=人、`actor_token`=agent，**交换后的令牌同时携带两者身份**）。
   > ⚠️ **「`REQ-AUTH-1` 是 MUST 级要求」这个说法要收回**：它出自 `draft-daniel-ai-agent-internet-architecture-01`，那是 **Informational 的个人草案、无 WG 归属**——**这种草案里的大写 MUST 不产生任何规范效力**。它可作为「业界有人在这么想」的佐证，**不可作为「标准要求我们必须」的依据**。
5. **OAuth 公认存在「授权层 vs 执行层」缺口**——我们的诉求正落在这个洞里。

**可直接借鉴的**：

- **Devin 的授权优先级**：`Deny > Ask > Allow > Default`——**"deny 永远赢"**。对我们的四态机是现成参考。
- **Temporal 的 `ApprovalData{approver, decision, comments, timestamp}`**——官方原文明说要「**结构化对象而非布尔**」，直接印证我们的「强行通过必须带理由」。
- **拦截点定在「提案生成后、外部调用发起前」**——与我们的闸门位置一致（LangGraph 在 `after_model` hook 中断）。
- **NIST MANAGE 4.1 含 `appeal and override`**——与我们的 `overridden` 同源。
- **防篡改 + 选择性披露** · **可撤权**（含「暂停 agent **不删**历史审计证据」）——这几条同样出自 `draft-daniel` 个人草案，**无规范效力，当设计参照即可**。

**⚠️ 关于合规要求（EU AI Act / NIST）——不要把别人的义务抄成我们的。**

原始报告反复强调两点，本整合早前把它们丢了：

1. **这些条款只适用于「高风险 AI 系统」。** 如果 GM 不构成高风险系统，Art 12 / 19 等条款**不直接约束我们**。
2. **NIST AI RMF 的 Playbook 原文自述是「建议，非要求」。**

⇒ 准确的说法是：**欧洲法律要求高风险系统保留自动日志 ≥6 个月、支持事后解释**；我们若要对齐，是**设计选择**（为了可信与可审计），**不是法定义务**——除非将来被认定为高风险系统。

**最有用的意外收获：一份现成的审计字段清单。**

IETF `REQ-AUD-1` 直接给出了审计记录的七元组：

> `agent 身份 · 问责主体 · 授权上下文 · 请求标识 · 时间戳 · 策略约束 · 结果状态`

再叠加 OMP 草案的 `routing rationale`（路由理由）+ `explicit rule reference`（显式规则引用）——**这就是我们「判断记录」字段设计的起点**，不必从零想。

**明确不要做的**：

- ⚠️ **OTel GenAI 属性仍是 `Development`、内容字段为 `Opt-In`**——不要冻进审计契约。
- ⚠️ **别把思维链当问责依据**（与 `REQ-AUD-3` 冲突）——理由字段只能做可选辅助，问责靠**可校验的规则引用**。
- ⚠️ **反面案例**：GCP Vertex AI 用「系统托管的高权限身份」，2026-01 出现提权漏洞（低权限用户注入代码 → 取凭据 → 读会话历史）——这正是我们要避开的形态。

### 2.9 自动化审查 / 门禁 / 合并判官（专项调研，已完成）

详细报告：[调研-自动化审查与合并门禁-2026-10-13.md](调研-自动化审查与合并门禁-2026-10-13.md)（约 1.6 万字，每条结论带来源）

**这是分量最重的一份**——它直接判定「能拦事」这条差异到底成不成立。

**总览**：共同架构形态 `状态检查 → 判断 → 动作 → 留痕`，**在 30 年、4 个技术世代里高度一致**。

**拦截强度五档**（可直接映射我们的三级动作）：

| 档 | 动作 | 拦在生效前？ |
|---|---|---|
| 0 | 只发评论 | 否 |
| 1 | 发 check 但结论是 **neutral** | 否 |
| 2 | 发可失败的 check | **只有被设为 required check 才拦** |
| 3 | 直接行使否决权（request changes、Gerrit `-2`） | 是 |
| 4 | 平台级硬门（required checks、merge pool） | 是——物理上合不进去 |

**关键分界**：档 1 与 2 之间是「我记录了一个异议」与「我让门关上了」；档 2 与 3 之间是「我能让门关上」与「我替你踩刹车」。

#### ⭐ Gerrit 的六态状态机，是我们四态机的直系祖先

`NOT_APPLICABLE` / `UNSATISFIED` / `SATISFIED` / **`OVERRIDDEN`** / **`FORCED`** / `ERROR`

三条直接修正我们的设计：

1. **`FORCED` 必须与 `OVERRIDDEN` 分开。** FORCED = 绕过整个体系（直接用 push 合并）；OVERRIDDEN = 在体系内被覆盖。**若把「人绕过 GM 直接干」记成「GM 被推翻」，会得出「GM 判断力差」的错误结论——实际是 GM 根本没机会判断。** 这会直接污染我们「被推翻记录是唯一改进输入」这条判据的数据质量。
2. **`NOT_APPLICABLE` 要单独存在。** 不适用的策略不该出现在报告里（Mergify 同款设计：*Inactive rules are ignored, not shown as failing*）。**依据列表一旦把「不适用的规则」算成失败，人就再也不看它了。**
3. **`ERROR`（评估本身出错）也不能当成通过。**

另有一条反直觉语义值得抄：Gerrit 原文 **"the submit requirement is overridden regardless of whether the `submittableIf` evaluates to true or not"**——**覆盖判定独立于「拦得对不对」**。不需要先证明「GM 拦对了」，才能记录「人被推翻了」。

#### ⭐ 另外四条硬约束

**① 覆盖要分「破窗」与「豁免」两类**（GitHub ruleset）
- 标准 bypass = **"break glass"**，产生**醒目审计信号**
- `exempt` = **静默跳过**，只给可信高频自动化
- **如果不分：一个常驻可信 bot 每次都在「推翻」GM，会彻底污染推翻率统计。**

**② 不要做「发现即 neutral」式的假拦截**（Cursor Bugbot）
Bugbot 发现问题时 check 发的是 `neutral`，而 GitHub 的 required check 定义里 **neutral 算通过**——「设成 required check」只保证它**跑过**，不保证它**没意见**。
⇒ **GM 的二级动作若做成「记录了一个 neutral 的结论」，就是看起来留了痕、实际没有任何阻力，比不拦更糟**——它制造了「已经有人管了」的错觉。

**③ 判据与阻塞强度解耦**（reviewdog 的教科书设计）
`-level`（决定 check 结论）与 `-fail-level`（决定退出码，**默认 `none`**）是两个独立旋钮。
⇒ **同一套判据可以从「观察期只发消息」平滑升级到「留痕」再到「待人确认」，不必改判据本身。**

**④ 被管辖者不能修改管辖它的策略**（Bugbot 与 Greptile 给出同一个答案）
两者都**从 base 分支读自己的配置**，PR 改不到自己头上的规则。Bugbot 原话：*does not read the PR head version, so a PR cannot change how Bugbot reviews itself.*
⇒ **要在读取路径上实现，不能靠约定。**

#### 其他可直接借的

- **Prow 的 `[APPROVALNOTIFIER]`** 是留痕标杆：已满足的**划掉并标注谁批的** + 逐条列出未满足项（回答「差哪一项、谁补、补了谁批的」）。
- **CodeRabbit Learnings** 是「被推翻 → 改进」闭环的现成实现：learning = 自然语言 + 元数据（来源 PR / 文件 / **是谁说的**）；**⭐「未经合并验证的经验不扩散」**——开着 PR 上创建的 learning 先只作用于该 PR，PR 合并后才升级为仓库级；`approval_delay`；记录 Usage / Last Used / **Created by**。
- **停用规则必须写 reason，且印在人看得到的地方**（Mergify 的 `disabled.reason` 印在 Summary check run 里，*so others know why*）。
- **留一条不经过规则的管理通道**（Gerrit 的自我锁死警告：submit requirements 存在 `refs/meta/config`，改它要走 code review，而走 code review 要通过该分支的 submit requirements——**配错就再也改不回来**）。
- **判据三态要含「证据不足」**（CodeRabbit 的 `Passed` / `Failed` / **`Inconclusive`**）——报告原话说 `Inconclusive` 是**精髓**：**模型证据不足时应当承认，而不是猜**。
  > ⚠️ **我们的四态机里没有「证据不足」的位置**——这与 Gerrit 的 `ERROR` 是同一类需求：**判断本身没做成，既不能算通过，也不能算拦下。**
- **判据反模式表**（CodeRabbit，我们的 LLM 判据直接可用）：含糊（"verify best practices"）/ **信息不可得**（"确认 PR 已被 @security-team 批准"——判据执行者根本看不到审批状态）/ 要求推测 / 要求改 review。正面原则：具体可执行 · 明确 pass-fail 标准 · **一个检查只问一件事** · 复杂规则给例子。

#### 明确不要学的

1. **不要把「拦截」做成「被审者能自己解除」**——CodeRabbit 的 request-changes 能阻塞，但**默认允许 PR 作者自己用 `@coderabbitai approve` 覆盖**。⇒ 我们的 `overridden` 里「人」是**责任主体**不是**作者**：应要求推翻者 ≠ 被判定变更的作者。
2. **不要用命令式脚本承载判据**——Danger 无策略分层 / 无结构化依据 / 无覆盖语义；Gerrit 弃用 Prolog；Mergify 弃用 autoqueue；Bors-NG 停更。**声明式战胜图灵完备。**
3. **不要用「静默豁免」解决「误拦太烦」**——误拦应当**回流成判据的修订**，而不是把闸门拆掉。
4. **不要把 dashboard 全量展示当留痕**——**留痕要存全，展示要分层**（默认只显示「差哪一项」，展开才给完整依据链）。
5. **不要忽视依据的可信来源**——GitHub 官方承认 *Any person or integration with write permissions can set the state of any status check*。**若 GM 的 blocked / allowed 是一个「谁都能写的共享状态」，它就能被绕过或伪造。**

#### 🎯 这条差异的最终判定

**「判断 → 拦截 → 人裁决」的闭环本身不是新的。** Gerrit 用声明式规则把它做得比我们完整（六态 + `overrideIf` + `passingAtoms` 原子条件 + 策略可试跑）。

**但有两个位置确实是空的**：

1. **LLM 判据全部停在「默认不阻塞」。** CodeRabbit 是唯一跨进「行使否决权」档位的（`request_changes_workflow`），而且**默认关闭**；Bugbot 发现问题默认 `neutral`；reviewdog 默认 `fail-level=none`。
2. **「按判据成熟度逐个升级阻塞强度」这个机制，这一族里没有任何现成实现。** 报告原话：新判据先只发消息，跑够样本、误报率可接受后再升到留痕 / 待人确认——**这个机制这一族里没有现成实现，是要自己造的。**

⇒ **差异点收敛为一句话**：把 LLM 的判断接入一整套已经成熟的「拦截 → 覆盖 → 留痕」机制，并且**让阻塞强度能随判据成熟度分级演进**。声明式那半边别人做完了，LLM 这半边别人停在门口没进来。

### 2.10 多 Agent 协作框架（专项调研，已完成）

详细报告：[调研-多Agent协作框架-2026-10-13.md](调研-多Agent协作框架-2026-10-13.md)（90 KB，覆盖 10 个框架 + 2 个横向专题；来源分四级标注：官方文档 / GitHub 源码 / arXiv / 协议规范 / 第三方）

**这份调研的价值是「印证」而非「发现新东西」**——它用 10 个框架的横截面，独立验证了前面几份报告指向的空白。

**最硬的一条：10 个框架，0 个内置跨运行持久任务板。**

状态持久化的上限是「会话 / 线程 / 单次运行的可恢复快照」：LangGraph 是 checkpointer + Store（**官方明说没有任务板**）、AutoGen 的 `save_state()` 返回 dict **要自己落盘**、OpenAI SDK 的 `Session` 只存对话历史。

**行业做法是把状态放到框架外**：DBOS 用 `list_workflows(PENDING)` 组「待批收件箱」· Temporal 把 agent 调用做成 Activity · **GitHub Copilot coding agent 用 issue 入队 + draft PR 当状态机，且发起人不能自批**。

**第二条：所有框架的「管理者」都是有角色、没身份。**

| 框架 | 管理者机制 | 能否单独授权 / 停用 |
|---|---|---|
| CrewAI | `manager_llm` / `manager_agent` 二选一 | **不能**——传实例时带 tools 直接抛异常；`hierarchical` 强制有 manager |
| AutoGen v0.2 | `GroupChatManager` 默认 auto **不是一次 LLM 调用**，是嵌套两 agent 对话 + 正则匹配角色名，耗尽后退回 round robin | 不能——群聊内部的选择器 |
| AutoGen v0.4 | `SelectorGroupChat` 每条消息一次模型调用 | 不能——`selector_func` 只是一个函数 |
| LangGraph | supervisor = 「一次 LLM 调用 + handoff tool」 | **不能，且官方已放弃该包**（原文 "no longer actively maintained"） |
| Semantic Kernel | manager 作编排器构造参数注入 | 不能——官方原文「不是 Agent、不进 members、无身份与权限」 |
| OpenAI Agents SDK | 有 manager 说法，**没有 manager 类** | 不能 |
| Google ADK | 干脆没有 supervisor 概念（`sub_agents` 层级 + `transfer_to_agent`，父 agent 退场） | 少数反例——coordinator 与 subagent 都有独立身份 |

唯一有独立状态的是 **AutoGen Magentic-One 的 Orchestrator**（Task Ledger / Progress Ledger 双账本），但**账本是提示词内概念、不可持久化**。

**第三条：没有任何一家记录「谁授权了这个动作」。** 记录的都是系统流水。审批全是**工具级二元**（最好的是 LangGraph 四态 `approve` / `edit` / `reject` / `respond`、ADK 可结构化回填、AutoGen 带 reason），**没有业务动作的三级分级**。最接近的是 ADK 的 Event 流水 + 可选的 **Tool Call Integrity 插件（用密钥签名每个 function call，验签通过才允许执行）**。

**三条对本项目的直接判断**：

1. **GM 不能实现为「框架里的 supervisor 节点」**——那些节点的生命周期就是 run，而 GM 要常驻。
2. **协作状态必须自建持久层**——这是 10 个框架的共同空白，不是我们没找到。状态留平台侧、执行器无状态。
3. **MCP 层不要自造审批原语**——MCP 没有 tool approval 规范；`elicitation` 被规范限死（扁平 schema + 原始类型、MUST NOT 索取敏感信息、accept 只表示「同意这次交互」）**且它不是授权原语**。要做「暂停等人批准」应走 **Tasks 扩展的 `input_required`**。而「所有动作经平台中转」这个位置，正是 **Interceptors WG（SEP-1763，2026-04 立）仍在 Draft 的地方**——短期自建合理，中长期可对齐。

**⚠️ 两处未取到原文**（是「没查到」不是「没有」）：OpenAI 的 guardrails-approvals 文档整站 WAF 返回 403（等价机制以 SDK 文档补齐）；ChatDev 1.0 的持久化与权限审计细节在素材传递中被截断，结论不完整。

**⚠️ 四个被二手资料传错的名字**（后续引用这些框架时别照二手抄）：ChatDev 的 `ComposedChat` / `Assistant` / `cyclic` **都不存在**（真实符号是 `ComposedPhase` / `RoleType.ASSISTANT` / `cycleNum`）；AgentVerse 的 `expert_generation` / `Controller` **全仓零命中**（真实机制叫 `role_assigner`）。

**⚠️ 一处框架自身的不一致**：CrewAI 官方文档与源码三处对不上（`Agent.max_iter` 文档 20 / 源码 25；memory 路径；`Crew.memory` 属性表还留着已被 PR #4420 删除的三层 memory 措辞）。报告以源码为准——**要引 CrewAI 的做法时别照文档抄**。

1. **LLM 判据全部停在「默认不阻塞」**——CodeRabbit 是唯一跨进否决权档位的，而且默认关闭；Bugbot 发现问题默认 `neutral`；reviewdog 默认 `fail-level=none`。
2. **「按判据成熟度逐个升级阻塞强度」没有任何现成实现。**

⇒ **差异点收敛为**：把 LLM 的判断接入一整套已经成熟的「拦截 → 覆盖 → 留痕」机制，并让阻塞强度能随判据成熟度分级演进。**声明式那半边别人做完了，LLM 这半边别人停在门口没进来。**

**⚠️ 上表第三行同样不成立（第二条修正）：**

「面向真实工程协作」**不是差异点，是场景选择**。理由：§2.9 证明了 **Prow / Gerrit / Mergify / Zuul / GitHub / Bors / Graphite 整族三十年来做的就是这件事**——它们全部工作在 Git / CI / 门禁之上。主张「别人没做过面向工程交付物的协作」是一戳就破的。

⇒ 正确的姿势：把「面对真实的工程交付物」当作**我们选的场景**，而不是**我们的护城河**。方案 §六给的三条理由（需求真实存在 · 事实源头齐全 · 失败代价可控）**本身就足够支撑这个选择**，不需要附加「别人没做过」这个可被证伪的主张。

> 这条的教训与上一条不同：上一条是「前提变了没回头改」，这一条是「**把场景选择包装成了差异点**」——听起来更有分量，却多了一个能被证伪的承诺。

> **教训（写在这里防复发）**：§2.9 推翻了本节判断，但本节当时没有回头改——**同一份文档里同时存在两个相反结论**。这不是疏忽，是流程缺失：**新结论落地时必须回头清零依赖旧前提的段落**，否则文档会带着自相矛盾进入下游。同类错误在同一项目内两天内出现两次（另一次见 `待决问题.md` 第 3 条的错题本）。

三类最典型的失真值得记住：

1. **限定条件脱落**——个人草案被写成不带限定的行业事实（OMP 已 `Expired`、`REQ-AUTH-1` 的 MUST 无规范效力、MCP-AX 的三种信任锚被窄化成一种、NIST 的「非要求」限定消失）。**这是最隐蔽的一类：错误方向一致地偏向「把不确定说成确定」。**
2. **前提变了、结论没跟着改**——§2.9 推翻了 §四的「待核」判断，但 §四当时没回头改，导致同一份文档里长期并存两个相反结论。**已在 §四就地保留错误并修正**，作为流程缺失的物证。
3. **一手抓取 ≠ 独立复核**——§2.1（mcp_agent_mail）来自**直接抓取该仓库 README**，**没有原始调研报告背书**，却是全篇权重最高的章节。内容本身核对无误，但它的取证方式与其他节不同，阅读时请注意这个区别。

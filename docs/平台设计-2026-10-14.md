## 一、题目：静默失效

### 1.1 一句话

> **这个平台存在的理由只有一个：让「不该沉默的地方」沉默不了。**

**静默失效**指那类**不报错、不崩溃、只是安静地走错**的事。

代码里它长这样：`if` 写反会崩、测试会红；但「缓存键少放一个因子」不会崩 —— **它只是安静地给你旧结果**。

协作里它长这样：**没有人说「这条我看过」，于是「没人看」和「看过了没问题」长得一模一样。**

### 1.2 为什么这是协作里的题目，而不只是代码里的

判断一个变更有没有问题，靠的是「有人看过并且表了态」。而这件事的三样东西 —— **有人看、看过有结论、结论有依据** —— 在现有的协作工具里**全都没有强制载体**：

| 现状 | 它的静默失效 |
|---|---|
| 变更提上来了没人审 | 看起来和「审过了没问题」一样 |
| 有人审了但没留结论 | 看起来和「没人审」一样 |
| 平台的服务挂了 | 看起来和「这段时间没变更」一样 |
| 一条判据从没命中过 | 看起来和「没什么可拦」一样 |

**这四种「一样」，没有一种是靠「大家注意一点」能解决的** —— 它们都需要机制。

### 1.3 五类形态（本文全篇的靶子）

| # | 形态 | 表面上看起来像 |
|---|---|---|
| **S1** | **判断没做成** | 没发现问题 |
| **S2** | **没人看过** | 看过并且默许了 |
| **S3** | **平台根本没看到这次变更** | 这次变更没问题 |
| **S4** | **拦不住**（判据从不命中 / 根本没启用） | 没什么可拦 |
| **S5** | **结论对，但有前提** | 无条件成立 |

**五类都有一条共同的判据**（来自调研第七轮）：

> **一个标签如果可能对应两种截然不同的现实，它就不是个合格的探针。**

**第五节会把这张表再展开一次** —— 每一类失效各自被什么机制挡住，以及那个机制现在做了没有。**那是全篇的证据面。**

## 二、内核：一个环

旧方案给的是「六个概念」：事件、策略、判定、动作、留痕、人。它们是**并列**的。

改成**环**之后方向就出来了 —— 而且环上多了一条原来没有的回流：

```
                        ┌─────────────────────────────┐
                        │                             │
   ①事件 ──→ ②判断 ──→ ③动作 ──→ ④留痕 ──→ ⑤人的反应 │
                        │                             │
                        └── ⑥记忆 ──→ 新的判据 ───────┘
```

### 环上每个环节在干什么，以及它可能怎么静默失效

| 环节 | 做什么 | 它的静默失效形态 |
|---|---|---|
| **① 事件** | 把一次变更送进来 | **S3** —— 没送进来，就什么都没发生 |
| **② 判断** | 每条策略各出一次结论 | **S1** —— 判断没做成，看起来像没命中 |
| **③ 动作** | 把判断说出去（评论 / 建任务 / 挂起） | 动作声明了却没实现 → 命中被静默吞掉 |
| **④ 留痕** | 落一条判断记录 | 掉了就是没发生过 |
| **⑤ 人的反应** | 人说这条判断对不对 | **S2** —— 没人回写，看起来像没意见 |
| **⑥ 记忆** | 从记录里归纳出模式 | 归纳出来的东西过时了还在影响判断 |

**回流（⑥ → 新的判据）是旧的六概念里没有的**：判断记录不该只用来事后查，它该**反过来改变判断**。这条回流见第三节。

### 2.1 GM 在这个环上的位置

**GM 不是平台的起点，它是这条环的执行者** —— 订阅事件（①）、做判断（②）、执行动作（③）、落记录（④）、归纳记忆（⑥）。

而 **⑤ 只能由人做**：GM 不能替自己表态。这条边界很重要 —— 一个能给自己打分的判断者，等于没有判断者。

## 三、三层治理

环上的资产分三层，**各层的治理强度完全不同**：

| 层 | 是什么 | 谁能改 | 靠什么保证它不出问题 |
|---|---|---|---|
| **判断记录** | 每次判定的事实 | **没人能改**（只追加） | 它本身就是留痕 |
| **记忆** | 从记录里归纳出的模式 | **GM 自动** | 四条失效触发 + 可检验性安全阀 |
| **策略** | 固化下来的判据（墙） | **人** | 版本 + 观察期 + 双轨对照 |

### 3.1 三层之间有毕业关系

```
判断记录  →  记忆  →  策略
（每次判定）  （归纳出的模式）  （固化成判据，机械执行）
   事实层        模式层            墙
```

**来源**（两处独立撞出来）：调研里的「**规则是愿望，hook 才是墙**」与「**纠偏即时机械化：高频纠偏 → 沉淀为铁律，错只犯一次**」。

**目标一句话：错只犯一次。** 同一个坑第二次出现时，不该还靠 GM「记得」它。

**判据（方向清楚，阈值待定）**：一条记忆被**反复用上**、且它影响过的判断**被人采纳**，就该提议**升级为策略**。

> ⚠️ 升级 ≠ 改判据。**双轨**改的是**已有**判据（影响现有判断，评审成本高）；**升级**是**新增**判据（只是多一道闸，评审成本低）。**所以升级可以走得比双轨快。**

### 3.2 记忆这一层的入口检查与失效机制

**入口检查三条**（都不过的不该进来）：

| 判据 | 问的问题 | 出处 |
|---|---|---|
| **可检验** | 它**错了**，有记录显示得出来吗？ | 设计 §3.10 |
| **可执行** | 它**对了**，我该做什么？ | 调研第五轮 |
| **删掉会犯错** | 它**不在**，会出事吗？ | 调研第四轮 |

**第四条是安全阀**：**只有可检验的记忆才能自动生效** —— 无法失效的记忆等于永久记忆，而一个永久错误的前提会把它影响过的每一次判断都带偏。

**四条失效触发**：生存期（TTL，标 stale 不删）· **反向证据**（与近期判断记录矛盾时自动撤下 —— 这是 GM 相对通用记忆工具多出来的能力，**它有判断记录可对照**）· 锚点（绑可探测的值，含**绑判据版本**）· 冷退。

**还有一条与总量有关的闸**（阈值待定）：调研第四轮那句话是 —— 常驻配置膨胀到一定程度，**模型会选择性忽略，反而降低质量**。选择性忽略**不报错**：模型照样自信地给出判断，只是有些规则它已经不再真的在看了。

### 3.3 策略这一层的两条既有约束

- **观察期**：新判据先只发消息（级别 1），升级到「挂起合并」由人看着数据决定
- **升级判据的分母是「看过」**，不是「评估次数」（`reviewed` / `total` 两个数在控制台的观察表里并列）。用评估当分母等于**用冷漠稀释信号** —— 为什么这一字之差是原则问题而不是口径偏好，控制台里有完整说明，**事实源是 `public/console.html` 的 `TIPS`**，此处不复制

## 四、架构原则：每一维都该是「插进去」的

**来源**：调研第九轮那个案例的验收项 —— **新抽象层存在，且原有组件零改动**。它把「没破坏现状」从一句承诺变成了**机器可查的验收项**。

**照到平台上，每一维都该满足**：

| 加什么 | 应该是 |
|---|---|
| 一条策略 | **一个文件 + 装配里一行** |
| 一个事件源 | 实现 `EventSource` 接口 |
| 一个动作 | 实现 `ActionRunner` 接口 |
| 一个出口 | 复用 `wiring.ts` 的装配 |

**判据**：**若加一个新东西需要修改已有的管道代码 —— 那说明缺的是一个扩展点，该补扩展点，而不是让每加一次就动一次管道。**

**它已经照出三个缺口**：

| 缺口 | 现状 | 待办 |
|---|---|---|
| **`trigger`（触发）** | `Policy` 接口只有 `evaluate` 与 `disposal`；**管道对每个事件跑每一条策略** | T7 |
| **`notFor`（不负责判断什么）** | 「不看什么」比「看什么」更能防职责重叠，而这条没写下来 | T8 |
| **冲突仲裁** | 两条策略意见相反时，实际行为是 `pipeline.ts` 的「取级别最高」—— **是实现细节，不是规则** | 设计 §3.11 二 |

## 五、机制对照：五类失效，各自被什么挡住

**这一节是全篇的证据面。** 它回答的不是「我们做了哪些东西」，而是「**每一类失效，凭什么说自己被挡住了**」。

| 失效形态 | 挡住它的机制 | 现状 |
|---|---|---|
| **S1** 判断没做成 | 判定结局**三态**（`hit`/`miss`/`error`）；`error` 单独一列**不许并进 miss**；评论里明写「**这不等于通过**」 | ✅ 已实现 |
| **S2** 没人看过 | 观察期统计拆出 **`reviewed`**（有人回过写的次数），升级判据用它当分母；控制台「待回应」一屏 | ✅ 已实现 |
| **S3** 平台看不到 | **主动申报**（`submit_change`）+ 每次判定都表态（含「没发现问题」）；**MCP 不提供用法，所以另发一份 skill** | ✅ 已实现 |
| **S4** 拦不住 | 「零命中」信号 + `off` 态（**策略被停用**与**跑了但没事件**现在长得一样） | 📋 T4 / T11 |
| **S5** 结论有前提 | 判断记录需要能表达「**条件成立（注明已知缺口）**」 | 📋 T13 |
| 改了不生效 | 单一事实源守卫 + **人造漂移夹具**（抓不到 = 守卫无效）+ 统计按策略版本分组 | ✅ 部分 |

**每条机制都要能回答「它挡的是哪一类」** —— 答不上来的机制，要么是防御过度，要么它自己就是新的静默失效源。

### 5.1 两条横向贯穿的判据

**一、一次判定只动一次手，而且每次判定都要表态。**

两个方向都要防：命中时按策略各刷一条评论，**评论噪音会让人静音它**；未命中时什么都不说，**「沉默」就同时意味着「看过了没问题」和「GM 根本没跑」**。所以：**先跑完所有策略再动一次手，把这次判定合成一条评论**，且**包括什么都没发现的时候**。

**二、判断必须带依据，且依据要分类。**

**依据分四类**：`changed_file`（客观事实）· `rule`（策略自己给出的理由）· `gather`（这次取到了哪些数）· `model`（哪家模型下的判断）。

⚠️ 四类里只有 `changed_file` 是**可复现的客观事实**；`rule` 是措辞、不是推理过程。这条口径的完整说明在控制台里，**事实源是 `public/console.html` 的 `TIPS`**，此处不复制。

### 5.2 每个动作都要过三条件：退出 / 幂等 / 回滚

**来源**：调研第二轮宪法模板里的「安全三条件」（计费 / 库存 / 权限类动作必填）+ 第四轮「机械门禁不因减文本而撤」。

**它是「加一个动作」的验收条件**，不是建议：

| 条件 | 问什么 | 不过会怎样 |
|---|---|---|
| **退出** | 这个动作能不能中止？ | 一个停不下来的动作，只能等它做完 |
| **幂等** | 同一件事重复触发会不会做两遍？ | 重复发评论 / 重复建任务 —— **而且每次看起来都很"成功"** |
| **回滚** | 做错了能不能收回？ | 错的处置留在原地，没人能撤销 |

**为什么要单独定这条**：平台的动作**分三级**，级别越高越难收回（1 只发消息 · 2 建任务改状态 · 3 挂起合并）。**级别 3 的动作一旦做错，代价不是「多了一条评论」** —— 而「能不能回滚」这件事，**在设计动作的那一刻就要想清楚，不能等出事才想**。

#### 现有动作逐个过一遍

| 动作 | 退出 | 幂等 | 回滚 |
|---|---|---|---|
| **本地评论**（`CommentAction`） | ✅ 删文件 | ✅ 同 id 覆盖 | ✅ 删文件 |
| **GitLab 评论**（`GitLabCommentAction`） | ⚠️ 发出去就发了 | ✅ 管道层保证不重发（`hasJudged` 三元组） | ✅ `npm run undo` |
| **挂起合并**（`GitLabHoldMergeAction`，级别 3） | ✅ 人放行 = 撤销 | ✅ label 用整体设置而非追加 | ✅ `npm run undo` 删评论；标记由撤销流程去掉 |

#### ⚠️ 级别 3 的「拦」在当前环境里落在哪儿（实测定论）

**自建 GitLab 是社区版**（实测 `GET /api/v4/version` → `15.7.2`、`enterprise: false`），
而 **Blocking merge requests 是 Premium 特性** —— `/merge_requests/:iid/blocks` 返回 **404**
（同一时刻 `/merge_requests/2` 返回 200，所以不是接口写错）。

**所以「拦」落不到 GitLab 的阻断 API 上**，只能落在**分支保护的合并权限**上：
只有当 Allowed to merge 被收窄到 GM 时，「GM 不批准」才真的等于「合不了」。

**而当前环境不是这样**（实测）：

| 分支 | 状况 |
|---|---|
| `main` | 受保护，但 **Allowed to merge = Maintainers** —— 所有 maintainer 都能合 |
| `test` | **根本没有保护** |

**结论：现在这个环境里，`hold_merge` 拦不住任何人。**

**这就是它为什么要做「拦得住吗」的自检。** 评论发出去了、标记打上了，
看起来「GM 拦了」，而实际上谁都能合掉 —— 那种「看起来做了」正是平台存在的理由要防的东西。
所以动作执行完会带上一条 `warning`（`ActionResult.warning`），管道把它打到日志里，
正文里也写一份：

> ⚠️ **平台自检**：目标分支 `main` 的 Allowed to merge 是「Maintainers」——不止 GM 能合，这次挂起**拦不住那些人**

**它不是 `ok: false`**（动作确实执行了，说失败是撒谎），**也不能默默通过**（那就是新的静默失效）。
它必须被看见 —— 而这条约束有先决条件：**主干保护配置要先做**，那属于环境侧改动，不是代码。

**顺带一条**：没有 GitLab 时（mock 源）**不提供本地版的 `hold_merge`** ——
「挂起合并」在本地无从表达，硬造一个假的会更坏（它会看起来成功）。
那种组合下，声明了级别 3 的策略会走到「平台没有它的实现」那条分支并如实报出来。

## 六、控制台

**定位**：**控制台是 GM 的另一张脸，不是第二个头脑。**

平台里**只能有一个会判断的东西**。控制台自己不下判断 —— 它的每条 AI 输出只有两种合法身份：

| 身份 | 含义 | 落库 |
|---|---|---|
| **转述** | 把已有判断记录（含依据）换个说法呈现 | 不落，指回原记录 id |
| **提问** | 组织语言、归纳、追问，但不宣称结论 | 不落 |

**若控制台自己也下判断**，平台就有两个会判断的东西：一个进了判断记录、有策略版本、有观察期数据；另一个只在界面上说了句话，说完就没了。**那才是真正的黑盒 —— 而且是那种「看起来更透明」的黑盒，因为它长得像个仪表盘。**

**五块**：待办（第一屏）· 观察 · 全局 · 问话 · 播报。加上策略管理（**控制台是操作台，不只是看板**）。

**命门是「待办」那一屏**：如果第一屏是数据总览，打开两次就不会再打开；如果是「有 3 件事等你决定」，它会变成习惯。

**细节见** [控制台设计](控制台设计-2026-10-13.md)（§3.1–3.11 是十一条判断，不在这里重复）。

## 七、接入：MCP 给能力，skill 给用法

**MCP 提供能力，不提供用法。** `tools/list` 给的是工具名与参数 schema，它不告诉接入的 Agent：什么时候该用（干完活要申报吗）、怎么组合、有什么坑（`title` 是**被检验的主张**而不是依据）。

后果很具体：**Agent 干完活不知道要 `submit_change`，平台就什么都看不到** —— 而「平台看不到」与「这次变更没问题」，在界面上长得一模一样。**这正是 S3。**

所以平台对外发**两份东西**：

| 出口 | 给什么 | 形态 |
|---|---|---|
| **MCP** | 能力 —— 能做什么 | 工具 |
| **skill** | **用法 —— 什么时候用、怎么用、坑在哪** | 一份 `SKILL.md` |

两条路**共用同一份正文**（发布到技能注册中心，或由 `get_usage_guide` 返回），**不各写一份**。skill 只写用法，**不复制工具描述与判据正文** —— 复制就是第二份事实源。

## 八、边界：不做什么

| 不做 | 理由 |
|---|---|
| **不写代码**，也不做代码生成 | 平台是载体，一旦它开始产出代码就变成开发者了 |
| **不做编排** | 谁干什么、怎么分工，那是编排器的事。**平台管「干完之后」** —— 谁判断、依据留不留、人怎么表态 |
| **不替人做决定** | 它可以拦、可以提示、可以留痕；**最后一票在人手里** |
| **不做任务看板 / 排期 / 需求流转** | 那是禅道的活。控制台上的每个数字要么来自判断记录、要么来自代码托管平台的客观事实，**没有第三个来源** |
| **控制台自己不下判断** | 见第六节。要下判断就走策略：有 id、有版本、有判据、进观察期 |

**这些边界的共同意义**：只要守住，平台就还是一个**载体**；破了任何一条，它就变成又一个需要人去适应、去维护的应用 —— 而那正是现有工具的毛病。

## 十一、已定死的设计约束

实现时别绕过它们，理由都在上文或专题文档里：

1. **未命中也要落记录** —— 否则无从知道「看过但没问题」，而观察期的分母正是「被评估了多少次」
2. **判断没做成 ≠ 通过** —— 三态结局，`error` 不执行动作、统计里单列
3. **每次判定都表态，包括什么都没发现的时候** —— 沉默承担不了「通过」这个含义
4. **一次判定只动一次手** —— 评论噪音会让人静音它，静音之后机制就等于不存在
5. **判断必须带依据**，依据分四类，`rule` 要标注它是措辞不是事实
6. **主张不是依据** —— MR 标题与描述由提交者自己写，只能是被检验的对象，写进 `gather` 白名单要在装配期报错
7. **取数白名单是权限边界** —— 加一项就是放宽一次，所以它是写死的注册表
8. **新判据先只发消息** —— 处置级别从 1 开始，升级由人看着数据决定
9. **只有「明确否定」进升级条件**，分母是「看过」
10. **升级判据与升级机制分开** —— 观察期只采集、不设判据（升级由人按按钮、可降级，必须对称）
11. **写默认关** —— 在真仓库上跑的第一阶段只做读；干燥跑走的是与真发同一条代码路径
12. **事件 id 带 commit sha** —— 「这个版本被审过没有」要有答案，而不是「这个 MR 被审过没有」
13. **每一维都是插进去的** —— 加新东西不该改管道
14. **复制 = 第二份事实源** —— 有守卫守着，且守卫本身要用人造漂移夹具验证有效
15. **GM 报数据，不要权限** —— 统计输出只陈述数字，不写「建议升级」这类话

# 自动化审查 / 门禁 / 合并判官 —— 调研报告

> 用途：为团队协作平台的核心角色 **GM**（订阅事件流 → 主动判断 → 分级行动 → 留依据）提供机制参照。
> 调研对象是 GM 的「机械化前身」：过去几十年里一直在做「自动判断一个变更能不能进主干」的成熟系统。
> 方法：web_search 定位 + web_fetch 抓官方文档正文核对。**每条关键结论附来源 URL；官方文档未写明的标「未找到」或明确标注为推断。**

---

## 一、总览

### 1.1 共同架构形态

这一类系统横跨三十年和四个技术世代，但骨架高度一致，可以归纳成四段：

```
状态检查（collect） → 判断（decide） → 动作（act） → 留痕（record）
```

| 段 | 各系统的实现 |
|---|---|
| **状态检查** | Prow Tide 用 GitHub search query 拉候选池；Gerrit 用 patch set + label 投票；Zuul 用 job 结果；GitHub 用 check runs / commit statuses；AI 审查用 diff + 仓库索引 |
| **判断** | 纯规则（标签状态 / CI 结果 / 文件路径 / 投票数）占绝大多数；模型判断在 2023 年后才出现，且**几乎都是「模型判断 + 结构化规则兜底」的混合形态** |
| **动作** | 五种粒度：发评论 / 打标签 / 发 check run（可失败）/ 直接行使否决（request changes、-2 投票）/ 执行合并或入队 |
| **留痕** | 分三个载体：**人读的评论**（Prow 的 APPROVALNOTIFIER 评论）、**机器 + 人都读的 check run**（Mergify、Bugbot）、**结构化结果对象**（Gerrit 的 submit requirement 结果含 `passingAtoms`、CodeRabbit 的 Passed/Failed/Inconclusive + reasoning） |

### 1.2 主要流派（这是本报告最有解释力的分类）

按「判断依据的形式」分两派，按「拦截强度」分五档。**两个维度是正交的**。

**按依据分：**

| 流派 | 代表 | 特征 |
|---|---|---|
| **A. 声明式规则** | Prow Tide、Gerrit Submit Requirements、GitHub branch protection / rulesets、Mergify | 判断依据是**可枚举、可校验、可模拟**的表达式；规则本身能当代码审查 |
| **B. 命令式脚本** | Danger、Bors（bors.toml 部分）、部分 Prow plugin | 判断依据是跑一段代码；表达力强，但**无策略层、无覆盖机制、无法自动校验** |
| **C. 结果搬运层** | reviewdog | 自己不判断，只把别人的判断（linter 输出）按 diff 过滤后送回 PR——**它是「依据的传递者」而非「判断者」** |
| **D. 模型判断（混合）** | CodeRabbit、Greptile、Qodo、Bugbot | 模型做语义判断，但**触发、严重度阈值、是否阻塞、能否自我放宽全部由结构化配置控制** |
| **E. 顺序协调器** | Zuul、Bors、GitHub Merge Queue、Graphite、Mergify Queue | 判断对象不是「单个变更好不好」，而是「**一批变更按什么顺序进主干才不互相破坏**」 |

**按拦截强度分（GM 的三级分级可以直接映射到这里）：**

| 档 | 动作 | 例子 | 能否拦在生效前 |
|---|---|---|---|
| 0 | 只发评论 | Qodo 默认、reviewdog `-reporter=github-pr-review` | 否 |
| 1 | 发 check run，但**发现问题时结论是 neutral** | Bugbot 默认（「findings default to neutral」） | 否（除非另行配置 fail-on-unresolved） |
| 2 | 发可失败的 check / status | reviewdog `-fail-level=error`、Danger 的 `fail` | **只有被设成 required check 才拦** |
| 3 | 直接行使否决权 | CodeRabbit request-changes review、GitHub「Request changes」review、Gerrit `Code-Review -2` | 是 |
| 4 | 平台级硬门 | GitHub required status checks、Gerrit submit requirement、Tide 的 merge pool | 是（变更物理上合不进去） |

**洞察**：档位 2 和档位 3 之间的分界，就是「我能让门关上」与「我替你踩刹车」的区别。多数 AI 审查工具停在档位 0–1；**只有 CodeRabbit 明确跨到了档位 3**（`request_changes_workflow`），而它同时保留了「人能显式覆盖」的出口。

### 1.3 「覆盖」是这一类的共同痛点，也是各系统差异最大的地方

各系统对人的覆盖的留痕强度，从弱到强大致是：

```
Danger / reviewdog（无机制，靠改 CI 配置）
  < Dependabot（命令有回执 👍，理由存在仓库中心位置但无结构化留痕）
  < Mergify（disabled.reason 写进 Summary check run；dequeue/queue 命令留在 PR 里）
  < GitHub ruleset（bypass 产生「prominent audit signals」，exempt 则静默）
  < Gerrit（overrideIf 表达式 + OVERRIDDEN 状态 + FORCED 状态，是**一等公民的状态机**）
  < CodeRabbit（`@coderabbitai approve` 是「显式覆盖」，且默认允许作者覆盖自己）
```

**Gerrit 和 GitHub ruleset 是这一维度上设计最成熟的**，理由见第三章对应小节。

## 二、逐系统

### 2.1 Prow（Kubernetes 的 CI/CD 机器人）

#### 它判断什么 · 判断依据的载体

Tide 的配置全部在 `config/prow/config.yaml` 的 `tide` 段。核心是 `queries`——**用 GitHub search 语法描述「哪些 PR 是候选」**：

- 字段：`orgs` / `repos` / `excludedRepos` / `labels` / `missingLabels` / `excludedBranches` / `includedBranches` / `author` / `reviewApprovedRequired`
- 底层映射到 GitHub 搜索 token：`labels: [lgtm]` → `label:lgtm`，`missingLabels: [do-not-merge]` → `-label:do-not-merge`，`reviewApprovedRequired` → `review:approved`
- 文档原话：「Every PR that needs to be rebased or is failing required statuses is filtered from the pool before processing」
- （来源：<https://docs.prow.k8s.io/docs/components/core/tide/config/>）

**检查的必需性由一个独立的策略层决定**，这是 Tide 设计里最值得看的一处。`context_options` 提供五级控制：

- `from-branch-protection: true`（复用 branch protection 的定义，避免两处规则打架）
- `required-contexts` / `optional-contexts` / `required-if-present-contexts`
- `skip-unknown-contexts`

文档给了一条重要警告：**如果没设这个选项、又没定义任何 prow job，Tide 会信任 GitHub combined status 并把所有检查都当必需**（除了它自己的 `tide` status）——这是一个「默认全信」的危险默认值。
（来源：<https://docs.prow.k8s.io/docs/components/core/tide/config/>）

**标签体系**：`lgtm`（技术审查完成）与 `approved`（OWNERS 审批）是两个正交的维度，缺一不可。

- `/lgtm` 由 reviewer 打；**PR 作者不能给自己打，但可以撤销**；**有新 commit 时 bot 自动撤销 lgtm**（"The bot retracts the label automatically if someone updates the PR with a new commit"）
- `/approve` 由 approver 打，**按目录粒度**：PR 修改的每个文件都必须被对应 OWNERS 里的某位 approver 批准
- 审批是**按目录做过集合覆盖**的：OWNERS 里的 approver 可以批准该目录及其所有子目录
- （来源：<https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/>）

#### 拦截方式

Tide 是一个**轮询式的 merge pool**：它周期性地（`sync_period` 默认 1m）查询符合 query 的 PR，成批跑必需测试，通过则合并。K8s 官方文档描述为「It uses GitHub queries to select PRs into 'tide pools', runs as many in a batch as it can ('tide comes in'), and merges them ('tide goes out')」。
（来源：<https://raw.githubusercontent.com/kubernetes/community/master/contributors/guide/pull-requests.md>）

三个**「先于合并」的阻塞手段**：

1. **`missingLabels` 里的 do-not-merge 家族**：`/hold` → `do-not-merge/hold`、标题 WIP → `do-not-merge/work-in-progress`、commit message 里用 GitHub 关键词（close/fix/resolve 等）→ `do-not-merge/invalid-commit-message`。官方明说「While either label is present, your pull request will not be considered for merging」
2. **`blocker_label`**：开一个带该标签的 issue，就会阻塞该仓库所有分支的合并；**issue 标题里写 `branch:name` token 可以把阻塞范围限定到具体分支**（支持引号，可重复出现多个 token）。这是一个「用一张工单当全局闸门」的机制。
   （来源：<https://docs.prow.k8s.io/docs/components/core/tide/config/>）
3. **`ok-to-test`**：外部贡献者的 PR 必须由 org member 打这个标签才会开始跑 CI——拦的不是合并，而是**资源消耗**（反滥用）。文档明确列出决策考量：PR 会不会浪费 CI 资源、是否需要更多改动、是否在借 CI 跑恶意代码。
   （来源：<https://raw.githubusercontent.com/kubernetes/community/master/contributors/guide/pull-requests.md>）

#### 人的覆盖方式 + 留痕

- `/approve cancel` 撤销审批；**撤销后 bot 会删掉 PR 上那个 status 并把该 approver 从集合里移除**（"If an approval is cancelled, the bot will delete the status added to the PR and remove the approver from the approver set"）
- `/lgtm cancel` 撤销；新 commit 自动让 lgtm 失效
- `/hold` / `/hold cancel`、改标题去掉 WIP
- `/retest` 重跑失败的测试（flake 场景）
- **留痕的核心载体是一条由 bot 维护的评论 `[APPROVALNOTIFIER]`**，会原地更新，内容包括：
  - 当前是 **APPROVED** 还是 **NOT APPROVED**
  - `The following people have approved this PR: *approver1, approver2, approver3, PRAuthor*`
  - 建议补充的 approver 名单
  - 折叠的 `∇ Details` 段里**逐条列出尚未满足的目录**：
    ```
    Needs approval from an approver in each of these OWNERS Files:
    * ~/A/B/E/OWNERS~ [approver1]     ← 已满足，划线并标注是谁批准的
    * /A/C/G/OWNERS                    ← 未满足
    ```
  - （来源：<https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/>）

  这是**「依据」可读性的一个标杆**：它不只说「没通过」，而是逐条列出**差哪一项、由谁补、补了谁批的**。

- **PR dashboard 会展示「你的 PR 与合并条件的差距」**：官方描述为 "shows the difference between your PR's state and the merge criteria so that you can easily see all criteria that are not being met and address them"。
  （来源：同上 K8s pull-requests.md）

#### 一个极值得注意的设计决策：OWNERS_ALIASES 而不用 GitHub Teams

文档原话：

> Note that items in the OWNERS files can be GitHub usernames, or aliases defined in OWNERS_ALIASES files. ... However, GitHub Team names are not supported. **We do not use them because there is no audit log for changes to the GitHub Teams. This way we have an audit log.**

（来源：<https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/>）

**这是一条被时间检验过的判断：审批权归属必须落在有审计日志的载体上。**

#### 权限模型

- OWNERS 文件放在仓库里，**随代码走、通过 PR 修改**（因此权限变更本身也走 code review）
- 子目录继承父目录的 approver；`OWNERS_ALIASES` 定义组
- 「Any collaborator on the repo may use the `/lgtm` command」——但 `/approve` 必须是 OWNERS 里的 approver，非 approver 打 `/approve` **不会生效**（"the PR will not be approved"）
- Observer/权限不足者可以评论但无法推进

#### 附带发现：Tide 会记录自己的动作历史

Tide 把它采取的动作（触发测试、合并）记在内存里，**可选用 `--history-uri` + `--gcs-credentials-file` 周期 flush 到 GCS 以跨重启保留**。文档明说这是严格可选的，但实例频繁重启、或用户想查看更久历史时「nice to have」。
（来源：<https://docs.prow.k8s.io/docs/components/core/tide/config/>）

**这与 GM 的「把判断的依据留下来」直接同构**——而且它给的答案是：**动作日志可以只是内存 + 可选持久化，不必一开始就上重存储**。

### 2.2 Gerrit（代码审查 + 投票体系）

Gerrit 是这一族里**模型最完整**的系统。它把「判断」拆成了三层：Label（投票）→ Submit Requirement（可提交条件）→ Submit Rule（求值）。

#### 它判断什么 · 投票的分值语义

预置两个 label，语义在文档里写得极清楚：

**Code-Review**（来源：<https://gerrit.nordix.org/Documentation/config-labels.html>）

| 分值 | 含义 | 是否阻塞 |
|---|---|---|
| `-2` | This shall not be submitted | **Any -2 blocks submit**，且**跨所有 patch set 有效**——reviewer 必须主动改票 |
| `-1` | I would prefer this is not submitted as is | 不阻塞 |
| `0` | No score | — |
| `+1` | Looks good to me, but someone else must approve | — |
| `+2` | Looks good to me, approved | **Any +2 enables submit**（必须是**最新 patch set** 上的 +2） |

**Verified**：`-1 Fails` 阻塞、`+1 Verified` 使能（CI 投这个）。

这套五档分值比「通过/不通过」二元制多了一个**中间态 `-1`**：表达「我不喜欢但我不拦你」——这是给「异议但不否决」留的位置，GM 的三级分级里没有对应物，值得借鉴。

#### 判断依据的载体：三代的演化（这是一个很有价值的「时间检验」样本）

1. **第一代：Label function**（`MaxWithBlock` / `AnyWithBlock` / `MaxNoBlock` / `NoBlock` / `NoOp` / `PatchSetLock`）——**已弃用**，文档明说「updates that set `function` to a blocking value will be rejected」，新 label 应显式设为 `NoBlock` 再改用 submit requirement
2. **第二代：Prolog submit rules**（`rules.pl`）——**已弃用**，「support for them will be dropped in future Gerrit releases」
3. **第三代：Submit Requirements**——当前推荐

**弃用的理由可以从替代品的形态反推**：submit requirement 是**声明式表达式**（可校验、可测试、可继承、可在 dashboard 上呈现），而 Prolog 是**图灵完备的脚本**。这与本报告 1.2 里 A 派战胜 B 派的趋势一致。
（来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>）

#### Submit Requirement 的字段与状态机（**本报告最值得照搬的一处**）

配置在 `project.config`：

```
[submit-requirement "Code-Review"]
  description = At least one maximum vote for label 'Code-Review' is required
  applicableIf = -branch:refs/meta/config
  submittableIf = label:Code-Review=MAX,user=non_uploader AND -label:Code-Review=MIN
  overrideIf = ...
  canOverrideInChildProjects = true
```

字段语义：
- `applicableIf`（可选）：这条要求**适不适用于**这个变更。不适用则在 UI 里隐藏
- `submittableIf`（**必填**）：何时可以提交
- `overrideIf`（可选）：**何时这条要求被「覆盖」**。文档原话：
  > When this expression is evaluated to true, the submit requirement state becomes `OVERRIDDEN` and the submit requirement is no longer blocking the change submission. This expression can be used to enable bypassing the requirement in some circumstances, **for example if the uploader is a trusted bot user or to allow change submission in case of emergencies.**
- `canOverrideInChildProjects`（默认 **false**）：子项目能否覆盖这条要求

**状态机六态**（这是 GM 四态的直系祖先）：

| 状态 | 含义 |
|---|---|
| `NOT_APPLICABLE` | `applicableIf` 为假 |
| `UNSATISFIED` | 适用，但 `submittableIf` 和 `overrideIf` 都为假 |
| `SATISFIED` | 适用，`submittableIf` 为真且 `overrideIf` 为假 |
| **`OVERRIDDEN`** | 适用，且 **`overrideIf` 为真**——注意：**此时无论 `submittableIf` 真假，都算被覆盖** |
| **`FORCED`** | **用 git push 的 `submit` 选项直接合并、绕过 code review** |
| `ERROR` | 表达式解析失败（可配置为返回 500 而非 ERROR） |

（来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>）

**这六态对 GM 的四态有三条直接的启示**：
1. `NOT_APPLICABLE` 与 `UNSATISFIED` 的区分——**「这条规则不适用」必须和「这条规则没通过」分开**。（GM 的四态里没有这一维）
2. `OVERRIDDEN` 的判定**独立于 `submittableIf`**——被覆盖了就是被覆盖了，不需要先满足条件再覆盖。这与「人能带理由强行通过」的语义完全一致。
3. `FORCED` 是**绕过整个体系**的旁路，与「在体系内被覆盖」是不同状态。GM 需要区分「GM 拦了、人推翻了」和「人根本没走 GM 这条路」——后者不该计入 GM 的推翻率。

#### 「依据」的粒度：passingAtoms

Gerrit 提供 REST 端点**在改动之前先测试 submit requirement**：

```
POST /changes/{id}/check.submit_requirement
{ "name": "Code-Review", "submittability_expression": "label:Code-Review=+2" }
```

响应：

```json
{
  "name": "Code-Review",
  "status": "SATISFIED",
  "submittability_expression_result": {
    "expression": "label:Code-Review=+2",
    "fulfilled": true,
    "passingAtoms": ["label:Code-Review=+2"]
  }
}
```

**`passingAtoms` 是「依据」能达到的最细粒度**：不是「通过了」，而是「因为这一条原子条件成立了」。GM 如果要留依据，这是可以直接照抄的目标形态。
（来源：同上）

#### 表达式的算子（值得注意的几个）

- `label:Code-Review=MAX,user=non_uploader`——必须是非上传者投的票（**防自批**）
- `label:Code-Review=MAX,user=non_author` / `non_committer` / `non_contributor`——不同强度的防自批（文档诚实地指出 `non_author`/`non_committer` 可以配合 Forge Author/Forge Committer 权限伪造，**不够强的场景下防不住**）
- `label:Code-Review>=1,users=human_reviewers`——要求**所有人类 reviewer** 都投过票（忽略 service user 和 change owner；**没有任何人类 reviewer 时这条不匹配**）
- `distinctvoters:[Code-Review,Trust]&count>1`——跨 label 的**不同投票人**计数
- `file:"^.*\.(cc|cpp)$",withDiffContaining='...'`——按**改了哪个文件、改了哪段内容**触发
- `hasfooter:"Bug"`——要求 commit message 里有某个 footer
- `has:submodule-update`——是否动了 submodule
- `is:true` / `is:false`——永远真/假（用于子项目重定义继承来的要求）

（来源：同上）

#### 其他值得注意的机制

- **`PatchSetLock`**：一种「锁住 patch set」的 label function——设上之后**不能创建新 patch set，rebase 和 abandon 都被阻塞**。用途：**跑昂贵 CI 的时候防止有人偷改**。支持重叠锁（多个锁账号可以同时锁同一个变更）。
- **`copyCondition`**（投票粘性）：新 patch set 上传时，投票是否从旧 patch set 复制过来由它决定。支持按 `changekind` 判断：`NO_CHANGE`（只有 SHA 变了）/ `NO_CODE_CHANGE`（只有 commit message 变了）/ `TRIVIAL_REBASE` / `MERGE_FIRST_PARENT_UPDATE` / `REWORK`。不复制过来的投票叫 `outdated`，**投票失效会把该 reviewer 加进 attention set**（需要重新审）。默认：Code-Review 用 `TRIVIAL_REBASE`，Verified 用 `NO_CODE_CHANGE`。
- **`allowPostSubmit`**：提交后能否投票。文档补了一句很有分寸的话——无论如何，提交后的新票必须不低于旧票，「**This avoids creating the false impression that a post-submit vote can change the past and affect submission somehow**」。
- **投票权限是分级的**：`label-Snarky-Review = -3..+3 group Administrators` / `-2..+2 group Project Owners` / `-1..+1 group Registered Users`。**同一 label，不同角色能投的分值范围不同**。
- **`canOverride`**：label 能否被子项目覆盖。
- **`branch`**：label 的适用范围可以限定到分支（`refs/heads/video-1.0/*`）。
- **Trigger votes**：不影响可提交性、纯粹用于触发流程的投票（如 `Presubmit-Ready` 触发集成测试），在 UI 里单列一节。

（来源：<https://gerrit.nordix.org/Documentation/config-labels.html> + submit-requirements 文档）

#### 一个「自我锁死」的警告（踩坑记录，值得抄进设计评审清单）

> Since submit requirements are stored as part of the project configuration in the `refs/meta/config` branch, changing them through code review requires to pass the submit requirements that apply to the `refs/meta/config` branch. Hence **by misconfiguring submit requirements for the `refs/meta/config` branch you can make further updates to submit requirements through code review impossible.**

恢复路径：直接 push `refs/meta/config`，或用 REST `Update Submit Requirement` 端点。
（来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>）

**教训：当「规则本身也受规则管辖」时，必须留一条不经过规则的管理通道。** GM 的策略三段（触发/判据/处置）如果也由 GM 自己守门，会有同样的风险。

#### 继承与 dashboard

- Submit requirement 从父项目继承；子项目可以覆盖（若 `canOverrideInChildProjects` 允许），但**必须整段重写**，不能只改一个字段
- 要移除继承来的要求：把 `applicableIf` 和 `submittableIf` **都设为 `is:false`**
- 父项目禁止覆盖时，子项目里同名要求**被忽略**
- Dashboard 空间有限，所以管理员要用 `gerrit.config` 的 `dashboard.submitRequirementColumns` **挑选哪些要求显示在 dashboard 上**，名字会缩写（`Foo-Bar` → `FB`）

**这条「dashboard 必须挑选、不能不选」的设计很务实**：依据多了以后，全展示等于没展示。

### 2.3 Mergify（合并队列 / 自动合并规则引擎）

#### 它判断什么 · 判断依据的载体

两套并行的规则引擎，共用同一套条件语法：

**① Workflow Automation（`pull_request_rules`）**：name / conditions / actions 三者中 name+conditions+actions 必填，description / disabled 可选。条件是 **AND 列表**，可用 `and`/`or`/`not` 组合。动作目录包括：assign / backport / close / comment / copy / dismiss_reviews / edit / label / merge / queue / rebase / request_reviews / review / update / squash。
（来源：<https://docs.mergify.com/workflow/rule-syntax/>）

**② Merge Protections（`merge_protections`）**：结构是 `name` / `description` / `if` / `success_conditions`。语义写得很清楚：

- 所有 `if` 为真 → 规则 **active**
- active 时，所有 `success_conditions` 都为真 → 规则 **succeed**
- **一条 active 但失败的规则会让整体 `Mergify Merge Protections` check 失败**
- **inactive 规则被忽略，且不显示为失败**

条件示例：`base = main` / `title ~= ^feat:` / `label = security-reviewed` / `files ~= ^src/` / `check-success = ci/build`。
（来源：<https://docs.mergify.com/merge-protections/custom-rules.md>）

**「inactive 不显示为失败」这一条值得单独记**：这是「依据」的信噪比问题——不适用我的规则，不该出现在我的报告里。

#### 拦截方式：队列 + 三个条件集

Merge Queue 的 PR 状态机（官方图）：

```
Dequeued → Queueing → Queued → Validating → Merged
```

- `queue_conditions`（进队条件）→ `merge_conditions`（合并条件）**两个独立的条件集**
- 进队列后的验证阶段：**临时把 PR 与 base 分支合并、重新触发 CI**，然后检查 `merge_conditions`
- 默认 serial 模式按队列顺序合并，但**测试是并行的**：`max_parallel_checks` 默认 5
- 默认 `batch_size` 为 1
- 失败/不再满足 `queue_conditions` → 自动出队

（来源：<https://docs.mergify.com/merge-queue/lifecycle.md>）

**处理冲突的方式很有讲究**：与队列前方 PR 冲突时**不移除，而是 held**——保留位置、check run 报 "checks deferred"、状态评论里**点名它在等哪些 PR**。后续分两种：前方 PR 出队未合并 → 恢复；前方 PR 合并 → 冲突被确认，移除队列。
（来源：同上）

**`conflict_resolvers`**：对「有机械答案的冲突」声明自动解决策略（`union` / `ours` / `theirs`），可指定 paths 或 `package-manager` + `directories`（如 npm 的 manifest 与 lockfile 必须一致地合并）。文档坦诚指出局限：只对 `merge_method: merge-batch` 或 `fast-forward` 生效；仓库自己的 `.gitattributes` 在这里无效（因为 Mergify 在无工作树的裸克隆里拼批次）。
（来源：同上）

**几个自适应超时/重试设计**：

- `checks_timeout: auto`（默认）：用**该队列、该 base 分支最近 7 天成功运行的 P95 时长 + 安全边际**算超时；重试和二分产生的运行被排除在测量之外；攒不够约 20 次运行则**不设超时**
- 超时出队时报 `checks-timeout` reason，**分别列出「还在跑的检查」和「从没上报过的检查」**——后者通常意味着 `merge_conditions` 里的 check 名跟 CI 实际发布的对不上（一条很实用的诊断）
- `max_checks_retries`（默认 0）：自动重试失败 CI，每次重试重建 draft PR；状态报告显示 "attempt 2/3"
- `checks-interrupted`（被外部取消）与 `checks-failed` 分开：前者不需要改代码，重新入队即可

（来源：同上）

#### 留痕：三种载体

1. **单一 check run**："Mergify Merge Queue"，标题随状态变化（"In merge queue" / "Running merge queue checks"）
2. **队列标签**：`queued_label`（默认 `queued`）/ `checking_label`（默认无，表示正在被检查，**占用 CI 容量的就是这些**）/ `dequeued_label`（默认 `dequeued`）
3. **状态评论**：`status_comments` 三档 `all`（含进队、CI 进度、最终结果）/ `outcomes`（只报最终结果和失败原因）/ `none`
   > ⚠️ **本文档内部矛盾（2026-10-13 复核指出，待核实）**：此处与后文「④ 不要把 dashboard 全量展示当留痕」一节对同一项的记载不一致——那里写「默认 `outcomes`」。**三档可配是确定的，默认值以哪一处为准未核实**，引用时请勿写默认值。

另有一处很细的诚实设计：**"Nothing landed" 报告**——当等价改动已在前面落地、rebase 后所有 commit 变成空，合并不动 base 分支，但 GitHub 仍把 PR 标记为 merged 且 Files changed 显示完整 diff。Mergify 在合并状态评论开头加一节说明这两件事，**免得作者读完整个报告才发现这次合并什么都没发出去**。
（来源：同上）

#### 人的覆盖 + 留痕

- **`@mergifyio queue`** 手动入队 / 重新入队（会把状态重置为中性）
- **`@mergifyio dequeue`** 手动出队。文档定义了它取消的两种状态：在队列中、以及**在等待满足 `queue_conditions` 的 pending 命令**（后者不取消的话，条件一旦满足还会入队）。**出队后不会自动回队**
- 不支持 `queue_conditions` 的 PR 自动出队（如它所依赖的标签被摘掉）
- **`disabled: {reason: ...}`**：**把规则留在文件里但停用，Mergify 在 Summary check run 里把该规则划掉并把 `reason` 打印在下面**，让其他人知道为什么停用。这是「停用一条规则」这一动作的留痕范本。
  （来源：<https://docs.mergify.com/workflow/rule-syntax/> + <https://docs.mergify.com/commands/dequeue.md>）

**未找到**：Mergify 的「带理由强行绕过一次具体判断」的显式 override 机制。它的覆盖语义是「改规则 / 停用规则 / 手动出队」，而不是「这次我推翻你的判断」。（这是与 Gerrit `overrideIf` 的关键差异）

#### 权限模型与配置校验

- 配置文件在仓库内（`.mergify.yml` 类），**通过 PR 修改**；dashboard 上建规则会把同样的 YAML **通过 PR 提交**到配置文件
- **每次 push 都会校验配置**并在 PR 的 Checks 标签报问题
- CLI 支持本地校验与**模拟**：`mergify config validate` / `mergify config simulate <PR URL>`
- GitHub App 身份行动

（来源：<https://docs.mergify.com/workflow/rule-syntax/>）

`config simulate` 这个能力很关键：**规则改动可以在生效前对着一批真实 PR 试跑**。GM 的策略改动也需要这个。

### 2.4 Danger（danger.systems，PR 规则检查）

#### 它判断什么 · 依据的载体

Dangerfile 是**命令式代码**（Ruby / JS / Swift / Kotlin），拿到一个 DSL 对象自由判断。API 面只有三个输出函数 + 一个 markdown：

```js
fail(message, file?, line?)     // Fails a build, outputting a specific reason for failing into a HTML table
warn(message, file?, line?)     // Highlights low-priority issues, but does not fail the build
message(message, file?, line?)  // 与 warn 只差 emoji
markdown(message, file?, line?) // 往 Danger 评论的表格下方加原始 markdown
```

结果对象结构：`DangerResults { fails, warnings, messages, markdowns, meta }`。

（来源：<https://danger.systems/js/reference.html>）

**DSL 提供的数据源**（这是它真正的价值——一个统一的「PR 上下文」抽象）：

- `danger.github.pr`：author_association（`COLLABORATOR`/`CONTRIBUTOR`/`FIRST_TIMER`/`MEMBER`/`OWNER`/`NONE`）、labels、additions/deletions、changed_files、base/head、merged、locked 等
- `danger.github.reviews`：每条含 `state: APPROVED | REQUEST_CHANGES | COMMENT | PENDING`、body、commit_id
- `danger.github.commits` / `requested_reviewers` / `issue.labels`
- `danger.git`：`modified_files` / `created_files` / `deleted_files` / `commits` / `base` / `head`
- `danger.git.fileMatch`（Chainsmoker）：glob 匹配后返回 `modified`/`created`/`edited`/`deleted` 四个布尔
- `danger.git.diffForFile` / `structuredDiffForFile` / `linesOfCode(pattern)` / `JSONDiffForFile` / `JSONPatchForFile`
- `danger.utils.href/sentence`、`danger.github.utils.fileLinks` 等

（来源：<https://danger.systems/js/reference.html>）

#### 拦截方式（**推断，需注意**）

文档只说 `fail` 是 "Fails a build"。Danger 本身跑在 CI 里，**它让承载它的那次 CI 失败**；要真正拦住合并，需要把这个 CI job 设成 required status check。

> ⚠️ **标注**：这一句「需要设成 required check 才真正阻塞」是**从 GitHub 平台机制推断的，Danger 官方文档未明确表述**。未找到 Danger 文档里关于「如何让 fail 阻塞合并」的说明。

#### 人的覆盖方式

**未找到内置的覆盖或豁免机制。** FAQ 里唯一的规避手段是把 Danger 整个跳过（例如只在有 token 时才跑：`[ ! -z $DANGER_GITHUB_API_TOKEN ] && yarn danger ci || echo "Skipping Danger for External Contributor"`——这个例子的用途是「只对内外部贡献者中的内部人运行」）。
（来源：<https://danger.systems/js/guides/faq.html>）

覆盖只能靠改 CI 配置或改 Dangerfile——**这两件事都发生在合并之前，因此覆盖本身也走 code review**。这是一个「间接留痕」：覆盖行为被记录在提交历史里，而不是被记录在「这次判断被推翻」的事件流里。

#### 权限模型与跨仓库

- 配置在仓库内（`Dangerfile`），随代码走
- 认证用 `DANGER_GITHUB_API_TOKEN`
- **多仓库复用 Dangerfile 在 FAQ 里的原话是「Ish, it's currently quite complex to set up」**，官方指向 `Peril`（托管版 Danger，可以响应几乎任意 GitHub webhook 类型）
- （来源：<https://danger.systems/js/guides/faq.html>）

#### 小结

Danger 代表**B 派（命令式脚本）**，它的强项是表达力（任意逻辑都能写），弱项是：
- 没有策略分层（没有「触发/判据/处置」的分离）
- 没有「依据」的结构化载体（依据就是那段人写的 message 字符串）
- 没有覆盖语义
- 没有规则校验/模拟
- 跨仓库复用难

**它是「一个能写任意判断的钩子」，不是「一个判断系统」。**

### 2.5 reviewdog（自动 review 评论）

#### 它判断什么

**它自己不判断。** README 开篇即说：它「provides a way to post review comments to code hosting services ... by integrating with any linter tools with ease. It uses an output of lint tools and posts them as a comment if findings are in the diff of patches to review」。
（来源：<https://github.com/reviewdog/reviewdog>）

它的两个核心机制：

**① 输入归一化**——把任何工具的任意文本输出转成结构化诊断：

- `errorformat`：Vim errorformat 的移植（`%f:%l:%c: %m`），可从 stdin 解析几乎任何 linter 输出
- 预定义 format（`-f=golint` 等，上百种）
- **RDFormat**（`rdjson` / `rdjsonl`）：自定义的通用诊断格式，支持多行范围评论、severity、**带 URL 的规则编号**、代码建议
- checkstyle XML、SARIF 2.1.0、unified diff

**② diff 过滤**——`-filter-mode`：`added`（默认，只看新增/修改行）/ `diff_context`（±N 行）/ `file`（改过的文件内都报）/ `nofilter`。

（来源：<https://github.com/reviewdog/reviewdog>）

#### 拦截方式：**评论与拦截解耦**（这是它最值得借鉴的一处）

**`-level` 决定 check 的结论**，而 **`-fail-level` 决定进程退出码**，两者独立：

| `-level` | GitHub Status |
|---|---|
| `info` | neutral |
| `warning` | neutral |
| `error` | **failure**（默认） |

而退出码：

> By default (`-fail-level=none`) reviewdog will return `0` as exit code **even if it finds errors**. reviewdog will exit with code 1 with `-fail-level=[any,info,warning,error]` flag if it finds at least 1 issue with severity greater than or equal to the given level.

（来源：<https://github.com/reviewdog/reviewdog>）

**这两条合起来说明**：同一个工具，既能当「只评论不拦」，也能当「评论且拦」，**切换点是配置而不是架构**。GM 的三级分级如果按这个思路设计——**判据产出「发现 + 严重度」，分级映射到「动作 + 是否阻塞」，两层解耦**——同一套判据就能在观察期（只评论）和收紧期（阻塞）之间平滑迁移。

#### 输出通道与权限

支持 11 种 reporter：`local`（默认）/ `github-pr-check` / `github-check` / `github-pr-review` / `github-annotations` / `github-pr-annotations` / `gitlab-mr-discussion` / `gitlab-mr-commit` / **`gerrit-change-review`** / `bitbucket-code-report` / `gitea-pr-review`。

代码建议（suggestion）的支持矩阵显示：**只有 `github-pr-review` 和 `gitlab-mr-discussion` 支持**，check 类 reporter 都不支持（因为 check API 本身不支持）。

权限上有几处实际约束值得注意：

- `github-pr-check` **依赖 GitHub Checks API，而该 API 只对 GitHub App 和 GitHub Actions 开放**——所以要么在 Actions 里跑，要么装 reviewdog App
- 装 App 的路径依赖作者自建的服务器，README 里作者自己坦白：「The server is running with haya14busa's pocket money for now and I may break things, so I cannot ensure that the server is running 24h and 365 days」
- **fork PR 的优雅降级**：来自 fork 的 PR 其 `GITHUB_TOKEN` 没有 Check/Review API 写权限，reviewdog 退化为用 Actions logging command 发 annotation（有数量上限）

（来源：<https://github.com/reviewdog/reviewdog>）

#### 覆盖与留痕

**未找到覆盖机制 / 覆盖留痕。** 配置在 `.reviewdog.yml`（runner / cmd / errorformat / format / name / level），随代码走。

### 2.6 GitHub 原生

#### 2.6.1 CODEOWNERS

- 位置：`.github/` → root → `docs/`（按此顺序取**第一个找到的**）；每个分支一份；**用 PR 的 base 分支那一版**
- 语法：gitignore 风格 pattern + `@user` / `@org/team`；**最后匹配的 pattern 优先**
- 限制：文件 < 3 MB（超了不加载）；**语法错的行被整行跳过**；`!` 取反、`#` 转义、`[]` 字符范围都不支持
- 与 branch protection 联动：开启 "Require review from Code Owners"。**任何一个 owner 批准就够**（文档给了明确例子：`*.js @global-owner1 @global-owner2` 时「approvals from both are not required」）
- 自保护建议：把 CODEOWNERS 文件本身也指定 owner（`/.github/CODEOWNERS @owner_username` 或整个 `/.github/`）
- 用户/团队必须有**显式 write 权限**

（来源：<https://raw.githubusercontent.com/github/docs/main/content/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners.md>）

#### 2.6.2 Branch protection（**required status checks 的三态定义是关键**）

设置项全集：require PR reviews / require status checks / **require conversation resolution** / require signed commits / require linear history / require merge queue / require deployments to succeed / lock branch / do not allow bypassing / restrict who can push / allow force pushes / allow deletions。

**最关键的一条定义**：

> Required status checks must have a `successful`, `skipped`, or **`neutral`** status before collaborators can make changes to a protected branch.

**即：`neutral` 算通过。** 这一条直接决定了 Bugbot 那类「发现问题但默认 neutral」的工具**不能**拦住合并（见 2.8.4）。

其他值得抄的机制：

- **可以指定某个 GitHub App 作为该 check 的期望来源**：「you can select an app that has recently set this check as the expected source of status updates. If the status is set by any other person or integration, merging won't be allowed.」——**防止别人伪造同名 status**。选 "any source" 就得人工核对
- **strict vs loose**：strict 要求分支 up-to-date（默认），loose 不要求（合并后可能发现与 base 不兼容）
- **Request changes 的 review 会阻塞**，且**只有该人自己 approve 才能解除**；该人不可用时，**有 write 权限的人可以 dismiss 这个阻塞 review**（这是一个明确的「覆盖」通道）
- **陈旧审批**：push 影响 diff 的提交会让 approval 失效（可选开关）
- 替代方案：「要求**最近一次可审查的 push** 必须由 push 者之外的人批准」——文档解释了取舍：这样不必 dismiss 所有陈旧审批，但如果担心 PR 被劫持（往已批准的 PR 里加未审内容），dismiss 更安全
- **默认管理员和拥有 "bypass branch protections" 权限的自定义角色不受限制**；可以开启 "Do not allow bypassing the above settings" 把限制也套上
- **只有一条 branch protection rule 生效**（多条命中同一分支时哪条生效难以预知）——**rulesets 没有这个限制**

（来源：<https://raw.githubusercontent.com/github/docs/main/content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md>）

#### 2.6.3 Merge queue

- 由 branch protection 的 "Require merge queue" 开启；**分支名含通配符的 protection rule 不能开 merge queue**
- 临时分支前缀 `gh-readonly-queue/{base_branch}`；Actions 要监听 **`merge_group`** 事件，第三方 CI 要监听该前缀分支的 push
- 可配：merge method / build concurrency(1–100) / **"Only merge non-failing pull requests"** / status check timeout / **merge limits（min/max + wait time）**
- **"Only merge non-failing" 关闭时的语义值得注意**：组内前面的 PR 可以带着失败的检查入组，**只要组内最后一个 PR 通过**——因为那意味着「整组合并后的组合」通过了。文档说明用途：有间歇性失败、不想让假阴性堵住队列
- FIFO；组内包含 base 最新版本 + 队列前方所有 PR 的改动；某 PR 失败 → 自动移出并重建后面的临时分支
- **Jump to the top**：会导致 commit graph 断裂、**所有在途 PR 全量重建**，文档明确警告「Heavily utilizing this feature can slow down the velocity of merges for your target branch」

（来源：<https://raw.githubusercontent.com/github/docs/main/content/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue.md>）

#### 2.6.4 Ruleset 的 bypass vs exempt（**GM「overridden」的直接参照物**）

GitHub 2025-09 引入第二种 bypass 类型，官方把两者的区别讲得非常清楚：

> Unlike a standard bypass (i.e., **a "break glass" action that requires an explicit actor bypass and generates prominent audit signals**), an exemption **silently skips enforcement**. Use it for trusted, high-volume automation or migration scenarios where friction would otherwise slow you down.

配置路径：在 ruleset 的 "Bypass" 列表里找到该 actor → `…` → **Exempt**。

（来源：<https://github.blog/changelog/2025-09-10-github-ruleset-exemptions-and-repository-insights-updates/>）

**这是本报告里对 GM 最有价值的一条对比**：同样一个「放行」动作，被分成了两种性质完全不同的东西——

| | 标准 bypass | exempt |
|---|---|---|
| 性质 | 「破窗」 | 「豁免」 |
| 是否显式 | 需要 actor 显式绕过 | 静默跳过 |
| 是否留痕 | **产生醒目的审计信号** | 无 |
| 适用 | 紧急情况、人 | 可信高频自动化、迁移 |

**GM 的授权模型需要这一刀**：一个「可信 bot 一直不受这条规则约束」和「某人这次破例绕过了 GM 的判断」是两件完全不同的事，混在一起会让「被推翻的记录」失去统计意义。后者才是 GM 的改进输入，前者不是。

补充：还存在 **organization push rule bypass requests** 的 REST API（即**人可以「提交 bypass 请求」而不是直接绕过**）——这条路把覆盖行为变成了一个可审批、可记录的工单。
（来源：搜索结果指向 <https://docs.github.com/en/enterprise-cloud@latest/rest/orgs/bypass-requests>；该页正文因导航占位未取到全量内容，此条按标题与端点命名陈述，**建议复核**）

### 2.7 自动依赖更新

#### 2.7.1 Renovate

**判断依据**：完全结构化配置。`packageRules` + 匹配器（`matchUpdateTypes: ["minor","patch"]`、`matchCurrentVersion: "!/^0/"`、`matchDepTypes`、`matchPackageNames`、`matchFileNames`、`matchConfidence`、`matchJsonata` …）+ 动作（`automerge: true` 等）。**没有模型判断**。
（来源：<https://docs.renovatebot.com/configuration-options/>）

**automerge 的前提条件**（这是「门禁」的那一半）：

> By default, Renovate will not automerge until it sees passing status checks / check runs for the branch. If you have no tests but still want Renovate to automerge, you need to add `"ignoreTests": true`.

**这等价于「默认开启 required checks，除非显式关掉」——与 Prow Tide 的「默认把所有检查都当必需」是同一个默认值取向。**

**「拦在生效之前」的两个体现**：

- automerge 慢且保守：一次运行**只在一个 target branch 上合并一个分支/PR**（因为合并一个会改变其余分支的 git state），并且要求待合并分支**在合并前 up-to-date**
- PR body 里明确写出判断结果：**"Automerge: Enabled" / "Automerge: Disabled by config"**——读者能直接看到「为什么它没自动合」

**几种合并形态**：

- `automergeType=pr`（默认）vs `automergeType=branch`（先建分支不开 PR；测试过了**直接推 base 分支**；测试失败才开 PR 给你审）——branch 模式在 branch protection 面前会失败，文档明说了
- `platformAutomerge`（默认 true）：交给平台原生 auto-merge（GitHub auto-merge / GitLab merge train）
- `platformAutomerge=false` 时 Renovate 自己合；**如果它在 merge queue 的 bypass list 里就直接合，被拒则自己入队**

**与平台门禁的冲突清单（官方 troubleshooting 段，很有实操价值）**：committer 限制 / 要求 PR / **要求 review（可用 branch protection 的 "Allow specified actors to bypass required pull requests"，或装 `renovate-approve` helper app 自动批准）** / **CODEOWNERS 会要求 code owner 审批**。
（来源：<https://docs.renovatebot.com/key-concepts/automerge/>）

**覆盖方式**：改配置（PR 形式的自我修改）；`rebaseLabel` / `stopUpdatingLabel` 等标签控制；**集中配置可被单仓库覆盖**（org 级 `.github` 仓库托管 `renovate.json`，单仓库用 `matchPackageNames: ["*"] + automerge: false` 全部关掉）。
（来源：<https://docs.renovatebot.com/key-concepts/automerge/>）

**跨仓库**：self-hosted 一个实例可管多仓库；配置支持继承（`extends`）与集中托管。**未找到**其跨仓库「合并顺序协调」的能力（那是 Zuul/Graphite 的地盘）。

#### 2.7.2 Dependabot

- 自动开 PR，作者是 `dependabot` bot，默认带 `dependencies` 标签
- 默认自动 rebase 解决冲突（可用 `rebase-strategy` 关）；**一旦有人往它的分支推了额外 commit 它就停止 rebase**，除非你在 commit message 里加 `[dependabot skip]` / `[skip dependabot]` / `[dependabot-skip]` / `[skip-dependabot]` 允许它 force push 覆盖你的改动
- **注释命令全表**：`@dependabot ignore this dependency` / `ignore this major version` / `minor` / `patch`、`@dependabot rebase`、`@dependabot recreate`（**覆盖掉所有对 PR 的人工编辑**）、`@dependabot show <DEP> ignore conditions`；分组更新另有 `ignore <DEP>` / `unignore *` / `unignore <DEP>` / `unignore <DEP> <CONDITION>`
- bot 会以 **👍 回执**命令
- **覆盖的理由归属**：文档明确建议——ignore 类命令的偏好是**存在仓库级中心位置**的，但「for repositories with more than one contributor it is better to explicitly define the dependencies and versions to ignore in the configuration file. **This makes it easy for all contributors to see why a particular dependency isn't being updated automatically.**」
  ——这是官方文档里对「覆盖要留下可读理由」最直白的一次表态。

（来源：<https://raw.githubusercontent.com/github/docs/main/content/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/manage-dependabot-prs.md> 与 <https://raw.githubusercontent.com/github/docs/main/content/code-security/reference/supply-chain-security/dependabot-pull-request-comment-commands.md>）

**注意（重要）**：**官方注释命令表里没有 `@dependabot merge` / `approve`**。第三方教程（含 Microsoft Learn 的本地化页面）里出现的 `@dependabot merge` / `@dependabot squash and merge` 在官方 reference 中已不存在。**自动合并需要自己写 GitHub Actions workflow 调用 `gh pr merge`，或依赖平台 auto-merge。**
（这是从官方命令表反推的结论——命令表是「全部可用命令」的 reference 页。）

### 2.8 Zuul / Bors / Graphite —— 顺序协调器

这三个系统回答的问题与前几个不同：**不是「这个变更好不好」，而是「一批互相依赖的变更按什么顺序进主干才不互相破坏」**。

#### 2.8.1 Zuul（**speculative execution 是这一族最优雅的机制**）

**问题陈述**（官方 rST 原文）：

> The process of gating attempts to prevent changes that introduce regressions from being merged. This keeps the mainline of development open and working for all developers, and only when a change is confirmed to work without disruption is it merged.

**speculative execution（推测执行）**：

> Zuul's dependent pipeline manager allows for parallel execution of test jobs for gating while ensuring changes are tested correctly, **exactly as if they had been tested one at a time**. It does this by performing speculative execution of test jobs; **it assumes that all jobs will succeed and tests them in parallel accordingly.** If they do succeed, they can all be merged. However, if one fails, then changes that were expecting it to succeed are re-tested without the failed change.

具体到执行：改变 A、B、C、D、E 依次入队，则

```
Jobs for A: merge change A, then test
Jobs for B: merge changes A and B, then test
Jobs for C: merge changes A, B and C, then test
Jobs for D: merge changes A, B, C and D, then test
Jobs for E: merge changes A, B, C, D and E, then test
```

若 A、B 绿而 C、D、E 红：先合并 A、B；C 被报告失败并移出队列；**D、E 保留但状态变回未知（`D?`、`E?`），重新在 C 缺席的情况下测试**——「This queue is the same as if two new changes had just arrived」。

**Pipeline window（流控）**：

> By default, Zuul uses an algorithm inspired by the Transmission Control Protocol's flow control to determine the window size. It starts with the window set to a certain value (**twenty changes by default**). Each time a change successfully merges, the window is increased by one. Each time a change fails, the window is halved.

窗口是「队列头部允许同时开跑 job 的变更数」，超出的挂起等待。**每个 project queue 维护自己的窗口**，好让某个项目的不稳定测试不影响其他项目的窗口。

**cross-project testing**：把多个项目放进 dependent pipeline 的**同一个共享 change queue**，则「the commits for the changes ahead in the queue are automatically present in the jobs for the changes behind them」。

**cross-project dependencies（`Depends-On:`）**：

- 在 commit message（Gerrit）或 **PR 描述**（GitHub）的 footer 写 `Depends-On: <change-url>`
- 行为是 **DAG**：A 依赖 B，B 不能依赖 A
- 入队时序列化：B 在前、A 在后；**B 失败则 A、B 一起被移出，A 在 B 合并之前无法合并**
- 局限（文档明确写出）：如果不共享 change queue，Zuul **无法把它们一起入队**，必须第一个先合并；而且**如果第二个在第一个合并前就被批准，Zuul 无法对这个批准采取行动，需要一个新的 approval 事件才能把它入队**
- 支持**循环依赖**但需显式开启（`queue.allow-circular-dependencies`）

**Global repo state**：一个 queue item 用到的 git 仓库会被**冻结**（分支头 + tag），该 queue item 的所有 job 看到一致的状态——「even if one job starts running much later than another」。

（来源：<https://zuul-ci.org/docs/zuul/latest/gating.html>；正文取自 <https://opendev.org/zuul/zuul/raw/branch/master/doc/source/gating.rst>）

**恢复/覆盖手段**（来自 admin client 文档的目录）：recheck（重跑）、enqueue/dequeue、autohold（**保留失败现场供调试**，文档标记为 deprecated）、promote。

#### 2.8.2 Bors-NG（**已官方弃用，但它的论证值得留档**）

README 开头的弃用声明：

> **Deprecation notice**: Though I'll still merge bug fixes if they're provided, **new features will not be accepted.** If you want to implement a workflow like this, use GitHub's built-in merge queue.

**它的核心论证**（这是「为什么 PR 通过测试还不够」的经典表述）：PR #1 把 `bifurcate()` 改名，PR #2 新增一处 `bifurcate()` 调用。两个 PR 各自与 main 测试都通过，GitHub 都会给绿灯；**两个都合并后 main 变红**（Method not found）。

**解法**：不要测 PR head，**测合并结果**——

> Instead of merging, you add reviewed pull requests to a "merge queue" of pull requests that are tested against the main branch by copying it to a **staging** branch and merging into that. When the status of staging is determined (either pass or fail), bors reports the result back as a comment and merges staging into main if it was a pass.

**关键性质**：「Since the main branch contains the exact contents that were just tested, **bit-for-bit**, it's not broken.」

**批处理 + bisect**：一批失败则二分拆成两批重试，直到定位到单个 PR；单个 PR 失败就退回给作者。「The batching strategy is O(E log N), where N is the total number of pull requests and E is the number of pull requests that fail.」

**命令**：`bors r+` 批准并入队、`bors try` 只测不合（走 `trying` 分支，`r+` 走 `staging` 分支）。

**配置与权限**：仓库内 `bors.toml`（`status = ["ci"]` 声明必需的状态检查名）；用 GitHub App，README 里逐项列了所需权限并**逐项解释了为什么需要**（Commit statuses R/W 才能报测试状态、Issues R/W 因为 PR 就是 issue、Checks R/W 报新版状态…）；**admin 只能在数据库里加，没有 UI**。

（来源：<https://raw.githubusercontent.com/bors-ng/bors-ng/master/README.md>）

#### 2.8.3 Graphite

- **stack-aware 是它的差异化**：「The Graphite Merge Queue is the only merge queue that is stack-aware」，栈一起入队时可以**并行验证整个栈**（fast-forward merge，Graphite 独有设置），且**不必重跑 CI**——「since we have already validated the CI against that exact change」
- 如果在仓库设置里不强制，**用户仍可直接从 GitHub 合并、完全绕过合并队列**
- **与 GitHub 自己的 merge queue 不兼容**，二选一
- **留痕**：在 PR 上留评论的三个时机——**入队时 / 通过队列合并时 / 失败或被移出时**
- 另有 external merge queue integration（beta），可与其他合并队列并存但失去 stack 优化

（来源：<https://graphite.com/docs/graphite-merge-queue.md>）

### 2.9 AI 代码审查（CodeRabbit / Greptile / Qodo / Cursor Bugbot）

这一族的共同形态：**模型做语义判断 + 结构化配置控制边界**。四家的差异集中在「拦不拦」「能不能自我放宽」「怎么学习」三处。

#### 2.9.1 CodeRabbit（**这一族里唯一明确跨到「行使否决权」档位的**）

**判断依据**：模型（配 AST 规则、路径指令、知识库、MCP 工具）。

**拦截：`reviews.request_changes_workflow`**（默认关闭）。开启后：

> When enabled, CodeRabbit **requests changes** when a review posts actionable inline comments and **approves the pull request after the approval requirements are met**.

在 GitHub 上，「request changes」是一个会**阻塞合并**的 review state。批准的条件（原文列了五步）：

1. 最新 commit 已完成一次 review
2. 所有必须解决的 review thread 都已 resolved
3. 没有失败的 Pre-Merge Checks
4. **批准前再验证一次 PR HEAD 没有变过**
5. 满足上述后批准该 commit

**批准会保持 pending 的情形**（文档逐条列出）：最新 review 缺失/进行中/失败/被限流；当前 HEAD 不在 CodeRabbit 审过的 commit 里；有必解线程未解决；有 Pre-Merge Check 失败；在验证期间 HEAD 变了。

（来源：<https://docs.coderabbit.ai/pr-reviews/request-changes-workflow>）

**人的覆盖：「显式覆盖」（explicit overrides）**——文档原话：

> Top-level `@coderabbitai resolve` and `@coderabbitai approve` comments are **explicit overrides** when this workflow is enabled. Both commands resolve CodeRabbit-authored review threads and **can submit approval without requiring the latest commit to have a completed review or requiring Pre-Merge Checks to pass.**

**权限**：文档明确说 —— 默认 **PR 作者可以对自己的 PR 用这两个命令**；`reviews.allow_author_approval: false` 可禁止（**作者以外的其他人仍可用**）。这是一个「自我覆盖」的开关，默认开着。

（来源：同上）

**「依据」：Pre-Merge Checks 的输出三态 + reasoning**

自定义检查用**自然语言指令**写（不是表达式），agent 在**只读沙箱**里执行三步：Analyze → Verify（用 ast-grep / ripgrep / 沙箱 shell / web / 已连接的 MCP 工具**取证**）→ **Decide：输出 `Passed` / `Failed` / `Inconclusive` 并给出 reasoning**。

文档对「怎么写判据」给了一组很实用的反模式表（**这一节对 GM 的「判据用自然语言」这一段是直接可用的**）：

| 反模式 | 例子 | 为什么失败 |
|---|---|---|
| 含糊 | "Verify best practices" | 没有具体的通过/失败标准 |
| 信息不可得 | "Ensure PR is approved by @security-team" | agent 查不到审批状态 |
| 要求推测 | "Assess if there are obvious performance optimizations" | 没有确定标准，依赖主观判断 |
| 要求改 review | "Keep review comments concise" | 这是路径指令的活，不是检查的活 |

正面原则：**具体且可执行 / 定义清晰的通过-失败标准 / 一个检查只问一件事 / 复杂规则给例子**。

检查能力的边界也写得很明确（**「不能做什么」和「能做什么」同等重要**）：不能跑测试套件、不能访问 node_modules/dist/构建产物、不能执行仓库代码、不能发行内评论（结果只在摘要表里）、**不能查 PR 审批状态或 reviewer 分配**、不能修改 CodeRabbit 的 review。

（来源：<https://docs.coderabbit.ai/pr-reviews/custom-checks>）

**学习闭环：Learnings**（**这是对 GM「被推翻的记录是改进唯一输入」最直接的现成实现**）

- 形态：**自然语言陈述**（"prefer returning early with specific error codes rather than nested try-catch blocks"），存在按 Git 平台组织关联的内部数据库里
- 产生方式：① 在 PR/issue 上 **@coderabbitai 回复它的一条具体评论**；② 从文件导入（`@coderabbitai add a learning using docs/coding-standards.md`）
- **透明性**：CodeRabbit 在响应评论里加一个折叠的 **"Learnings Added"** 区块，**明确告诉人「这次对话改变了它未来的行为」**
- 记录内容：learning 文本 + **PR 号、文件名、GitHub 用户**等元数据
- 生效范围：`knowledge_base.learnings.scope` = `local`（只本仓库）/ `global`（全 org）/ `auto`（默认；公开仓库只用自己的，私有仓库用全 org 的）
- **审批门**：`approval_delay`（0–30 天，**默认 0 = 立即生效**）。设 >0 时新建的对话式 learning 进 **Pending approvals**，管理员可批准/拒绝，**超期自动批准**
- **作用域隔离（很关键）**：在开着的 PR 上创建的 learning **先只作用于该 PR**，该 PR **合并后**才成为仓库级、进入正常检索；**PR 被关闭而未合并则 learning 保持 PR 作用域**。源 PR 可检索自己最近 20 条
- **凭据脱敏**：写入时把可识别的凭据替换为类型标记（`***REDACTED_GITHUB_TOKEN***` / `***REDACTED_STRIPE_KEY***` / `***REDACTED_URI_PASSWORD***`），**仅写入时做，不回填历史**
- 治理界面：Learnings dashboard，四张 KPI 卡（**Total / Active（30 天内用过）/ Never Used / Created This Week**）+ 列（Usage / Last Used / Created At / Updated At）+ 详情（Description / Usage / **Created by** / Repository / 各时间戳），支持向量相似度搜索、按仓库/路径/用户过滤、编辑、删除、CSV 导出、API 增删改（写入限流 10 次/分/org）
- **官方承认它会腐坏，并给了维护建议**：「Quarterly review」/「**Delete contradictory learnings**」/「**Update rather than accumulate**」——「Multiple conflicting learnings on the same topic can produce inconsistent behavior」；还给了「learnings 似乎不生效」时的 workaround（加一条强制模型先复查 learnings 的强化规则）
- **官方的最佳实践**（这三条对 GM 尤其有用）：
  - **区分「模式」与「一次性例外」**——「Not every correction should become a learning. For one-time exceptions ... resolve the comment without creating a learning.」
  - **解释 why 而不只是 what**——「The 'why' helps CodeRabbit apply the learning correctly in **similar-but-not-identical** situations」
  - **回复到具体代码行的评论**（比 PR 上的泛泛评论能产生更精确的 learning）

（来源：<https://docs.coderabbit.ai/knowledge-base/learnings>）

#### 2.9.2 Greptile

**判断依据**：模型 + `greptile.json` / `.greptile/` 配置。关键配置项：

- `strictness`（1/2/3，**严重度阈值**）、`commentTypes`（logic/syntax/style）
- `autoReview`：`["open"]`（默认）/ 可加 `push`、`rebase`；`[]` = 从不自动审
- `triggerOnDrafts`、`labels` / `disabledLabels`、`includeAuthors` / `excludeAuthors`、`includeBranches` / `excludeBranches`、`includeKeywords` / `ignoreKeywords`（**支持 glob**）
- `ignorePatterns`、`customContext`（`rules` 带 `scope` / `files` / `other`）、`instructions`（自然语言）
- `context.repos` / `patternRepositories`：**跨仓库上下文**（读关联仓库如共享库/SDK）

（来源：<https://www.greptile.com/docs/code-review/greptile-json-reference.md>）

**拦截方式：`statusCheck: true`**——「Create a GitHub status check for each review. When enabled, Greptile posts a status check (pass/fail indicator) instead of a comment」。
（来源：同上）

**「能不能自我放宽」：`autoApprove`**（让 Greptile 批准低风险的 5/5 review）：

> **Unlike other settings, Greptile reads this from the PR's base branch, so a PR cannot loosen it for itself.**

**这是与 Bugbot 同构的一处设计**（见 2.9.4）：**审查者的配置从 base 分支读，PR 改不到自己头上的审查规则。**

**配置层级**：`.greptile/` > `greptile.json`（仓库根）> dashboard。注意 `greptile.json` 是**从 PR 的 source branch 读**的（"Settings are read from the source branch of the PR and override dashboard settings"）——所以**它自己能改的部分，PR 就能放宽**；而 `autoApprove` 被特别拎出来放在 base 分支读，说明这是有意为之的例外。

**学习闭环：Memory and Learning**（三条输入）

1. **读团队在 PR 上的评论**——反复出现的意见被提取成偏好（"Team consistently comments: 'Add error handling' → Greptile learns: Error handling is important to this team"）
2. **从对 Greptile 的回复学**——三类：正面回复（"Good catch! Will refactor this."）、**补充上下文的回复**（"In our domain layer, we prefer detailed functions for clarity" → 学「长度规则不适用于 domain 逻辑」）、**否定性回复**（"We don't document internal utilities" → 学「文档规则随代码类型而变」）
3. **从 reaction 学**——👍/👎

**「nitpickiness」的学习机制（很具体）**：

- **比较首末 commit 判断评论是否被采纳**：一致没被采纳 → 减少该类评论；被采纳 → 继续提
- **抑制规则**：连续 3 次被忽略就抑制该类评论（文档例：`❌ Missing semicolons (suppressed after 3 ignores)`）
- **但有不抑制的白名单**：**security issues 和 logic errors「always flagged / never suppressed」**
- 记录形态是计数对象：`{ made: 10, addressed: 0, reactions: -3 }`
- 还有「自动推断自定义规则」（从团队反复提的意见生成规则文本）

**声称的效果**：被忽略的评论减少 80%、建议采纳率 3 倍、审查周期更快。

（来源：<https://www.greptile.com/docs/how-greptile-works/memory-and-learning>）

#### 2.9.3 Qodo（原 Codium / Qodo Merge）

- `review` 工具扫 PR 变更生成反馈；手动 `/review`，或用配置 `pr_commands = ["/review", ...]` 在 PR 打开时自动跑
- **输出是评论 + 标签**（不是 check）：`possible security issue` 标签、`Review effort [1-5]: x` 标签
- 可配置的分节：`require_score_review` / `require_tests_review`（默认 true）/ `require_estimate_effort_to_review`（默认 true）/ `require_can_be_split_review` / `require_security_review`（默认 true）/ `require_ticket_analysis_review`（默认 true，**会检查 PR 是否满足了关联 ticket 的需求**）
- `persistent_comment`（默认 true）：**每次新 review 编辑上一条评论**而不是新发
- `extra_instructions`：自然语言引导
- **注意：Qodo v1 正在 sunset**，文档页顶部有明确警告并指向 sunset 计划
- **未找到**：Qodo 的自动合并 / 阻塞合并能力，也没有找到覆盖机制

（来源：<https://docs.qodo.ai/v1/tools/tools-list/review.md>）

#### 2.9.4 Cursor Bugbot（**「check 的状态语义」在这里讲得最清楚**）

**判断依据**：模型分析 PR diff。自动跑，或 `cursor review` / `bugbot run` 手动触发。
**用已有评论做上下文**：「reads connected PR comments (top-level and inline) to avoid duplicate suggestions and build on prior feedback」。

**CI check 的三态（必读）**：

| 结论 | 触发条件 |
|---|---|
| `success` | 没发现问题，**且没有早先残留的未解决 Bugbot 评论** |
| **`neutral`** | **发现了问题**、被更新的 commit 取消、或内部错误——**「This is the default conclusion when Bugbot reports findings」** |
| `failure` | 发现了问题**且该 check 配置为对未解决问题失败** |

文档原话（**这是「拦住」这件事上最关键的一句**）：

> If you use branch protection, require the Bugbot check or build status to make sure Bugbot runs before merge. **Requiring the status alone does not block merges on findings because findings default to `neutral`.** If fail-on-unresolved-issues behavior is available for your organization, enable it to make unresolved findings produce a failing status.

**结合 GitHub 的 required check 定义（`successful` / `skipped` / `neutral` 都算通过），这段话的完整含义是：Bugbot 的「发现问题」在平台层面是一个「通过」状态。** 把它设成 required check 只能保证「它跑过」，不能保证「它没意见」。

**配置与「不能自我放宽」**：

`.cursor/config/bugbot.yaml`（`triggers.drafts` / `triggers.frequency` / `review.effort` / `review.smartPrompt` / `review.incremental` / `prSummary.riskScore` / `autofix.mode`），全部字段可选，>64KB 忽略。

> Bugbot reads `.cursor/config/bugbot.yaml` at the repo root **from the PR's base branch**, the branch the PR merges into. ... **Bugbot does not read the PR head version, so a PR cannot change how Bugbot reviews itself. Use code review and `CODEOWNERS` to control who can change this file.**

**优先级**：PR 作者的个人覆盖 > 仓库配置文件 > dashboard 团队/组织设置。**`autofix.mode` 只能降不能升**——「it can change Commit to Existing Branch to `newBranch` or `disabled`, but it can't turn Autofix on when the dashboard has it off」。
（来源：<https://cursor.com/docs/bugbot>）

## 三、对本项目的启示

按「值得直接借鉴 / 值得借鉴但要改 / 明确不要学」三类给。每条附理由与来源。

### 3.1 值得直接借鉴的机制

#### ① 覆盖动作要分「破窗」与「豁免」两类（**最高优先级**）

- **做法**：标准 bypass = 显式、必须留痕、产生醒目的审计信号；`exempt` = 静默、只发给可信高频自动化。
- **理由**：GitHub 官方对两者的区分正是 GM 需要的——「a 'break glass' action that requires an explicit actor bypass and generates prominent audit signals」vs「silently skips enforcement」。**GM 声称「被推翻的记录是最有价值的改进输入」，那么这条输入的信噪比就是生死线**：一个常驻的可信 bot 每次都在「推翻」GM，会把统计彻底污染。
- **落地**：`overridden` 只由「人在体系内推翻本次判断」产生；「某主体本来就不受这条策略约束」走 `exempt`，不进推翻率。
- 来源：<https://github.blog/changelog/2025-09-10-github-ruleset-exemptions-and-repository-insights-updates/>

#### ② 四态之外补两态：`not_applicable` 与 `forced`

- **做法**：
  - `not_applicable`——**策略不适用于这个变更**，与「适用但没通过」分开
  - `forced`——**绕过整个 GM** 的动作（人在 GM 之外直接干了），与「在 GM 体系内被推翻」分开
- **理由**：Gerrit 的六态状态机里，`NOT_APPLICABLE` 与 `UNSATISFIED` 是分开的，`FORCED`（"The change was merged directly bypassing code review by supplying the submit option while doing a git push"）也与 `OVERRIDDEN` 分开。GM 若把「人绕过 GM 直接合并」记成「GM 被推翻」，会得出「GM 判断力差」的错误结论——实际是「GM 根本没机会判断」。
- 来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>

#### ③ 覆盖的判据用表达式，且**独立于「是否该拦」**

- **做法**：`overrideIf` 是一个独立表达式；**它为真就是覆盖，不管拦不拦得对**。
- **理由**：Gerrit 文档明说：「the submit requirement is overridden **regardless of whether the `submittableIf` expression evaluates to true or not**」。这一条让覆盖语义变得干净：不需要先证明「GM 拦对了」才能记录「人被推翻了」。
- **副产品**：`overrideIf` 天然支持精细的人员/场景限定（「if the uploader is a trusted bot user or to allow change submission in case of emergencies」）——GM 的「三级待人确认」可以复用同一个表达式求值器。
- 来源：同上

#### ④ 「依据」的粒度目标设为 `passingAtoms`

- **做法**：拦下时不是给一句理由，而是给出**哪几条原子条件成立了、哪条没成立**。
- **理由**：Gerrit 的 `check.submit_requirement` 响应里直接返回 `"passingAtoms": ["label:Code-Review=+2"]`——这是把「依据」做成机器可读结构的最细形态。GM 的判据是自然语言（LLM），无法逐条原子化，但**可以在触发段的规则上做到**：触发是结构化规则，所以「因为哪条触发规则命中」完全可以原子化。
- 来源：同上

#### ⑤ 策略定义要能**在生效前试跑**

- **做法**：新增/修改一条判据后，能对着一批历史事件或真实 PR 跑一遍，看它会拦谁。
- **理由**：Gerrit 有 `check.submit_requirement` 端点（在改动前测试），Mergify 有 `mergify config validate` + `mergify config simulate <PR URL>`（文档：规则改动可以在生效前对着一批真实 PR 试跑）。GM 的判据是 LLM 生成的判断，**误拦成本更高**（人会烦），试跑能力比这一族里任何系统都更需要。
- 来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>、<https://docs.mergify.com/workflow/rule-syntax/>

#### ⑥ 「不适用」的策略不该出现在报告里

- **做法**：策略未命中触发条件时，输出应该是「隐藏」，而不是「未通过」。
- **理由**：Mergify 明确写「Inactive rules are ignored (not shown as failing)」；Gerrit 的 `applicableIf` 为假时该要求在 UI 里隐藏。**依据列表一旦把「不适用的规则」也算成失败，人就再也不看它了。**
- 来源：<https://docs.mergify.com/merge-protections/custom-rules.md>

#### ⑦ 判据与阻塞强度**解耦**：判据产出「发现 + 严重度」，分级映射到「动作」

- **做法**：同一套判据，可以输出 `info`/`warning`/`error`，而「是否阻塞」由另一层配置决定。
- **理由**：reviewdog 是这个设计的教科书——`-level` 决定 check 结论（info/warning → neutral，error → failure），`-fail-level` 决定退出码，**默认 `-fail-level=none` 即使发现错误也返回 0**。GM 的「三级动作 + 判据」正好是这个形状；解耦之后，一条判据可以从「观察期只发消息」平滑升级到「留痕」再到「待人确认」，**不必改判据本身**。
- 来源：<https://github.com/reviewdog/reviewdog>

#### ⑧ 审查者自己的配置**从 base 分支读**，PR 改不到自己头上的规则

- **做法**：定义「GM 如何审查」的配置，从被合并的目标分支（而非待合并分支）读取。
- **理由**：两个独立实现给了同一个答案——
  - Bugbot：「Bugbot **does not read the PR head version**, so a PR cannot change how Bugbot reviews itself. Use code review and `CODEOWNERS` to control who can change this file.」
  - Greptile：`autoApprove`「**Unlike other settings**, Greptile reads this from the PR's base branch, so a PR cannot loosen it for itself.」
- **对 GM 的直接含义**：GM 管辖的策略文件，必须满足「被管辖的变更不能修改管辖它的策略」；且这条约束要**在读取路径上实现**，而不是靠约定。
- 来源：<https://cursor.com/docs/bugbot>、<https://www.greptile.com/docs/code-review/greptile-json-reference.md>

#### ⑨ 学习记录要绑定「来源，且要有作用域与审批门」

- **做法（CodeRabbit 的完整方案，几乎可以直接照搬）**：
  - learning = **自然语言陈述** + 元数据（来源 PR、文件、**是谁说的**）
  - **在开着的 PR 上产生的 learning 先只作用于该 PR，PR 合并后才升级为仓库级；PR 关而未合并则保持 PR 作用域**
  - `approval_delay`（0–30 天，默认 0）；启用后进 pending approvals，**超期自动批准**
  - scope：仓库级 / 组织级 / auto
  - 记录 **Usage / Last Used / Created by / Created At**，Dashboard 有 **Never Used** 和 **Created This Week** 两张卡
  - 写入时凭据脱敏
- **理由（这几条为什么重要）**：GM 把「被推翻的记录」当唯一改进输入，那么**误改进的代价和漏改进一样大**。
  - 「开着的 PR 上的 learning 先只作用于该 PR」= **未经合并验证的经验不扩散**，这是最聪明的一条
  - `Created by` + `Usage` + `Last Used` = **可以判断哪条经验在起作用、哪条是死记录**
  - 官方的维护建议明确了它会腐坏：「Delete contradictory learnings」「Update rather than accumulate」
- 来源：<https://docs.coderabbit.ai/knowledge-base/learnings>

#### ⑩ 记「为什么」而不只记「是什么」

- **做法**：被推翻时，人给的理由要进记录，且要**引导人给 why**。
- **理由**：三处独立佐证——
  - CodeRabbit 最佳实践：「**Explain the why, not just the what**」——「The 'why' helps CodeRabbit apply the learning correctly in **similar-but-not-identical** situations」
  - CodeRabbit：「**回复到具体代码行的评论**比 PR 上的泛泛评论能产生更精确的 learning」
  - Dependabot 官方：「better to explicitly define the dependencies and versions to ignore in the configuration file. **This makes it easy for all contributors to see why a particular dependency isn't being updated automatically.**」
- **对 GM**：「人能带理由强行通过」这个设计里，**理由的采集方式**比强制必填更重要——GM 应该像 CodeRabbit 引导 @回复那样，**把「为什么」的提问嵌在推翻动作发生的那个位置**（具体的评论行、具体的判断项），而不是让人填一个独立的表单。
- 来源：<https://docs.coderabbit.ai/knowledge-base/learnings>、<https://raw.githubusercontent.com/github/docs/main/content/code-security/how-tos/secure-your-supply-chain/manage-your-dependency-security/manage-dependabot-prs.md>

#### ⑪ 审批权归属必须落在**有审计日志**的载体上

- **做法**：GM 的「谁有权推翻」这份名单，必须有变更审计日志。
- **理由**：Prow 宁愿自己维护 `OWNERS_ALIASES` 文件也不用 GitHub Teams，官方理由写得很直白：「**We do not use them because there is no audit log for changes to the GitHub Teams. This way we have an audit log.**」
- 来源：<https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/>

#### ⑫ 「依据」的呈现要向「差哪一项、谁补、补了谁批的」这个粒度看齐

- **做法**：拦截消息里逐条列出**尚未满足的条件**，已满足的划掉并标注**由谁满足的**。
- **理由**：Prow 的 `[APPROVALNOTIFIER]` 评论就是长这样：

  ```
  Needs approval from an approver in each of these OWNERS Files:
  * ~/A/B/E/OWNERS~ [approver1]     ← 划线 + 谁批的
  * /A/C/G/OWNERS                    ← 差这一项
  ```
  且 K8s 另有 PR dashboard「shows the difference between your PR's state and the merge criteria so that you can easily see **all criteria that are not being met** and address them」。
- 来源：<https://docs.prow.k8s.io/docs/components/plugins/approve/approvers/>、<https://raw.githubusercontent.com/kubernetes/community/master/contributors/guide/pull-requests.md>

#### ⑬ 留一条**不经过规则**的规则管理通道

- **做法**：GM 的策略文件被 GM 自己管辖时，必须显式留一条逃生通道。
- **理由**：Gerrit 用血写下的警告——submit requirements 存在 `refs/meta/config` 分支，改它要走 code review，而走 code review 要通过 `refs/meta/config` 的 submit requirements；**配错了就再也改不回来了**。恢复路径是「直接 push 该分支」或走 REST 管理端点。
- **对 GM**：策略三段（触发/判据/处置）如果也受 GM 门禁，需要一条**旁路的管理通道**（且这条通道的使用必须留痕——否则它成了新的静默豁免）。
- 来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>

#### ⑭ 动作历史可以先轻量，但**要留持久化接口**

- **做法**：GM 的动作日志先写内存/本地，但设计上留一条「周期 flush 到外部存储」的路径。
- **理由**：Prow Tide 就是这么做的——动作历史（触发测试、合并）存内存，**可选**用 `--history-uri` + `--gcs-credentials-file` flush 到 GCS；文档说这是严格可选的，但实例频繁重启、或想查更久历史时「nice to have」。
- 来源：<https://docs.prow.k8s.io/docs/components/core/tide/config/>

#### ⑮ 停用一条规则时，**必须写原因，且原因要出现在人看得到的地方**

- **做法**：规则不删、标记 disabled，附 `reason`，并把它打印在状态输出里。
- **理由**：Mergify 的 `disabled: {reason: "paused during the release freeze"}` ——「Mergify strikes the rule through in the **Summary check run** and prints the reason under it, **so others know why**」。
- 来源：<https://docs.mergify.com/workflow/rule-syntax/>

### 3.2 值得借鉴但要改的

#### ① 「判据用自然语言交给 LLM」——借鉴三态输出与反模式表，但**要加确定性兜底**

- **借鉴**：CodeRabbit 的 Pre-Merge Checks 输出 `Passed` / `Failed` / **`Inconclusive`** 三态 + reasoning，是全行业对「LLM 判据」最务实的形态。**`Inconclusive` 是精髓**：模型证据不足时应当承认，而不是猜一个结论。
- **要改**：
  - CodeRabbit 的 checks **不能发 inline comment**（结果只在摘要表里）、**不能查 PR 审批状态**——这些限制来自它的沙箱设计。GM 的判据要判断「这里有问题」，很可能需要读协作事件流之外的上下文，**边界要自己划并写进文档**。
  - 官方列的四条反模式里，**「要求推测」和「信息不可得」是 LLM 判据的两大失效模式**，GM 的判据评审清单应当直接收编这两条。
  - 更重要的一层：**LLM 判据的失败不是「判错」而是「不可复现」**。Gerrit 的表达式可测试、可模拟，LLM 判据不行。所以 GM 需要一条互补路径：**能用结构化规则表达的触发条件，不要写进自然语言判据**——这恰好就是 GM 已经设计的三段式的价值所在。
- 来源：<https://docs.coderabbit.ai/pr-reviews/custom-checks>、<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>

#### ② 「模型判断 + 默认不阻塞」——借鉴默认值，但要改掉「发现即 neutral」

- **借鉴**：AI 审查默认不阻塞是对的。这一族的默认值都指向「先观察」：Bugbot 发现问题的默认结论是 `neutral`；reviewdog 默认 `-fail-level=none`；CodeRabbit 的 `request_changes_workflow` **默认关闭**。
- **要改**：GM 的定位是「主动判断这里有问题」，**不能默认停在「只发消息」**——否则与一个聊天机器人无异。合理的改法是**按判据成熟度分级**（新增判据先只发消息，跑够样本、误报率可接受后再升到留痕/待人确认），而不是全局默认弱化。这个「按判据逐个升级」的机制，这一族里**没有现成实现**——是 GM 需要自己造的。
- 来源：<https://cursor.com/docs/bugbot>、<https://github.com/reviewdog/reviewdog>、<https://docs.coderabbit.ai/pr-reviews/request-changes-workflow>

#### ③ 学习闭环——借鉴 Greptile 的**信号来源**，但要改掉它的**透明度**

- **借鉴**（Greptile 的三条输入信号很全，且第三条 GM 目前没有）：
  1. 读团队在 PR 上的评论（**团队自己之间的讨论**也是信号）
  2. 从对 Greptile 的回复学——特别区分「正面 / 补充上下文 / 否定」三类
  3. **从 reaction 学**（👍👎 是最低成本反馈）
  - **定量抑制规则**：「连续 3 次被忽略就抑制该类评论」；**security / logic 类从不抑制**——这条「有白名单的降噪」比一刀切合理。
- **要改**：Greptile 的机制在文档里**没有说人能否查看、编辑、删除学到的东西**（对比 CodeRabbit 有完整的 Learnings dashboard + Created by + 审批门 + API）。GM 声称「被推翻的记录是最有价值的改进输入」，那么**学到的东西必须可见、可审、可删**。否则 GM 会慢慢长出一个没人能审计的判断偏好，而它还在拦事。
  - 补充一条从 CodeRabbit 学来的、Greptile 没有的：**「未经合并验证的经验不扩散」**（learning 在 PR 合并前只作用于该 PR）。
- 来源：<https://www.greptile.com/docs/how-greptile-works/memory-and-learning>、<https://docs.coderabbit.ai/knowledge-base/learnings>

#### ④ 跨仓库协调——**先不要做**，但要把接口留出来

- **借鉴**：Zuul 的 `Depends-On:` footer 是这一族里成本最低、效果最直接的跨仓库协调机制——**在 PR 描述/commit message 里写一行，就形成一个 DAG 依赖**，被依赖项失败则依赖者一起被移出。GM 完全可以支持类似的原语（在协作事件流里声明「这件事依赖那件事」）。
- **要改 / 暂缓**：
  - Zuul 的完整形态（共享 change queue、speculative execution、pipeline window 流控）是**为「一次跑几小时的大规模 CI」设计的**，投入极大。GM 现在的场景不需要。
  - **但有一处必须现在就抄**：Zuul 文档明确写出不共享队列时的降级行为——「Zuul is unable to enqueue them together, and the first will be required to merge before the second can be enqueued. **If the second change is approved before the first is merged, Zuul can't act on the approval and won't automatically enqueue the second change, requiring a new approval event**」。**这是一处经典的「事件丢失」缺陷，GM 如果有依赖概念，第一版就要想清楚「被依赖项后完成时，依赖者怎么办」。**
- 来源：<https://opendev.org/zuul/zuul/raw/branch/master/doc/source/gating.rst>

#### ⑤ 「测合并结果而非各自 head」——思想照搬，机制按 GM 的粒度重写

- **借鉴**：Bors 的论证是这一族里最经得起时间考验的——**两个各自通过测试的变更，合并后可能一起坏**；解法是**测合并结果**（staging 分支，merge 后 base 精确等于刚测过的内容，"bit-for-bit"）。batched + bisect 是配套的高效定位手段。
- **要改**：GM 管的是协作事件（提交、构建、任务、对话），不是代码树合并。**「组合效应」在 GM 的场景里同样存在**（单独看都合理的变更，组合起来有问题——比如两个任务同时改同一个模块、两次构建同时占用同一资源）。但 GM 不能「测合并结果」（没有可执行的验证环境），**能做的是「判断组合」**：把「同时/相邻发生的多个变更」作为判据的输入之一。
- 来源：<https://raw.githubusercontent.com/bors-ng/bors-ng/master/README.md>

### 3.3 明确不要学的

#### ① 不要把「拦截」做成「必须靠另一个人批准才生效」才有意义的机制

- **现象**：CodeRabbit 的 `request_changes_workflow` 确实能阻塞，但**默认允许 PR 作者自己用 `@coderabbitai approve` 覆盖**（`reviews.allow_author_approval` 默认 `true`）。**默认配置下，被审的人可以自己解除审查者施加的阻塞。**
- **为什么不能学**：GM 的覆盖语义是「**人**能带理由强行通过」——这里的人在 GM 的语境里是**责任主体**，不是**作者**。默认允许作者自我解除，会让「被推翻的记录」退化成「作者不想改代码」的噪声，而不是真实的分歧。
- **替代**：三态里 GM 的 overridden 应当要求**主体对得上**（推翻者 ≠ 被判定的变更的作者），这一点可以直接借 GitHub 的 `user=non_uploader` 系列算子、以及「要求最近一次 push 由 push 者之外的人批准」的思路。
- 来源：<https://docs.coderabbit.ai/pr-reviews/request-changes-workflow>、<https://gerrit.nordix.org/Documentation/config-labels.html>、<https://raw.githubusercontent.com/github/docs/main/content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md>

#### ② 不要用命令式脚本承载判据

- **现象**：Danger 的 Dangerfile 表达力最强，但**没有策略分层、没有结构化依据、没有覆盖语义、没有规则校验/模拟、跨仓库复用「currently quite complex」**（官方 FAQ 原话）。Gerrit 明确弃用了 Prolog submit rules、Mergify 明确弃用了 `autoqueue`、Bors-NG 整个项目停更。
- **为什么不能学**：GM 的核心主张是「**判据、处置、留痕是三个可以分别演进的东西**」。命令式脚本把它们焊死在一个文件里——**这正是 Gerrit 用两代弃用换来的教训**。
- 来源：<https://danger.systems/js/guides/faq.html>、<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>、<https://raw.githubusercontent.com/bors-ng/bors-ng/master/README.md>

#### ③ 不要用「静默豁免」解决「误拦太烦」

- **现象**：面对误报，最省事的做法是（a）把整条规则关掉（b）给某个主体开静默豁免（c）把阈值调松到不报。
- **为什么不能学**：
  - GitHub 官方对 `exempt` 的定位很明确：给**可信高频自动化与迁移场景**用，不是给「这条规则太烦」用。
  - Mergify 提供了正确的替代——《stop the rule, but write the reason, and print it where people see it》。
  - CodeRabbit 还提供了第三种更精细的替代：**`approval_delay` 把新经验先放进待审队列**，而不是直接生效或直接丢弃。
- **替代**：误拦应当**回流成判据的修订**（这是 GM 的设计初衷），而不是把闸门拆掉。
- 来源：<https://github.blog/changelog/2025-09-10-github-ruleset-exemptions-and-repository-insights-updates/>、<https://docs.mergify.com/workflow/rule-syntax/>、<https://docs.coderabbit.ai/knowledge-base/learnings>

#### ④ 不要做「发现即 neutral」式的假拦截

- **现象**：Bugbot 发现问题时 check 结论是 `neutral`，而 GitHub 的 required check 定义里 **`neutral` 算通过**。所以「把它设成 required check」只保证它跑过，**不保证它没意见**。
- **为什么不能学**：GM 的二级动作（建任务/改状态）如果做成「记录了一个 neutral 的结论」，那就是**看起来留了痕、实际没有任何阻力**——比不拦更糟，因为它制造了「已经有人管了」的错觉。
  > ⚠️ **上述比喻不严谨（2026-10-13 复核指出）**：二级动作（建任务 / 改状态 / 指派 / 打标签）**本身就是「生效了」的**，在这个动作模型里没有 `neutral` 这个取值——「记了个 neutral 的结论」**不成立**。这条约束的**实质仍然成立**（别把"留痕"做成"没有任何阻力"的样子），但表达落点应是「**中间态要显式命名**」（见下一条），而不是借 `neutral` 打比方。
- **替代**：要拦就发一个**语义明确的阻塞信号**（可失败的 check / 明确的 status），否则就诚实地归到一级（只发消息）。**中间态要显式命名**（如「已记录异议但未阻塞」），而不是用平台语义上等于「通过」的状态来表示。
- 来源：<https://cursor.com/docs/bugbot>、<https://raw.githubusercontent.com/github/docs/main/content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md>

#### ⑤ 不要把「dashboard 全量展示」当留痕

- **现象**：依据多了以后，全展示等于没展示。
- **为什么不能学**：Gerrit 专门为此做了取舍——管理员要用 `dashboard.submitRequirementColumns` **挑选哪些 submit requirement 显示在 dashboard 上**，且名字会缩写（`Foo-Bar` → `FB`）。Mergify 也给了三档 `status_comments`（`all` / `outcomes` / `none`）。
  > ⚠️ **本文档内部矛盾（2026-10-13 复核指出，待核实）**：此处原有的「默认 `outcomes`」与上文 Mergify 一节记载的「`all`（默认）」**互相冲突**。**三档可配是确定的，默认值未核实**——引用时只写「三档可配」，不要写默认值。
- **对 GM**：留痕要**存全**（Gerrit 的 `passingAtoms`、CodeRabbit 的 reasoning 都存全），但**展示要分层**——默认只显示「差哪一项」，展开才给完整依据链。
- 来源：<https://gerrit-documentation.storage.googleapis.com/Documentation/3.14.3/config-submit-requirements.html>、<https://docs.mergify.com/merge-queue/lifecycle.md>

#### ⑥ 不要忽视「依据的可信来源」

- **现象**：GitHub 的 required status check 可以指定**由哪个 GitHub App 设置**才算数——「If the status is set by any other person or integration, merging won't be allowed」。选 "any source" 的话，「you can still manually verify the author of each status, listed in the merge box」。
- **为什么不能学（反面）**：任何**有 write 权限的人或集成都能设置任意 status**（官方原话：「Any person or integration with write permissions to a repository can set the state of any status check」）。也就是说，**如果 GM 的阻塞信号是一个「谁都能写的共享状态」，它就可以被绕过或伪造，而且这种绕过不留痕**。
- **对 GM**：若 GM 的 blocked/allowed 状态要与外部系统（CI、任务系统）互通，**必须能验证信号来源**，而不只是读一个布尔值。
- 来源：<https://raw.githubusercontent.com/github/docs/main/content/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches.md>

# GM 动作审计 · 人在回路 · Agent 身份 · 合规留痕 —— 业界做法调研

> 调研日期：2026-10-13 ｜ 方法：web_search + web_fetch 官方文档/规范原文（禁用二手摘要下结论）
> 服务对象：团队协作平台中 LLM 驱动的角色 **GM**（订阅协作事件流 → 判断问题 → 在授权范围内行动）
> 约束：动作三级（自主/留痕/待确认）· 四态（pending/blocked/allowed/overridden）· 全程可审计 · GM 本身是可撤权的成员而非特权进程

## 结论速览（先看这五条）

| # | 结论 | 直接影响 |
|---|---|---|
| 1 | **「为什么做这个决定」在主流可观测性标准里没有结构化字段**。OTel GenAI semconv 有 82 个 `gen_ai.*` 属性，无任何 rationale/decision 类字段 | 「依据什么」要自建，别指望现成 schema |
| 2 | 行业标准**明确反对**把模型推理链（CoT）当作可问责的必要条件（IETF `REQ-AUD-3`） | 审计留痕 ≠ 存思维链；理由字段应是辅助而非主体 |
| 3 | 「三级动作」有现成的命名可借：OMP 草案的 `AUTONOMOUS / ASSISTED / ESCALATED`，且它同时给出 `routing rationale` + `explicit rule reference` | 三级 + 理由 + 规则引用可以照抄结构 |
| 4 | 「Agent 是不是一等身份」已有明确答案与实现：AWS AgentCore 的 **workload identity** 是独立身份原语，IETF 更把它写成 MUST 级要求（`REQ-AUTH-1`） | GM 应当有自己的身份，不是模拟人类账号 |
| 5 | OAuth 体系存在公认缺口：**只有授权层证据（grant-layer），没有执行层证据（execution-layer）** | 我们的「每个动作一条执行证据」是业界公认空白 |

# 第一块 · Agent 可观测与追踪

## 总览

这一块的产品分两个阵营：

- **标准派**（OpenTelemetry GenAI semconv、Langfuse、Weave、Phoenix/OpenInference）：数据模型基于 OTel 的 trace/span，追求跨厂商可移植。
- **平台派**（LangSmith、AgentOps）：自建数据模型，字段更贴合自己的 UI 与评估流程。

**共同点**：都记录「做了什么」——输入、输出、工具调用、参数、结果、token、耗时、错误、状态。层级都是 trace（一次运行/一轮交互）→ span（每个步骤）→ 更细的子 span。
**共同缺口**：**没有一家把「为什么做这个决定」做成结构化字段**。最接近的三处，都不是我们要的东西（详见各节末尾的「看似相关但不是」）。

## 1.1 OpenTelemetry GenAI 语义约定

- **解决什么问题**：给「LLM/Agent 的遥测数据」定一套跨厂商字段名，使 trace 可以脱离具体 SDK 迁移与比对。
- **核心机制**：把 agent 运行拆成若干固定命名的 span，用属性（attribute）承载细节。
- **关键字段/接口**（来源：<https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-agent-spans.md>）：
  - **span 名**：`invoke_agent {gen_ai.agent.name}` · `create_agent {gen_ai.agent.name}` · `invoke_workflow {gen_ai.workflow.name}` · `plan {gen_ai.agent.name}` · `execute_tool {gen_ai.tool.name} {gen_ai.skill.name}`
  - **span kind**：`invoke_agent`/`create_agent` 为 `CLIENT`，`invoke_workflow`/`plan` 为 `INTERNAL`
  - **共 82 个 `gen_ai.*` 属性**（实测 grep 去重）。分组示例：
    - 身份：`gen_ai.agent.id` / `.name` / `.description` / `.version`、`gen_ai.provider.name`
    - 内容：`gen_ai.input.messages`、`gen_ai.output.messages`、`gen_ai.system_instructions`、`gen_ai.tool.definitions`
    - 工具：`gen_ai.tool.name`、`gen_ai.tool.call.id`、`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`、`gen_ai.tool.description`、`gen_ai.tool.type`
    - 会话：`gen_ai.conversation.id`、`gen_ai.workflow.name`
    - 技能（新增）：`gen_ai.skill.name`、`gen_ai.skill.description`、`gen_ai.skill.source.uri`、`gen_ai.skill.resource.name`
    - 记忆/检索：`gen_ai.memory.*`、`gen_ai.retrieval.*`
    - 评估：`gen_ai.evaluation.name` / `.result` / `.score.value` / `.score.label` / `.explanation`
  - **事件**：规范里**只有一个事件** `gen_ai.evaluation.result`（来源：<https://raw.githubusercontent.com/open-telemetry/semantic-conventions-genai/main/docs/gen-ai/gen-ai-events.md>）
- **成熟度**：**实验性偏成熟**。仓库已从主 `semantic-conventions` 迁到独立仓库 <https://github.com/open-telemetry/semantic-conventions-genai>；官网语义约定版本 1.44.0 中，GenAI 属性多标 `Development`，其中 `gen_ai.input.messages` / `output.messages` / `system_instructions` / `tool.definitions` 标为 **`Opt-In`**。**不适合当作长期稳定契约直接冻结**。
- **「为什么」**：**无**。整套属性里没有任何 rationale / decision / justification 字段。想还原动机，只能从未经裁剪的 `gen_ai.output.messages` + `gen_ai.system_instructions` + `gen_ai.tool.definitions` 里间接推断。

## 1.2 LangSmith

- **解决什么问题**：LangChain 生态的 trace 存储、调试、评估与数据集管理。
- **核心机制**：每个执行单元是一条 **Run**（即 span），用 `dotted_order` 表达层级与顺序。
- **关键字段**（来源：<https://docs.langchain.com/langsmith/run-data-format>）：`id`、`name`、`run_type`、`inputs`、`outputs`、`error`、`status`、`start_time`/`end_time`、`events`、`tags`、`extra`、`trace_id`、`dotted_order`、`parent_run_id`、`child_run_ids`、`direct_child_run_ids`、`parent_run_ids`、`feedback_stats`、`total_tokens`/`prompt_tokens`/`completion_tokens`、`total_cost`、`session_id`、`reference_example_id`、`serialized`、`first_token_time`
  - `run_type` 取值：`chain` / `llm` / `embedding` / `prompt` / `tool` / `retriever` / `parser`
  - `dotted_order` 格式：`<run_start_time>Z<run_uuid>.<child_start_time>Z<child_uuid>...`，不变式：`id` = 最后 36 字符、`trace_id` = 第一段
- **成熟度**：**生产可用**（商业 SaaS，有 bulk export / BigQuery 等落地通道）。
- **「为什么」**：**无专门字段**。`extra` 是任意 JSON 对象，可自行塞入理由，但那是约定而非契约。

## 1.3 Langfuse

- **解决什么问题**：开源自托管的 LLM 可观测平台，trace + 评估 + Prompt 管理。
- **核心机制**：三层 —— **Session**（可选，跨 trace 分组，如一轮对话）→ **Trace**（一次请求/操作）→ **Observation**（每个步骤）。存储上把 trace 级属性**冗余到每一行 observation** 以加速查询。
- **关键字段**（来源：<https://langfuse.com/docs/observability/data-model>）：
  - observation 级：`id`、`type`（`span` / `generation` / `event`）、`name`、`latency`
  - trace 级（每行复制）：`trace_id`、`trace_name`、`user_id`、`session_id`
  - 可附加：environments、tags、metadata（任意 KV）、releases & versions
- **成熟度**：**生产可用**，明确「built on OpenTelemetry」，可同时投递到 Langfuse + Datadog 等多个后端。**注意坑**：短生命周期应用**必须显式调用 `flush()`**，否则退出时丢数据。
- **「为什么」**：**无专门字段**（`metadata` 可自由承载）。

## 1.4 AgentOps

- **解决什么问题**：Agent 运行的健康度、成本、错误追踪，强调**零侵入**。
- **核心机制**：`agentops.init()` 后自动探测已安装的 LLM provider 并自动埋点；另有 Decorators 手工加 span；再加进程级监控。
- **关键字段**（来源：<https://docs.agentops.ai/v1/concepts/core-concepts>）：
  - **Session**（一次工作流执行实例）：`ID`、`Project ID`、`Starting Timestamp`、`Ending Timestamp`、`End State`（成功/失败）、可选 `End State Reason`（含"用户触发中断 SIGINT"）、`Tags`、`Host Environment`、`Video`
  - 会话内：LLMs / Tools / Operations（统称 Spans）、Errors、Agents、Threads
  - 支持单会话与并发 trace 两种模型（`start_trace()` / `end_trace()`）
- **成熟度**：**生产可用**（商业 SaaS + 开源 SDK）。
- **「为什么」**：**无**。有 `End State Reason`（为什么结束），但那是终止原因，不是决策依据。

## 1.5 Arize Phoenix + OpenInference

- **解决什么问题**：开源（可自托管）的 LLM trace 与评估平台；OpenInference 是 Arize 自己的一套语义约定，**不依赖 OTel GenAI 约定**。
- **核心机制**：以 `openinference.span.kind` 标注每个 span 的类型，后端据此重建 trace 结构。
- **关键字段/接口**（来源：<https://raw.githubusercontent.com/Arize-ai/openinference/main/spec/semantic_conventions.md>）：
  - `openinference.span.kind`（**所有 span 必填**）取值 11 种：`LLM` · `EMBEDDING` · `CHAIN` · `RETRIEVER` · `RERANKER` · `TOOL` · `AGENT` · `GUARDRAIL` · `EVALUATOR` · `PROMPT` · `DECISION`
  - 保留属性（节选）：`input.value`、`output.value`、`llm.model_name`、`llm.provider`、`document.*`、`embedding.*`、`tool.*`、`session.id`
  - 标注类：`annotation.annotator_kind`（`HUMAN`/`LLM`/`CODE`）、`annotation.explanation`（**"Reason or evidence for the result"**）、`annotation.label`、`annotation.identifier`
- **成熟度**：**生产可用**（Phoenix 开源可自托管；OpenInference 有多语言 SDK）。
- **「为什么」**：⚠️ **这里最容易踩坑，必须分清**：
  - `DECISION` span kind **不是**「Agent 的决策理由」。原文定义是 *"a call to a decision model, which scores or selects among candidate options provided in the request rather than generating free-form text"*，举例是 TypeSafe 的 Jev 模型，配套属性是 `decision.model_name` / `decision.provider` / `decision.system` / `decision.token_count.*`。**它描述的是一次"打分/选择"类型的模型调用，与"为什么这么做"无关。**
  - `annotation.explanation` 是**评审者事后给出的理由/证据**（annotator 是 HUMAN/LLM/CODE），属于评估标注，不是 Agent 在决策时刻的自述。

## 1.6 W&B Weave

- **解决什么问题**：W&B 生态的 LLM/Agent 追踪与评估。⚠️ **文档站已从 `docs.wandb.ai` 迁移到 `docs.coreweave.com/products/wandb/weave/...`**（W&B 已并入 CoreWeave）。
- **核心机制**：为多轮 agent 场景定义了一套**显式层级**，每一层对应一种 OTel span（来源：<https://docs.coreweave.com/products/wandb/weave/guides/tracking/trace-agents.md>）：

| 概念 | SDK 类 | OTel span | 说明 |
|---|---|---|---|
| Agent | （无类） | **无 span**，按 `agent_name` 分组 | 一个 agentic 应用 |
| Conversation | `Conversation` | **无 span**，按 `conversation_id` 分组 | 一次会话/运行 |
| Turn | `Turn` | `invoke_agent` | 一轮「用户消息 → agent 完整回复」 |
| LLM call | `LLM` | `chat` | 一次模型 API 调用 |
| Tool call | `Tool` | `execute_tool` | 一次工具调用 |
| Sub-agent | `SubAgent` | `invoke_agent` | 嵌套 agent 调用 |

  - **重要设计**：Conversation 不靠父 span 而靠 `conversation_id` 属性分组，**每个 Turn 自成一条 OTel trace** —— 为并行执行与分布式追踪让路。
  - 记录字段：`llm.input_messages` / `output_messages` / `usage`、`tool.name` / `arguments` / `tool_call_id` / `result`、`include_content`（可关闭正文采集）
- **成熟度**：**生产可用**；显式声明遵循 OTel GenAI 语义约定，接受任意 OTel span 且所有属性可查询。
- **「为什么」**：✅ **这是六个产品里唯一有明确 reasoning 字段的**。SDK 提供 `llm.think("User wants weather data, I should call get_weather.")`，以及 `llm.record({ ..., reasoning })` 一次性写入。**但它记录的是「模型自述的理由」，属于内容级字段，不是可校验的规则引用。**（来源同上）

## 第一块小结：能不能记录「为什么」？

| 产品/标准 | 决策理由字段 | 性质 |
|---|---|---|
| OTel GenAI semconv | ❌ 无 | — |
| LangSmith | ❌ 无（`extra` 可自塞） | 约定，非契约 |
| Langfuse | ❌ 无（`metadata` 可自塞） | 约定，非契约 |
| AgentOps | ❌ 无（有 `End State Reason`，指终止原因） | — |
| Phoenix/OpenInference | ⚠️ 有 `DECISION` kind 与 `annotation.explanation`，**都不是决策理由** | 分别是决策模型调用、事后评审 |
| Weave | ✅ 有 `reasoning` / `think()` | 模型自述文本 |

**结论**：如果把「依据什么」理解为**可校验的结构化引用（走了哪条规则、哪条策略、哪次授权）**，那么**这六个产品/标准全都没有**。它们最多提供「模型自述的理由文本」（Weave）或「任意 KV 容器」（LangSmith `extra` / Langfuse `metadata`）。

# 第二块 · 人在回路（HITL）的标准模式

## 总览

三个层次的做法，成熟度递减：

1. **有正式规范/文档的标准模式**：LangGraph（interrupt + time travel）、Temporal（Signal/Update + Approval Pattern）、AWS Step Functions（`.waitForTaskToken`）。
2. **产品级约定**：GitHub PR 的 required reviewers、Copilot coding agent 的 "Approve and run workflows"。
3. **交互式 Agent 产品的审批 UX**：Devin 的五档权限模式、Cursor 的三档执行模式。

**三个共性问题在本块末尾统一回答**：拦截发生在动作生效前还是后？中断后状态怎么保存与恢复？有没有「带理由批准/拒绝」的标准做法？

## 2.1 LangGraph：interrupt + HITL Middleware + 时间旅行

- **解决什么问题**：在 Agent 的图执行中，把「模型提议的动作」拦下来交给人决定。
- **核心机制**（来源：<https://docs.langchain.com/oss/python/langchain/human-in-the-loop.md>）：
  - 中间件挂在 **`after_model` hook** —— 即「模型已生成响应，但**任何工具调用尚未执行**」的时刻。→ **拦截发生在动作生效之前**。
  - 命中策略则发出 `interrupt`，图状态由 **checkpointer 持久化**，之后可恢复。
  - **策略配置** `interrupt_on`：`{工具名: True | False | InterruptOnConfig}`；`InterruptOnConfig` 含 `allowed_decisions`、`description`、`when`（谓词，接收 `ToolCallRequest`，返回 True 才中断 —— **支持按参数条件拦截**，如「只拦 workspace 之外的写入」「只拦非 SELECT 的 SQL」）
- **关键接口**：中断请求结构 = `action_requests[]`（`name`/`arguments`/`description`）+ `review_configs[]`（`action_name`/`allowed_decisions`）；恢复用 `Command(resume={"decisions":[...]})`，**多个动作时每条决定必须与动作顺序一一对应**。**必须配置 checkpointer**（生产用 `AsyncPostgresSaver` / `MongoDBSaver`）并传 `thread_id`。
- **四种决定**（这是本调研里最直接可用的一个设计）：

| 决定 | 语义 | 备注 |
|---|---|---|
| `approve` | 按原参数执行 | |
| `edit` | 改参数后执行 | 官方警告：大幅改动会让模型重估方案，可能重复执行 |
| `reject` | 跳过执行，并把反馈回传给 agent | 可带 `message` 说明理由；对副作用工具应明确"是放弃、还是问追问、还是换更安全的做法" |
| `respond` | 不执行工具，把人的回复直接当工具结果返回 | 仅用于 `ask_user` 类工具；**不能用来拒绝副作用工具**，否则模型以为执行成功了 |

- **时间旅行**（来源：<https://docs.langchain.com/oss/python/langgraph/use-time-travel.md>）：
  - **Replay**：用历史 checkpoint 的 config 重新 invoke，checkpoint 之前的节点不重跑，之后的**会重跑**（含 LLM 调用、API 请求、interrupt）。
  - **Fork**：`update_state(checkpoint_config, values)` 从过去某点**分叉**出新分支（**不**回滚原线程，原执行历史完好保留）。
  - ⚠️ **interrupt 在时间旅行中一定会被重新触发** —— 节点重跑，`interrupt()` 会再次暂停等新的 `Command(resume=...)`。这是「重放会重新要授权」的重要性质。
- **成熟度**：**生产可用**（LangGraph 主线能力，但 `when` 谓词需 `langchain>=1.3.3`）。

## 2.2 Temporal：Signal / Update + Approval Pattern

- **解决什么问题**：长事务/长流程里等待外部人工决定，且要保证状态可持久恢复、超时可处理、留痕完整。
- **核心机制**（来源：<https://docs.temporal.io/develop/python/workflows/message-passing> 与 <https://docs.temporal.io/design-patterns/approval>）：
  - 三种消息原语：

| 原语 | 方向 | 能否改状态 | 能否返回值 | 是否进 Event History |
|---|---|---|---|---|
| Query | 读 | ❌ 只读 | ✅ | ❌ 不进 |
| Signal | 写 | ✅ | ❌ | ✅ `WorkflowExecutionSignaled` |
| Update | 读写 | ✅ | ✅（调用方等待） | ✅（**校验失败时不写** `WorkflowExecutionUpdateAccepted`） |

  - **官方的 Approval Pattern**：工作流用 `workflow.wait_condition(lambda: ..., timeout=...)` **阻塞等待**，Signal 到达则处理决定，超时则走拒绝/升级路径。
  - **关键设计：决定不是一个布尔值，而是一个结构化对象**：
    ```python
    @dataclass
    class ApprovalData:
        approver: str
        decision: str      # "APPROVED" / "REJECTED" / "ESCALATED"
        comments: str      # ← 理由
        timestamp: int
    ```
    官方明确说明这么做的理由：*"gives you a structured way to pass rich context through the Signal rather than a plain boolean"*。
  - **Update validator** 可在决定**写入 History 之前**拒绝它（validator 抛异常 → Update 被拒、`WorkflowExecutionUpdateAccepted` 不写入、调用方收到 "Update failed"）。→ **拦截可以在生效之前，且拒绝本身不留"已接受"的痕**。
- **成熟度**：**生产可用**（Temporal 是成熟的持久化执行引擎，Approval 是其官方设计模式之一）。
- **「带理由批准/拒绝」**：✅ **有**，`ApprovalData.comments` 是官方示例里的标准字段。

## 2.3 AWS Step Functions：Wait for Task Token

- **解决什么问题**：让一个状态机停下来，等外部系统（含人）回调后再继续 —— 官方点名的场景就是 *"A task might need to wait for a human approval"*。
- **核心机制**（来源：<https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html>）：
  - 三种服务集成模式：**Request Response**（发完就走）· **Run a Job (`.sync`)**（等工作完成）· **Wait for a Callback (`.waitForTaskToken`)**（等令牌回来）。
  - 在 `Resource` 末尾加 `.waitForTaskToken`，并在 `Parameters` 里通过 `"TaskToken.$": "$$.Task.Token"` 把令牌传给下游（如塞进 SQS 消息）。
  - 外部完成时调用 **`SendTaskSuccess`** / **`SendTaskFailure`**（心跳用 `SendTaskHeartbeat`），工作流才继续。
- **关键字段/接口**：Context object 里的 `Task.Token`；`HeartbeatSeconds` 设超时（示例为 600 秒），超时任务以 `States.Timeout` 失败。可等待到**一年服务配额**。
- **两个硬限制**：① **令牌必须在同一 AWS 账号的主体间传递**，跨账号无效；② Express Workflows **不支持** `.waitForTaskToken`，只有 Standard 支持。
- **成熟度**：**生产可用**。
- **「带理由批准/拒绝」**：❌ **无标准字段**。回调只能带任意 payload，理由是自建约定。

## 2.4 审批队列模式

- **GitHub Actions 的 required reviewers / 环境审批**、以及 **Copilot coding agent 的 "Approve and run workflows"** 是这一类最典型的落地。
- **核心机制**（来源：<https://github.blog/changelog/2026-03-13-optionally-skip-approval-for-copilot-coding-agent-actions-workflows/>）：Copilot 开 PR 或推代码后，被**当作开源项目里的外部贡献者**对待 —— **GitHub Actions 工作流不会运行，直到有权限的人点击 "Approve and run workflows"**。官方给出的理由是工作流可能拿到 token、secret 或仓库权限。管理员可在仓库设置里**关闭**这个人工审批，让工作流直接跑（默认仍是需要审批）。
- **成熟度**：**生产可用**（平台默认行为）。
- **要说的实话**：**「审批队列模式」并不是一个有正式规范名字的标准**。本调研没有找到任何标准化组织或规范文档把它定义成一个具名模式；它是一类产品实现（PR review、环境审批、工单审批）的统称。**这一点写下来是为了避免把产品行为冒充成标准。**

## 2.5 AI 产品的审批 UX

### Devin —— 五档权限模式 + 四级优先级

- **解决什么问题**：让 Agent 在「不打断」与「不闯祸」之间有一个可调的档位，并能按项目/全局持久化授权。
- **核心机制**（来源：<https://docs.devin.ai/cli/reference/permissions.md>）：
  - **五档模式**（每种工具在不同档位下是 Auto 还是 Prompt 不同）：

| 工具类型 | Normal | Accept Edits | Smart | Bypass | Autonomous(沙箱) |
|---|---|---|---|---|---|
| 只读（read/grep/glob） | Auto | Auto | Auto | Auto | Auto |
| 网络抓取 | Prompt | Prompt | 判定安全才 Auto | Auto | Auto |
| Shell 命令 | Prompt | Prompt | 判定安全才 Auto | Auto | Auto |
| 文件编辑 | Prompt | Auto（工作区内） | Auto（工作区内） | Auto | **Prompt** |

  - **Smart 模式**用快速模型判定「是否明显安全」，且**无论模型怎么判，以下类别永不自动放行**：包安装、会改动状态的 git 操作、`rm`/`sudo` 等破坏性或提权命令、`kubectl delete` 等破坏性云命令、读写 dotenv/密钥/agent 自身配置的操作。
  - **规则优先级**（同级配置内）：**Deny > Ask > Allow > Default**。原文：*"A deny rule always wins. An allow rule never overrides a matching deny, regardless of how specific the allow rule is."*
  - **授权持久化五档**：仅本次 / 本次会话（内存）/ 本项目（`.devin/config.json`，**会随 git 共享给团队**）/ 本项目本地（`.devin/config.local.json`）/ 全局用户配置。
  - **配置优先级**：组织/团队策略 > 会话级授权 > 项目本地 > 项目 > 用户。**组织级 deny/ask 不可被下级覆盖。**
  - **规则的表达方式**：作用域型 `Read(glob)` / `Write(glob)` / `Exec(prefix)` / `Fetch(URL pattern)`，以及工具型 `edit` / `exec` / `read` / `grep` / `glob` 和 MCP 型 `mcp__server__tool` / `mcp__server__*` / `mcp__*`。
  - **「带理由批准」的一种变体**：命令审批弹窗不只是 yes/no，还有 **Edit command**（就地改命令再跑）与 **Describe change to command**（用大白话描述你要它改成什么）。
- **成熟度**：**生产可用**（Smart 模式标注为逐步放量）。

### Cursor —— 三档执行模式 + LLM 分类器

- **核心机制**（来源：<https://cursor.com/help/ai-features/terminal.md>）：**Auto-review（3.6+ 默认）** / **Allowlist** / **Run Everything**。
  - Auto-review：白名单命令直接跑；其余**尽量进沙箱跑**；再剩下的由 **LLM 分类器**按「安全性 + 与用户请求的匹配度」决定放行或拦截；**被拦的命令可以带你的批准重试**。
- **成熟度**：**生产可用**。与 Devin 的差别：Devin 用规则 + 永不放行清单兜底，Cursor 更依赖分类器 + 沙箱。

## 第二块小结：三个共性问题

| 问题 | 答案 | 证据 |
|---|---|---|
| **拦截在生效前还是后？** | **生效前**是三种规范模式的共同设计。LangGraph 在 `after_model` / 工具执行前中断；Step Functions 在任务处暂停等令牌；Copilot 在 Actions 运行前卡住；Temporal 的 Update validator 可在写入 History 前拒绝。 | 见 2.1 / 2.2 / 2.3 / 2.4 |

# 第三块 · Agent 的身份与授权

## 总览

答案是清晰的：**业界正在把 Agent 从「模拟人类账号」推向「一等身份」**，而且已经有了可用的实现（AWS AgentCore）和 MUST 级的标准要求（IETF 草案）。但仍然存在**公认未解决的缺口**（见 3.5）。

## 3.1 OAuth 的 on-behalf-of：RFC 8693 令牌交换

- **解决什么问题**：让「代表某人行动的中介」在不把原始用户令牌原样转发的前提下，拿到一张**为下游资源定制的、更窄的**令牌。
- **核心机制**（来源：<https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/on-behalf-of-token-exchange.md>）：
  - 用 `grant_type=urn:ietf:params:oauth:grant-type:token-exchange`（RFC 8693），**`subject_token` = 入站的用户令牌**，**`actor_token` = agent 自己的身份**。
  - 另一条路是 `grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer`（RFC 7523 §2.1），把入站令牌当 JWT 授权授予。
  - RFC 8693 规范原文：<https://www.rfc-editor.org/rfc/rfc8693.txt>
- **关键点**：*"The exchanged token carries **both the agent's own identity** and the original caller's identity"* —— 这正是「委托链条」的标准实现方式：**授权服务器替你做最终授权判断，包括是否允许这次委托**。
- **成熟度**：**生产可用**（RFC 标准，2026 年 4 月起在 AWS AgentCore 上 GA，覆盖 14 个区域）。

## 3.2 AWS Bedrock AgentCore Identity：把 Agent 当一等身份

- **解决什么问题**：多跳调用（User → Agent → Tool A → Tool B）中「每一跳带什么身份」的问题。
- **为什么不能用老办法**（官方列出的四条，来源：<https://builder.aws.com/content/3EOwdM2gsKqzXKO7OmyfWcRATWV/securing-agentic-workflows-identity-propagation-with-amazon-bedrock-agentcore>）：
  1. **权限只会累积不会收窄** —— 用户令牌 scope 通常很宽，Tool B 只需要对一个资源做一次操作。
  2. **混淆代理（confused deputy）风险** —— Tool A 拿着全量用户令牌可以冒充用户调别的工具，下游分不清合法与恶意。
  3. **审计链断裂** —— 原文：*"your access logs say 'user X did this'; but they never tell you **which agent acted on behalf of user X**, or which tool in the chain originated the call."*
  4. **中途重新弹授权不可扩展** —— 不能每次访问新下游都做一次 OAuth 跳转。
- **核心机制 —— 三个原语**：
  - **Workload identity（工作负载身份）**：原文称之为 *"a **new identity primitive**; agent-specific, with its own ARN; that says **who the agent is**, separate from who the user is"*。创建 Runtime 时**自动分配**，由 Service-Linked Role（`AWSServiceRoleForBedrockAgentCoreRuntimeIdentity`）背书。**官方比喻：agent 有自己的护照，用户有自己的护照；agent 代用户行动时两本护照都在场，不会只有一本。**
  - **Token vault**：KMS 加密、**按「agent–user 配对」隔离** —— 为 A 用户存在 X agent 上的令牌，B 用户拿不到、Y agent 也拿不到；自动刷新；受监管场景可换客户自管 KMS 密钥。
  - **Inbound / outbound 分离**：inbound = 谁能调用 agent（`IAM SigV4` 或 `JWT Bearer via OIDC`，二选一互斥）；outbound = agent 能访问什么（**2LO** 机器到机器、**3LO** 用户委托）。
- **关键接口**：
  - `get-workload-access-token-for-jwt --user-token <入站JWT>` → `workloadAccessToken`
  - `get-resource-oauth2-token --oauth2-flow ON_BEHALF_OF_TOKEN_EXCHANGE --scopes "repo:read"` → **只带 `repo:read`、只对这一用户、只对这一 provider 的**下游令牌
  - 请求头 **`X-Amzn-Bedrock-AgentCore-Runtime-User-Id`** 指定"代哪个用户"；调用它需要额外的 IAM 权限 `bedrock-agentcore:InvokeAgentRuntimeForUser`（**刻意与普通调用分开**）
  - ⚠️ 官方红线：*"**derive this value from authenticated principal context, never from a client-supplied parameter**"* —— 从前端传 `userId` 转发给这个头，等于自己造了一个冒充原语
  - **Gateway + Lambda interceptor**（即**外部动作经平台中转**的现成实现）：AgentCore Gateway 是一个 MCP 网关（agent 侧说 MCP，工具侧说 REST/Lambda）；**REQUEST interceptor 在网关调用目标工具之前运行**，**RESPONSE interceptor 在目标返回后、agent 看到结果之前运行**；每个网关最多各挂一个。请求拦截器做身份强制转换：取出入站 JWT → 换下游窄令牌 → 替换 Authorization 头 → 返回。**原始用户令牌永不越过网关进入工具。** 默认 `passRequestHeaders: false`（安全优先，不把 Authorization 头透给拦截器）。
  - 工具级授权可用 JWT scope 约定 `mcp-target-<id>` / `mcp-target-<id>:<toolName>`。
- **成熟度**：**生产可用**（OBO 2026-04 GA；Lambda interceptor 的 CDK 构造标注为 alpha）。

## 3.3 GCP Vertex AI：Service Agent 模型（反面教材）

- **做法**：Agent 不以自身身份运行，而是**继承一个系统托管、项目级权限的 Service Agent 身份**。
- **具体事实**（来源：<https://www.thaicert.or.th/en/2026/01/19/privilege-escalation-vulnerability-discovered-in-google-vertex-ai-allows-low-privilege-users-to-become-service-agents/>）：
  - 受影响组件：**Vertex AI Agent Engine** 与 **Ray on Vertex AI**。
  - 根因是**不安全的默认配置**：只有「修改 reasoning engine 设置」权限的用户即可注入恶意 Python 代码；代码在服务计算环境内执行，**通过云元数据服务（metadata service）取到 Reasoning Engine Service Agent 的凭据**。
  - 该 Service Agent 是 *"system-managed identities with **elevated permissions**"*，可访问**会话历史、模型记忆、存储位置、执行日志**。
  - Ray on Vertex AI 上，**只读权限用户**也能通过 Console 工具触达计算环境控制组件，进而从元数据服务提取 Custom Code Service Agent 的令牌，对 Cloud Storage / BigQuery / Pub/Sub 取得完全控制。
  - 官方缓解建议：用自定义 IAM 角色收紧 Service Agent 权限、关闭不必要的系统控制工具访问、部署前审查代码、监控对元数据服务的访问。
- **成熟度**：**已修复/有缓解建议的已知问题**（2026-01 通报）。
- **对本项目的意义**：这是「Agent 跑在一个共享的、权限过宽的系统身份之下」的典型代价 —— 恰好是我们要求「GM 必须是可追溯、可撤权的一等成员，而不是特权后台进程」时要避开的形态。

## 3.4 MCP 的授权规范（OAuth 2.1 + Resource Indicators）

- **解决什么问题**：MCP 客户端如何安全地访问受保护的 MCP 服务器。
- **核心机制**（来源：<https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/index.md>）：
  - **角色**：受保护的 MCP server = OAuth 2.1 **资源服务器**；MCP client = OAuth 2.1 **客户端**，*"making protected resource requests **on behalf of a resource owner**"*（原文即"代表资源所有者行动"）。
  - **依赖的标准栈**（规范原文列举）：OAuth 2.1 draft-13、RFC 6750（Bearer）、RFC 8414（AS 元数据）、RFC 7591（动态客户端注册，**已废弃仅兼容保留**）、**RFC 8707（Resource Indicators）**、**RFC 9728（Protected Resource Metadata）**、RFC 9207（iss 标识）、OIDC Discovery、Client ID Metadata Documents。
  - **几条 MUST / SHOULD 级要求**：
    - 授权服务器 **MUST** 实现 OAuth 2.1；MCP server **MUST** 实现 RFC 9728。
    - 客户端 **MUST** 实现 RFC 8707 —— `resource` 参数**必须同时出现在授权请求与令牌请求中**，且必须指向它打算使用的那个 MCP server；MCP server **MUST** 校验令牌**确实是签发给自己的**（audience 绑定）。
    - 最小权限：server **SHOULD** 在 401 的 `WWW-Authenticate` 里带 `scope`；客户端 **SHOULD** 优先用这个 `scope` 而不是 `scopes_supported`。
    - **Step-up 授权流**：运行时 scope 不足 → 403 + `error="insufficient_scope"` + 所需 scope；客户端把「先前已请求的 scope」与「本次挑战的 scope」**取并集**后重新授权，并**必须有重试上限**。
    - 客户端 **MUST NOT** 把令牌发给自己之外的其他 MCP server。
  - **安全考量章节**明确覆盖：令牌 audience 绑定与校验、令牌盗用、通信安全、授权码保护、**mix-up 与 confused deputy 攻击**、开放重定向。
- **成熟度**：**已发布规范**（本文档对应 2026-07-28 版），但授权本身对 MCP 实现而言是 **OPTIONAL**；且规范自述是"实现所选标准的一个子集"。
- **注意边界**：这套东西管的是「**客户端访问受保护服务器**」，**不是**「平台内部某个角色动作要不要人批准」。别把两者混为一谈。

## 3.5 IETF 的两个草案（本块最有价值的部分）

### 3.5.1 `draft-daniel-ai-agent-internet-architecture-01`

*Architectural Requirements for Supporting AI Agents on the Internet*（2026-08-28，Informational）
来源：<https://datatracker.ietf.org/doc/html/draft-daniel-ai-agent-internet-architecture-01>

它把需求编号化了，直接可用：

**§10 认证、授权与委托** —— 开篇断言：*"**Authorization is a central gap for AI-agent use cases.**"*

| 编号 | 要求 |
|---|---|
| `REQ-AUTH-1` | 架构**必须**区分 **agent 身份**与它所代表的人/组织的身份 |
| `REQ-AUTH-2` | 授权证据**必须**受 audience 限制，且**应当**对资源与操作做窄化 |
| `REQ-AUTH-3` | 多跳委托**应当**以**可验证形式**保留原始主体与每一次授权步骤（允许对不需要完整链条的中介做隐私化披露） |
| `REQ-AUTH-4` | 委托**应当**表达时限、交易/额度上限、上下文约束，以及**是否允许再委托** |
| `REQ-AUTH-5` | 资源服务器**必须**能在**不信任中间 agent 未认证声明**的前提下判定当前请求的有效权限 |
| `REQ-AUTH-6` | 被委托的权限**必须**可撤销或天然短期有效；撤销语义**应当**处理进行中的多 agent 链条 |

**§15 溯源、可审计性与问责**

| 编号 | 要求 |
|---|---|
| `REQ-AUD-1` | 审计证据**应当**支持关联：**agent 身份 · 运营方/问责主体 · 授权上下文 · 请求标识 · 时间戳 · 实质性策略约束 · 结果状态**（涉支付时还有支付引用） |
| `REQ-AUD-2` | 审计证据**应当**防篡改，并**应当**支持选择性披露 |
| `REQ-AUD-3` | **协议不得把收集私有推理轨迹（private reasoning traces）作为问责的前提条件** |
| `REQ-AUD-4` | 审计标识**应当**做范围限定，以减少跨服务追踪 |
| `REQ-AUD-5` | 当证明结果/验证方/评估策略对某个信任决定是实质性的时，审计证据**应当**能标识或引用它们 —— 且**不应**因此要求披露私有推理、敏感证据或无关负载数据 |

**§16 撤销、暂停与紧急控制** —— 开篇：*"Autonomy and machine-speed execution make revocation a **first-order protocol requirement**."*

| 编号 | 要求 |
|---|---|
| `REQ-REV-1` | 凭据与委托权限**应当**支持短有效期，并在风险需要时支持显式撤销 |
| `REQ-REV-2` | 撤销父委托**应当**按明确语义使依赖的再委托失效或受限 |
| `REQ-REV-3` | 服务**应当**支持**快速暂停被入侵的 agent 或密钥，而不要求删除历史审计证据** |
| `REQ-REV-4` | 紧急控制**应当** fail-safe，且**应当**避免单一全局特权"总开关" |

`REQ-AUD-1` 这一条几乎是给我们「谁授权、依据什么、结果如何」写的字段清单。

### 3.5.2 `draft-chen-oauth-agent-authz-use-cases-04`

*Agent Authorization use cases and gap analysis*（OAuth 工作组方向的 gap 分析草案，2026-10）
来源：<https://www.ietf.org/archive/id/draft-chen-oauth-agent-authz-use-cases-04.txt>

**三个结构性缺口**（§3）：

| 缺口 | 内容 |
|---|---|
| **授权上下文缺口** | 用户在 T1 给出高阶意图（"帮我规划巴黎旅行"），agent 在 T2（数小时后）请求具体权限（`scope=booking_api`）。授权服务器和用户**都拿不到 T1 的上下文**，只能弹一个泛化的同意框 —— 用户要么因不确定而拒绝合法请求，要么盲目批准。规范里**没有标准机制接收并校验这个"意图"上下文**。 |
| **委托链缺口** | A→B→C 多跳后，资源服务器**只能验证 C 的令牌对 C 有效**，无法"回溯"确认这条链起源于用户的合法授权。原文结论：*"This prevents end-to-end security, **makes auditing impossible**, and complicates the enforcement of progressively narrower permissions down the chain."* |
| **批量撤销缺口** | 只能逐令牌撤销（RFC 7009），造成**漏洞窗口** —— 攻击者可用仍有效的其余令牌继续访问。需要标准化的原子级"kill switch"。 |

**§6 七条重大缺口**（编号为原文顺序）：

1. **从"预先批准"转向"持续对话"** —— OAuth 的模型是一次性拿全权限；agent 需要随任务演进**动态、即时**授予。
2. **缺少标准化的交互通道** —— 框架内**没有**让 agent "暂停"并安全地向用户请求中间决定、或响应资源服务器实时授权挑战的机制。
3. **无法表达委托链** —— 标准令牌无法安全表示多步委托链，这是自动化复杂多 agent 业务的关键阻塞。
4. **撤销机制不足** —— 单令牌撤销 API 不够；缺任务级与批量级撤销的标准 API。
5. **授权按客户端建模，而非按组** —— 没有"一组客户端作为一个任务组、共享一份授权"的概念：无组成员表示、无迟到成员准入、无组级生命周期与原子撤销。
6. **授权层 vs 执行层缺口** —— OAuth 擅长定义 *Grant-Layer Authority*（agent 被允许做什么），但**缺少生成 *Execution-Layer Evidence* 的标准机制**：即"用户在**某个具体高风险动作发生的那一刻**给出明确同意"的、**不可否认的密码学证明**。原文点破：*"grant-layer tokens prove **potential**, not the legitimacy of a specific, executed transaction."*
7. **缺少机器可读的终态处置** —— 客户端收到资源服务器的授权挑战后失败或拒绝时，没有标准方式把这个"处置结果"回传，资源服务器只能从沉默中猜测。

**第 6 条正是我们第一块和第 2.5 节都撞到的那个洞**：授权层证明"有资格"，执行层要证明"这一次确实被授权了"。

- **成熟度**：**草案阶段**（Informational Internet-Draft，6 个月有效期）。**不能当标准引用，但作为需求清单极有价值。**

## 3.6 W3C 侧

- **未找到** W3C 关于 agent identity 的正式规范、工作草案或工作组章程。检索到的只有 W3C 公共凭据社区组（public-credentials）邮件列表上关于 "LLMs and Agents usage in the CCG" 的讨论串（如 <https://lists.w3.org/Archives/Public/public-credentials/2026Apr/0162.html>），**未见产出规范成果**。按"不猜"的要求，此处标注为**未找到**。

## 第三块小结：Agent 是不是一等身份？

| 问题 | 答案 | 证据 |
|---|---|---|
| Agent 是不是被当成一等身份？ | **正在成为一等身份，且已有生产实现。** AWS AgentCore 的 workload identity 官方称之为 "a new identity primitive"，有独立 ARN、自动分配、由 SLR 背书，并明确与用户身份"是两本护照"。IETF 更把「架构必须区分 agent 身份与委托方身份」写成 **MUST**（`REQ-AUTH-1`）。 | 3.2 / 3.5.1 |
| 还是只是模拟人类账号？ | **GCP Vertex 侧更接近"继承一个高权限系统身份"**（Service Agent），代价是权限过宽 + 已出现提权漏洞。 | 3.3 |
| 有没有"代表某人行动"的委托链？ | **有标准做法**：RFC 8693 令牌交换，`subject_token` = 人、`actor_token` = agent，换出的令牌**同时携带两者身份**。但 IETF 明确指出：**跨多跳的委托链在标准 OAuth 里仍无法表达**（gap #3）。 | 3.1 / 3.5.2 |
| 权限边界怎么表达？ | 有产品级做法（scope + JWT scope 约定 `mcp-target-<id>:<toolName>`；MCP 的 `scope` 挑战与 step-up 流），也有标准级要求（`REQ-AUTH-2` audience 限制 + 窄化；`REQ-AUTH-4` 时限/额度/上下文约束/可否再委托）。**但没有一个统一、机器可读的"权限边界描述格式"标准。** | 3.2 / 3.4 / 3.5.1 |

# 第四块 · AI 治理与合规对记录的要求

## 总览

**适用边界先说清**：EU AI Act 的日志义务（Art 12 / 19）**落在"高风险 AI 系统"上**，不是所有 AI 系统；Art 86 的解释权也有窄条件。NIST AI RMF 是**自愿框架**，其 Playbook 内容明示为"建议而非要求"。因此：**如果 GM 不构成高风险系统，这些条款不直接约束我们** —— 但它们的字段要求是极好的参照系。

## 4.1 EU AI Act（Regulation (EU) 2024/1689）

来源：<https://artificialintelligenceact.eu/article/12/> 等（条款逐条页，含生效日期）

### Article 12 — Record-Keeping（记录保存）

- **适用范围**：高风险 AI 系统（Chapter III Section 2）。**生效：Annex III 下的高风险 2027-12-02；Annex I 下的高风险 2028-08-02**（依 Art 113(c)）。
- **12(1)**：高风险 AI 系统**在技术上必须支持在整个生命周期内自动记录事件（logs）**。
- **12(2)**：为确保与其预期目的相称的**可追溯性**，日志能力必须能记录与以下事项相关的事件：**(a) 识别可能导致系统呈现风险（Art 79(1) 意义下）或发生实质性修改的情形**；（条款在 (b) 及之后继续，完整列举见原文链接）。
- **12(3)**：对特定类别（如远程生物识别）另有要求 —— 记录使用时段、参考数据库等。

### Article 19 — Automatically Generated Logs

- 提供者**必须保存 Art 12(1) 所述、由其高风险 AI 系统自动生成的日志**，"in the extent such logs are under their control"。
- **保留期限：至少六个月**（除非适用的欧盟或成员国法律另有规定）。

### Article 13 — Transparency and Provision of Information to Deployers

- **13(1)**：高风险 AI 系统**必须**以使其运行**足够透明、以便部署者能解释系统输出并恰当使用**的方式设计与开发。"应确保**适当类型与程度的透明度**"。
- 关键点：这里的"透明"是**面向部署者（deployer）的解释能力**，不是面向公众的模型可解释性论文。

### Article 14 — Human Oversight（人工监督）

- **14(1)**：高风险 AI 系统**必须**以（含适当人机界面工具）**使自然人能够在其使用期间有效监督**的方式设计与开发。
- **14(2)**：人工监督的目标是**预防或最小化**在使用中可能出现的对健康、安全或基本权利的风险。

### Article 26 — Obligations of Deployers

- **26(1)**：部署者**必须**采取适当的技术与组织措施，确保按照使用说明使用系统。

### Article 86 — Right to Explanation of Individual Decision-Making

- **生效：2026-08-02**。受影响人**有权**就部署者基于 Annex III 所列高风险 AI 系统输出作出的、产生法律效力或类似显著影响其健康/安全/基本权利的**个体决策**，获得**对决策的解释**。
- **注意这是"事后的、面向受影响个体的解释权"**，不是"必须记录模型推理过程"的义务。

### 4.1 小结：法规要求「留什么痕」

| 要求 | 条款 | 落到字段上是什么 |
|---|---|---|
| 自动、全生命周期、可追溯的事件记录 | Art 12(1)(2) | **事件 + 时间 + 可追溯标识**，能识别风险情形与实质修改 |
| 日志保留 ≥ 6 个月 | Art 19 | 保留策略 |
| 部署者能解释输出 | Art 13(1) | 面向使用者的解释材料（文档/UI），不必然是逐次推理 |
| 有效人工监督 | Art 14 | 监督接口与干预能力 |
| 受影响个体的解释权 | Art 86 | 事后解释材料（按请求提供） |

## 4.2 NIST AI RMF

来源：<https://www.stigviewer.com/controls/ai-rmf/MEASURE%202.8> 与 <https://www.stigviewer.com/controls/ai-rmf/MANAGE%204.1>（对 NIST AI RMF 1.0 子类的引用与转述）

- **MEASURE 2.8**：*"Risks associated with transparency and accountability – as identified in the MAP function – are examined and documented."*
  - **Suggested Actions 里明确点名了留痕**：*"Instrument the system for measurement and tracking, e.g., by **maintaining histories, audit logs** and other information that can be used by AI actors to **review and evaluate possible sources of error, bias, or vulnerability**."*
  - 同段还建议：与 UI/UX、HCI、人-AI 团队专家协作校准控制；**对不同受众（操作员、最终用户、决策者、被决策者）测试所提供的解释**，并为有后果的决策**提供救济途径（recourse）**。
- **MANAGE 4.1**：*"Post-deployment AI system monitoring plans are implemented, including mechanisms for capturing and evaluating input from users and other relevant AI actors, **appeal and override**, decommissioning, incident response, recovery, and change management."*
  - ⚠️ 注意 `appeal and override` 出现在这里 —— **"推翻/申诉"是框架级承认的机制**，这与我们四态里的 `overridden` 同源。
- **⚠️ 重要限定（原文自带）**：*"These are suggestions NIST offers, **not requirements**, and satisfying one does not establish conformance with this subcategory."* —— Playbook 内容是建议，不是合规判据。
- **未找到**：NIST **AI 600-1（Generative AI Profile）** 中关于 incident logging / provenance 的**具体子类编号**。检索未定位到可引用的原文条款，故不臆测。

## 4.3 「AI 审计日志」的实践建议：IETF OMP 的 EU AI Act Profile

这是本块**最具体**的一份材料，因为它把 Art 12 拆成了可实现的字段。

来源：<https://datatracker.ietf.org/doc/draft-veridom-omp-euaia/>（`draft-veridom-omp-euaia-00`，2026-04-02，Informational，作者隶属 Veridom Ltd）

**它把 Article 12 拆成六项要求**：自动生成 · 防篡改 · 运行期记录 · 参考数据库状态捕获 · 输入数据记录 · **决策可追溯性**。

其中 **§3.6 决策可追溯性** 给出的记录内容，几乎就是我们要的「依据什么」：

> OMP Audit Trace 为**每一个决策**记录：
> - 意图类别（intent class）与分类置信度；
> - 三个置信度分量（C_m, C_p, C_d）；
> - **每一个生效的 Watchtower 门（gate）的评估结果**；
> - **路由结果（`AUTONOMOUS` / `ASSISTED` / `ESCALATED`）+ 路由理由（routing rationale）+ 显式规则引用（explicit rule reference）**；
> - 对 ASSISTED 与 ESCALATED 结果，记录 **Named Accountable Officer 的身份与解决动作**。

此外要求：Proof-Point 机制**必须**能在请求后 **30 秒内**为任意时间窗生成监管复核包，供直接提交监管机构。

**§4.4 Audit Trace schema 扩展（EUAIA Profile 下 REQUIRED 字段）**：

| 字段 | 类型 | 含义 |
|---|---|---|
| `euaia_annex_iii_category` | string | 适用的 Annex III 类别，如 `"5b-credit-scoring"` |
| `euaia_article_14_oversight` | boolean | 本次交互是否适用 Art 14 人工监督；为 true 时 WT-EUAIA-01 必须已被评估 |
| `source_state_hashes` | array | 本次交互查询的每个外部数据源一条记录：`source_id` · `query_timestamp_ms` · `response_hash`（响应的 SHA-256）· `h_s = SHA-256(canonical_form(response) ‖ query_timestamp_ms)` |
| `pseudonymisation_applied` | boolean | 提交前是否对个人数据做假名化 |
| `proof_point_version` | string | 生成该 Trace 的规格语义版本，本版为 `"VERIDOM-EUAIA-v1.0"` |
| `supervisory_authority_jurisdiction` | string | 有管辖权的监管机构所在成员国 ISO 3166-1 alpha-2，如 `"DE"` |

- **成熟度**：**实验性 / 强烈保留**。这是**单一公司提交的个人草案**（OMP 核心规范也是另一份草案），**不是 IETF 工作组产出，不具标准效力**。它的价值在于**它把 Art 12 翻译成了字段**，可以直接当设计参照，但**不能当合规依据引用**。

## 4.4 「可解释性」要求到什么粒度？

这是本块最值得说清的一点，**答案是：法规与主流标准都没有要求记录模型的推理过程**。

| 证据 | 内容 |
|---|---|
| **IETF `REQ-AUD-3`**（3.5.1） | *"Protocols **MUST NOT** require collection of **private reasoning traces** as a condition of accountability."* —— 明确禁止把收集推理链当作问责前提。`REQ-AUD-5` 再次重申：审计能力"**不应要求披露私有 agent 推理**"。 |
| **EU AI Act Art 12** | 要求的是「自动记录**事件**」与「确保**可追溯性**」，指向的是事件流与标识，**不是推理内容**。 |
| **EU AI Act Art 13** | 透明度目标是"让部署者能**解释系统输出并恰当使用**" —— 是能力要求，不是逐次记录思维链。 |
| **EU AI Act Art 86** | 给受影响个体的是**事后的解释权**（按请求提供解释），同样不是"每步都存 CoT"。 |
| **NIST MEASURE 2.8** | 留痕的目的是让 AI actors 能**复核可能的错误、偏见或脆弱性来源** —— 是复核用途，不是还原推理。 |

**⚠️ 用户要求里点名要查的 GDPR Article 22 / Recital 71 —— 本次未取到一手原文核实**，因此不在报告中给出关于它们的具体断言。已核实并可引用的是上面五条。**（标注为部分未完成，不臆测。）**

**结论**：留痕的落点是 **「谁（身份）· 代表谁（委托主体）· 依据什么（授权上下文与规则引用）· 何时 · 请求标识 · 策略约束 · 结果状态」**，而推理链是**可选、辅助、且不应被强制**的内容。

| A11 | **审计证据防篡改与选择性披露** | IETF `REQ-AUD-2`（3.5.1） | 设一个"防篡改 + 可选择性披露"的验收项 |

## B. 需要改造（有原型，但形态不匹配）

| # | 借鉴对象 | 为什么不匹配 | 改造方向 |
|---|---|---|---|
| B1 | **LangGraph 的 interrupt + checkpointer** | 它是「**图内**暂停」——一次图执行跑到某节点停下等 `Command(resume)`。GM 是**长期驻留的事件流订阅者**，不存在"一次图执行"这回事 | 改成「**动作提案（proposal）+ 外部队列 + 决定入口**」：GM 发出提案并挂起该动作，状态存在平台侧，决定从审批入口回填，GM 不阻塞等待 |
| B2 | **Temporal 的 Approval Pattern** | 它要引入一个完整工作流引擎，且"等一个 Signal"绑定在单个 workflow 实例上 | 只借它的**数据结构**（`ApprovalData{approver, decision, comments, timestamp}`）与**"决定是对象不是布尔"**这条原则，不必引入引擎 |
| B3 | **Step Functions `.waitForTaskToken`** | 令牌**不能跨 AWS 账号**、Express 工作流不支持、且回调 payload 无标准字段 | 借"**令牌式回调**"的思路做长等待（令牌 → 决定 → 回调），理由字段自建 |
| B4 | **MCP 授权规范** | 它管的是「**客户端访问受保护服务器**」，不是「平台内角色动作要不要人批准」 | 只在**GM 访问外部能力**时套用（scope、audience 绑定、step-up）；**不要**把它当成内部审批模型 |
| B5 | **OTel GenAI semconv** | 属性多为 `Development`、关键内容字段是 `Opt-In`，仓库刚从主仓库迁出 | 可以**作为 trace 层的对齐目标**（span 命名、`gen_ai.agent.id` 等），但**不要把 `gen_ai.*` 冻进我们的审计契约** —— 审计契约要自己定义并版本化 |
| B6 | **Weave 的 `reasoning` 字段** | 它记录的是**模型自述的理由文本**；IETF `REQ-AUD-3` 明确说不得把推理链当问责前提 | 理由字段做成**可选、辅助、不参与问责判定**；问责靠 `rule reference` + `授权上下文` 这类**可校验**字段 |
| B7 | **Devin / Cursor 的权限模式** | 都是**单人对单 agent 的交互式授权**（"你"批准"你的"agent） | 移植到**多人团队**：需要一个"**授权主体**"模型 —— 哪一级动作由谁（角色）批、授权范围多大、能否转授（借 `REQ-AUTH-4` 的"是否允许再委托"） |
| B8 | **NIST AI RMF 的 MEASURE 2.8 / MANAGE 4.1** | 是**建议性 Playbook**，原文自述"not requirements" | 当**设计检查清单**用，不当合规判据 |

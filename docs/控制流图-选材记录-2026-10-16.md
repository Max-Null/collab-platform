# 控制流图的选材记录（2026-10-16）

> **这张图选了 13 个节点、13 条边；被考虑过又拿掉的更多。**
> 这份记录就是那些拿掉的部分 —— 因为**漏掉一条链路是这类图最不容易被发现的缺陷**：
> 图上少一条，看起来与「本来就只有这些」毫无区别。
>
> 图本身在 [`report/控制流-一次变更的生命周期-2026-10-16.html`](report/控制流-一次变更的生命周期-2026-10-16.html)，
> 规格在同目录的 `.candidate.json`（规格在，图就能重生成）。
> **数据基准：2026-10-16 的 `master`。**

## 一、为什么值得做这张图

判据只有一条：**这图里有没有「不看图就想不到」的东西？** 有，三处：

| # | 不看图想不到的 | 为什么想不到 |
|---|---|---|
| ① | **三种结局是分列的**：命中 / 未命中 / **判断没做成** | 多数人对「自动审核」的直觉是两态：过 / 不过。而这里第三态单独计数 —— 因为「取不到数」「模型调不通」既不是通过、也不是不通过 |
| ② | **「未命中也要留痕」是一条实线，而动作默认关** | 直觉是「没问题的就不记」；这里反过来：**不记就分不出「看过没问题」与「没看过」**，而观察期的分母全靠它 |
| ③ | **「判断没做成」不在动作泳道，在策略泳道** | 它不是动作，是**事实** —— 一个关于「这次判断没真的发生」的事实 |

如果这三条都不成立，这张图就只是一张更花哨的方框图，不该做。

## 二、进图的东西（一句话各是什么）

| 泳道 | 节点 | 一句话 |
|---|---|---|
| GitLab（只读） | 合并请求 / 分支推送 | 两种事件源：前者有主张有落点，后者的主张就是提交消息 |
| 常驻进程 | 轮询 | 每 300 秒一轮，只读；每轮落一条心跳 |
| 策略层 | 触发检查 | 不关心的事件静默跳过（**跳过不是「判定为没问题」**） |
| 策略层 | 取数 | 只取白名单内的；**取不到 ≠ 空** |
| 策略层 | 判据 | 路径规则 + 模型判据，两条策略各判一次 |
| 策略层 | 判断没做成 | 取不到数 / 模型不通 / 不是约定格式 |
| 结局与处置 | 命中 / 未命中 | 前者的处置入口，后者的终点 |
| 动作层 | 评论 | 写开关默认关（干燥跑） |
| 判断记录 | 判断记录 | 三态都落、只追加、永不删 |
| 人与出口 | 控制台 / MCP | 人与 Agent 读它的地方 |
| 人与出口 | 回写反应 | 采纳 / 否定 / 无视 —— 观察期唯一的输入 |

## 三、考虑过、又拿掉的（**每条都要写清并到了哪**）

这一栏是必填的：**「不画」若不说清去了哪，就等于「从此消失」** —— 而它与「判断后排除」在结果上长得一模一样。

| 候选 | 它想回答什么问题 | 为什么没单独成图 | 并到了哪 |
|---|---|---|---|
| **心跳**节点 + 「平台状态读它」那条边 | 常驻还活着吗 | 换过三种路由都被判几何不可行；更根本的是：心跳讲的是**常驻健不健康**，而这张图讲**一次变更怎么走完** —— 不是同一条链 | `轮询` 的副标题：「只读 · 每轮落一条心跳」 |
| **两条策略拆成两个节点**（路径规则 / 模型判据） | 这几条策略有什么不同 | 画过。两个节点各自连三个结局 = 5 条出边，在「判据 → 结局」之间挤成一团，validate 报了 16 条诊断 | `判据` 的副标题：「路径规则 + 模型判据」 |
| **「不动手」节点** | 未命中与没做成之后做什么 | 画过。它引出的两条边与相邻边抢同一条走廊 | `判断记录` 的副标题（「三态都落」）+ 结论卡三 |
| **三条「→判断记录」虚线**（三态各自连过去） | 是不是每一态都留痕 | 画过（三条）。三条平行边共享走廊，是当时最大的一类诊断来源；而「三态都落」写在节点上已经够了 | `判断记录` 的副标题（「三态都落 · 永不删」）+ `命中 → 判断记录` 那条边的标签改成「每次判定都落一条」 |
| **观察期**节点 | 回写之后呢 | 它属于「回写之后」，超出了「一次变更」的范围 —— 放进来会让这张图没有终点 | 结论卡二：「观察期的分母是『被评估了多少次』，回写是它唯一的输入」 |
| **「三种结局」分组框** | 强调三态必须分开 | 结局节点从动作泳道移到策略泳道后，那个框覆盖不到它们了 | 阶段条上的标签：「三种结局必须分开」 |
| **模型用量** | 每次判定花了多少 token | 它是判断记录的**附属数据**，不是链路的一站 | ⚠️ **没并到哪** —— 见下一节 |

## 四、没进图、也没并到哪的（**这份记录真正要暴露的东西**）

上面那张表里每一条都写了去处，但下面这几条没有 —— 它们是**回指一遍才发现的缺口**。

**做法**：把 `src/` 下的每一个模块与图上的 13 个节点对一遍，凡「代码里有、图上没有对应物件」的就是缺口。

| 缺口 | 它是什么 | 判断 |
|---|---|---|
| **两个动作只画了一个** | 实际有两个写动作：`评论`（`action/gitlab-comment.ts`）与 **`挂起合并`**（`action/hold-merge.ts`） | **该补** —— 图上的「动作层」现在只站着一个节点，读者会以为只有一个动作 |
| **撤销** | `undo.ts` —— 发出去的动作要能收回 | **该补** —— 结论卡三写着「发出去的要能收回」，而图上找不到「收回」这个物件 |
| **合并提交跳过** | 推送事件源跳过合并提交（它的 diff 是合集，不跳过会把同一处变更判两遍） | 可以并入 `轮询` 的副标题：它决定「什么样的推送不会成为事件」 |
| **每日简报** | `briefing.ts` —— 平台主动说话的那条出口 | 可以只在文档里：它与「控制台 / MCP」并列，但不在「一次变更」这条链上 |
| **模型用量** | `usage.ts` —— 每次判定的 token 与耗时 | 同上一类：它是判断记录的**附属数据**，不是链路的一站 |
| **防轮次叠加的闸 / 令牌自愈** | 常驻的自我保护 | 可以只进文档：属于「轮询怎么活下来」，不是「变更怎么走完」 |

⚠️ **前两条是真的漏了**。而「撤销」那条还暴露了一个更深的问题：**结论卡里出现了图上没有的物件**。卡片不是图的注脚 —— 它是这张图的一部分，讲图上看不到的事就是脱节。这与「story 里提到的每个角色都要在 nodes 里有对应节点」是同一条规矩。

## 五、这张图自己的边界

- **它是静态的**。图回答「这个平台是怎么工作的」，控制台回答「现在发生了什么」—— 两者互补，不能互相替代。
- **数据基准是 2026-10-16 的 `master`**。链路是随代码变的：如果 `daemon.ts` / `policy/` / `action/` 下的东西变了，这张图就该重采，而不是只看增量。
- **它不画时序**。「谁先谁后、等了多久」不属于泳道图能讲清的范畴（那是 `sequence` 那一类的事）。
- **它没有画「两条策略」的并行**。这是明确取舍的结果（见第三节），不是遗漏。

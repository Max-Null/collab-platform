# 首次真实接入记录（2026-10-13）

两份外部依赖第一次真的接上：模型（上游模型服务那套）与 GitLab（自建 `gitlab.example.com`）。
下面记跑出来的结果、真实数据逼出来的代码改动，以及一条卡在设计前提上的发现。

端点路径要先探：根路径与 `/v1` 都是 404，OpenAI 兼容路径是 **`/compatible-mode/v1`**（`/models` 返回 200）。

### GitLab 的认证方式是被实测逼出来的

仓库里没有 PAT，凭据管理器里是 `root` + 密码（target `git:https://gitlab.example.com`）。

- `GET /api/v4/version` 无认证 → **401**
- 同端点带 Basic auth → **401**（GitLab 的 API 不吃 basic auth，这点和 git 操作不同）
- `POST /oauth/token` 走 password grant → **200**，拿到 `access_token`，`expires_in` 7200

于是平台支持两种凭据形态：`GITLAB_TOKEN`（PAT，走 `PRIVATE-TOKEN` 头）优先；没有就 `GITLAB_USER` + `GITLAB_PASSWORD` 换 OAuth 令牌（走 `Authorization: Bearer`）。

**形态由调用方明说，不靠猜字符串前缀** —— 猜错的表现是 401，而 401 跟「令牌真的错了」长得一模一样，排查时不会有人想到是发错了头。这条是踩过才写下来的：第一版代码只发 `PRIVATE-TOKEN`，用 OAuth 令牌跑出 401，错误信息里看不出任何关于「头」的线索。

## 真实数据逼出来的两处改动

### 一、「取不到」与「取到了但是空的」必须分开报

第一版把两者混为一谈：`if (!value) missing.push(name)`。空数组与取数失败走同一个分支，理由写成「取数失败：… 在事件 X 里取不到」。

真实数据上这不成立：MR !1 的 `changedFiles` 与 `diff` **取到了，就是空的** —— 那是「这次变更没有任何改动」，不是「接口出了问题」。两种都不该做判断，但事后看记录的人需要一眼分清当时是哪种；混成一句话，排查就得从头再跑一遍。

现在 `missing`（字段缺席）与 `empty`（取到了但为空）分开收集、分开写进依据。

### 二、事件源要能取历史状态

`state` 默认只取 `opened`。加这个开关不是为了日常跑，是为了拿真实的历史 MR 做演练 —— 一个刚接入的平台最缺素材，而历史 MR 是现成的、只读的、早就没人会因为它多出一条评论而受影响。

`GITLAB_MR_STATE=all` 由此而来。

## 两条观察（还没有结论，只是记下来）

### 判据偏严：`feat: 配置管理` 被判「不符」

MR !2 的标题只有四个字，实际带了端口、依赖、注解、包重构。判它「不符」**技术上对**，工程上却未必 —— 一个大功能上线带一串配套改动是常态，而标题本来就写不下。

这条不该现在就动判据。改动它需要「命中之后到底对不对」的分布，而那个分布要靠观察期攒。**一条真实误报就是观察期的第一条数据，不是调参的理由。**

### 判据不稳定：同一个 MR 两次跑，items 表述不同

同一 MR 连跑两次，结论（命中）一致，但 items 的措辞与切分不同：一次是「包路径重构 / 端口 / Feign / 依赖」四条，另一次四条但表述与顺序都变了。

`temperature: 0` 不保证确定性（推理型模型尤其）。这意味着**「同一条策略对同一次变更给同一个答案」不成立**，判断记录里那句结论是**那一次**的结论。

对留痕的影响要正视：回看一条判断记录时，看到的是当时模型说过的话，重跑未必复现。所以依据里记的是**取数来源与模型名**，而不是「可复现的推理过程」。

## 一条卡在设计前提上的发现：团队不用 MR

三个仓库的 MR 数量：

| 仓库 | id | MR 合计 | opened | merged | closed | 默认分支 |
|---|---|---|---|---|---|---|
| `my-group/my-agent` | 235 | 1 | 0 | 0 | 1 | main |
| `my-group/my-frontend` | 236 | **0** | 0 | 0 | 0 | master |
| `my-group/my-app` | 232 | 2 | 0 | 1 | 1 | main |

而提交是活跃的（各仓库最近 100 次提交，最新分别在 09/23、09/21、09/21），分支也很多（`feature/2026-09/*`、`feature/2026-10/*` 十几条）。**实际的工作方式是「功能分支 → 直接推 `test`」**：

- `my-app` 的 `test` 最后提交 **10/12**，`main` 停在 **08/21**
- `my-agent` 的 `test` 最后提交 **10/10**，`main` 停在 **09/28**
- `frontend` 只有一个 `master` 在动
- 全平台提过 MR 的只有一个人（`某位同事`）

### 这冲击的是已定案的第 6 条

`docs/待决问题.md` 第 6 条定的门禁形态是：**主干 protected，`Allowed to push` 为空、`Allowed to merge = GM + 管理员`，普通开发者只能提 MR。**

那是**要建成的形态**，不是**现有形态**。现有形态里没有 MR 这道工序，于是：

- 平台接上去，**看不到绝大多数变更** —— 事件源订阅 MR，而 MR 不存在
- 「改动与声称是否相符」这条策略**吃不到饭**：它需要 MR 的描述，而 push 没有描述
- 反过来，「敏感路径」那条策略**不需要 MR** —— 它只看文件列表，push 事件一样能判

### 三条可选路径（待定，不是结论）

1. **平台只做 MR 链路，接入的前提是团队先开始走 MR** —— 门禁本来就要改流程，平台是配合流程的，不是替代流程的。代价是平台落地与流程变更绑在一起。
2. **事件源扩到 push**，审查单元从「MR」变成「一次推送」 —— 敏感路径那条立刻能跑；但「改动与声称」那条会长期缺输入，因为 push 没有可检验的主张。
3. **两条链路并存**：push 触发规则类判据，MR 触发判据类判据。平台内部按「这次变更有没有主张」分流。

第 3 条看起来最像最终形态，但在没确认「团队愿不愿意走 MR」之前先不做 —— 那是个流程问题，不是技术选型问题。

## 复现命令

```powershell
$env:GITLAB_BASE_URL = "https://gitlab.example.com"
$env:GITLAB_USER     = "root"
$env:GITLAB_PASSWORD = "<凭据管理器里那条>"
$env:GITLAB_PROJECT  = "my-group/my-app"
$env:GITLAB_MR_STATE = "all"

$env:LLM_BASE_URL = "https://<你的模型服务端点>/compatible-mode/v1"
$env:LLM_API_KEY  = "<上游配置中心里那条>"
$env:LLM_MODEL    = "qwen3.6-plus"

node --experimental-sqlite dist/src/index.js --source=gitlab --stats
```

`GITLAB_WRITE` 不设即为干燥跑：正文照常渲染并落到 `var/comments/`，不往 GitLab 发任何东西。

# MCP 生态与 Agent 协议选型调研报告

> 调研时间：2026-10-13　｜　服务对象：团队协作平台设计（MCP 对外提供能力，内置 LLM 角色 GM）
> 资料来源分层标注：**【规范】** = 官方规范明确规定　**【SEP】** = 官方提案，已 Final 或已落地　**【孵化】** = 官方工作组进行中　**【第三方】** = 外部测量 / 厂商文档 / 开源项目

## 第一部分：MCP 生态里现成的能力

### 1.1 官方参考服务器：只有 7 个，且明确「不是生产件」

官方 [modelcontextprotocol/servers](https://github.com/modelcontextprotocol/servers) 现在只保留 7 个参考实现：Everything、Fetch、Filesystem、Git、Memory、Sequential Thinking、Time。**其中没有任何任务管理、项目管理、通知、协作类 server。**

更关键的是仓库 README 的原文警告：

> The servers in this repository are intended as **reference implementations** ... They are meant to serve as educational examples for developers building their own MCP servers, **not as production-ready solutions**.

曾经常被引用的 GitHub / GitLab / Slack / Sentry 等 server **已全部归档**到 [servers-archived](https://github.com/modelcontextprotocol/servers-archived)（Slack 转由 Zencoder 维护）。**结论：官方层面没有可直接复用的协作类 server，且不建议把 reference server 当产品用。**

### 1.2 生态规模与质量：一半能用，契约还会漂

【第三方】独立测量项目 [State of the MCP Registry](https://operatorsheets.github.io/state-of-mcp/)（2026-07-30~08-02 全量探测官方 registry，10,716 个活跃远程端点 / 7,676 个 operator，数据文件公开可复算）：

| 结果 | 端点数 | 占比 |
|---|---|---|
| 匿名握手成功 | 5,346 | 49.9% |
| 活着但要 key（401/403/402/429） | 2,643 | 24.7% |
| 真的坏了（死主机 / 404 / 超时） | 2,039 | 19.0% |
| 其他（重定向、429、异常响应） | 688 | 6.4% |

同页另外两条对选型更有价值的观测：

- **只有 18% 的 server 声明 `outputSchema`** —— 绝大多数工具「返回什么全凭运气」，这对一个要靠 MCP 结果驱动 GM 建任务的平台是直接风险。
- **4.4% 的 server 在 36 小时内改了工具契约**（后 36 小时只有 3 个）—— 作者自己在页面上修正过这条的解读，但「调用方学到的东西会过期」这个事实成立。

### 1.3 「多 Agent 共享一块任务板」——有人做了，但都不成熟

有，且不止一个。查到三个真正对口的方向：

**(a) [Routa](https://github.com/phodal/routa)**（MIT，TypeScript + Rust，活跃）—— 最贴近本项目的需求。定位是「workspace-first 多 Agent 协作平台」，核心设计就是**把看板当作规划面 + 协调总线**：

- 集成面同时提供 **ACP、MCP、A2A、AG-UI、A2UI、REST、SSE**
- 看板每个泳道由一个 specialist 承担，且**下游 lane 的 prompt 刻意不信任上游产物**（Backlog Refiner 产出规范 YAML story → Todo Orchestrator 重新解析并拒收弱 story → Dev Crafter 再检查 → Review Guard 独立复核每个验收标准 → Done Reporter）。
- 支持 `schedules, webhooks, background tasks` —— 即它自己也意识到「光靠 Agent 主动轮询不够」。

**(b) [jentrix-au/stacks-ai](https://github.com/jentrix-au/stacks-ai)** —— 定位「面向 AI Agent 的通用看板」：任务 / bug / 支持 / CRM / roadmap 共用一块板，**人和 Agent 都通过内置 MCP server 操作**。技术栈 Next.js 16 + Prisma 7 + Auth.js v5，可自托管。（README 直连抓取多次失败，此处依据 registry 与仓库描述页。）

**(c) MCP 官方 registry 本身**（[registry.modelcontextprotocol.io](https://registry.modelcontextprotocol.io/)）—— 只是目录，不是任务板；这里列出是为了说明「官方没有提供共享任务板这种原语」。

**判断：作为「参考设计」有价值，作为「依赖」不行。** 三者都还没有形成事实标准，且它们各自解决的是「代码交付看板」，与本项目的「通用团队协作 + GM 主动建任务」不是同一个问题。

### 1.4 「Agent 收件箱 / 通知」有没有标准化做法？

**【规范】没有。** 分三层说清楚：

1. **MCP 核心规范里没有任何「收件箱」原语**。只有 notifications（协议状态变更）与 tools（拉取式）。
2. **最接近的是官方 Tasks 扩展**，但它走的是「任务句柄 + 轮询」，不是收件箱。见第二部分 2.4。
3. **A2A 协议里有一个事实上的收件箱**：`Task` 对象 + `ListTasks` + push notification，见第三部分 3.4。这是目前协议层对「Agent 收件箱」最完整的表达——但它属于 A2A 而不属于 MCP。

## 第二部分：MCP 协议能力边界（重点）

### 2.0 先厘清版本，否则会得出相反结论

必须先把版本对齐，因为**同一个问题在不同版本上的答案是相反的**：

| 版本 | 状态 | 与本次调研相关的关键变化 |
|---|---|---|
| [2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/changelog) | Final，**生态 86% 在用** | elicitation 首发；server 可在 SSE 流发请求与通知（措辞用 SHOULD） |
| [2025-11-25](https://modelcontextprotocol.io/specification/2025-11-25/changelog) | Final，仅 1% 在用 | URL 模式 elicitation；**实验性 tasks**（`tasks/get`、`tasks/result`、`tasks/list`、`tasks/delete`） |
| [2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/changelog) | **Current（最新）** | 破坏性重构：去 session、去 GET 流、去 SSE 重投；server-initiated requests 被 MRTR 取代；tasks 移出核心 |

官方版本说明页 [Versioning](https://modelcontextprotocol.io/docs/2026-07-28/learn/versioning) 明确：**current = 2026-07-28**。所以「规范怎么说」要按 2026-07-28 回答，但「能不能用」要按 2025-06-18 回答。

### 2.1 notifications 类消息有哪些？能承载业务内容吗？

**完整清单**（源自规范各章节，另见 ContextForge 的[汇总表](https://ibm.github.io/mcp-contextforge/latest/architecture/adr/034-centralized-notification-service/)）：

| 通知 | 方向 | 用途 |
|---|---|---|
| `notifications/initialized` | C→S | 握手完成 |
| `notifications/tools/list_changed` | S→C | 工具列表变了 |
| `notifications/resources/list_changed` | S→C | 资源列表变了 |
| `notifications/prompts/list_changed` | S→C | 提示词列表变了 |
| `notifications/resources/updated` | S→C | 已订阅的资源变了 |
| `notifications/roots/list_changed` | C→S | 根目录变了（2026-07-28 **已移除**） |
| `notifications/message` | S→C | 日志 |
| `notifications/progress` | 双向 | 长任务进度 |
| `notifications/cancelled` | 双向 | 取消请求 |
| `notifications/tasks/created` | S→C | 任务已创建（2025-11-25 实验性） |
| `notifications/subscriptions/acknowledged` | S→C | 订阅已确认（2026-07-28 新增） |

**能承载业务内容吗？规范未规定。** 精确的答案是三句话：

1. JSON-RPC 层面 `notifications` 的 `params` 是开放对象，[基础协议](https://modelcontextprotocol.io/specification/2025-06-18/basic/index)只说「Notifications **MUST NOT** include an ID；接收方 **MUST NOT** 回应」。**规范没有为「用 notifications 携带业务事件」定义任何语义。**
2. 规范**逐条定义了**每个通知的用途，其中两个可能与业务沾边，但都被限制死了：
   - `notifications/message` 的用途被定义为**日志**（[Logging](https://modelcontextprotocol.io/specification/2025-06-18/server/utilities/logging) 章节：severity + logger + data），且 2026-07-28 起「servers **MUST NOT** emit `notifications/message` for requests that did not include this field」——**它是请求作用域的，不是广播通道**。Logging 本身在 2026-07-28 被 **Deprecated**。
   - `notifications/progress`（[Progress](https://modelcontextprotocol.io/specification/2025-06-18/basic/utilities/progress)）有硬性约束：**MUST only reference tokens that were provided in an active request, and are associated with an in-progress operation**，且「Progress notifications **MUST** stop after completion」。
3. 所以：**notifications 是协议状态变更通道，不是业务消息总线。「你有 3 条待办」不属于其中任何一条的既定语义。**

### 2.2 关键立法：SEP-2260 从规范上禁止了「平台主动推送」

这是本次调研最重要的发现，也是对本项目设计假设最直接的支持。

**[SEP-2260: Require Server requests to be associated with a Client request](https://modelcontextprotocol.com.cn/seps/2260-Require-Server-requests-to-be-associated-with-Client-requests.md) —— 状态：Final（Standards Track），创建于 2026-02-16，作者 MCP Transports Working Group。**

其 Abstract 原文：

> This SEP clarifies that `roots/list`, `sampling/createMessage`, and `elicitation/create` requests **MUST** be associated with an originating client-to-server request ... **Standalone server-initiated requests of these types outside notifications MUST NOT be implemented.**

它甚至给了一段反面示例代码，直接点名本设计假设想要的东西：

```python
# ❌ PROHIBITED: Standalone server push
async def background_task():
    while True:
        await asyncio.sleep(60)
        # Try to initiate sampling without any client request context
        await session.create_message(...)  # NOT ALLOWED
```

**它给出的四条理由，几乎逐条对应本项目的权衡**（原文摘）：

1. *Simplifies transport implementations* —— transports 不必支持任意 server-initiated 请求/响应流；
2. *Clarifies user experience* —— 用户能理解 sampling/elicitation 是因为**他自己发起了动作**，而不是凭空出现；
3. *Reduces security surface* —— 客户端对「为什么要这份信息」有上下文；
4. *Aligns with practice* —— 扫描 GitHub 发现**除 SEP 作者自己刻意构造的一个仓库外，没有任何实现这么做**。

> **这条正好把本项目「不做推送」的理由从「工程取舍」升级成了「规范遵从」。** 原文对 Timeout 的一句提醒也要记下：嵌套请求会把父请求时长拉长到包含人工响应时间，**实现者 MUST 确保传输超时足够长**（这条在 2.3 会再出现一次）。

### 2.3 elicitation：能做「平台主动问 Agent 一件事」吗？——不能

【规范】**状态：引入于 2025-06-18，规范原文自己声明「design may evolve」；2025-11-25 增加 URL 模式；2026-07-28 改为经 MRTR 承载。**

- 能力是真实的：可以带 JSON Schema 收集结构化输入，模式有 `form`（在带内收集）与 `url`（带外导航，敏感信息不过 client）。
- 三种结果动作：`accept` / `decline` / `cancel`。
- 客户端必须声明 `elicitation` capability，**服务器 MUST NOT 发送客户端未声明的能力**。

**但它做不了「平台主动问 Agent」**，两道锁：

1. **必须嵌套在客户端请求里**（[Elicitation 规范](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)原文：user input requests occur *nested* inside other MCP server features）。2026-07-28 起格式变为 `InputRequiredResult.inputRequests`，客户端**重试原请求**并带上 `inputResponses`（[MRTR](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr)）。
2. **SEP-2260 明确禁止独立发起**（见 2.2）。

另有一条安全硬约束：**Servers MUST NOT use form mode elicitation to request sensitive information**（密码、API key、token、支付凭据），这类交互必须走 URL 模式。

**对本项目的含义**：GM 想问 Agent/人一件事，只能在某次 `tools/call` 内部提；想「择机主动发起提问」，MCP 给不了。

### 2.4 一个被忽视的细节：Tasks 官方选择了「轮询是默认」

**【SEP】[SEP-1686 Tasks](https://modelcontextprotocol.io/seps/1686-tasks) —— Final，但已迁移。**

它先承认了裸轮询的问题（原文）：

> agent-driven polling is both unnecessarily expensive and inconsistent — it relies on prompt engineering to steer an agent to poll at all.

解决方案**不是**推送，而是协议级的 task primitive：客户端生成 taskId（为了幂等重试）、服务器发 `notifications/tasks/created` 让客户端开始轮询、并给 `pollFrequency` 建议值（requestor **SHOULD** respect this value）。

而在 2026-07-28，**Tasks 被移出核心协议，成为官方扩展**（[SEP-2663](https://modelcontextprotocol.io/seps/1686-tasks)）：`tasks/get` 轮询替换了阻塞式 `tasks/result`，新增 `tasks/update` 供客户端投喂输入，**并允许服务器「无需逐请求 opt-in 就主动返回任务句柄」**。

官方扩展文档 [MCP Tasks](https://modelcontextprotocol.io/extensions/tasks/overview) 把这件事说得毫无歧义：

> **Polling is the default.** If a server supports notifications, clients can rely on them instead of polling.

它还专门解释了为什么不用 4 种替代方案（tool-splitting、transport-layer、resource-based、每次能力声明）——其中对 resource-based 的批评很关键：*the resource subscription model ... as it is push-based, it requires clients to wait for notifications of resource changes rather than actively polling for status*。

**采用度警告**：Tasks 是 extension，**默认关闭、需显式 opt-in**；官方 [client-matrix](https://modelcontextprotocol.io/extensions/client-matrix)（社区维护）里 Claude web / Claude Desktop / VS Code Copilot / Cursor / ChatGPT 等主流客户端**一个都没有列出 Tasks 支持**；且 2025-11-25 那版实验性 tasks 全球只有 5 个 server 在用。

### 2.5 sampling：已 Deprecated

**【规范】[2026-07-28 弃用注册表](https://modelcontextprotocol.io/specification/2026-07-28/deprecated) 明确：**

| 特性 | 弃用版本 | 迁移路径 | 最早移除 |
|---|---|---|---|
| Sampling | `2026-07-28` | **Integrate directly with LLM provider APIs** | 2027-07-28 及以后的首个版本 |
| Logging | `2026-07-28` | stdio 用 stderr；可观测性用 OpenTelemetry | 同上 |
| Roots | `2026-07-28` | 用工具参数 / 资源 URI / server 配置传目录 | 同上 |

2025-06-18 那版 sampling 的语义（server 借 client 的 LLM 做推理、client 保持模型选择权、无 server API key）从设计上确实是「server 主动发起」，加上规范要求 human-in-the-loop 审批，实际可用性一直很差。**新实现不应该再基于 sampling 做任何设计。**

### 2.6 「MCP 作为推送通道」——官方正在做，但没做完

**【孵化】[MCP Triggers and Events Working Group](https://modelcontextprotocol.io/community/working-groups/triggers-events)**（Charter 创建于 2026-03-24，Lead 为 AWS 的 Clare Liguori 与 Anthropic 的 Peter Alexander）。Mission Statement 原文：

> Today, clients learn about server-side updates by **polling or holding an SSE connection open**. This WG will specify a standardized callback mechanism—**webhooks or similar**—that lets servers push notifications when new data is available, with defined ordering guarantees that hold across all transports.

几个必须知道的边界：

- **明确排除**「修改现有 notification 原语」（`notifications/resources/updated`、`notifications/tools/list_changed` 等），也排除 session 模型改动（归 Transports WG）。
- 与 Agents WG 有交叉：**SEP-1686 (Tasks) 把 webhook 式任务完成通知列为 future consideration，该机制归这个 WG**。
- 孵化仓库 [experimental-ext-triggers-events](https://github.com/modelcontextprotocol/experimental-ext-triggers-events) 顶部写着 **⚠️ Experimental ... do not represent official MCP specifications or recommendations**。
- **Active Work Items 表：`SEP: Events in MCP v1 RFC` 状态 = `Ideating`，Champion = TBD。**

**结论：截至 2026-10-13，MCP 官方承认「主动推送」是缺口、正在设计，但还没有可遵循的规范、没有 RFC、没有 champion。**

### 2.7 Streamable HTTP / SSE：一条已建立的连接上，server 能主动发业务消息吗？

这要分版本回答，而且答案在最新版变成了「不能」。

**【规范】2025-06-18 版 [Transports](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)** —— 这是本项目终端实际上跑的版本：

| 通道 | 规范原文 | 性质 |
|---|---|---|
| POST 响应流（SSE） | server **MAY** send JSON-RPC *requests* and *notifications* before the response. These messages **SHOULD** relate to the originating client *request*. | 措辞是 SHOULD，**不强制**关联 |
| GET 独立流（SSE） | server **MAY** send JSON-RPC *requests* and *notifications* on the stream. These messages **SHOULD** be unrelated to any concurrently-running request from the client. | 历史上唯一允许「unsolicited」的窗口 |

也就是说，**在 2025-06-18 上确实存在一条理论上能主动推的缝**——但 SEP-2260 要修的就是它（把 SHOULD 改成 MUST 关联），且原文说明其「use is entirely optional and cannot be relied upon by MCP Server authors」。所以**这条缝不能当地基**。

**【规范】2026-07-28 版 [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)** —— 缝被焊死了：

> The server **MUST NOT** send independent JSON-RPC *requests* on this stream. Server-to-client interactions (sampling, elicitation, list-roots) are embedded as input requests inside an `InputRequiredResult` per MRTR, **not delivered as separate requests on this or any other stream**. This is a change from Streamable HTTP in protocol versions `2025-03-26` through `2025-11-25`.

同版还：删除 GET 端点、删除 protocol-level session、删除 `Last-Event-ID` 断点续传（*A broken response stream loses the in-flight request; clients **MUST** re-issue it as a new request with a new request ID*）。

**唯一保留的「长连接」是 [`subscriptions/listen`](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions)，但它有白名单：**

```
toolsListChanged | promptsListChanged | resourcesListChanged | resourceSubscriptions[]
```

规范原文：**The server MUST NOT send notification types the client has not explicitly requested.** 且明确「Request-scoped notifications such as `notifications/progress` and `notifications/message` **continue to flow on the response stream of the request they relate to**, not the `subscriptions/listen` stream」。**业务待办不在白名单里。**

### 2.8 规范推荐什么替代方案？

**规范没有一句话直接写「你应该轮询」。** 但有四条互相印证的线索，指向同一件事：

1. **SEP-2260** 的 Implementation Guidance 给出的正式替代路径是：把「独立发起的请求」改成 **lazily perform these requests within the scope of a client-to-server request that requires that information**。翻译过来就是：**把主动推送降级为「客户端下次来的时候顺带处理」**——与本项目的「轮询 + 顺带投递」是同一个机制。
2. **Tasks 扩展**：*Polling is the default.*
3. **Triggers and Events WG** 把「migration guidance from polling-based approaches」列为自己的文档交付物之一 —— 官方把 polling 视为**现状基线**，要提供的是**从轮询迁移出去**的指南（还没写）。
4. **设计原则** [Design Principles](https://modelcontextprotocol.io/community/design-principles) 里的 **Composability over specificity**：*We don't add protocol features for use cases that can be constructed from these existing building blocks.* —— 现有 building block 就是「工具调用 + 返回内容」。

## 第三部分：Agent 间协议

### 3.1 Google A2A：状态、定位、落地

**状态**（[官方公告，2026-08-27](https://a2a-protocol.org/latest/blog/2026/08/27/a-new-chapter-for-a2a-joining-the-agentic-ai-foundation/)）：

- 已被 **Agentic AI Foundation (AAIF)** 接受为 **Growth Stage** 项目；AAIF 是 **Linux Foundation** 旗下。
- **与 MCP 同一个基金会**（AAIF 其他项目：MCP、goose、AGENTS.md）。公告原文：*By operating under the Linux Foundation-directed AAIF alongside sibling projects like MCP...*
- 稳定 **v1.0** 规范已发布；**超过 150 家组织**支持。
- 声称的生产落地：供应链、金融服务、移动平台；Google Cloud、AWS Bedrock AgentCore Runtime、Microsoft Azure AI Foundry 原生支持；企业 SaaS 侧 ServiceNow、Salesforce、Atlassian、SAP 用它连接跨产品工作流；框架侧 LangGraph、CrewAI、Pydantic AI、AG2、IBM BeeAI。

> 注：「已捐给 Linux Foundation」这个问法的答案是：**已捐，但不是直接捐给 LF 本体，而是捐给 LF 旗下的 AAIF，且与 MCP 同门。**

**与 MCP 的分工**（[A2A 官方 MCP 对比页](https://a2a-protocol.org/latest/topics/a2a-and-mcp/) 的原文框架）：

> **MCP is vertical.** It deepens a single agent. ... **A2A is horizontal.** It connects agents across that boundary.
> Used together, MCP gives each agent **depth**, and A2A gives your system **reach**.

官方还专门讨论了「A2A Agent 是否可以表示为 MCP Resource」：可以，但只适合**well-defined、可被 tool-like 无状态调用**的技能；A2A 的核心价值在于*stateful, collaborative interactions that go beyond a typical tool call*。

### 3.2 A2A 解决什么问题（数据结构层面）

核心对象（[Core Concepts](https://a2a-protocol.org/latest/topics/key-concepts/)）：

| 对象 | 作用 |
|---|---|
| **Agent Card** | JSON 元数据文档：身份、能力、endpoint、技能、认证要求 → 支撑**发现** |
| **Task** | 有唯一 ID 与明确生命周期的**有状态工作单元** → 支撑长任务跟踪与多轮协作 |
| **Message** | 一轮通信，role = user / agent |
| **Part** | 内容容器：`text` / `raw` / `url` / `data`（结构化 JSON） |
| **Artifact** | Agent 在任务中产出的**可交付物**（有 `artifactId`、name、可增量流式传输） |
| **contextId** | 服务器生成的标识符，**把多个 Task 和独立 Message 归到一组** |

**交互机制三种**（这是 A2A 最值得本项目借鉴的部分）：

- **Request/Response (Polling)** —— 客户端轮询
- **Streaming with SSE** —— 低延迟增量
- **Push Notifications** —— *The server calls a client-provided webhook on a significant task update. This suits very long-running tasks or disconnected clients.*

### 3.3 A2A 的 Push Notification 长什么样（本项目应直接照抄的安全清单）

源自 [Streaming & Asynchronous Operations](https://a2a-protocol.org/latest/topics/streaming-and-async/)：

- **能力声明**：server 在 Agent Card 里设 `capabilities.pushNotifications: true`。
- **配置对象** `TaskPushNotificationConfig`：`url`（HTTPS webhook）+ 可选 `token`（供客户端校验）+ 可选 `authentication`（供 server 认证到 webhook）。可在初始 `SendMessage` 里给，也可用 `CreateTaskPushNotificationConfig` 单独给。
- **触发时机**：由 server 自行决定，典型是 terminal state、`input-required`、`auth-required`。
- **载荷**：`StreamResponse` 对象，与流式操作同格式。
- **客户端收到后**：用 `GetTask` + `taskId` 拉完整任务（**推送只做「叫你一声」，不搬运完整状态**）。

安全要求（双向、写得很细，可直接作为本项目的检查表）：

- Server 侧：**SHOULD NOT 盲信客户端给的 URL**（SSRF / DDoS 放大器风险）→ 域名白名单、所有权验证（challenge-response）、egress 防火墙；**MUST** 按配置的方案认证到 webhook（Bearer/API key/HMAC/mTLS）。
- 接收侧：**MUST** 严格验证来源（JWT 签名对 JWKS、HMAC、API key），校验 `TaskPushNotificationConfig.token`；**SHOULD** 用 timestamp 拒绝过旧通知，关键通知用一次性 ID（JWT `jti` / event ID）防重放；密钥轮换用 JWKS。

### 3.4 重点：这些协议里有没有「收件箱 / 任务委派 / 审批」的标准形态？

**A2A 有，而且是明确的。** 逐条对照：

**① 任务委派（有）**
`SendMessage` 建任务 → server 返回 `Task`（含 `taskId` + `contextId` + `status`）。后续跟进：同 `contextId` 发新 Message，用 `referenceTaskIds` 指回原任务；`contextId` 还支持**并行 follow-up**（官方例子：Task1 订机票 → Task2/3 基于 Task1 并行订酒店与雪地摩托 → Task4 基于 Task2 加 SPA）。

**② 收件箱（有，形态是「任务列表 + 状态」）**
A2A 的方法集就是一套 inbox API：

| 方法 | 作用 |
|---|---|
| `SendMessage` / `SendStreamingMessage` | 投递 / 建任务 |
| `GetTask` | 取单个任务完整状态 |
| **`ListTasks`** | **列出任务（可按 context 过滤、分页）** ← 这就是「收件箱」 |
| `SubscribeToTask` | 断线后重新订阅某任务的更新流 |
| `CancelTask` | 取消 |
| `Create/Get/List/DeleteTaskPushNotificationConfig` | 推送配置管理 |

规范里 `ListTasks` 的示例查询包括 *All tasks from a specific context*、*All working tasks across all contexts*。**这就是「Agent 的待办落在平台上、不依赖它的上下文记忆」在协议层的标准表达。**

**③ 审批请求（有，但不是独立对象，是状态 + 带外凭据）**
A2A 的任务状态（[TaskState](https://a2aproject.github.io/a2a-java/1_2_0_Final/apidocs/org/a2aproject/sdk/spec/TaskState.html)，另见 [Life of a Task](https://a2a-protocol.org/latest/topics/life-of-a-task/)）：

- 终态：`completed` / `failed` / `canceled` / `rejected`
- **中断态**：**`input-required`**、**`auth-required`**

`input-required` 就是协议层的「需要人/上游给一个答复才能继续」；`auth-required` 就是「需要授权」。规范还给了两条工程规则：**任务到达终态后不可重启**（任何 refine 必须在同 `contextId` 下新建任务，保证 task 不可变、溯源干净）；**审批类交互的凭据不放在任务对象里**，而由第 7 章的 in-task authorization 与带外流程处理。

> 一句话：A2A 把「审批」建模为 **任务进入 `input-required` / `auth-required` + 推送通知 + 带外凭证**，而不是发明一个 `Approval` 对象。这个建模方式比自造审批对象更耐用。

### 3.5 AG-UI 解决什么

[官方介绍](https://docs.ag-ui.com/introduction)：**开放、轻量、事件驱动**的协议，标准化 **AI Agent 如何连接面向用户的应用程序**。

官方对三件套的分工（[MCP, A2A, and AG-UI](https://docs.ag-ui.com/agentic-protocols)）原文：

> **MCP** Connects agents to **tools and context**. / **A2A** Connects agents to **other agents**. / **AG-UI** Connects agents to **users** (through user-facing applications). ... AG-UI as the "kitchen sink" protocol.

概念面覆盖：Events、Messages、State Management、**Interrupts**、Tools、Subagents、Capabilities、Generative UI Specs。已有 1.0 规范与 TS/Python/.NET SDK，且「AG-UI contributors have recently added handshakes, allowing AG-UI to 'front for' agents through MCP and A2A」。

**对本项目的意义**：GM 与人的交互（审批弹窗、进度展示、人在回路）如果要做 Web 端，AG-UI 是比自研 SSE 协议更标准的选择；但它**不解决 Agent 之间的待办投递**，所以不替代本项目对 inbox 的需求。

### 3.6 其他协议：ACP 已并入 A2A，ANP 是另一个方向

- **ACP（Agent Communication Protocol）—— 已终止独立发展。** [官网首页](https://agentcommunicationprotocol.dev/introduction/welcome) 顶部横幅原文：**「ACP is now part of A2A under the Linux Foundation!」**，并附 [迁移指南](https://github.com/i-am-bee/beeai-platform/blob/main/docs/community-and-support/acp-a2a-migration-guide.mdx)。ACP 原本是 IBM/BeeAI 主导的 RESTful agent 协议（Async-first、无 SDK 必需、离线发现），现在其能力由 A2A 的 HTTP+JSON/REST binding 承接。**结论：新设计不必考虑 ACP，选 A2A 即覆盖。**
- **ANP（Agent Network Protocol）** —— 方向是**去中心化的 agent 身份与描述**，走 W3C Web Agents CG 通道（[2025-02 邀请演讲](https://lists.w3.org/Archives/Public/public-webagents/2025Feb/0001.html)、[2025-11-12 W3C 会议](https://www.w3.org/events/meetings/aaf35157-20e5-47f8-91a7-2db38aeb3cfc/)）。解决的是「跨组织、无需中心登记处地发现和信任一个 agent」，与本项目「企业内部团队协作」的诉求距离较远；**若将来要对外开放到多家公司互操作才有意义**。
- **MCP-AX（IETF draft）** —— 严格说不是 agent 间协议，而是 **MCP 聚合协议**，但对本项目的第三条设计直接相关，见第四部分。

## 第四部分：结论

### 4.1 「轮询 + 顺带投递、不做推送」在 MCP 规范下是否成立？

**成立，而且是规范下唯一稳妥的选择。** 三条独立证据：

1. **规范禁止了替代方案。** [SEP-2260](https://modelcontextprotocol.com.cn/seps/2260-Require-Server-requests-to-be-associated-with-Client-requests.md)（Final）禁止 standalone server-initiated requests，并明确把「background task 里主动 push」列为 PROHIBITED。2026-07-28 进一步用 MRTR 把 server-initiated requests 整个模式换成「客户端重试原请求」。
2. **官方在 Tasks 里选了同一个默认。** [MCP Tasks 扩展](https://modelcontextprotocol.io/extensions/tasks/overview)：*Polling is the default.* 且其 [SEP-1686](https://modelcontextprotocol.io/seps/1686-tasks) 虽然承认裸轮询「昂贵且不一致」，但解法是**协议级任务句柄 + 建议轮询间隔**，不是推送。
3. **推送本身在官方那里还没设计出来。** [Triggers and Events WG](https://modelcontextprotocol.io/community/working-groups/triggers-events) 的 RFC 状态是 `Ideating`、champion `TBD`；孵化仓库自我标注为 experimental、不代表官方规范。

**有没有更好的现成方案？有一个，但不完全覆盖：**

- **最接近的可选项是官方 Tasks 扩展**（[官方 doc](https://modelcontextprotocol.io/extensions/tasks/overview)）——它比「顺带投递」更能解决「长任务」这个场景，且有 `input_required` + `tasks/update` 的中途交互语义。**但它是 extension、默认关闭、需要客户端显式 opt-in，而官方 client matrix 里主流客户端一个都没列。** 所以它今天只能作为「将来的对齐目标」，不能作为依赖。
- **需要注意：本项目「顺带投递」与 Tasks 解决的问题并不完全重叠。** Tasks 解决的是「我发起的那个调用很久没返回」，而本项目的 GM 场景是「**没有任何调用在飞行时**，平台侧发生了一件事，需要告知 Agent」。后者在 MCP 里**完全没有任何原语**——这正是 Triggers & Events WG 要补的洞。

**规范的推荐替代方案（明确写出来的部分）**：SEP-2260 的 Implementation Guidance 给的是 **lazily perform these requests within the scope of a client-to-server request** —— 即「等客户端下次来的时候顺带做」。这与本项目的设计完全一致。

### 4.2 协作类 MCP 工具有现成可复用的吗？

**没有可直接复用的。可参考的三个来源：**

| 来源 | 可参考什么 | 成熟度 |
|---|---|---|
| [Routa](https://github.com/phodal/routa) | 「看板即协调总线」的完整设计：lane specialist、上游产物不被下游信任、evidence contract、Review gate | MIT，活跃，但面向代码交付 |
| [jentrix-au/stacks-ai](https://github.com/jentrix-au/stacks-ai) | 「人和 Agent 共用一个 board，通过内置 MCP server 操作」的产品形态 | 开源、可自托管 |
| [IBM ContextForge](https://ibm.github.io/mcp-context-forge/latest/best-practices/selecting-an-mcp-gateway/) | 企业级 MCP+A2A 网关的完整能力清单与[通知服务 ADR](https://ibm.github.io/mcp-context-forge/latest/architecture/adr/034-centralized-notification-service/) | Apache 2.0，IBM 内部 16 万+ 用户生产验证 |

**ContextForge 的 ADR-034 特别值得读**，它做了与本项目同构的一件小事：把所有 MCP 通知集中到一个服务，对高频 `list_changed` 做**默认 5 秒防抖**合并。它明确拒绝的方案之一就是 *Polling Only: Rejected: Inefficient.* —— 也就是说，**网关厂商在「协议状态同步」上用事件、在「业务待办」上另行设计**，这个分界与本项目的判断一致。

**官方参考 server 里没有任何任务/协作类，且明确标注「not production-ready」。**

### 4.3 A2A 值不值得在设计中考虑？

**值得，但要分清「现在用什么」和「将来对齐什么」。**

**现在就值得吸收的是它的数据模型，而不是它的传输：**

- **别自创待办对象的词表。** 用与 A2A Task 状态机同构的状态集：`submitted / working / input_required / completed / failed / cancelled`（A2A 另有 `auth-required`、`rejected`）。将来要对接 A2A 时是映射，不是翻译。
- **别自造审批对象。** 审批 = 任务进入 `input_required`（或 `auth-required`）+ 通知 + 带外凭证。A2A 就是这么建模的。
- **别自研推送安全方案。** A2A 那套双向验证清单（SSRF 防护 + JWT/JWKS + timestamp + 一次性 ID + token 校验）是现成的规范，照抄即可。

**将来让别的 Agent 平台接入时，A2A 是目前唯一有网络效应的选择：**

- 与 MCP 同属 AAIF/Linux Foundation，不存在治理对冲；
- 150+ 组织、主流云与 SaaS 原生支持；
- 官方明确 A2A 与 MCP 是互补而非竞争（垂直 vs 水平）；
- **ACP 已并入 A2A**，避免了在多个候选协议里下注。

**一条务实的判断**：本项目对外的 MCP 接口是「垂直」能力（GM 是工具/资源），将来别的平台要把本平台当作**一个 Agent** 来协作，那才是 A2A 的介入点。所以 **MCP 先行、A2A 留接口** 是对的次序——只要现在不做出与 A2A 数据模型冲突的设计。

### 4.4 第三条设计（外部能力经平台中转）的规范支撑

这条设计同样有据可依：

- **【提案】[MCP-AX（IETF draft-abbott-mcp-ax-00）](https://datatracker.ietf.org/doc/draft-abbott-mcp-ax/00/)** —— 定义了 Aggregator / Subserver 架构、**递归命名空间委派**（`infra.edge.stm32h7.dma2d_status`）、`tools/list` 递归聚合与 `tools/call` 路由。四条对本项目直接适用的规范要求：
  1. **逐跳独立鉴权**：*Each aggregation boundary is an authentication boundary. Credentials **MUST NOT** be forwarded across aggregation hops.*（原文点明这是 SNMP community string 的教训）
  2. **作用域限制**：注册为 `read` 的 subserver **MUST NOT** 收到 write/admin 操作。
  3. **命名空间防冒用**：**aggregator 是前缀分配的唯一权威**，subserver 不得自带前缀。
  4. **不可逆性门控**：`reversible: false` 且 `mutable: true` 的工具标记 `irreversible_mutable`；gated 模式下 aggregator **MUST** 拦截 `tools/call`，返回 `confirmation_required`，等 `mcpax/confirm`（**带外部签名的 `proof` 字段**）才真正下发。原文解释为什么必须有 proof：*Without this requirement, an autonomous model client can trivially self-confirm ... rendering the gate ineffective.*
- **【第三方】[IBM ContextForge](https://ibm.github.io/mcp-context-forge/latest/best-practices/selecting-an-mcp-gateway/)** —— 生产级实现，给出了「虚拟服务器」（按团队/Agent 组合工具子集，最小权限）、team-scoped RBAC、零信任密钥注入（Agent 只拿到 scoped token，永不接触原始 key）、审计追踪等具体做法。

**注意 MCP-AX 是 Individual Internet-Draft，不代表 IETF 背书，也无 RFC 地位——可以借鉴设计，不能引用为规范。**

### 5.1 通知/待办投递（设计 1）

1. **保持「不做长连接推送」的决定**，理由从「工程取舍」升级为「规范遵从」——引 SEP-2260 Final 即可说服评审。
2. **顺带投递的位置要设计对**：建议在**每个** `tools/call` 的 result 里带一个轻量字段（如 `_meta.pending_notifications` = `{count, items[], cursor}`），**同时**在 `content` 的文本里留一行人话摘要。原因：不同终端对结构化 `_meta` 的处理能力不一致，纯文本兜底能保证 Claude Code / 自写脚本都不会漏。
3. **必须补一条兜底通道，这条是硬需求**。顺带投递的语义是「有调用才有送达」，而 GM 的价值恰恰在「没人调用时也能建任务」。**平台侧必须有独立的、与 MCP 无关的送达路径**（定时唤醒、企业 IM 出站、或人看的看板）。**否则「GM 主动建任务」在产品上是静默失败的。**
4. **将来与 MCP Tasks 对齐的钩子**：把通知/任务对象的字段名对齐官方 Tasks 扩展（`status` / `taskId` / `pollIntervalMs`），一旦目标客户端支持 Tasks 扩展，可平滑迁移到「服务器主动返回 task 句柄 + 客户端轮询」。**现在不要依赖它**——extension 默认关闭，且主流客户端支持矩阵里一个都没有。
5. **接口对齐协议版本 2025-06-18**，这是生态 86% 的版本。同时**不要**把新特性当基础：`subscriptions/listen`、MRTR、`server/discover`、无 session 模型都属于 2026-07-28，今天接不上。

### 5.2 收件箱（设计 2）

1. **形态建议：任务对象 + 游标式列表接口**，而不是消息队列。理由：A2A 的 `ListTasks` 就是这个形态（支持按 context 过滤、分页），且任务对象天然带生命周期，符合「Agent 的待办落在平台上、不依赖上下文记忆」。
2. **状态集直接采用**：`submitted → working → input_required → completed / failed / cancelled`（可选 `auth_required`）。**这套词表同时兼容 A2A TaskState 和 MCP Tasks 扩展状态**，一次设计两头通。
3. **加游标/幂等语义**。MCP 是跨连接的、且 2026-07-28 起规范明确「无状态、连接不等于会话」，所以投递必须**幂等到「同一 Agent 重复拉取不产生副作用」**，并用游标（`since_id` / `cursor`）而非「已读未读」布尔位。
4. **inbox 里的项要能「被回答」而不只是「被读」**。参照 A2A `input-required`：每条待办应带 `reply_required: true/false`，需要回答的项由 Agent 调用一个回复工具提交，而不是靠它记住。

### 5.3 外部能力经平台中转（设计 3）

1. **方向正确，且有规范级支撑。** 按 MCP-AX 的四条硬要求做：逐跳独立鉴权、不跨跳转发凭据、作用域限制（read 注册的 subserver 收不到 write 操作）、**聚合器是命名空间前缀的唯一权威**（防止外部 MCP 冒用别的命名空间）。
2. **工具命名空间用 `<vendor>.<server>.<tool>` 点分前缀**，并在 `tools/list` 里透传能力注解（至少含 `mutable` / `reversible` / `latency_class`）。理由：**聚合器是唯一看得见爆炸半径的地方**，注解是让上游做策略的前提。
3. **高风险工具必须做门控，且 proof 不能自签**。若某个外部操作不可逆，平台要拦截并返回「需确认」，确认凭据必须来自**请求方之外的信任锚**（人工签名 / 策略引擎签的 nonce / 带外审批服务）。MCP-AX 的原话值得贴在设计文档里：*Without this requirement, an autonomous model client can trivially self-confirm ... rendering the gate ineffective.*
4. **注意工具契约漂移**（第三方测量：36 小时内 4.4% 的 server 改了契约，且只有 18% 声明 `outputSchema`）。中转层应做**契约快照 + 变更告警**，否则 GM 会基于一个已经不存在的工具契约建任务。
5. **参考 ContextForge 的「虚拟服务器」**：不是把外部 MCP 的全部工具直接透出，而是按 Agent/团队组合白名单子集——既是最小权限，也顺带解决了工具爆炸导致的提示词膨胀。

### 5.4 与 A2A 的关系：留接口，不现在实现

1. **现在做**：把 inbox/任务的状态词表、`contextId`（把相关任务归组，支持并行 follow-up）、`Artifact`（任务产出物）这三个概念先在自己的数据模型里定好，命名对齐 A2A。成本是零，收益是将来能映射。
2. **将来做**：当有外部 Agent 平台要接入时，再实现 A2A 的 HTTP+JSON/REST binding（`SendMessage` / `GetTask` / `ListTasks` / push notification config 四件套），把本平台暴露为一个 A2A Server。**此时 MCP 侧接口不用动**——A2A 官方明确二者互补。
3. **不要投注 ACP**。ACP 已并入 A2A（官网横幅原文可引用），选 A2A 即覆盖其能力。
4. **如果要做面向人的界面**（GM 的审批弹窗、进度展示、人在回路），把 **AG-UI** 列入候选，而不是自研 SSE 事件协议；它已有 1.0 与三套 SDK，且官方支持通过 MCP/A2A 握手来「front」agent。

### 5.5 三条需要盯着的信号

1. **MCP Triggers and Events WG 的 RFC** —— 一旦该 SEP 落地，本项目「不做推送」的取舍值得重估。当前状态：`Ideating`，champion `TBD`。盯 [charter 页](https://modelcontextprotocol.io/community/working-groups/triggers-events)的 Active Work Items 表。
2. **MCP Tasks 扩展的客户端采纳** —— 盯 [client-matrix](https://modelcontextprotocol.io/extensions/client-matrix) 是否出现 Tasks 列，以及 Claude Code / DSH 是否支持。一旦支持，可以把「顺带投递」升级为「服务器返回 task 句柄 + 客户端按 `pollIntervalMs` 轮询」。
3. **生态协议版本迁移** —— 盯 [State of the MCP Registry](https://operatorsheets.github.io/state-of-mcp/) 的版本分布表。当 2026-07-28 版本占比抬头时，`subscriptions/listen` 与 MRTR 才值得接入。

## 附：规范未规定的事项（明确列出，不要猜）

- **「业务待办通知」在 MCP 中没有任何原语、任何语义、任何保留字段。** 规范未规定，不要指望将来向下兼容——Triggers & Events WG 的产出会是**新机制**。
- **MCP 规范没有「收件箱」概念**，也没有「任务列表」概念（实验性 tasks 只有 `tasks/list`，且已在 2026-07-28 被移除，改为 `tasks/get` 轮询）。
- **规范没有规定「Server 应该怎么提醒客户端有别的事」**。SEP-2260 只规定了「不许主动发起」，没有规定「那该怎么做」。
- **A2A 规范没有 `Approval` 对象**。审批由 `input-required` / `auth-required` 状态 + 带外授权表达（第 7 章 in-task authorization），不要去找一个不存在的审批类型。
- **A2A 的 artifact 版本链不属于协议规范**。官方明确：*this linkage is not part of the A2A protocol specification*，由客户端自己维护版本历史。
- **MCP registry 是目录不是质量信号**。官方测量（第三方）显示 19% 端点真的坏了，且「刚更新过 registry 条目」与「端点可用」不相关（被取代的 server 中 42% 新旧地址都死了）。

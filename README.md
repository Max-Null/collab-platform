# collab-platform

人和 AI Agent 共用的团队协作平台。

**它防的是一类特定的东西：静默失效** —— 不报错、不崩溃、只是安静地走错的事。协作里它长这样：**没有人说「这条我看过」，于是「没人看」和「看过了没问题」长得一模一样。**

核心角色是 **GM**（常驻、订阅协作事件流、主动判断、在授权范围内行动、把依据留下来），但 GM 只是这条链路上的执行者 —— 完整的设计见 **[平台设计](docs/平台设计-2026-10-14.md)**。

> 工作名，正式名称待定（见 `docs/待决问题.md` 第 5 条）。
> 📖 **[文档索引](docs/README.md)** —— 16 份文档分了「结论 / 事实记录 / 过程材料」三层，从那里读起。

## 现在什么状态

**功能齐、测试绿、随时能启用。** 但它**没有在真实团队里跑过** —— 得说清这意味着什么：

| 已经验证过的 | 还没验证过的 |
|---|---|
| 四段链路在**真实模型**（qwen3.6-plus）与**真实 GitLab** 上跑通：判定过真实的提交与 MR，并抓到过一次真实的「改动与声称不符」（在一个 `changeStatus` 方法里加了入参判空与错误返回，而提交消息没提） | **没有人在真实工作流里回写过反应** —— 观察期那一层全靠这个，所以它等于没被验证 |
| 常驻轮询、幂等、干燥跑、撤销、MCP 出口、控制台、守卫，都有实测证据 | **写开关从没打开过** —— 平台从未往任何仓库发过一条评论 |
| 测试全绿 + 单一事实源守卫 | **两级以上的策略冲突没发生过**（只有两条策略） |

**一句话**：它能跑，也跑对过；但**「有人在用」这件事没有发生**，而一批设计（观察期、升级判据、双轨、记忆的毕业路径、控制台待办）全都建立在它之上。

> 那批东西的准确说法是「**设计好了**」，不是「**能用了**」。

## 当前实现

| 段 | 当前实现 |
|---|---|
| ① 事件 | `MockEventSource`（本地样例）／ `GitLabPollSource`（**只读**轮询合并请求）／ `GitLabPushSource`（**只读**轮询分支提交 —— 团队不用 MR 时，只订阅 MR 等于什么都看不到） |
| ② 策略 | `review-sensitive-path`（纯规则：路径匹配）· `review-claim-mismatch`（LLM 判据：改动与声称是否相符） |

| ④ 留痕 | `RecordStore`（SQLite）—— 判断记录，含结论、依据、取数来源、判断模型、外部引用、撤销时刻 |
| 运行 | CLI（跑一次）· `npm run watch`（常驻轮询，**每轮落一条心跳**）· `npm run console`（控制台：**第一屏是项目**，平台自身的状态收成顶栏一个徽标）· MCP 出口 |
| 对外 | MCP 工具 + 一份[使用指引](skills/platform-usage/SKILL.md)（**能力与用法是两回事**） |

测试覆盖：glob 边界、三态结局、留痕完整性、观察期统计（含「看过」分母）、评论正文格式、gather 白名单边界、GitLab 轮询合成、写开关关与开、写失败如实报错、幂等、撤销、模型用量的解析与渲染边界、装配期的配置校验、**平台状态的四种判定**（从没跑过 / 在跑 / 迟了 / 已经停了，以及心跳不进任何观察期分母）、**推送事件源的合并跳过**（合并提交的 diff 是合集，不跳过就会重复计数）、**令牌过期自愈**（401 换一个再重发，且只重试一次）、**心跳格带**（空白必须留成空隙、片宽随跨度伸缩、一片里有失败就算没成）、**简报的纪律**（没内容就不发）、**观察表点图的数据通路**（逐条而非从聚合数字反推）、**项目视图的聚合**（一次变更的定论取最严不取多数、按紧急度而非时间排、老记录不许补一个假项目名、快照字段坏掉不让整页打不开），以及一条端到端（模型响应 → 判断记录）—— **最后那条是刻意的**：链路上少接一根线，零件测试照样全绿。另有 `check-ssot.mjs` 守「同一句话不许有两份」——**它自己用人造漂移夹具验证过有效**。

## 跑起来

```bash
npm install
npm test        # 编译 + 跑测试 + 跑守卫
npm run demo    # 编译 + 用样例事件跑一遍，带观察期统计
```

需要 Node ≥ 22.5（用到内置的 `node:sqlite`，启动加 `--experimental-sqlite`，已写进 npm scripts）。

### 接真实 GitLab

```bash
$env:GITLAB_BASE_URL = "https://gitlab.example.com"
$env:GITLAB_PROJECT  = "my-group/my-app"

# 首选：Personal Access Token（不过期，权限可以只给 read_api）
$env:GITLAB_TOKEN    = "<PAT>"

# 备选：用户名 + 密码换 OAuth 令牌（两小时过期，只适合先跑起来看一眼）
# $env:GITLAB_USER     = "<用户名>"
# $env:GITLAB_PASSWORD = "<密码>"

node --experimental-sqlite dist/src/index.js --source=gitlab --stats
```

两种形态发的头不同（`PRIVATE-TOKEN` / `Authorization: Bearer`），由平台按你给的变量选，不猜前缀 —— 猜错的表现是 401，跟「令牌真的错了」分不开。

再配 `GITLAB_WRITE=true` 才会真的往 MR 发评论；**不配就是干燥跑**，正文照常渲染并落到 `var/comments/`。

`GITLAB_MR_STATE` 默认 `opened`；设成 `all` 可以拿**历史 MR** 做演练 —— 只读、现成、早就没人会因为它多出一条评论而受影响。`GITLAB_MR_LIMIT` 默认 20。

### 不让它悄悄死掉：看门狗

常驻会**静默死掉** —— 2026-10-16 实测过一次：没有报错、没有遗言，`err.log` 是空的、
`out.log` 停在六轮完全正常的记录之后。发现它的是一张图，而我恰好打开看了一眼；
**半夜死掉就没人知道**。

所以有一个系统计划任务每 5 分钟检查一次：

```powershell
schtasks /Query /TN collab-platform-watchdog    # 它跑没跑、上次结果
Get-Content var/watchdog.log                    # 它做过什么（健康时这个文件不增长）
```

判据是**心跳的沉默时长**：日志每轮都写，所以它的修改时间就是最后活动时间；
超过 20 分钟就动手 —— 进程还在就先杀掉（那是卡住了，不杀会跟新进程抢同一个日志文件），
然后起一个新的。

⚠️ **阈值是 20 分钟而不是 5**：机器休眠唤醒后常驻要等一轮才写日志，
卡太紧会把好端端的进程重启掉 —— 而**一个误报率高的看门狗，最后会被人关掉**。

⚠️ **用计划任务，不用常驻的守护进程**：守护进程自己也会死，而死掉的守护进程
不会告诉你它死了 —— 那正是它要防的问题。计划任务由系统调度，不依赖任何活着的进程。

⚠️ **它健康时一个字都不写**。会定时汇报「一切正常」的看门狗，与没有看门狗是一回事。

### 控制台：第一屏是项目，不是仪表盘

```bash
npm run console        # http://127.0.0.1:8790
```

打开它就是三块项目方块：**哪个仓库要你管几件**、哪个暂时安静。下面是「要你管的」，分两组 ——
**判断没做成**（斜纹底）与**命中**（实心边框）。要点开看原因、要表态，都在那一屏里完成。

**为什么不是一张平台运行仪表盘。** 那版第一屏的第一句话是「从没跑过」，第二块是库文件路径，
第三块是「事件 3 → 判定 6 → 表态 3 → 留痕 6」。它回答的全是「这个平台自己活得怎么样」，
而管理员打开控制台问的是「我的仓库现在怎么样」——两者不是同一个问题，混在一屏的结果是
**他得先学会运维概念，才看得懂自己的项目**。

**为了让「项目」成为第一屏，数据层补了一列。** 判断记录原本不存 `project / author / title /
changed_files`，于是库是一本**按策略记的账**（哪条策略判了多少次），而项目视图要的是
**按变更记的账**。界面变不出一份不存在的数据，所以这四列是先补的，界面是后改的。

**四种空法，四件不同的事**（这是全篇那条判据落到它自己第一屏上）：

| 状态 | 界面说什么 | 为什么不能混 |
|---|---|---|
| 常驻在跑、有数据 | 不提示 | 主场景 |
| 常驻在跑、一条没判过 | 「在看，但还没有变更进来」 | 查订阅分支对不对 |
| 常驻没跑、库里有数据 | **红色**：「底下这些是旧数据，平台现在没在看」 | 与「最近真的没有变更」长得一模一样 —— 不区分，就会把「没人盯着」读成「没事发生」 |
| 一条记录都没有 | 「还没有东西进来过」 | 不是「项目很干净」 |

⚠️ 「从没跑过」与「跑过但停了」也是两种状态（前者还没部署，后者是挂了），所以顶栏徽标
分四种而不是两种。

### 链路图（活点地图）

一张图回答「这个平台是怎么工作的」，而且**叠着此刻的真实状态**：

```bash
npm run diagram:live   # 从 archify 的产物 + 当前库，生成到 var/diagram/live.html
npm run console        # 然后打开 http://127.0.0.1:8790/diagram
```

图本身画的是**设计上的链路**（谁在什么时候把东西交给谁），叠上去的是**每一步此刻的状态** ——
哪一步在失败（红点）、哪一步在等人（黄点）。两者缺一不可：只有设计，看不出「现在断在哪一步」；
只有状态，看不出「它本来该往哪走」。

⚠️ **两种打开方式，看的是两种东西**：

- **从控制台打开**（`/diagram`）：页面 fetch `/api/overview`，看的是**此刻**。
- **双击那个 HTML 文件**（`file://`）：看的是**生成那一刻的快照** —— 状态在生成时就烤了进去，
  页头会写明快照时刻（「状态快照 · 10-16 15:20 生成，**不是现在**」）。
  `file://` 下浏览器禁止 fetch，所以只能这样；好处是这份文件可以直接发给别人。

一份文件两种用法，但**任何时候都得知道自己在看哪一种** —— 一份看不出时刻的快照，
与「此刻」长得一模一样。同理：真拉不到状态时页面会**明说**，绝不静默留白，因为
「图上没有标记」与「一切正常」也长得一模一样。

图的源稿在 `docs/report/控制流-一次变更的生命周期-*.html`（archify 生成，几何与配色都由它保证）。
`npm run diagram:live` **只注入状态层，不改源稿** —— 所以图重新生成之后重跑一次这个命令即可。

### 让它常驻跑（不是手工跑一次）

```bash
npm run watch                                        # 前台常驻，每 300 秒一轮
node dist/src/daemon.js --source=mr --state=opened   # 订阅合并请求
node dist/src/daemon.js --source=push --branch=test  # 订阅某个分支上的提交
node dist/src/daemon.js --source=mr,push             # 两个都订阅（⚠️ 见下）
node dist/src/daemon.js --once                       # 只跑一轮就退出，用来试
```

**默认订阅 push，不是 MR。** 这个默认值匹配的是**团队的实际形态**，而不是设计中的形态：
接入记录里那三个仓库合计 3 条 MR，而提交是活跃的 —— 实际工作方式是「功能分支直接推 `test`」。
只订阅 MR 的平台上，每轮都成功、每轮都是 0 个事件，**而它自己看不出这与「真的没有变更」的区别**。

⚠️ 两个都订阅时，MR 合并后的那些提交会各自再报一次（同一处变更判两遍），
而观察期的分母最怕重复计数 —— 团队真的开始走 MR 之后，应当只留 `mr`。

**为什么需要它**：**一个要人手动触发的闸门等于没有闸门。** 手工跑只能验证代码对不对，不算平台在工作。常驻之后，有人在 GitLab 提了 MR，它下一轮就会判、会留痕。

**四条刻意的设计**：

- **一轮失败不让进程死** —— GitLab 抖一下、模型超时一次，下一轮继续。一个跑着跑着悄悄死掉的守护进程比没有更坏：**它的失效形态正是这个平台在防的那一类（看起来在跑，其实早就不跑了）**
- **写开关与它无关** —— 常驻只解决「什么时候看」，不解决「要不要说话」。`GITLAB_WRITE` 默认关，在真仓库上开写是另一件要单独决定的事
- **每轮都打一行统计**，哪怕什么都没发生 —— 否则「没有输出」同时意味着「这轮没有新变更」和「这轮挂了」
- **跳过已判过的不打日志** —— 20 条 MR × 2 条策略就是每轮 40 行，会把真正该看的行淹掉

**怎么让它一直跑**（这一层交给环境，平台不假设）：前台挂一个终端、或用系统的计划任务/服务管理器把它拉起来。⚠️ 目前没有做开机自启 —— 那取决于它跑在哪台机器上。

### 撤销一次已经发出去的动作

```bash
npm run undo -- --judgment 12            # dry-run：只打印将要发生什么
npm run undo -- --judgment 12 --apply    # 真删
```

**为什么要有它**：动作的三条件是「**退出 / 幂等 / 回滚**」，而**回滚原本是唯一空缺的那条** —— 本地评论删个文件就完了，发到 GitLab 的评论却收不回来。这条空缺只在写开关打开之后才成为真问题，所以更该在那之前就位。

**三条刻意的设计**：

- **默认 dry-run** —— 撤销是不可逆的写操作，「先看见将要发生什么」是它该有的默认姿势
- **不删判断记录，只标 `undone_at`** —— 「发出去了又收回」本身是该看得见的一件事，不是一件应该消失的事
- **找得到才撤** —— 没有记下外部引用（`externalRef`）的判定直接拒绝，**不猜**。猜错意味着删掉别人的评论，那比不撤严重得多

### 现有动作过一遍三条件

| 动作 | 退出 | 幂等 | 回滚 |
|---|---|---|---|
| 本地评论 | ✅ 删文件 | ✅ 同 id 覆盖 | ✅ 删文件 |
| GitLab 评论 | ⚠️ 发出去就发了 | ✅ 管道层保证不重发（事件 + 策略 + 版本三元组） | ✅ `npm run undo` |
| `hold_merge`（级别 3，未实现） | 设计时按三条件来 | 同 | 同 |

### 接模型（第二条策略要用）

```bash
$env:LLM_BASE_URL = "https://api.deepseek.com"
$env:LLM_API_KEY  = "<令牌>"
$env:LLM_MODEL    = "deepseek-flash"
```

**不配模型时第二条策略不会假装通过** —— 它落一条 `error` 记录，输出里明写「判断没做成 —— 这不等于通过」。空跑出「全部未命中」比什么都不跑更坏：那长得跟「系统很干净」一模一样。

三个可选的变量：

| 变量 | 作用 | 不配时 |
|---|---|---|
| `LLM_TEMPERATURE` | 采样温度 | `0` |
| `LLM_TIMEOUT_MS` | 单次调用超时 | `60000` |
| `LLM_EXTRA_BODY` | **厂商特有的请求参数**，JSON 对象，原样合并进请求体 | 不发 |

`LLM_EXTRA_BODY` 是给**思考控制**留的口子 —— 各家的参数名与取值都不一样（DeepSeek 是 `{"thinking":{"type":"enabled"},"reasoning_effort":"high"}`，百炼是 `{"enable_thinking":true,"thinking_budget":500}`），所以这里透传，不为某一家写死字段名。写错了（坏 JSON、不是对象）在装配期报错，不静默忽略。

**两个坑值得先说**：

- **思考模式会忽略 `temperature`。** DeepSeek 文档写着思考模式下不支持 `temperature` 等参数，「设置参数不会报错，但也不会生效」。所以默认那个 `temperature: 0` 在那种模型上**压不住随机性** —— 想让判据的可复现性真的成立，得先用 `LLM_EXTRA_BODY` 把思考关掉，或者接受「结论只是那一次的结论」。
- **思考模式的默认档位往往是开着的，而且是高档。** DeepSeek 的默认是「思考打开、effort 为 `high`」；平台不发这两个参数，于是每次判断都跑在最高强度上 —— 在**常驻轮询**这个用法下，那是成本与超时的主要来源。

## MCP 出口

`npm run mcp` 起一个 stdio MCP server（零第三方依赖，只用 `node:readline`）。人和 Agent 从这里接入：

| 工具 | 作用 |
|---|---|
| `get_usage_guide` | **返回一份使用指引**（`skills/platform-usage/SKILL.md`）——什么时候该找平台、三种动作怎么用、最容易写错的地方在哪 |
| `submit_change` | 把一次变更交给平台判定。**Agent 主动申报的入口** —— 干完活把改了什么、声称做了什么交代清楚 |
| `list_judgments` / `get_judgment` | 看判断记录，含全部依据（命中的文件、取数来源、判断模型） |
| `policy_stats` | 观察期数据：评估 / 命中 / 判断没做成 / 采纳 / 否定 / 无视 |
| `list_policies` | 看装了哪些策略、版本、判据说明与处置级别 |
| `record_reaction` | 回写人的反应与「为什么」—— 观察期升级的唯一输入 |

### 为什么还发一份 skill，而不只是 MCP

**MCP 提供能力，不提供用法。** `tools/list` 给的是工具名与参数 schema，它不告诉接入的 Agent：什么时候该用（干完活要申报吗）、怎么组合、有什么坑（`title` 是**被检验的主张**而不是依据，随手写会让判据判错）。

后果很具体：**Agent 干完活不知道要 `submit_change`，平台就什么都看不到** —— 而「平台看不到」与「这次变更没问题」，在界面上长得一模一样。

所以 MCP 与 skill 是两份出口、**同一份正文**：`get_usage_guide` 返回的就是 `skills/platform-usage/SKILL.md` 本身（每次现读，不缓存）。指引只讲用法，**不复制工具描述与判据正文** —— 复制就是第二份事实源。

> 这条纪律有守卫：`npm run guard`（已挂在 `npm test` 里）会检查文档有没有把控制台「?」的正文抄回来，也会检查漫游引用的说明文案是否存在。**守卫本身用「人造漂移夹具」验证过** —— 故意抄一段进去，它必须变红；抓不到就是守卫无效。

三条约定：**stdout 只走协议**（日志一律走 stderr，混进去的表现是「连接莫名断开」）；**写操作一律留痕**（这个出口没有「只试试不留下痕迹」的路径）；**拿不到就说拿不到**（判断没做成返回的是 error 说明，不是「没有发现问题」）。

MCP 出口与 CLI 走**同一套装配**（`src/wiring.ts`）。两边各装配一遍，迟早会在某条策略或某个开关上不一致，而那种不一致最难发现——从两个入口看同一个仓库，得到两种答案。

## 几条已经定死的设计约束

实现时别绕过它们，理由都在 `docs/` 里：

- **未命中也要落记录** —— 否则事后无从知道「看过但没问题」，而观察期的分母正是「被评估了多少次」。
- **每次判定都表态，包括什么都没发现的时候** —— 只在命中时说话，那「MR 上没有评论」就同时意味着「我看过且没问题」和「GM 根本没跑」。沉默承担不了「通过」这个含义，因为失败也长得一样；这是「评估失败不等于通过」在人的感知层的同一条判据。
- **一次事件只动一次手** —— 先跑完所有策略再处置，把这次判定合成一条评论。边判边动会在同一条 MR 上留下好几条评论，而评论噪音的代价是被人静音，静音之后这套机制就等于不存在了。
- **判断没做成 ≠ 通过** —— 判定结局是三态（`hit` / `miss` / `error`）而不是布尔。取不到数、模型调不通、模型返回的不是约定格式，都落 `error` 且**不执行任何动作**；统计里它单独一列，不许并进未命中。
- **判断必须带依据** —— 判断记录里结论（`reason`）与依据（`evidence`）是两个分开的字段，依据还分四类：命中的文件、规则、取到了哪些数、哪个模型下的判断。
- **主张不是依据** —— MR 标题与描述由提交者自己写、随时可以改，属于**被检验的对象**。它们照常喂给判据（要检验就得看得见），但写进 `gather` 白名单会在装配时直接抛错。
- **取数白名单是权限边界** —— 加一项就是放宽一次，所以它是写死的注册表，不是「事件里有什么就给什么」。白名单里出现未知来源同样在装配期报错，而不是运行时静默取空。
- **新判据先只发消息** —— 处置级别从 1 开始；升级到「挂起合并」由人看着数据决定，不做自动升级。
- **只有「明确否定」进升级条件** —— 采纳与无视都记，但不当判据。
- **动作缺失要显式暴露** —— 策略声明了某个动作而平台没实现时必须说出来，不能静默跳过。
- **写默认关** —— 在真仓库上跑的第一阶段只做读；写要靠配置显式打开。干燥跑走的是与真发同一条代码路径，落盘的就是会发出去的那份文本。
- **事件 id 带 commit sha** —— 同一个 MR 改一版就是一次新事件，于是「这个版本被审过没有」有答案，而不是「这个 MR 被审过没有」。
- **GM 报数据，不要权限** —— 统计输出只陈述数字，不写「建议升级」这类话。

## 与 GitLab 的关系

门禁形态已定（`docs/待决问题.md` 第 6 条）：主干只允许通过 MR 合并，`Allowed to merge = GM + 管理员`，普通开发者只能提 MR。

事件源选**轮询**而不是 webhook，三条理由：只要只读 token、不需要仓库管理员配合；不产生任何写操作；webhook 需要平台有 GitLab 够得着的地址，那是部署问题。代价是漏掉开了又关的短命 MR —— 那种 MR 本来也没人来得及审。

**首次真实接入的结果记在 [`docs/首次真实接入记录-2026-10-13.md`](docs/首次真实接入记录-2026-10-13.md)**，其中一条改变了对落地路径的判断：AI 中台三个仓库几乎不用 MR（frontend 0 条、agent 1 条、my-app 2 条），实际是「功能分支直接推 `test`」。第 6 条定的门禁形态在真实仓库上**还不存在** —— 事件源只订阅 MR 就看不到绝大多数变更。三条可选路径列在那份记录里，尚未定。

## 发布到公开仓

公开仓：<https://github.com/Max-Null/collab-platform> —— 本地分支 `public` 推到远端 `main`。

**它的历史从一个孤儿提交开始，这是有意的。** 公开前的开发历史含真实的内网地址与人名；与其逐提交去改（**改漏一处就全暴露，而且你不会知道**），不如从一次干净的提交开始。本地 `master` 保留完整历史，不随发布压缩 —— 它不跟着公开仓一起被压成快照。

### 更新流程

```bash
# ① 先扫敏感串 —— **这一步不能省**
#    用你那个环境的真值，别把真值抄进仓库（抄进来，扫描就会命中它自己）：
git grep -n -iE '<内网域名>|<内网 IP 段>|<代码托管平台的组名>|<上游项目名>|<工号格式>'

# ② 有命中就替换（对照表见 ef04fc6 那次提交）

# ③ 让 public 先对齐远端 main —— **这一步也不能省**（理由见下）
git checkout public
git pull --ff-only origin main

# ④ 让 public 的整棵树变成 master 的整棵树，压成一个提交推上去
#    ⚠️ **不要用 git merge --squash** —— public 是孤儿分支、与 master
#       没有共同祖先，合并必然冲突。真跑过一次，撞上了。
git rm -rq --cached .      # 清空 index，这样 master 里**删掉**的文件也会跟着消失
git checkout master -- .   # 把 master 的整棵树取过来
git add -A
# ⚠️ **身份要显式给** —— git 的邮箱取自本机配置，而那多半不是公开身份（理由见下）
git -c user.name='<公开用的名字>' -c user.email='<公开用的邮箱>' commit -m "..."
git log -1 --format='%an <%ae>'   # 确认作者是上面那个，不是本机配置里的
npm run check:publish              # 提交身份 + 与远端是否对齐；不过就别往下走
git push origin public:main
git checkout master
```

**为什么第 ① 步不能省。** `git grep` 只查工作区，而**新写的文档很容易带进内部信息** —— 这不是假设：2026-10-14 那次脱敏跑了三轮才干净。第一轮漏在**中文文件名**（`git ls-files` 默认把非 ASCII 路径转义成 `"docs/\345\215..."`，脚本拿到不存在的路径，**静默跳过**了所有中文文档）；第二轮漏在**独立出现的仓库名**（复查正则只写完整形式，漏掉了单独出现的那一个）。

**第三个坑是未跟踪文件。** `git grep` 默认只看**已跟踪**的文件，所以工作区里任何没进过 git 的东西 —— 本机工具留下的目录、临时笔记 —— 它都看不见；而第 ④ 步那句 `git add -A` 会把它们**一并加进发布提交**。两处合起来是一条完整的静默泄露路径：**扫描说干净，是因为它没看那一边；东西被带走，是因为 `-A` 不问该不该带。** 本机工具的目录应当先进 `.gitignore`，别指望扫描替你发现它。

**顺带一个自指教训。** 第一版把真实的敏感串写进了上面这条示例命令里 —— 于是每次扫描都命中它自己。**示例里放占位符，不放真值。**

**为什么第 ③ 步不能省。** `public` 每次发布都被整棵树覆盖，所以它的 HEAD 只代表**上一次发布**；而远端 `main` 会往前走 —— 发布可能是在另一台机器上做的，公开仓也可能收过 PR 并被合入。一旦两端分叉，最后那句 push 比的是**历史**而不是树：新提交的父是 `public` 当时的 HEAD，只要它不是远端 HEAD 的祖先，就会被判非快进、原样退回。**敏感串扫干净了、树也完全对，照样推不上去。**

**为什么用 `--ff-only`。** 分叉时普通 `git pull` 会替你处理掉它（按 `pull.rebase` 合并或变基），于是「`public` 与远端分叉了」这件事被一次成功的 pull 掩盖过去 —— 而发布线上多出来的那段历史，事后没人说得清是怎么来的。`--ff-only` 不处理，它停下，先让人看清远端多出来的那个提交是什么、再决定。

**为什么第 ④ 步的身份要显式给。** 第 ① 步扫的是**工作区里的内容**，而提交的作者与提交者**不在工作区里** —— 它是 `git commit` 那一刻从配置里取出来的元数据。而本机的 `user.email` 往往是公司邮箱，于是「敏感串扫干净了」并不等于「公开仓里没有内部信息」：**邮箱跟着每一次提交走，却没有任何一步在看它。** `-c` 显式给出公开身份、再 `git log -1` 回读一遍，这一步只花两秒。

**`npm run check:publish` 把这件事固化成检查。** 它扫 `origin/main..public` 上每个提交的作者与提交者，不在 `config/publish-identity.json` 的允许列表里就非零退出，顺带报 `public` 有没有落后远端。**靠人记得看，和有一条会红的检查，不是一回事** —— 守卫本身用人造夹具验过：喂一条内部邮箱的提交它会红，喂一条公开身份的就绿。

**而且重写不是万能解。** GitHub 文档写明：只做 force push 的话，带数据的提交仍可从**已有 clone/fork** 与 GitHub **按 SHA 的缓存视图**访问；清服务端缓存要联系支持，而支持只受理凭据类风险 —— 一个邮箱地址不属于那类。**所以在提交那一刻看住它，比任何事后补救都便宜。**

**为什么不逐提交推。** 公开仓的历史一旦含内部信息就只能重写历史，而重写漏一处等于全暴露。压成单个提交之后，**每次发布都是一个可独立检查的快照**。
